# Pinned Vanilla Mooncake Store notes

The baseline decision is frozen at commit
`f161118c18dbea1b56dd5c7908b9eaa440353e2e`, the commit referenced by local
`main` when audited. The current branch is `codex/aegiskv`, and its dirty
Master/Client files contain AegisKV changes. Therefore:

1. read baseline files with `git show f161118c:<path>`;
2. validate their Git blob and SHA-256 from `source-lock.json`;
3. never copy a current worktree file into `main`;
4. do not silently advance to the observed `origin/main` commit.

Master owns metadata, placement, leases and publication. Store Client and
Transfer Engine move bytes. `PENDING` allocation is charged but invisible;
`PutEnd`/finalization publishes a completed replica. MoonKVSim intentionally
models only DRAM Store for its first release even though the upstream source
contains persistent-storage functionality.

The exact source naming is `PROCESSING` before publication and `COMPLETE`
after `PutEnd`. A pending key already exists in Master metadata, so pinned
`GetReplicaList` returns `REPLICA_IS_NOT_READY`; MoonKVSim's empty query result
preserves invisibility but not that RPC error code. Pinned `PutEnd` marks every
matching `ReplicaType` complete. MoonKVSim's successful-replica subset and
atomic abort of the remainder is an explicit failure-accounting replacement,
not an external API match.

The source/API reference is generated by
`scripts/generate_mooncake_source_api_golden.py`. Its canonical artifact is
`reference/goldens/mooncake-f161118-store-te-source-api.json`, SHA-256
`2f118525d96b908abeb0c3feba2885fabeb90e87008aed00eb57af924cb806a1`.
It binds 27 source and official-test blobs plus the pinned `pybind11` and
`yalantinglibs` gitlinks. Generation uses exclusive-create/no-follow output;
`--check` compares canonical bytes. This is E1 source/API evidence only.

The pinned allocation source is best effort and uses distinct segments for
replicas of one slice. The official replication-factor-two/single-segment case
returns one replica. Exact random segment choice is intentionally replaced by
a seed-bound simulator permutation. Pinned FIFO `RemoveKey` returns success but
does not remove an entry because FIFO `AddKey` does not populate the shared key
index; the simulator now preserves that no-op.

Pinned capacity-pressure behavior is separate from those standalone
LRU/FIFO containers. `AllocateAndInsertMetadata` sets `need_mem_eviction_` and
returns `NO_AVAILABLE_HANDLE` when ordinary memory placement fails. A later
`EvictionThreadFunc` invocation may call lease/watermark-aware `BatchEvict`;
the failed `PutStart` is not retried synchronously. `BatchEvict` considers only
completed memory replicas with zero refcount, and separately filters leases and
hard/soft pins.

MoonKVSim uses an explicit DES replacement for the baseline pressure path: one
failed placement triggers a deterministic LRU scan, tentatively releases only
published `COMMITTED` DRAM replicas with zero Store source pins, retries the
best-effort allocator, and commits victim `COMMITTED_REPLICA -> FREE` plus new
`FREE -> PENDING_REPLICA` deltas in one resource transaction. A pending replica
is never a victim. Each live Store GET holds a source pin until either success
or failure, including multiple logical request aliases of one object. If no
legal victim can satisfy placement, geometry and allocation RNG state roll back
and `NO_AVAILABLE_HANDLE` remains the result. Every pressure attempt records
the upstream timing/lease fidelity gap; these tests are E2-toy conservation
evidence, not an upstream concurrency/timing differential.

### 2026-08-30 isolated build and selected official tests

The main tree and both gitlink commits were archived from Git objects into an
isolated `/tmp` directory; the dirty worktree was not copied or configured:

```bash
mooncake_src_tmp=$(mktemp -d /tmp/moonkvsim-mooncake-f161118.XXXXXX)
git -C /home/comp/zhanzhao/Mooncake archive --format=tar \
  f161118c18dbea1b56dd5c7908b9eaa440353e2e | tar -xf - -C "$mooncake_src_tmp"
git -C /home/comp/zhanzhao/Mooncake/.git/modules/extern/pybind11 archive \
  --format=tar 58c382a8e3d7081364d2f5c62e7f429f0412743b | \
  tar -xf - -C "$mooncake_src_tmp/extern/pybind11"
git -C /home/comp/zhanzhao/Mooncake/.git/modules/extern/yalantinglibs archive \
  --format=tar 7801bc9ad9021781f15217552214e325a1cf7373 | \
  tar -xf - -C "$mooncake_src_tmp/extern/yalantinglibs"
cmake -S "$mooncake_src_tmp" -B "$mooncake_src_tmp/build-golden" \
  -DBUILD_UNIT_TESTS=ON -DBUILD_BENCHMARK=OFF -DBUILD_EXAMPLES=OFF \
  -DWITH_STORE_RUST=OFF -DWITH_RUST_EXAMPLE=OFF -DUSE_CUDA=OFF \
  -DUSE_HTTP=OFF -DUSE_ETCD=OFF -DUSE_REDIS=OFF \
  -DSTORE_USE_ETCD=OFF -DSTORE_USE_REDIS=OFF -DUSE_NOF=OFF \
  -DCMAKE_BUILD_TYPE=Release
```

That first configure stopped at `find_package(yaml-cpp)`. A second configure
used the existing local dependency prefix
`/home/comp/zhanzhao/Mooncake/.deps-sglang-profiler`. `USE_HTTP=OFF` then exposed
a pinned-source build-combination defect: `HttpMetadataCleanupThreadFunc()`
dereferences the forward-declared `MetadataStoragePlugin`, whose definition is
included only under `USE_HTTP`. No upstream source was patched. Reconfiguring
with `USE_HTTP=ON` built the pinned `transfer_engine` and `mooncake_store`
targets successfully.

Seven selected official test binaries then ran from that isolated archive:
`topology_test`, `memory_location_test`, `allocation_strategy_test`,
`eviction_strategy_test`, `master_service_test`, `transfer_task_test`, and
`segment_test`. CTest passed all seven binaries; their GoogleTest totals were
248 passed and two upstream-skipped cases. The canonical local validation
record is
`reference/goldens/mooncake-f161118-official-test-validation.json`, SHA-256
`573373003657e9ccca0e1e80335c19de754e8d0b08a956259b6348384a322b17`.

This is an E2 external-official-unit subset, not a MoonKVSim differential. The
dependency prefix is not hash-locked, no RDMA device or CUDA kernel was used,
and test duration is not performance evidence. RPC/concurrency parity,
allocator extents, real data paths, communication calibration, and the known
`GetReplicaList`/`PutEnd` API differences remain open.
