# AegisKV：Agent 剩余执行时间预测调研与推荐

调研日期：2026-09-20。用户确认 Tracker 可以获取任务/对话内容、工具结果和运行时统计。本报告区分论文已报告的方法、本地已有诊断和面向 AegisKV 的建议；没有新增训练、模拟或物理实验，也没有修改论文当前算法。

**推荐结论（补充调研后更新）。** 不预设必须微调语言模型或调用生成式模型估时。优先比较历史状态/前缀检索、结构化特征的分位数 GBDT，以及冻结语义表示加轻量回归，均直接预测整个 Agent 当前任务的剩余秒数；Heddle 式监督微调作为更高成本的对照。随后在工作流层面处理误差，得到保守 Slack。新补查的流程剩余时间预测、Maestro、Magnus 和 CacheScout 见 [替代方法调研](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/docs/agent-runtime-prediction-20260920/ALTERNATIVES.md)。各路线的效果需要部署数据验证，其他论文的准确度不能代替 AegisKV 验证。

**先确定预测目标。** 用户已明确：工作流 DAG 的节点是 Agent，一个 Agent 内部有多轮 LLM 请求和工具调用。Tracker 在每个 step 的观测点预测该 Agent 从此刻到当前任务所需输出就绪的剩余墙钟时间，覆盖尚未发生的全部后续轮次；对于未启动 Agent，预测依赖满足后需要的时间。内部事件序列只是预测输入，不把每轮请求改成工作流 DAG 节点。若存在父 Agent 等待子 Agent，需明确标签与依赖计时方式，避免将同一等待在路径上重复累加。预测用于健康服务基线下的延迟容忍度，故障检测、恢复和重放成本由恢复模型单独估计。

墙钟时间包含正常排队、推理、工具和必要编排开销。预测目标应明确绑定服务配置与策略；离线标签若包含其他策略人为插入的等待，不能未经处理就视作不变的任务成本。模型能预测剩余 Token，并不意味着它已经预测了上述全部时间。

**已有本地证据为什么不足以保留原样 GBDT。** 当前 [诊断协议](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/experiments/data/agent-time-early/protocol.json)在“第一条请求完成后的第二条请求到达”这一时点预测整个 Agent 剩余时间；包含 1,443 个 Agent、170 个工作流，按工作流划分五折。特征主要是长度、耗时和模型，所有角色均记为 `Subagent`。这是一次离线诊断，没有物理重复运行，也没有时间顺序部署验证。

| 指标 | 原 GBDT | 训练折历史中位数基线 |
| --- | ---: | ---: |
| 中位绝对相对误差 | 75.87% | 76.23% |
| 平均绝对误差 | 417.54 s | 438.53 s |
| 相对误差不超过 20% 的样本比例 | 13.37% | 11.23% |

数字来自 [summary.json](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/experiments/data/agent-time-early/summary.json)，逐条结果在 [predictions.csv](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/experiments/data/agent-time-early/predictions.csv)。相对误差在真实剩余时间较短时会被放大，因此同时保留秒级误差。这组结果表明当前特征和训练设置尚未得到可靠效果；它不能证明所有 GBDT 都不适用，也不能证明加入语义必然改善。现有诊断没有明确工具完成事件或有区分度的语义角色，且每个 episode 只有一个预测时点；新设计需要逐 step 样本，并核对 episode 的结束标记是否对应用户定义的 Agent 任务完成。

**语义增强候选怎样实现。** 这是候选路线之一，应与无语义编码的统计/回归方法对照。第一层只编码当前可见内容，不生成一段“预计需要多久”的自由文本。第二层结合运行状态，学习与部署相匹配的剩余秒数分布。

| 层次 | 第一版选择 | 输入/输出 |
| --- | --- | --- |
| 语义表示 | 冻结文本编码器；可用 [Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)作为候选 | 输入任务目标、角色/工具约定、已有计划、最近相关生成与工具结果；输出短维度语义向量。公开模型卡支持可选输出维度；这只是可用编码器，不是已训练好的时间预测器 |
| 时间回归 | [LightGBM 的 quantile objective](https://lightgbm.readthedocs.io/en/stable/Parameters.html#objective) | 语义向量加结构化运行特征，训练条件分位数；输出中位剩余秒数与较低/较高分位数 |
| 校准 | 独立历史工作流上的残差或 conformal 校准 | 检查区间覆盖、时间漂移和任务族失配；参数由验证集选择 |
| Slack 计算 | 保留 CPM，对同一批联合时间情景分别传播 | 输出点估计、保守有效 Slack、置信/过期标记和回退原因 |

编码输入要有固定大小和可重复规则：保留原始任务与成功条件、明确结构化进度以及相关的新结果，避免每个 token 都重新编码完整长历史。编码窗口、向量维度和更新事件属于待验证配置。语义表示可以按事件缓存；时间回归器在新的 elapsed、工具状态或负载出现时可单独刷新。推理延迟、设备占用和对前台服务的干扰必须实测，不能因为参数少就先宣称开销可忽略。

结构化特征至少包括以下几类；未来实际值只用于训练标签与事后评估，不能进入输入。

| 特征类别 | 可用信息 |
| --- | --- |
| 身份与先验 | 工作流类型、模板/角色版本、当前模型、工具集、任务族；对新 subagent 不把实例 ID 当作可泛化语义 |
| 当前进度 | 已完成请求数、当前 LLM/tool/wait 状态、已观察 token 量、阶段/测试反馈、已发生重试、经过时间 |
| 工具状态 | 工具类型和输入规模、运行或排队时长、历史时延分布、失败/超时结果；已运行很久的工具要估计“尚未结束条件下”的剩余时间 |
| 服务状态 | 最近 TTFT/TPOT 或实测吞吐、缓存命中与未缓存输入、并发、等待队列、批处理和硬件配置 |
| 依赖边界 | 当前 Agent 实例、工作流依赖、所需输出、未解析分支状态；父子 Agent 的等待计时需避免重复 |

训练目标使用快照时刻之后的实际剩余秒数，直接学习 Agent 的残余时间。对于未启动 Agent 另给入口状态。完成时间减去当前时刻只用于构造标签；预测器已输出剩余时间后，不再重复减 elapsed。长尾可用对数目标或稳健损失对照，但是否有益由同一拆分验证。冻结语义表示加轻量回归能先检验内容是否提供增益；若仍不够，再比较小模型回归头或参数高效微调，不预设必须扩展到大模型。

**两类用户场景的处理。** 对重复固定角色，优先使用角色/模板/模型层次的历史分布作为基础，语义输入解释同一角色中的任务差异。对为新 subtask 创建的 subagent，使用任务描述、工具反馈和已完成进度，历史先验退回相似任务族或全局层次。两者使用同一输出接口；某一类证据不足时，不能将另一类任务上的精度外推过去。

工具环节单独值得注意：平均工具耗时减去已等待时间可能产生不合理的零值。应把“仍未完成”作为条件，使用同类工具的剩余寿命分布或带 elapsed 的条件回归。并行工具的关键等待由依赖关系决定，不能将所有工具耗时直接相加。超时、取消与未完成轨迹保留为删失或单独结果，不能只保留快速成功样本后宣称覆盖全部请求。

**Slack 应如何使用这些预测。** 不建议将所有 Agent 的时长统一取 P90 后直接做一次 CPM，就声称得到保守 Slack。Slack 是相对路径长度产生的余量：过度高估其他分支，可能把当前分支的 Slack 人为放大。

一个纯说明性例子：两条从现在并行到同一 join 的分支，A 的点预测为 80 s，B 为 100 s，点估计给 A 留出 20 s。但如果 A 的可能范围是 70–130 s，B 是 90–110 s，A 也可能成为较慢分支；这时不能承诺 A 有 20 s 余量。在这些范围确实同时覆盖真实分支时间的条件下，最不利组合给 A 的可用余量为零。所有时长都取较大值也不是通用解法：真实 A/B 为 100/110 s，若预测成 105/200 s，会把 A 的 10 s 余量错误放大为 95 s。

建议在同一工作流的时间情景中运行 CPM，再对每个请求的 Slack 取经校准的较低分位数。联合情景要保留同一模型、GPU、工具后端和工作流带来的相关误差；不能将各节点边际分位数独立拼接后当成联合保证。第一版可从按完整工作流/时间块抽取的残差情景开始，以点预测加保守残差边界作简单对照；样本数与风险容忍度由开销/效果扫描选定。

[Conformalized Quantile Regression](https://papers.neurips.cc/paper_files/paper/2019/hash/5103c3584b063c431bd1268e9b5e76fb-Abstract.html)提供校准预测区间的参考，但其有限样本边际覆盖有适用条件。节点时间区间的覆盖不能自动继承为整个 DAG 的 Slack 覆盖。对时间漂移可借鉴 [Adaptive Conformal Inference](https://arxiv.org/abs/2106.00170)，仍须检查反馈延迟、工作流内相关性和短期失配；长期覆盖性质不是每个 Agent 的硬保证。评估应直接校准/检查最终 Slack 的过估计风险。

未知 DAG 结构与预测误差是两种问题。再好的时间预测器也不能把尚未声明的依赖当作不存在。初版保留当前设计的保守约定：依赖不完整、预测过期或失配时回退零 Slack；若以后放宽到已闭合的局部 fork/join，需要明确这一区域的输出边界与下游关系，不能将其默认为完整工作流。零 Slack 只是保守优先级输入，实际准入仍受容量约束。

**运行过程的短伪代码。**

```text
收到请求、工具完成、显著进度变化或负载变化事件：
    更新当前可见的 Agent DAG、内部 step 记录和运行状态
    对受影响 Agent：
        内容变化时更新语义表示；否则复用缓存
        结合进度、工具状态和当前服务统计，预测剩余时间分位数
        应用独立历史数据的校准，检查过期和分布失配
    若依赖不完整或预测不可用：发布零 Slack 与原因
    否则：在共同时间情景上计算 CPM，发布保守 Slack
    KV Master 按现有策略事件消费新 Slack
```

刷新以有信息增量的事件为主；负载/长工具等待期间只更新便宜的状态与时间估计，并对语义编码限频。它不依赖 Adapter 的容量窗口，也不要求每新增一个 token 就运行语义模型。预测变动只先改变元数据；是否物理迁移仍由 KV Master 的收益、容量与稳定性规则决定。

**验证怎样做到足以服务论文。** 保留最小对照集：历史条件中位数/分位数、原数值特征 GBDT、语义表示加运行特征的分位数 GBDT、按本地数据实现的 Heddle 式语义回归器，以及只用于离线评估的真实剩余时间/Slack oracle。后者是本文复现路线，不冒充原作者实现。系统层再比较零 Slack、点估计 Slack、保守 Slack 与 oracle。

数据拆分以完整工作流和时间为单位；相同任务、相同代码仓库或模板的近重复应分组，单独测试未见角色/任务族及硬件/负载变化。训练、校准、最终测试互不混用；角色先验、特征降维及其他拟合变换只用训练部分估计。同一轨迹多快照有相关性，控制每条轨迹的权重，并按工作流聚合或 bootstrap 统计；不要把快照数当独立实验次数。预测器只看发生故障之前已可见的信息。

| 评估层次 | 必须报告的指标 | 为什么影响保护决策 |
| --- | --- | --- |
| 剩余时间 | MAE、误差分位数、按时长/阶段分组的相对误差、区间覆盖与宽度 | 区分绝对秒数误差、长尾和冷启动；相关性不能替代这些指标 |
| Slack | 过估计秒数、关键路径判定、错误认为恢复能被 Slack 吸收的比例 | 保护对象选错会直接暴露恢复延迟 |
| 系统 | 同一到达/缓存/资源条件下的故障 WCT、正常服务开销、保护占用与 oracle 差距 | 总是零 Slack 可能减少过估计但浪费预算，必须同时评估成本 |
| 在线成本 | 编码/回归/CPM 的 P50/P95 延迟、设备与内存占用、刷新频率、过期与回退比例 | 防止预测器本身干扰推理或只在不现实的刷新频率下有效 |

Oracle 的真实时间和完整 DAG 仅供事后对照。对于共享故障及共享恢复资源，需要在匹配到达、调度与负载的工作流回放中评估，不能用多个请求局部收益相加替代 WCT。首先复用已有 trace 做严格离线比较；若语义方案在跨工作流/时间验证中未带来稳定收益，就保留简单模型和保守回退，而不是通过删除困难任务制造精度。
