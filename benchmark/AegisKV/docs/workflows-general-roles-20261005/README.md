# 通用角色版 workflow：研究交叉汇合与软件修复主链

状态：**新提出的自建 DAG，尚未执行验证**。用户要求增加 Agent 分工和依赖、保持通用角色、在开头加入问题分析，随后指出两类 workflow 的结构过于相似。当前研究图为 9 个 Agent / 5 种角色 / 13 条依赖，软件图为 8 个 Agent / 5 种角色 / 12 条依赖。早先 5-Agent 图保存在 `before-planning-expansion/`；上一版共用结构模板的 9-Agent 图保存在 `before-distinct-topologies/`。

研究图 A--I、软件图 A--H 标识 Agent 实例。同一角色模板可以执行不同 job 分配的完整任务；图内小字是本次实例的任务范围，不是另一种细分角色。每个节点包含自己的连续多轮模型调用、独立历史和任务完成条件，调用轮数不预先固定，也不通过重复材料或机械自检保证多轮。历史兼容性与实际 KV 复用需要新的执行记录验证。

每条边表示后继消费前驱产物，并等待所有前驱任务完成。就绪任务独立启动，不设置全局层级屏障。节点和依赖在执行前固定；A 分析输入问题并为固定任务槽位填写具体内容，不动态创建角色、节点或边。

两图的结构区别来自产物流程：研究任务在三个证据分支之间做局部交叉汇合，然后并行写作和审阅；软件任务围绕一个候选修改形成定位、实现、整合的主链，回归用例从旁路汇入验证，原始诊断和候选 patch 直接供评审与整合读取。两图不再共用节点排列和依赖模板。研究图入口扇出为 3、最终汇合的前驱为 2；软件图入口扇出为 2、最终汇合的前驱为 3。两图的最长无权路径都是 4 条边，因此不能宣称软件图无权深度更大。

## 共同的开头：A 规划者

A 面向一类通用复杂任务，负责澄清目标、分析问题结构、确定资料范围、检查约束及验收条件，最后输出对应的任务说明与分支输入。角色模板不绑定 Obsidian、Astropy 或某一行业。研究图按稳定职责组织任务，不能把问题任意切成 `Research topic 1/2/3`。

它的产物包括原问题解释、预设工作职责的任务说明、共同证据范围及验收标准。研究图为 B 资料调研、C 比较研究、D 应用研究；软件图为 B 定位诊断、C 复现/测试分析。一次 job 的任务对象和证据由输入问题决定，这些职责及外层 DAG 不变。后续 Agent 原始上下文均带有原问题、A 的任务说明及必要的来源说明，前驱产物不能只剩不可追溯的摘要。

## 资料驱动的研究报告

通用角色：规划者、研究员、分析员、报告作者、评审员。

| Agent | 角色 | 本次任务范围 | 必须完成的前驱 |
|---|---|---|---|
| A | 规划者 | 问题分析、按固定职责分配任务及质量标准 | 无 |
| B | 研究员 | 资料调研：搜集/阅读/核查基础事实、定义、方法和证据，形成可追溯资料库 | A |
| C | 研究员 | 比较研究：依据材料比较方案、观点或解释，整理比较依据、差异和争议 | A |
| D | 研究员 | 应用研究：分析适用环境、边界条件、限制、风险及反例，并保留原始来源 | A |
| E | 分析员 | 将 B 的事实证据与 C 的比较结果结合，形成有依据的解释和论证 | B、C |
| F | 分析员 | 将 C 的比较结果置于 D 的应用条件中，评估适用性、权衡和不确定性 | C、D |
| G | 报告作者 | 综合 E/F 撰写报告初稿，保留原始引用和证据路径 | E、F |
| H | 评审员 | 针对 F 的证据和结论独立审阅，直接核对 D 的原始材料/来源 | D、F |
| I | 报告作者 | 基于 G 初稿及 H 审阅意见，完成修订、补证及定稿 | G、H |

并行与交错：资料、比较、应用三个完整职责同时就绪；各 Agent 都可访问 A 指定的同一真实材料集合，C/D 不需要等待 B 的资料库才能独立调研。E 只等 B/C，F 只等 C/D，因此任一局部分析无需等第三个研究员。H 不等待 E 或 G，可以在 G 尚未开始或正在写作时审阅证据。I 等待初稿与审阅两类产物。D→H 是直接原始证据的产物依赖，虽然执行顺序已可经 F 传递，保留它能明确审阅员可核查的输入范围。H 未读取 G 初稿，因此不能称为初稿逐句审查；I 自己负责最终文本与审阅意见的一致性。

一个具体但尚未执行的解释例是“依据给定材料，评估某项技术的采用条件”：B 调研能力与实证材料，C 比较替代方案，D 研究使用环境和限制；E 论证差异是否由证据支持，F 评估各方案在实际约束下的适用性；G 写报告，H 对 F 的适用性结论独立核证，I 修订。更换研究领域时，变化的是问题、材料和被比较对象，职责不变。该模板目前适合包含解释/比较/适用性判断的研究任务，不宣称覆盖全部 DeepResearchBench 问题。这个例子不是已有真实 trace，所述分工也没有生产典型性验证。

DeepResearchBench 可以提供真实问题来源。材料须来自相关真实文档，记录来源、时间范围和哈希。这里定位为给定资料上的研究与分析；本地检索时延待测，不把它等同于完整在线 DeepResearch。新角色拆分、依赖必要性和质量都需重新验证。

## 软件问题调查、修复与验证

通用角色：规划者、调查员、开发者、评审员、验证员。

| Agent | 角色 | 本次任务范围 | 必须完成的前驱 |
|---|---|---|---|
| A | 规划者 | 分析 issue、任务范围、验收条件与分支职责 | 无 |
| B | 调查员 | 定位原因，分析原实现、接口约束和相关代码证据 | A |
| C | 调查员 | 分析复现输入、现有测试、环境和缺失覆盖 | A |
| D | 开发者 | 根据 B 的诊断实施候选代码修改，附来源与原因说明 | B |
| E | 开发者 | 综合 B 的原因分析和 C 的复现/覆盖分析构建回归用例 | B、C |
| F | 评审员 | 将 D patch 与 B 的原实现/问题证据对照，审阅正确性和兼容性 | B、D |
| G | 验证员 | 在对应环境中整合 D/E 的候选代码和用例，执行验证 | D、E |
| H | 开发者 | 读取原 D patch、F 审阅和 G 验证记录，整合与修订最终产物 | D、F、G |

主链为 A→B→D→H；B/C 并行调查，D 只需等待 B，因此可以在 C 仍分析测试时开始修改。E 等 B/C 后构建回归用例，可与 D 并行。F 在 D 完成后可立即评审，不等 E；G 则必须等 D/E 后运行验证。B→F 直接传递原实现/诊断证据，D→H 直接传递完整候选 patch；这两条是明确的产物输入边，即使部分执行顺序已经经其他路径约束，也不应只保留摘要。D/E 使用独立工作区或 patch 产物，避免共享修改冲突。H 若再次修改代码，须在自己的局部任务内重新验证；不得把修改前的 G 测试结果宣称为最终 patch 的验证结果。失败或未解决问题应保留，不保证 Agent 会修复成功。

SWE-bench Verified 可以作为真实 issue 来源。实际执行须建立对应 pre-fix 仓库、依赖及测试环境，记录环境构建；官方 patch/test_patch/答案不得提前输入 Agent，独立评测与 Agent 可见材料分开。该固定模板要求 D 能从 B 的诊断开始实现，E 能从 B/C 生成用例；如果特定问题还需要其他前驱产物，应调整模板或按事先声明的适用规则选择任务。测试可能耗时较长，不能预先宣称满足短工具调用条件。

## 图稿、复现与证据边界

- `workflows-zh.drawio` / `workflows-en.drawio`：中文/英文可编辑源，各含两页。
- `research-report-zh.png` / `software-issue-zh.png`：当前中文预览。
- `research-report-en.pdf` / `software-issue-en.pdf`：当前英文矢量图，168 mm 宽。
- `native/`：嵌入 Draw.io 源的 PDF/SVG/PNG；`review/`：最终尺寸彩色/灰度预览、检查和本次纠正记录。
- `workflow-contract.json`：当前角色、实例、依赖及证据状态；两个 `before-*` 目录保留此前候选图稿和文档。

生成：在此目录运行 `python3 build_and_render.py`。延续既有浅绿/浅蓝/浅橙、细灰色正交箭头及 Agent 字母标识。没有把图自动插入主稿，也未修改 serving 图或旧实验。

增加这些有具体产物用途的分支，可以观察非同步就绪、多个局部汇合、并行审阅与执行，以及最终 join 前不同 Agent 的恢复紧迫性。节点多本身不证明 AegisKV 有优势：关键路径、Slack、工具等待和恢复代价必须从新实际执行与故障实验中测量。

本次只验证图形结构、语义和排版。全部 Agent 多轮、兼容 KV 前缀、工具时延、应用质量、依赖必要性、典型性以及完整 AegisKV 收益均尚未验证；旧 pilot 和此前候选设计都不构成当前 DAG 的执行证据。
