# 通用角色版 workflow：问题分析与交错依赖

状态：**新提出的自建 DAG，尚未执行验证**。本次用户要求增加 Agent 分工和依赖，同时保持角色通用，并在开头加入问题分析。两图各有 9 个完整 Agent 任务、5 种通用角色；研究图 13 条依赖，软件图 12 条依赖。上一版 5-Agent 图完整保存在 `before-planning-expansion/`。

字母 A--I 标识 Agent 实例。同一角色模板可以执行不同 job 分配的完整任务；图内小字是本次实例的任务范围，不是另一种细分角色。每个节点包含自己的连续多轮模型调用、独立历史和任务完成条件，调用轮数不预先固定，也不通过重复材料或机械自检保证多轮。历史兼容性与实际 KV 复用需要新的执行记录验证。

每条边表示后继消费前驱产物，并等待所有前驱任务完成。就绪任务独立启动，不设置全局层级屏障。节点和依赖在执行前固定；A 分析输入问题并为固定任务槽位填写具体内容，不动态创建角色、节点或边。

## 共同的开头：A 规划者

A 面向一类通用复杂任务，负责澄清目标、分析问题结构、确定资料范围、检查约束及验收条件，最后输出对应的任务说明与分支输入。角色模板不绑定 Obsidian、Astropy 或某一行业。

它的产物包括原问题解释、B/C/D 三个预设槽位的任务说明、共同证据范围及验收标准。一次 job 的任务内容由输入问题决定；整个外层 DAG 不变。后续 Agent 原始上下文均带有原问题、A 的任务说明及必要的来源说明，前驱产物不能只剩不可追溯的摘要。

## 资料驱动的研究报告

通用角色：规划者、研究员、分析员、报告作者、评审员。

| Agent | 角色 | 本次任务范围 | 必须完成的前驱 |
|---|---|---|---|
| A | 规划者 | 问题分析、三个子问题及质量标准 | 无 |
| B | 研究员 | 子问题一：搜集/阅读/核查证据并形成完整结论 | A |
| C | 研究员 | 子问题二：同一研究员模板，另一任务范围 | A |
| D | 研究员 | 子问题三：同一研究员模板，第三任务范围 | A |
| E | 分析员 | 对 B/C 两方面做专题推理、比较与结论形成 | B、C |
| F | 分析员 | 综合 C/D 两方面评估适用条件、冲突和不确定性 | C、D |
| G | 报告作者 | 综合 E/F 撰写报告初稿，保留原始引用和证据路径 | E、F |
| H | 评审员 | 针对 F 的证据和结论独立审阅，直接核对 D 的原始材料/来源 | D、F |
| I | 报告作者 | 基于 G 初稿及 H 审阅意见，完成修订、补证及定稿 | G、H |

并行与交错：B/C/D 同时就绪；E 只等 B/C，F 只等 C/D，因此任一局部分析无需等第三个研究员。H 不等待 E 或 G，可以在 G 尚未开始或正在写作时审阅证据。I 等待初稿与审阅两类产物。D→H 是直接原始证据的产物依赖，虽然执行顺序已可经 F 传递，保留它能明确审阅员可核查的输入范围。H 未读取 G 初稿，因此不能称为初稿逐句审查；I 自己负责最终文本与审阅意见的一致性。

一个具体但尚未执行的解释例是“依据给定材料，评估某项技术的采用条件”：B/C/D 分别研究技术能力、比较基准、应用限制；E 综合能力和基准，F 综合基准与限制；G 写报告，H 对 F 的适用性结论独立核证，I 修订。角色模板本身仍面向任意需要多方面证据的研究报告。这个例子不是已有真实 trace，所述分工也没有生产典型性验证。

DeepResearchBench 可以提供真实问题来源。材料须来自相关真实文档，记录来源、时间范围和哈希。这里定位为给定资料上的研究与分析；本地检索时延待测，不把它等同于完整在线 DeepResearch。新角色拆分、依赖必要性和质量都需重新验证。

## 软件问题调查、修复与验证

通用角色：规划者、调查员、开发者、评审员、验证员。

| Agent | 角色 | 本次任务范围 | 必须完成的前驱 |
|---|---|---|---|
| A | 规划者 | 分析 issue、任务范围、验收条件与分支职责 | 无 |
| B | 调查员 | 实现路径、问题原因和相关代码证据 | A |
| C | 调查员 | 接口语义、兼容性约束及预期行为 | A |
| D | 调查员 | 现有测试、复现输入、测试环境和缺失覆盖 | A |
| E | 开发者 | 根据 B/C 实施候选代码修改，附来源与原因说明 | B、C |
| F | 开发者 | 根据 C/D 构建表达预期行为的回归用例 | C、D |
| G | 评审员 | 审阅 E patch 的正确性、范围、兼容性和代码质量 | E |
| H | 验证员 | 在对应环境中整合 E/F 的候选代码和用例，执行验证 | E、F |
| I | 开发者 | 根据 G/H 整合与修订，检查最终产物并输出 patch 和验证记录 | G、H |

并行与交错：B/C/D 并行；E 无需等 D，F 无需等 B。E/F 使用独立工作区或补丁产物，避免共享修改冲突。G 可以在 E 完成后立即评审，不用等待 F；H 必须等 E/F 后运行。I 接收两者完整产物，若再次修改代码，须在自己的局部任务内重新验证；不得把修改前的 H 测试结果宣称为最终 patch 的验证结果。失败或未解决问题应保留，不保证 Agent 会修复成功。

SWE-bench Verified 可以作为真实 issue 来源。实际执行须建立对应 pre-fix 仓库、依赖及测试环境，记录环境构建；官方 patch/test_patch/答案不得提前输入 Agent，独立评测与 Agent 可见材料分开。该固定模板要求 F 能从行为契约和现有测试生成用例，G 能从 E 完整 patch/context 评审；如果特定问题需要额外产物，需调整模板或按事先声明的适用规则选择任务。测试可能耗时较长，不能预先宣称满足短工具调用条件。

## 图稿、复现与证据边界

- `workflows-zh.drawio` / `workflows-en.drawio`：中文/英文可编辑源，各含两页。
- `research-report-zh.png` / `software-issue-zh.png`：当前中文预览。
- `research-report-en.pdf` / `software-issue-en.pdf`：当前英文矢量图，168 mm 宽。
- `native/`：嵌入 Draw.io 源的 PDF/SVG/PNG；`review/`：最终尺寸彩色/灰度预览、检查和本次纠正记录。
- `workflow-contract.json`：当前角色、实例、依赖及证据状态；`before-planning-expansion/`：上一版图稿和文档。

生成：在此目录运行 `python3 build_and_render.py`。延续既有浅绿/浅蓝/浅橙、细灰色正交箭头及 Agent 字母标识。没有把图自动插入主稿，也未修改 serving 图或旧实验。

增加这些有具体产物用途的分支，可以观察非同步就绪、多个局部汇合、并行审阅与执行，以及最终 join 前不同 Agent 的恢复紧迫性。节点多本身不证明 AegisKV 有优势：关键路径、Slack、工具等待和恢复代价必须从新实际执行与故障实验中测量。

本次只验证图形结构、语义和排版。全部 Agent 多轮、兼容 KV 前缀、工具时延、应用质量、依赖必要性、典型性以及完整 AegisKV 收益均尚未验证；旧 7/8-Agent pilot 和上一版 5-Agent 设计都不构成新 DAG 的执行证据。
