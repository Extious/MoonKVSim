# 新实验的 workflow 选择与构建

2026-10-05 后续：研究报告角色已扩展到适配的产品/技术/方法比较任务；原软件市场场景是其中一个实例。新论文集成和完整实验协议见 [workflow-evaluation-20261005](../workflow-evaluation-20261005/README.md)。下文保留起步实例和历史设计决定；其中“未修改论文”仅描述当时状态。新应用完整 trace 仍未采集。

2026-10-04 最新决定：围绕当前 AegisKV 算法构建有实际用途的应用场景，不再等待一个公开 trace 完全符合全部设计约束。推荐 **真实公开任务 + 本项目实现的应用 DAG + 实际模型执行产生的完整 trace**。公开 trace 支撑执行模式和应用类别；自采 trace 是正式实验输入。本文是可实现的实验设计，没有执行模型、生成性能结果或修改论文。

## 1. 选什么

| 用途 | 选择 | 具体输入与产物 |
| --- | --- | --- |
| 主场景 | 多产品软件市场研究报告 | DeepResearchBench 的真实研究任务；首个实现实例用任务 93：比较视频编辑/创作工具市场中的 Adobe、CapCut、DaVinci Resolve、Final Cut Pro 等产品。输入是有来源的产品资料、用户/行业分析及市场资料；输出是有证据索引的市场研究报告 |
| 第二场景 | 代码仓库变更评审 | SWE-bench Verified 的真实 issue 与对应 `base_commit` 代码快照；首个实例用 `astropy__astropy-12907`：分析嵌套 CompoundModel 的 separability 判断问题，交付根因、改动方案、影响分析与回归测试方案 |
| 外部参照 | 原样应用的 trace | Open Deep Research 的并行研究行为、MAST 的真实软件任务通信、SyFI 的用户编码调用特征；与新应用分别报告 |

任务 93 和 Astropy issue 是实现用的起步实例，不是根据 AegisKV 收益筛选的正式测试集。DeepResearchBench 100 条任务已下载；SWE-bench 样本仅保存任务输入字段，没有把正确补丁、测试补丁或答案字段提供给应用。输入来源与哈希见 [SOURCE_MANIFEST.json](SOURCE_MANIFEST.json)。

正式任务按应用目标、来源、资料规模抽样，包含短、中、长任务。DRB 中的其他市场/产品比较问题可以扩展主应用；更广的研究领域不能不经适配就套用同一角色模板。SWE-bench 的 issue 只作真实任务来源：本应用交付评审报告，**不声称这是原始 SWE-bench 修复任务，也不以官方解题率评价评审报告**。

## 2. 为什么自己采集

- 公开紧凑 trace 对 prompt 正文、真实 token、完整任务前驱的支持不一致，无法直接承担本论文的全部实验。
- 应用代码由本项目编写，但材料来自真实任务，LLM 请求实际执行，分支时长、轮数、历史增长和工具耗时实际记录。这是自采执行 trace；不是人工指定时间的合成 trace。
- 固定任务 DAG、连续局部调用和保留完整历史是明确的应用实现选择。不能把它们称为所有上游应用的原样行为。
- NVIDIA 的原始研究应用有动态委派和压缩；新应用固定角色、保留 Agent 自己的完整调用历史。适配后的前缀行为必须重测，不能继承其公开统计。

当前 NVIDIA 入口源码确实提供 `--enable_tracing`，保存 compact 与 full 两种 trace；已保存源码作阅读，未执行。它可以帮助建立原样参照，但不能从“full”文件名就假定已包含本实验需要的逐调用 token 与全部 Agent-task 前驱字段。

## 3. 主场景：视频编辑软件市场研究

材料准备阶段先冻结资料快照、文档 ID、来源 URL/版本/日期及哈希，准备产品说明、典型用户/创作场景资料、商业模式和市场资料。材料准备时间单独记录。主要实验测量的是 **已有资料上的分析与报告生成阶段**；若增加在线检索端到端变体，则保留并计入所有检索耗时，不把离线阶段标作原始在线 Deep Research。

| Agent | 直接前驱 | 第一项请求大意 | 后续请求大意与实际产物 |
| --- | --- | --- | --- |
| A 产品研究 | 无 | 根据产品资料建立功能、平台、工作流及证据表；区分来源事实和推断 | 按真实产品/文档组补充未覆盖项，核对可比性与来源，完成产品表 |
| B 用户与场景 | 无 | 从用户/行业资料归纳创作者群体、任务需求及选择标准 | 补充不同群体的证据，检查需求冲突，完成用户—需求表 |
| C 商业与市场 | 无 | 从市场资料整理收入模式、市场口径和竞争环境 | 核对时间、统计口径与来源差异，完成市场证据表并标明缺失项 |
| D 产品—场景匹配 | A、B | 用 A 的产品能力与 B 的需求，建立产品—创作场景匹配矩阵 | 检查每个匹配项是否有两侧证据，修正过度推断，完成细分场景比较 |
| E 竞争定位 | A、C | 综合产品差异和商业证据，分析各产品的竞争定位 | 核对商业结论与产品事实是否一致，完成竞争格局章节 |
| F 需求缺口与趋势 | B、D | 根据用户需求与匹配矩阵，分析未满足需求及可能的产品演进方向 | 检查缺口是否真实、趋势是否有证据，完成机会与限制章节 |
| G 报告编辑 | E、F | 综合竞争格局和需求/趋势章节，生成面向原始研究问题的完整报告 | 核对问题覆盖、事实冲突和证据索引，修订并交付报告 |

这是一张本项目设计的任务 DAG。A/B/C 并行；D 只等待 A/B，可以与尚未结束的 C 并行；E 与 F 分别等待所需产物，彼此不互等。不要设置整层完成屏障。中间产物包含所引用的上游结论、证据 ID 和必要事实，保证下游没有隐含的未声明 Agent 依赖。

这里的复杂性来自三个不同输入领域和两个不同局部综合任务。无需为了图的复杂程度添加边，也不规定 C 必须慢于 A/B。

## 4. 第二场景：真实仓库 issue 的变更评审

从 issue 对应的 `base_commit` 准备只读代码/文档/已有测试快照。选择代码材料的规则和文件范围在比较恢复策略前固定，不参考正确补丁。文件读取/检索可以作为实测本地短工具；严格无工具变体则在 Agent 启动前提供资料包。两者分别标记，保留输入准备和工具的真实耗时。

| Agent | 直接前驱 | 第一项请求大意 | 后续请求大意与实际产物 |
| --- | --- | --- | --- |
| A 行为与接口 | 无 | 从 issue 和 API 文档定义期望行为、当前异常及接口约束 | 检查嵌套/非嵌套和边界输入，完成行为契约 |
| B 实现与调用关系 | 无 | 从现有代码定位相关实现与调用路径，引用文件/符号 | 沿必要代码路径补充证据、排除无关路径，完成实现说明 |
| C 现有测试与覆盖 | 无 | 检查已有测试对所述行为的覆盖及遗漏 | 对照边界场景核对遗漏，完成测试覆盖表 |
| D 根因分析 | A、B | 比较行为契约与实现路径，提出证据支持的根因 | 用代码和 issue 中的现象检查根因，完成根因说明 |
| E 兼容与回归风险 | B、C | 分析相关实现的使用范围及已有测试覆盖不足所带来的风险 | 检查风险依据和受影响接口，完成风险清单 |
| F 改动方案 | D | 提出与根因对应的最小改动方案及备选项 | 核对改动范围、边界情况和可执行步骤，完成方案 |
| G 回归测试方案 | C、D | 根据根因与覆盖缺口设计能区分修复前后行为的测试 | 核对断言、边界输入及已有测试关系，完成测试方案 |
| H 最终评审 | E、F、G | 综合方案、风险与测试计划，形成可交给开发者的评审报告 | 检查方案和测试能否覆盖风险，解决报告内冲突并交付 |

该 DAG 有共享前驱、多个局部汇合和跨层依赖；D 完成即可启动 F，F 不等待 E。测试执行与代码修改不属于此评审应用的产物，不以省略耗时冒充完整修复流程。评审质量可通过证据引用、根因与已知问题是否一致、测试方案是否可落地进行独立核验；应用完成后可在独立验证环境检查方案，不把验证用正确补丁泄露给生成过程。

## 5. 多轮与连续执行具体怎么实现

每个 Agent 在启动前取得全部必需前驱产物。它的内部请求只依赖自己的历史和已准备材料，不向其他 Agent 申请中途反馈。保留同一 system、全部 user/assistant 消息和真实工具结果；完成一次请求后进行本地协议检查，再追加新请求并立即提交。实际 GPU 开始时间可能受服务队列影响，必须分别记录。

多轮对应资料阅读、形成产物、证据核查和必要修订。比如 A 可以按不同产品资料组依次补充同一产品比较表；第二项任务是检验事实和可比性后形成交付版本。轮数随资料组和未解决问题变化，安全调用上限在 pilot 后冻结。不能追加无意义“再想一次”、sleep 或 padding；不能只把一次调用里的分步思考当作多次调用。所有 Agent 均有形成产物与核查产物的应用步骤，但没有要求每个角色相同轮数或运行时间。

记录完整序列化输入/token 和最长公共 token 前缀；聊天消息的 append-only 并不足以保证 tokenizer/chat template/推理内容处理后的 token 前缀完全相同。上下文溢出时报告失败或明确采用另一个带压缩的变体，不能静默裁剪后继续声称完整历史。

## 6. 怎样支撑典型性与论文 story

论文可以表述为：我们实现并采集了两个基于真实公开任务的多 Agent 应用，分别完成证据驱动的研究报告和仓库变更评审；应用采用并行专业分析、局部综合及最终核查等协作模式。任务来源和外部执行参考分别支撑现实需求与运行方式；具体 DAG 是本项目实现。

DeepResearchBench 作者根据真实用户查询主题分布构建研究任务，支持任务类别的现实需求。NVIDIA 报告的研究运行支持并行研究 Agent 和生成时间主导的一个实际例子；这不能证明本项目七节点 DAG 的生产发生频率。MAST 支持多角色软件任务的真实交互，SyFI 支持真实用户编码调用特征；两者都不能单独证明本项目八节点任务 DAG。

实验应沿一条链组织：

1. 正常运行显示各 Agent 的实际历史增长、调用次数、请求衔接、执行重叠和依赖。
2. 在同一 workflow 中，材料范围和职责不同导致剩余工作及故障影响不同；用实际 DAG/执行估计并评价这种差异。
3. 在相同故障、相同资源预算下，比较按历史/重建代价保护与按暴露于 workflow 的延迟保护。
4. 在受保护 Agent 内，额外测量真实模型的逐层 KV 需求和 DRAM/HBM 恢复时间，再评价有限 Peer-HBM 的价值。应用角色本身不证明访问热点集中。

主图展示接近应用正常执行特征中位数的真实案例，选择时不看 AegisKV 恢复收益。极端长历史、大 Slack 等压力情形可以另列受控实验，不能代替自然输入结果。两类应用提供应用范围证据，不能凭两个自建 DAG 声称涵盖全部生产多 Agent 工作流。

## 7. 实验执行顺序

先把两个起步任务跑通，核验输出质量与采集字段，再各执行约 20 个无故障 pilot；20 是起步规模，不是统计充分性证明。pilot 使用真实资料和实际模型，记录全部任务及失败原因。随后根据观测变异和所需精度确定正式样本量，冻结应用、任务集、模型/tokenizer、提示、停止条件和资料快照。

每个请求至少记录 `workflow_id`、`agent_id`、`invocation_id`、任务前驱、完整 messages/输入 token、前缀 hash、提交/开始/结束、执行 worker、工具起止与输出、产物引用。还需记录 workflow 结束/质量状态、实际 KV/命中/备份与故障恢复事件；仅有客户端日志不能证明物理 KV 行为。

正式比较使用相同冻结输入、故障规则和预算。固定内容的服务回放要保留前驱完成约束，不能把无故障绝对提交时间固定后禁止后继随恢复延后；其性能结论与在线生成时的应用质量验证分开。旧实验结果不进入新场景选择或新结论。
