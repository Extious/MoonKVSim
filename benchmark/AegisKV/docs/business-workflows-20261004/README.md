# 企业业务场景与逐轮 prompt

当前优先方案：企业软件采购选型、新品发布营销。它们替代先前论文审阅与新闻综合作为首选设计；先前图与说明保留为已引用的设计记录。尚未执行模型、接入生产应用或形成新实验结果。

两类业务都有公开企业 Agent 方案或实现依据，具体化后的工作产物也容易核验。这里选择的是“资料已备齐后进行文档推理与生成”的部分流程，固定角色、局部就绪 DAG、完整 Agent 历史及下面的逐轮拆分由本项目设计；不声称原应用就是此拓扑或已验证低工具耗时。

## 场景一：企业软件采购选型

具体用户任务：一家 300 人的软件公司，要比较三家知识库供应商；第一年含实施费用上限 12 万元，六周内上线，满足 SSO、权限、审计和导出等要求，交付建议书及采购前验证清单。金额与供应商材料只是演示，不是当前市场报价。

| Agent | 完整任务 | 示例输入的基础请求 |
| --- | --- | --- |
| A 需求分析 | 原始采购需求 → 可检查的需求矩阵 | 抽取要求；检查漏项、冲突与优先级并定稿 |
| B 产品比较 | 三家方案 → 统一事实比较表 | 读取甲；读取乙并保留甲；读取丙；核查口径并定稿 |
| C 安全约束 | 企业政策与三家方案 → 准入与缺证表 | 建立准入检查；审查证据、范围和未知项并定稿 |
| D 需求匹配 | A+B → 需求与候选匹配矩阵 | 逐项匹配；检查完整性与证据并定稿 |
| E 风险审查 | B+C → 风险与验证动作清单 | 列风险；去重、检查影响和验证动作并定稿 |
| F 选型草案 | C+D → 预选方案与取舍 | 形成预选；找反例并定稿，保留尚未整合的风险审查 |
| G 决策报告 | E+F → 最终建议书 | 用风险校核预选；按原始需求验收与定稿 |

为什么边必要：D 需要知道“要什么”和“各产品有什么”；E 需要知道“方案事实”及“公司准入条件”；F 可以先根据适配与准入形成预选；G 再用独立风险审查检验它。E 不审查尚未完成的 F 草案，F 不等待 E，因而没有隐含反馈环。

## 场景二：新品发布营销

具体用户任务：为示例企业知识库“知页”准备七天发布活动，面向研发与运营负责人，交付官网、邮件、公众号文案及 Day-3 至 Day+3 排期，统一 CTA 为“预约产品演示”。三个渠道与资产 ID 在用户任务中已确定；应用仅交付内容包，不发布内容或发送邮件。

| Agent | 完整任务 | 示例输入的基础请求 |
| --- | --- | --- |
| H 产品卖点 | 产品材料 → 有依据的功能与利益表述 | 抽取事实；检查卖点边界并定稿 |
| I 客群分析 | 两组访谈 → 客群与痛点 | 分析运营；分析研发；对照证据并定稿 |
| J 品牌规范 | 品牌及渠道规则 → 发布检查表 | 整理品牌约束；加入渠道限制并定稿 |
| K 传播主题 | H+I → 痛点—产品—主题映射 | 构建主张；核查客群与产品依据并定稿 |
| L 渠道策略 | I+J → 渠道用途与客群覆盖 | 分配三个渠道用途；检查覆盖与规则并定稿 |
| M 渠道文案 | J+K → 三个完整内容资产 | 官网；邮件；公众号；跨渠道核查并定稿 |
| N 活动排期 | K+L → 七天活动与资产需求 | 制定排期；检查触达上限、客群及资产 ID 并定稿 |
| O 交付编辑 | M+N → 可验收的发布包 | 将文案绑定排期并修订；最终验收与定稿 |

为什么边必要：传播主题要匹配产品与客群，渠道策略要匹配客群与规范。M 生产预先规定的内容资产；N 规划这些资产的用途与时间，不需要读 M 的成稿；O 检查内容与排期是否相容。M/N 可以独立推进，不设整层屏障。

## 连续多轮的具体含义

每个 Agent 只创建一次任务身份和 system prompt。第一轮得到全部直接前驱的不可变产物，并得到必要原始证据；后续请求保留全部先前消息与实际回复。逐份文档或分渠道工作在同一个 Agent 内完成。所有后续材料在任务开始前已存在于本地，编排器直接拼入消息，不引入网络检索或其他 Agent 的轮间等待。

完成基础步骤后，只有具体 issues 触发追加修订；上限为两轮，仍未解决则保留 needs_review。供应商数量、访谈文件和条件修订会改变调用次数，35 只是当前演示协议的基础请求总数。它不是测量，也不保证每个角色自然都需要此拆分；正式选择要检查分轮的质量价值，保留与合并调用比较的结果。

服务端排队仍可能造成相邻轮执行间隔；每轮完成、下一轮提交和开始要分别记录。实际 token 前缀和 KV 驻留另行检查，不用累计 messages 自证命中。完整 prompt 不裁剪；超出模型窗口时记录不适用或失败，不能静默改写历史。
