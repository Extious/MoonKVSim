# AegisKV 真实应用 workload：2026-10-04 约定

状态：用户需求已确定；以下主应用是待实现、待实测的方案。尚未产生新应用 trace、新实验结果或新的性能结论。旧实验不作为选择依据，全部实验需要重做。

## 1. 最新需求

- 使用有明确输入、实际模型执行和有用输出的真实多 Agent 应用。
- 每个参与的 LLM Agent 都有多轮调用，保留自己的任务说明、收到的信息和此前输出，使历史随任务推进而增长。
- 主场景优先不使用外部工具；使用工具的扩展场景必须记录真实耗时，验证其确实较短。
- 多个 Agent 构成一个 workflow，有实际的数据依赖、并行工作和完成后的汇总。
- 场景适配当前论文；重新采集、校准和执行实验，不沿用旧结果、旧图中的数字或旧实验规模。

“真实应用”与“现成应用原样运行”需分清：在公开框架上实现真实文档分析任务，可以形成真实应用执行证据，但必须说明这是新实现或适配版本，不能称为未经修改的上游 benchmark 或生产流量。

## 2. 当前论文的图语义

依据当前 [Background](../paper/background.tex) 与 [System Design](../paper/system_design.tex)：一次 invocation 是一次 LLM 调用；Tracker 的剩余图节点是一个未完成的 Agent 任务，一个任务可以包含多次 invocation。当前 System Design 明确要求执行前已知固定 Agent-task DAG；边 `a -> b` 表示 `b` 等待 `a` 的整个任务完成，内部调用次数和完成时间未知。

因此，直接适配的形态是固定任务之间的并行与汇合，各 Agent 在自己的任务内部迭代。若两个不同 Agent 在任务完成前反复互相反馈，展开调用可以得到 invocation DAG，但不能据此声称它满足当前 Agent-task DAG。需要扩展论文模型时应另行明确修改，不能静默改变语义。

图必须在第一个 Agent 开始前登记。规划 Agent 可以补充已登记角色的任务内容，不能在执行中随意新增角色或依赖。确定性切分器、拼接器和本地校验函数不计为 LLM Agent。

## 3. 优先应用：多文档协作分析与报告编写

输入为真实公开文档和实际分析问题，例如对一组论文进行方法、证据与限制的对比，或对一组产品规格形成有来源定位的需求报告。文档集、问题和来源快照在运行前固定；输出需要回答问题、引用原文位置并保留未解决的矛盾。

建议固定任务拓扑：规划 Agent -> 多个并行分析 Agent -> 汇总 Agent -> 编辑 Agent。

| Agent 任务 | 有实际意义的多轮过程 | 完成条件 |
| --- | --- | --- |
| 规划 | 生成分析清单，再核查清单是否覆盖用户问题和已分配文档 | 清单覆盖任务要求，或达到预先规定的调用上限 |
| 各分析分支 | 分批阅读分配的真实内容，形成证据记录，核查遗漏/矛盾，修订分支结论 | 文档已处理、证据检查完成，或明确输出未解决项 |
| 汇总 | 根据已完成分支生成报告，检查来源支持和分支间冲突，再修订 | 输出满足报告结构并标注剩余问题 |
| 编辑 | 完整审阅报告，核查引用/逻辑，再形成最终修订稿 | 通过约定的输出要求，或标记未通过项 |

所有阶段都保留同一 Agent 的完整消息序列。核查和修订是该 Agent 内部的新 LLM 调用；若实现成独立 Reviewer Agent，必须重新核对任务依赖，不能冒充同一个 Agent。调用上限是运行保护条件，不能作为运行时已知的最终调用次数。实际轮数由应用过程与停止条件产生，未通过检查的输出保留失败标记。

上述角色与步骤是候选实现，不构成典型性证据。是否需要规划/编辑角色、如何分工和何时复查，必须由真实任务与应用依据确定。不得为满足“每个 Agent 多轮”给天然单轮角色硬加调用或隐藏这些角色；不满足条件的应用应如实作为边界案例，不能宣称它已满足主场景。确定性编排器可以承担分配与汇合，但不能将没有模型调用的组件计为 Agent。

主场景直接接收准备好的文档内容，不进行在线搜索。workflow 计时从提交完整输入开始，到最终结果完成；内部模型核查、依赖等待、队列和应用处理时间均计入。准备公开数据集属于离线准备，不能将这种设置解释为在线检索速度的改进。

这是一项待实现的新应用方案。分支耗时、历史增长、可复用前缀和 Slack 必须由实际运行确认，不预设它们足够大或一定产生恢复收益。禁止随机 token 拼接、无意义补长、人为睡眠和重复整个 DAG 来制造轮数或分支差异。

## 4. 现成应用与框架的核验结论

以下是公开一手实现的检查，不是对本项目旧实验的分析。

| 候选 | 已确认的能力 | 尚不满足或需要核验的条件 |
| --- | --- | --- |
| ChatEval：生成文本的多 Agent 评价 | 官方示例使用两个角色、多轮讨论，配置为 `chat_history` 且 `tools: ~`；代码传入累计消息 | 讨论存在跨 Agent 的逐轮依赖，与当前任务完成后才启动后继的语义不同；最终评价还修改首条 prompt，原样执行不能保证历史 KV 前缀持续延长 |
| AutoGen Reflection：代码生成与审阅 | 官方代码含实际模型调用与反复修改；Coder 提交完整累计历史 | Reviewer 每轮重建“当前代码 + 最近反馈”的 prompt，未提交完整累计历史；两者互相反馈也需要额外的任务图解释 |
| LangGraph 报告编写示例 | 提供并行 worker 和汇总结构，使用实际 LLM 调用 | 原示例 worker 只调用一次，汇总是字符串拼接，不能当作“每个 Agent 多轮”的现成 workload；其 worker 动态创建也需要改为执行前登记 |
| Self-Refine | 作者实现说明包含生成、反馈、修订的循环以及历史保留 | 是内部迭代方法，本身不是多 Agent workflow；接入后仍需核验模板和实际 token 前缀 |

因此，目前不能宣布已有某个上游原样应用满足全部条件。优先方案可采用公开框架的并行编排和有意义的内部迭代方法，但应公开具体适配内容，并在真实执行后再确认是否适合作为主 workload。

## 5. 新采集的必要内容

- 固定应用版本、任务来源、原始文档、提示模板、模型/权重、tokenizer、chat template、推理后端和并行配置的版本或哈希。
- 独立记录 `workflow_id`、`agent_id`、`invocation_id`、固定任务 DAG 和实际调用依赖。Agent 身份限定在该 workflow 内，不以相同角色名混同不同用户任务。
- 保存模型实际收到的消息、输入 token IDs、接受的输出 token IDs 和停止原因。核对当前输入与此前已处理输入/输出序列的最长公共前缀；不能只看消息数量、文本长度或 prompt hash。
- 分别报告全体调用与后续调用的前缀覆盖率。前缀覆盖只是潜在复用；实际缓存命中、KV 字节和恢复读取来自服务端记录。
- 记录 workflow 提交/完成、任务就绪/完成、调用提交/开始/结束及工具开始/结束时间；区分依赖等待、排队、模型服务、本地处理和外部工具。无工具不代表无等待。
- 工具扩展场景报告真实耗时分布及 workflow 时间占比，预先定义“短”的判定规则；没有实测前不贴短工具标签，不删除慢工具样本或将其时间归零。作为工具调用的另一个 LLM 仍计为模型工作。
- 保存输出和质量核验，包括文档来源定位、问题覆盖、矛盾与未完成项。不得通过只保留长历史、正 Slack 或恢复收益为正的样本来筛选主数据集。

## 8. 如何构建及检验典型性

不能凭一个手写 DAG 保证其代表所有多 Agent 应用。可检验的目标是：在“固定 Agent 任务依赖、各 Agent 有实际多轮历史、无工具或短工具”的明确应用类别中，有来源、有质量验证、有无故障执行分布支持的代表性。工具密集或动态任务图的应用属于范围外，不能将其改成静态无工具版本后仍称为上游原样应用。

### 8.1 从真实任务和应用构造执行

- 以公开应用源码为优先参照，记录版本及对其角色、历史、停止条件和工具的每一项改动。不能把“使用了 LangGraph/AutoGen”作为应用代表性证据。
- 第一阶段评估两类任务来源：研究文档的证据问答，以及多文档新闻摘要。可分别采用 [QASPER](https://aclanthology.org/2021.naacl-main.365/) 和 [Multi-News](https://github.com/Alex-Fabbri/Multi-News) 的真实文档任务。QASPER 是单篇论文问答，不能称为现成多论文 benchmark；两者均不是已经采集的多 Agent serving trace。
- 每条 workflow 对应一个真实输入与一个用户所需的最终输出。根据问题所需的证据/文档分工，各分析 Agent 完成阅读、整理、必要核查和分支输出；汇总 Agent 在所需分支完成后综合、检查并修订。依赖来自实际输入输出关系，角色数量与多轮需求先于恢复实验确定。
- 一个 Agent 的多轮过程使用同一身份与自己的累积消息，新增文档内容、反馈和输出按实际发生顺序记录。轮数由任务完成条件产生，调用上限只防止失控；不设相同固定轮数，不通过额外调用拉长 KV。
- 公开框架的并行编排与 Self-Refine 的内部迭代可作为实现方法；组合后的应用属于本项目新实现，需要独立验证，不是原作者已验证的端到端工作负载。

### 8.2 先建立参考集，再冻结正式测试集

建议每类先执行约 20 个独立任务作为无故障 pilot，检查应用与采集是否可用；这个数字是起步规模，不是典型性或统计充分性的证明。pilot 不产生正式性能结论。

参考执行不启用 AegisKV、不注入故障、不按恢复收益筛选。能运行的上游应用按其原设置采集并单独保存；新应用使用真实任务分布采集。若没有未适配应用或外部任务分布作参照，只能报告任务驱动的新应用特征，不能声称已验证生产代表性。

按任务来源、文档数量和自然长度分层抽样，保留短、中、长任务与失败案例。工作负载特征与结果统计都以独立 workflow 为单位；同一任务的计时重复不增加独立任务数量。正式样本量依据 pilot 的变异及预先规定的置信区间精度确定，正式测试前冻结任务名单、模型、提示模板、停止条件、排除规则和采集版本。

### 8.3 检查的分布与质量

| 检查项 | 记录与比较 |
| --- | --- |
| 任务与协作结构 | Agent 数、依赖深度、并行宽度、join 结构与串行工作比例；每项有实际任务依据 |
| 多轮与历史 | 各 Agent 实际调用次数、完整输入/输出长度、历史增长、token 公共前缀及真实 KV 占用 |
| 时间构成 | 模型服务、队列、依赖等待、本地处理和工具耗时；工具 p50/p95 与时间占比分开报告 |
| 分支差异 | 分支剩余时长、故障位置处 Slack 的全分布，保留零 Slack 与分支接近的情况 |
| 完成质量 | 任务完成率、答案/摘要质量、来源支持、未解决项及超时；自评不能作为唯一质量真值 |

比较参考集与新 workload 的中位数、分位数和分布，并按应用分开报告。扩大样本不能替代应用多样性；在可用范围内增加独立应用实现或第二类任务，使用另一兼容模型检查结果是否依赖单一模型。把多种任务套入同一模板只能证明任务输入多样，不能证明应用编排多样。

不得用“长上下文、大 Slack、热点集中、恢复加速明显”作为主任务筛选条件。调用失败或输出质量较差的任务保留并报告；成功样本的延迟指标应明确其条件，不能把失败提前退出的时间当作快速完成。

### 8.4 选择论文展示案例

正式采集后，先按 Agent 数、调用次数、历史长度、并行结构和工具占比等非恢复收益特征选取接近本类中位特征的真实 workflow，再固定其 ID 用于相关 Motivation 图。选择过程必须在查看 AegisKV 效果前完成；强收益案例只能作为明确标注的个案，不能代替群体分布。

如果新运行显示前缀复用弱、多数分支无 Slack 或热点难预测，应保留结果并调整论文适用范围、应用选择的依据或系统设计。不能通过增加等待、无意义轮次和 padding 来使数据符合预期。现阶段上述构建与代表性验证均待执行。

## 9. 同一 Agent 的连续调用与两个场景图

2026-10-04 用户进一步要求：同一 Agent 的多轮调用连续。当前场景约束为：Agent 启动前获得所需外部依赖；其任务内部的下一轮只依赖自己的上一轮输出与本地已有材料，没有等待其他 Agent、用户或外部工具的步骤。一轮返回并完成本地停止检查后，立即追加历史和下一轮说明并提交调用。跨 Agent 的后继仅在整个前驱任务完成后启动。

这约束的是应用依赖，不保证服务端队列或 GPU 执行没有间隔。新采集必须记录相邻轮的完成、提交和开始时间，分别核验本地衔接与服务端排队；仍需核验实际 token 前缀及 KV 驻留，不能只凭“连续”推定命中。

已绘制的两个构造场景为：论文证据问答（A/B/C 并行，完成后汇合至 D）和多文档新闻摘要（E/F 并行，汇合至 G，再至 H）。全部 Agent 显示各自的多轮连续链与历史 KV 增长，但没有实测轮数或时间。它们是待实现与验证的场景，不构成应用代表性或性能证据，也没有替换当前论文图。

同日进一步明确：必须有实际执行重叠的并行 Agent，不能将有分叉的 DAG 在应用层串行执行。图已改为显式分叉—汇合布局，蓝色区域标出相互独立的分支。实现时并发启动全部兄弟分支，配置至少两个可独立执行的 DP 实例；W1 三分支全并行需要至少三个。TP 组内部的多个 rank 不计为独立 Agent 执行实例。新 trace 以实际调用服务区间和 worker 身份验证重叠，不能只凭提交或排队重叠下结论。

并行分支的剩余工作差异才可能提供可吸收恢复延迟的 Slack；拓扑本身不保证正 Slack 或算法收益。分支时间由真实任务产生，不能加 sleep、固定轮数或 padding 来制造差异。共同故障、共享资源以及零 Slack 的情况都需保留并重测。
