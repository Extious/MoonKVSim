**同一请求中不同 token 段的 KV 保护价值**

少量 Peer HBM 与 DRAM 共同保存一个请求的历史 KV。请求级优先级已经确定；本分析只讨论请求内部的 token 段，暂不展开分层恢复，不使用“越靠后重算越贵”的解释，也不向原本的 dense 模型添加近似稀疏化。

在这些条件下，应区分三种价值来源：原生模型规定的访问差异、恢复路径造成的等待差异，以及备份进度造成的状态完整性差异。后两种不要求稀疏 attention，但也不能被写成 token 内容具有天然的重要性。相关文献支持这些机制的存在，尚未替代对有限 Peer 容量下恢复收益集中性的验证。

| 候选 | 不同段为何有差异 | 是否适合当前静态完整备份场景 | 初步判断 |
|---|---|---|---|
| 原生固定访问段 | 某些初始块、局部块由模型规则确定为必需 | 是，限定对应原生模型 | 机制直接、可解释；单独固定规则创新有限 |
| 原生动态访问的恢复工作集 | 少数段在恢复初期更可能被访问，且难以及时预取 | 是，限定原生动态稀疏模型 | 最贴近请求内选段，但与现有 offload 缓存工作接近 |
| 少量慢路径段 | 段的所在节点、排队和实际传输布局造成不同读取成本 | 是，前提是实际存在路径差异 | 适合 dense 精确恢复；依赖真实部署证据 |
| 最新未完成 DRAM 提交的段 | 决定能否维持较新的完整恢复点 | 需要把范围扩大到在线备份过程 | 容错动机强，但不属于相同完整快照内的读取价值排序 |
| 请求内部共享分支的前缀 | 一段 KV 服务多个候选分支，具有复用价值 | 需要一个逻辑请求包含多条生成分支 | 适合采样、搜索工作负载；不适用于严格单序列请求 |

**1. 原生规则中的必需段：有模型结构证据的选择**

NSA 同时具有 compression、selection 和 sliding-window 三个分支。其论文实验配置在 selection 分支每次选择 16 个块，每块 64 个 token，其中包含固定激活的 1 个初始块与 2 个局部块；另有 512-token 的滑动窗口分支。这说明特定模型确实可以原生地赋予不同历史段不同的访问地位，无需在推理时删除 dense attention 项。[^1]

一个可核算的例子是：在 64K 历史长度下，3 个固定块只涉及 selection 分支候选 token 的 192/65536，约 0.29%，却占每次选中块数的 3/16，即 18.75%。这只是该分支、相应层和 KV 组下的访问数量比较，不是全部 KV 字节的比例，也不是恢复时间改善比例。不同分支有各自的 KV 状态，必须把它们纳入容量和读取核算。

可研究的放置方法是先保护由原生规则确定的近期必需块，再用剩余预算覆盖动态选择的块。局部块随逻辑进度移动，其价值来源是当前访问规则，而非后段计算成本。模型规则不强制访问的历史段，仍保存在 DRAM；未来被选中时必须读取。

另一个相关结构来自 Gemma 3：它采用 5 个局部层与 1 个全局层交替的设计，局部窗口为 1024 tokens。这支持 token 位置与 layer 联合决定所需状态的分析，但全局层仍需要其完整历史。[^2]

这里有两个边界。首先，已经永久离开原生局部窗口、也不再被任何分支需要的状态，不应计入“本来必须恢复”的 KV 分母。其次，“固定保护初始块和窗口”很可能只是基线，论文贡献还要包括恢复期限、动态段选择或保护成本方面的新问题，不能单靠识别模型已有掩码。

**2. 原生动态访问中的恢复工作集：关注实际阻塞读取**

在原生动态稀疏模型中，一段 KV 的价值取决于恢复后的近期 query 是否会选中它，以及 DRAM 能否在其使用前完成搬运。可以把恢复后若干步实际需要的历史 KV 记为 A_1、A_2、……、A_H。备份集合应该覆盖高概率、来不及预取的读取；历史 attention 分数本身并不是最终目标。

ECHO 提供了较直接的机制证据。它面向原生 DSA 模型，把索引 K cache 保留在 GPU，并对所选 MLA KV 做缓存和 recall；预取没有覆盖的必需 token，会在 attention 前进行 guaranteed recall。其 InfiniteBench 实验中，多数层的 GPU pool 命中率为 0.97–0.99，另有层为 0.95 和 0.88，支持选择结果具有复用性的研究方向。[^3]

这些数值来自正常服务、论文指定的 GPU pool 配置和跨 decode 步平均，不能推出“故障前只备份 5% 字节就能达到 99% 恢复命中率”。尤其应分清以下三个集合：一层一次 query 的选择集合、所有层与 KV 组的物理字节并集，以及恢复初期多步选择的并集。第一个集合很小，不保证后两个集合仍小。

故障本身也不意味着模型在相同逻辑进度突然换了一种语义访问模式。恢复特殊性主要在于目标 GPU 的缓存冷启动、故障前可用信息有限，以及有限的 DRAM 预取窗口。因此，可成立的研究问题是：能否用故障前可得的近期索引轨迹，构造一个小而有效的恢复初始缓存？

评价时要记录“首次需要且尚未到达的字节”和真实等待，而非把每次逻辑命中都当成一次 DRAM 读取。某段一旦搬进恢复 GPU 并持续驻留，再次访问可能已没有额外恢复成本；只有发生未完成加载或再次换入时，复用才继续影响传输。按层、按组的索引和 compression 等额外状态也必须计费，不能把它们当成免费存在。

这条路线与 ECHO 的运行期缓存和预取非常接近。新贡献必须通过对照体现：故障前有限 Peer 放置如何初始化目标 GPU 的工作集，以及它相对于正常缓存策略、纯 DRAM 的原生 recall 和离线最优选择能减少多少首个可提交输出的等待。

**3. 少量慢路径段：dense 模型也可以有不均匀的恢复价值**

即使每个历史 token 都必须参与 attention，不同段仍可能有不同的物理读取路径。例如，一个请求的大部分段在相近的 DRAM 节点上，少数段位于拥堵节点、不同 NUMA 路径或难以有效聚合的传输布局中。真正需要观察的是这些差异在当前部署中是否存在，并且能否在故障前预测。

Mooncake 的调度分析明确指出，KV 传输时间不仅由字节数决定，还受发送节点拥堵影响，并通过复制热点块缓解获取拥堵。这支撑对不同存储来源成本的建模；它没有证明一个请求的少量段总会主导故障恢复。[^4]

Strata 则指出，小页与分散布局可能让 KV 传输不能充分利用带宽，并实现 GPU-assisted I/O 与不同层级的布局管理。其机制提醒我们，同样的逻辑 token 数并不自动意味着相同的物理 I/O 成本；同时，它也是必须纳入的强基线，因为许多碎片开销可以通过更好的搬运实现消除。[^5]

在并行读取的简化模型中，恢复屏障可写为：

    T_load(S) ≈ max over paths j of [queue_j(S) + bytes_j(S) / bandwidth_j]

如果只是把一个已经很快完成的段移到 Peer，剩余慢路径仍决定完成时间；移走拖慢最晚完成路径的段，则可能直接缩短屏障。实际分层流水执行应将其放进完整事件图计算，而不是只使用这个全量读取公式。

例如，假设 95% 字节走一条 2 ms 完成的路径，5% 字节走另一条 10 ms 完成的路径，且两者并行。若后者能预先放到 Peer 并在 2 ms 内到达，读取屏障可由 10 ms 降至 2 ms。这只是说明可能性的假设例子，不是测得的 80% 改善。

该方向的风险同样清楚：如果所有段都来自同一块已注册 DRAM、统一布局和固定带宽，且不存在可识别的等待差异，那么按相同字节大小选段的价值可能几乎相同。不能靠人为设置一个极慢的段制造论文动机，也不能仅用低效逐页复制作为对照。应先在优化后的实现上测得段级差异仍然存在，再设计 Peer 策略。

**4. 异步备份的提交窗口：新鲜状态的保护价值**

这是一条不同于“后段重算更慢”的容错思路。在常规 append-only decode 中，旧 token 的 KV 通常已经固定，而新增 token 的 KV 正在生成和复制。只有最新的一小段尚未完成 DRAM 提交时，它会限制最新可用的一致恢复点。

一个候选协议是让新段优先完成 Peer 备份，同时由源端推进 DRAM 复制；DRAM 副本提交后，该段的 Peer 空间才可按策略释放给更新状态。这不要求预先假定所有 Peer 数据都具有 DRAM 副本，但需要明确每一段的复制状态、token 游标以及跨层/跨 shard 的一致性。

DéjàVu 已有按 token 增量、异步复制 KV 的机制，并跟踪复制到哪个 generation step；故障恢复时，从尚未完成复制的相关步骤重新执行。它直接支持“复制进度会影响恢复点与重放范围”这一事实。[^6]

新的研究问题可以是：在给定 Peer 容量和复制干扰预算下，能否显著缩短未保护状态窗口？比较指标应包括故障时的复制落后量、需要重放的 token 数、输出一致性及实际服务开销。

必须把这一问题与当前静态放置问题分开：若同一时刻全部 KV 已经在 Peer 或 DRAM 完整提交，且比较各策略时恢复点完全相同，提交新鲜度本身不会再使某段读取更有价值。普通模型也不会因为最新段“更新过”而使相同字节的加载自动变慢。在该条件下，仍要回到原生访问差异或真实路径差异。

**5. 一个逻辑请求内部的分支共享：有条件的扩展**

如果一个逻辑请求执行多个候选采样或树形搜索，共享前缀可被多个分支重复使用，而某个分支的独有后缀只服务该分支。Hydragen 证明，可以将共享前缀与独有后缀的 attention 分开计算，再合并为数学上等价的完整 attention，并扩展到树形共享结构。[^7]

这允许研究具有多个消费者的 KV 段，例如保护能够帮助更多关键分支启动的共享状态。但不能把逻辑复用次数直接乘到物理传输字节上：若恢复 GPU 本来只加载一次共享前缀，各分支已共享同一份驻留 KV，就未必有相应的重复传输可省。

因此，需要针对目标指标证明边际收益，例如同一个问题的多个候选完成时间或搜索路径等待。严格单序列请求没有这项差异；它也不能重新包装已经完成的请求级 Slack 排序。

**当前不应作为独立动机的说法**

- “system prompt、检索证据或工具定义语义更重要”：这可能影响注意力或输出敏感度，但对必须读取所有历史的 dense 精确恢复，尚不能推出可减少传输等待。需要原生访问规则或其他机制把语义与实际读取联系起来。
- “先到的任意一段能启动局部 attention”：精确 attention 确实可分段计算后合并，但在大小和路径相同的条件下，其他任意段也可能提供相同的启动作用。这支持流水化，不自动支持特定内容段更重要。Hydragen 提供了相关精确分解机制。[^7]
- “压缩摘要可以代替完整 dense KV”：原生模型已训练使用的压缩分支可以按原模型执行；事后给 dense 历史增加摘要会改变计算合同。索引或压缩状态也属于额外状态类型，不能直接冒充原始 token 段。
- “少量未提交 KV 解锁大量完整状态，所以收益等于全部状态”：必须根据可运行恢复点和实际关键路径核算，不能把被依赖的字节数量当作节省时延。

**应先验证的两个问题**

第一，对原生模型记录真实 block/token selection，冻结一个故障逻辑位置，仅允许使用故障前轨迹做选择。比较固定必需段、最近访问、访问频率、恢复期限感知与离线 oracle，在不同 Peer 字节预算下的首个可提交输出时间及前若干步等待。全 DRAM 对照应使用相同的原生访问与预取机制。若原生工作集按层、组和时间求并集后不再小，或低预算在线策略不能覆盖近期阻塞读取，应保留该负结果。

第二，对 dense 模型测量优化后 DRAM 读取的段级完成时间，保留源节点、NUMA/网络路径、传输批次和竞争信息。固定 Peer 字节数，比较随机段、位置段和根据故障前可观测路径选择的段。若这些策略相差很小，说明该环境缺少内容段选择的依据，分层恢复仍可作为独立路线保留。

本补充分析的判断是：原生动态工作集最贴近 token 段选择；慢路径段是可以扩展到 dense 精确恢复的候选；提交窗口与分支共享分别需要扩展在线备份或请求结构的假设。尚无本地 GPU 或故障恢复实验结果用于证明这些候选的收益。
