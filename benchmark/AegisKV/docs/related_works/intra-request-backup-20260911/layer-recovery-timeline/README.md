# 分层恢复时间线：少量 Peer HBM，其余 DRAM

本图解释一种基于分层 KV 管理的恢复执行方式，是分析性示例，不是 LayerKV 论文的故障恢复实验，也不是当前 MoonKVSim 已实现机制的证明。

LayerKV 的相关原始机制是按层管理 KV 位置、使用独立 CUDA 传输流，并在 decode 中逐层把历史 KV 从主机内存加载到 GPU。其正常运行策略可以交错保留部分层的 KV；它并未提出本图中的“故障后先从 Peer 加载首层”策略。来源：[LayerKV，第 3.1.2 节与第 4 节](https://arxiv.org/html/2410.00428v3)。

## 时间线的含义

- t=0 前：故障检测、选择恢复 GPU、准备模型权重、恢复一致的 token 游标及 KV 位置元数据。图中不计这些启动成本。
- t=0：同时启动 Peer 与 DRAM 的历史 KV 加载。两者合起来保存全部所需状态；不要求 Peer 中的部分另有 DRAM 副本。
- 首层历史 KV 到达后：对当前待处理 token 执行首层计算，同时加载后续层的历史 KV。这里移动的是已经计算好的历史状态，不是重新运行整个 prompt。
- 后续层：等上一层输出的当前 token 隐藏状态、本层所需的全部历史 KV 都就绪，再执行该层。新生成的当前 token KV 正常写入恢复 GPU。
- 最后一层结束后：经过输出头与采样才能产生下一个输出 token。只完成首层并不能提交输出。
- 本例假设恢复 GPU 能保留全部恢复后的 KV；完成一次加载后，继续普通 decode。若 GPU 无法容纳全部 KV、每轮还需换入换出，则是持续分层 offload 模式，需要逐轮核算传输。

## 可核算的假设与结果

共 10 层，每层历史 KV 字节量相同；每层 DRAM 加载 1 ms，Peer 加载 0.1 ms，当前 token 的整层计算 2 ms。假设两条传输路径与计算能够并发，队列各自顺序运行，有足够缓冲，且没有共享资源竞争导致的额外减速。

Peer 中的 10% KV 指“第 1 层全部历史 token 的 KV”，不是“所有层前 10% token 的 KV”。

| 事件 | 全 DRAM，按层流水 | 首层 Peer，其余 DRAM |
|---|---:|---:|
| 首层 KV 就绪 | 1 ms | 0.1 ms |
| 首层计算 | 1–3 ms | 0.1–2.1 ms |
| 第二层 KV 就绪 | 2 ms | 1 ms |
| 第二层计算 | 3–5 ms | 2.1–4.1 ms |
| 全部历史 KV 搬入完成 | 10 ms | 9 ms |
| 第十层计算结束 | 21 ms | 20.1 ms |
| 首个新输出就绪 | 21 ms + 输出头及采样时间 | 20.1 ms + 输出头及采样时间 |

第二种方案在 1 ms 时已经拿到第二层 KV，但要等到 2.1 ms 第一层计算结束，才能开始第二层计算。其余加载都在 GPU 需要它们之前完成，所以不会再产生 KV 等待。

按整层边界简化，令 a_l 为第 l 层历史 KV 到达时间，C_l 为该层当前 token 的计算时间：

    s_l = max(f_(l-1), a_l)
    f_l = s_l + C_l,  f_0 = 0
    R = f_L + T_head

这是整层计算的简化模型；更细粒度实现还可能在历史 KV 就绪前提前执行部分投影等算子。这里不要求整层成为最细的调度单位。

## 对研究问题的直接含义

首层 Peer 在这个例子里减少 0.9 ms 的启动等待，使首个输出提前 0.9 ms。忽略共同的输出头时间，21 → 20.1 ms 是约 4.3% 的整体下降。若所有层都在 Peer，本例也约为 20.1 ms：因此少量 Peer 获得全部额外 Peer 加速，与整体加速幅度很大是两个命题。

若使用“全部 DRAM 加载完再开始计算”的方案，则为 10 + 20 = 30 ms，加上输出头时间。30 → 21 ms 来自分层流水，21 → 20.1 ms 才来自本例的 Peer 放置；论文必须分别归因。

此例不证明首层总是最重要。若每层 DRAM 加载变成 5 ms，首层计算虽然在 2.1 ms 结束，第二层 KV 仍要到 5 ms 才就绪，会新增 2.9 ms 等待。真实 Peer 选择应考虑哪一层或哪一组块无法在使用期限前从 DRAM 到达，以及选择其他块后这些期限怎样变化。
