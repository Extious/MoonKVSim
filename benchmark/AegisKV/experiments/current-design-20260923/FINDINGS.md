# 首轮结果解读

数值来自本目录 `STATISTICS.json`、`paired-workflows.csv` 和逐运行 `summary.json`。
均为未校准模型结果；dense/构造 sparse 各包含三个种子、共九个工作流样本。

1. **目前主要收益来自完整 DRAM 检查点。** Dense 场景的平均故障 WCT 为无备份
   10.9539 s、DRAM-only 10.8157 s、AegisKV 10.8143 s。代表性 seed=7 的目标调用
   重建量从 6,247 tokens 降到 103 tokens。DRAM-only 与 AegisKV 避免的是相同重建。

2. **当前参数没有证明 HBM 有显著的额外收益。** Dense 平均 WCT 只再减少约 1.4 ms。
   构造 sparse 场景中 AegisKV 为 10.7845 s，DRAM-only 为 10.7829 s，AegisKV
   反而约慢 1.6 ms。保留全部逐 ID 结果；不根据这些小样本反向调参制造正收益。

3. **重试队列会限制观察到的收益。** Dense seed=7 的目标调用在 retry worker 上
   排队 1.6186 s；这部分对三个策略相同。故障检测、排队和恢复执行分别计时，
   并通过精确加和验收。WCT 的跨工作流影响由实际队列/DAG 推进产生，没有把单 Agent
   的 Slack 截断式直接当作最终工作流完成时间。

4. **256-token 粒度不能保证异步尾部至多 256。** 慢复制场景 seed=7 中，检查点只
   提交到 1,024 tokens，故障时已有 6,247 tokens，因而需要重建 5,223 tokens。
   若论文要保留“至多 256”的保证，需要额外的生成背压或其他可证明的提交条件。
   当前实现如实记录滞后，不把未提交数据当成可恢复检查点。

5. **容量和 λ 会让目标 Agent 退回重建。** 本轮 DRAM 压力及 λ=1 s 场景中，目标
   Agent 没有完整 DRAM 检查点，故障 WCT 与无备份相同。这是筛选/完整检查点粒度的
   边界，不应从最终汇总中删除。

下一阶段若要得到论文级结论，需要换入经过依赖与精确前缀核验的真实 Agent trace、
原生稀疏选择序列、校准的剩余时长预测与 L/K、以及连续批处理/传输干扰成本。
当前默认 L/K 和带宽都是实验配置，不能称作已离线校准的部署参数。

源文件、字节账和链路速率的独立核对见 `AUDIT.json`；85 项测试及检查记录见
`VALIDATION.json`。初次路由错误和修正统计字段前的数据分别保留在相邻目录，当前
`MANIFEST.json` 固定了最后一次重跑实际使用的代码和论文设计。
