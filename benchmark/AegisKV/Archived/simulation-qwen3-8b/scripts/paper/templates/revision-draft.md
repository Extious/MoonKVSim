## Motivation

多 Agent 应用将一次任务组织为模型调用、工具调用与汇合结点组成的依赖图。用户等待整个 Workflow 完成，而汇合结点必须等待所有前驱。因此，恢复时间的节省只有传递到依赖图的完成时间时，才产生用户可见收益。本文以 Workflow Completion Time（WCT）作为保护目标，即从 Workflow 首个请求释放到最后一个请求完成的时间。

[Mooncake](https://www.usenix.org/conference/fast25/presentation/qin) 利用分布式 KV 存储减少重复计算，[DéjàVu](https://proceedings.mlr.press/v235/strati24a.html) 将 KV 流式复制用于故障恢复。AegisKV 关注这一能力在多 Agent 工作流中的资源分配问题：当容量和复制带宽有限时，应保护哪些已生成状态，才能减少故障对整个 Workflow 的影响，同时控制正常推理的代价？这个问题需要同时理解分支时间差、故障恢复代价以及保护与前台服务的竞争。

### Observation 1：并行分支具有显著的执行时间差

公开 [CC/Weka 轨迹](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126)提供了分支执行不均衡的观测依据。我们保留存在共同重叠区间的并行分支组，并对每个 Workflow 取最大的最长与最短分支持续时间差。图 {{ref:motivation-branch-gap}} 中，124 个符合条件的 Workflow 的中位差值为 140.6 s，P90 为 1,570.3 s。这说明不同分支距汇合完成的时间余量可能相差很大；持续时间差本身并不等于故障时刻可使用的 Slack。

### Observation 2：重算代价的排序不等于 Workflow 损失的排序

图 {{ref:motivation-recovery-exposure}} 使用同一个五分支轨迹示例，分离恢复暂停中被并行执行吸收的部分与推迟汇合的部分。对每条分支分别在 349.5 s 假设一次故障，保持其他分支的执行不变。若恢复增加的时间为 $T_i$、分支到原汇合终点的间隔为 $s_i$，暴露的延迟为

$$
J_i=\max(0,T_i-s_i).
$$

A3 的假设重算时间最长，为 46.6 s，但其 52.4 s 的间隔可吸收全部暂停；A4 的重算时间较短，为 35.9 s，却因处于关键分支而全部暴露给 Workflow。仅按 KV 大小或重算时间选择保护对象，可能把资源分配给不改变完成时间的分支。保护优先级需要结合 Agent 的执行位置、恢复代价与剩余 Slack。

{{row:motivation-branch-gap,motivation-recovery-exposure}}

图 {{ref:motivation-recovery-exposure}} 是轨迹锚定的反事实算例。其暂停参数沿用旧 Qwen3-235B/A100 模型预测，不能作为可部署并行配置的性能测量；该旧预测的 PP 配置未获得物理验证。这个算例说明评价目标的差别，不估计部署收益。真实故障还会改变排队和其他分支的进度，因而后文同时检查恢复过程与完整 WCT。

算例中的 Slack 来自离线轨迹终点；在线决策只能使用当前估计。上式仅描述单分支暂停且其他分支及资源竞争保持不变的情形，不作为多个分支同时恢复时的完整 WCT 公式。

### Observation 3：长上下文放大故障后的重算代价

Agent 在多轮模型调用中积累上下文；当执行该请求的 GPU 故障，未保留的 KV 必须重新计算。图 {{ref:motivation-recompute}} 固定模型和并行配置，只增加需要重建的前缀长度。上下文从 16 Ki 增至 128 Ki tokens 时，Qwen3-8B 的完整前缀重算预测由 0.49 s 增至 9.16 s，Qwen3-32B 则由 1.72 s 增至 32.82 s，分别增长 18.7 与 19.1 倍。

{{fig:motivation-recompute}}

长上下文使一次故障后的状态重建成为不可忽略的计算开销。它能否转化为同等幅度的 Workflow 延迟，仍取决于分支 Slack、恢复来源与排队。该图沿用旧论文的上下文—重算曲线，使用历史 AIConfigurator SILICON 预测；不包含检测、传输、排队或故障实测，也不与后文 DP8/TP1 模拟混合统计。

三条 Observation 导出 AegisKV 的设计目标：优先保护会影响 Workflow 终点的 Agent 状态，通过已提交前缀减少长上下文重算，并在有限的 DRAM 与 Peer HBM 中保留高价值副本。保护同时可能改变正常复用、占用前台显存并消耗 CPU 与带宽，因此其正常成本与故障收益必须共同评价。

这些观测形成三个设计要求。首先，保护价值应考虑当前 Agent 的 Slack，不能仅按状态大小或重算时长排序。其次，共享前缀必须作为物理对象管理，避免重复复制和重复计费。最后，备份借用必须能随前台压力退让；内存容量可行不代表传输与控制没有干扰。三个要求分别由 Agent 价值与租值准入、独立分层副本和前台约束控制实现，并在评估中分别检验。

## System Design

### 系统模型与故障范围

AegisKV 管理已生成 KV 的保护，应用侧仍拥有 Workflow 依赖关系、请求输入和执行进度。系统使用执行时已经可见的结点与状态，不提前获知未知工具结果或未来分支。目标是降低故障条件下的 Workflow 完成时间；正常复用、计算、控制和传输成本是共同约束，而非可以忽略的免费资源。

本文考虑执行 GPU 的 fail-stop 故障：该设备的 primary、正常可复用 cache 与本地备份 KV 均不可用，应用、Router、元数据服务及其他故障域继续运行。副本必须位于源设备以外的存活故障域；同机另一 GPU 不自动构成节点掉电保护。当前评估固定设备故障和停机时长，不涵盖控制平面故障、网络分区或相关节点故障。模型权重、输入以及已确认的输出 token 序列和位置必须能够在健康 Worker 获得，以重放未被 KV 保护的已确认后缀，KV 保护也不替代工具调用副作用的事务恢复。

### 面向物理 KV 对象的系统架构

图 {{ref:system-overview}} 展示 AegisKV 的系统架构。应用侧提供当前可见的 Workflow DAG 与 Agent 状态；价值接口结合恢复代价与 Slack 更新 Agent 的保护优先级，池级准入决定保留哪些物理 KV chunk。目标 GPU 上的独立显存控制器根据前台需求和 forward 反馈约束备份借用。

{{fig:system-overview}}

源 Worker 持有正常推理的 primary KV。密封的 C0、C1 独立复制到 Peer HBM 和 DRAM Store；每条路径分别分配空间、执行传输并确认提交。一层拒绝或丢失副本，不改变另一层已提交的同名对象。多个 Agent 共享 C0 时，同一存储池只计一份物理容量。Peer Worker 的前台 P0、P1 与备份 C0、C1 占用不同物理地址。

图中两条复制路径表示独立候选，不保证每个块始终具有两份副本；容量、准入和传输完成情况决定各层实际可读前缀。保护决策被拒绝时，正常推理继续执行，并保留回退到存活层或重算的路径。

Router 撤销旧执行权限，将请求迁移到原有的健康 Worker，不增加额外恢复 GPU。图中的 Peer 与恢复 Worker 表示角色，可以由同一健康设备承担。恢复过程在新的 primary 分配中装入兼容、连续、已提交的前缀，再重算缺失后缀并恢复解码。图中恢复的是 C0、C1，重算的是 C2；pending 副本不可读。副本身份包含模型、数据类型、布局和分片，不能跨不兼容布局复用。分片布局改变时，只有所有必需分片均兼容且可用的前缀才能参与恢复。

### Agent 价值、共享对象与池级准入

应用侧随请求进度与工具返回更新可见的剩余 DAG。对正在执行的结点估计剩余时间，对已知但尚未开始的结点估计完整时间；未知分支不预先计价。请求携带本次决策使用的 Slack 快照，池内一次估值与准入试算使用同一份快照。后续请求可以携带更新值，但不在一次试算中混入变化的预测。预测 Slack 只是恢复损失的估计依据，不保证真实剩余执行时间。

准入以物理块为容量单位，以 Agent 的价值和信用为保护依据。一次请求只触发当前 Agent 在相应块上的估值与续租；其他共享者可以结算已经发生的租金，但不会因为这个请求而重新估值或补回信用。共享块聚合租后份额，却只占一份物理容量。候选块与可释放尾块进行容量竞争；在读、未完成复制或仍有必要后继的前缀，不因账面淘汰立即变成可用空间。

这种方法把请求级收益与共享物理容量联系起来，但各 Agent 的信用之和不是完整 DAG 期望损失的精确解，也不直接继承经典缓存算法的最优性保证。保护当前恢复价值还可能与保留未来重访前缀发生冲突；有效复用实验和算法 2 消融将检验这一取舍。算法 2 仍在调整，本稿固定以上接口与语义，后文冻结版本的数值不用于证明尚未实现的修订。

### 副本发布、回收与恢复的约束

价值估计、账本提交、复制发布和物理释放具有不同的完成条件。试算不改变真实可读集合；复制完成及身份核验后才发布副本，释放确认后容量才可复用。三条约束贯穿正常路径与恢复路径：

| 约束 | 设计含义 | 需要观察的结果 |
|---|---|---|
| 已提交且兼容的连续前缀才可读 | 不读取 pending 或缺分片对象；独立确认两条复制路径 | 已提交覆盖率、实际恢复来源、失效身份拒绝 |
| 物理地址释放前持续计费 | copying、committed、reclaiming 与 recovery-primary 分开计量；额度下降不提前复用地址 | 实际占用、回收完成、前台分配可行性 |
| 故障后旧执行权限失效 | 新路由装入前缀并从已提交进度继续，处理迟到的完成事件 | 无重复或缺失输出位置；完整 WCT 与后续释放变化 |

这些是设计契约，不能仅由流程图证明。状态与输出检查用于验证实现正确性；性能实验另行判断减少的重算是否足以抵消复制和争用。

发布要核对副本代次、源执行权限和所需分片；迟到 ACK 不能发布过期对象。回收先撤销新读取资格，再等待已固定读取或 DMA 结束并归还地址。未执行试算失败可以直接丢弃，执行阶段失败则按已经发生的分配和释放清理，不能假定已释放的旧副本自动恢复。

### 前台约束下的 Peer HBM 控制

Peer 控制器与价值及信用计算独立。它区分备份可用显存硬上限 $C_{\mathrm{HBM}}(t)$、授权字节数 $B(t)$ 和仍占用物理地址的备份 $U(t)$。硬上限扣除固定开销、前台分配、下一步需求与保留量，并受实际分配器限制，授权满足

$$
0\le B(t)\le C_{\mathrm{HBM}}(t).
$$

稳定且有备份需求时，Guarded AIMD 逐步增加授权；forward 预警触发乘法退让，新的前台需求直接裁剪硬上限。降低授权不等于立即释放物理地址：pending、committed 和 reclaiming 字节都持续计费，直到 DMA fence 与释放完成。前台分配必须检查真实物理可行性。

收缩期间 U 可以暂时高于新的 B，不能把授权差额直接视为已空闲地址。可借总额度须包含已借给保护的页，而非只读取当前 free bytes；正常可复用 cache 仍是前台占用。额度控制不能替代共享传输限速，forward 没有预警也不等于没有干扰。

这一区分也决定评估方式。前台缓存已经占满 HBM 时，安全控制器可能不允许 Peer 备份；此时不能用“系统配置了 Peer HBM”代替“故障时存在可用 Peer 副本”。恢复前缀装入完成后，后缀重算、调度等待与其他分支仍会影响最终 WCT。

因此，AegisKV 的预期适用区间是：有兼容且有用的已生成前缀、故障前有足够复制时间和可借资源，且恢复节省能穿过分支 Slack 传递到终点。在没有可借空间、链路接近饱和或预测明显偏差时，收益可能减小甚至反转。评估必须覆盖这些边界，不能只展示成功形成副本的故障。

## Evaluation

### 实验设置与证据范围

评估依次回答四个问题：正常保护引入了多少服务代价；同一故障如何改变同一 Workflow 的完成时间；变化能否由已提交副本、重算和排队解释；收益在多大资源与负载范围内成立。三条系列为 Mooncake、DRAM-only AegisKV 和 AegisKV。DRAM-only 保留 AegisKV 的 DRAM 准入并关闭 Peer，用于分离两类机制；它是内部对照，不代表另一套外部系统。

默认模型为 Qwen3-8B BF16，DP=8、TP=PP=1；模拟资源为 8×40 GiB GPU、1 TB DRAM Store、25 GB/s 共享路径，KV chunk 为 4096 tokens。输入包含 160 个 FanOutQA-derived Workflow，每个完整 DAG 执行两轮精确重访，共 2608 个请求，默认最大活跃 Workflow 数为 16。这是控制复用压力的负载构造，不代表生产重访频率。

F0 表示无故障，F1 表示一次预定故障。一次运行处理整套输入；逐 Workflow 图中的点是同一逻辑对象，完整运行的重复才用于估计运行间不确定性。本节图像使用冻结参考算法的离散事件模拟，GPU 时序尚未经过目标硬件标定；Mooncake 系列是共享引擎中的策略基线，不能称为完整原生 Mooncake 部署。新扩展只改变预定并发或故障注入，算法 2/3 保持冻结。

冻结模型的 DMA-to-forward 慢化系数为零。因此，它能反映已建模的容量、路由和共享传输排队，却不能检验保护 DMA 对真实 GPU forward 的减速。P2 的原生干扰测量用于补足这一缺口，当前模拟中没有 forward 慢化不构成无干扰证据。

WCT 从 Workflow 首个请求释放计到 DAG 完成。同一配置下按 Workflow ID 配对，逐对象曲线沿用冻结 Mooncake F0 顺序，三系统不各自排序。并发限制在 Workflow 释放前产生的等待不含在该 WCT 中；因此扩展同时报告完成速率或批次时长，不能仅用较小的已准入 WCT 宣称吞吐改善。

设 $W_{s,i}^{0}$ 是系统 $s$ 无故障时 Workflow $i$ 的 WCT，正常开销为 $O_{s,i}=W_{s,i}^{0}-W_{M,i}^{0}$，其中 M 表示同配置 Mooncake。故障效应先在同系统、同 ID 内计算 $D_{s,i}=W_{s,i}^{F}-W_{s,i}^{\mathrm{control}}$；保护收益定义为 $S_{s,i}=D_{M,i}-D_{s,i}$，正值表示故障增量更小。收益不能代替故障后的绝对 WCT，因而同时保留原始终点。固定追加故障以 K1 为 control、K2 为 F；单故障实验才以 F0 为 control。

所有配对还记录从实验起点计的释放时刻 R 和完成时刻 C，满足 $\Delta C=\Delta W+\Delta R$。以相同 ID 及配置比较，避免异质 Workflow 的全体原始 WCT P95 掩盖被故障影响的对象。当前数据均为探索性单次模拟，Workflow 共享资源，不能把 160 个对象当作 160 次独立重复。

以下“待绘图 P1–P8”是本稿尚缺证据的具体位置，其趋势均为待检验假设。每项给出图型、坐标、比较与可能反转的条件；在获得对应数据前不绘制结果曲线。未来实验沿用三系统配对输入，在参数与故障日程冻结后做独立完整重复；计划重复数、目标硬件及可接受退化边界记录在执行前协议中，不由现有结果反推。每个待绘位置优先补强或替换附近的诊断图，不意味着将所有候选继续累加为正文图。

这条事件轨迹解释了该离群点中的长停顿。该抢占时刻附近的 Peer pending/committed 占用为零，因此不能直接归因于 Peer 副本挤占；路由顺序、正常缓存布局与调度竞争的贡献尚未隔离。下一轮机制实验需要同时计量每次入队/恢复入队、被丢弃的前缀和实际执行的 prefill token；不能仅通过改变绘图分母修复问题。

{{resource_table}}

Python 参考 CPU 与模拟服务报价来自不同计量过程，不能视为两个可相加阶段，也不代表原生服务进程的 CPU 利用率。GET 流量减少同时伴随命中下降，不能单独解释为带宽效率提高。类似 [Ensō](https://www.usenix.org/conference/osdi23/presentation/sadok) 对计算与数据移动成本分别解释的方式，本系统需要把控制 CPU 和共享链路干扰分别测量，再联系到 Workflow 服务表现。只有预先规定的退化边界和独立配对测量支持时，才能使用“服务开销可忽略”的结论。

### 按固定 Workflow 的 Agent 进度触发单次故障

为比较相同逻辑进度下的故障影响，本组使用一轮完整 DAG：160 个 Workflow、1,304 个请求，重新运行三策略各自的无故障 F0；当前图 5–7 也复用这三次 F0，不重复计数。模型、资源、C=16、seed=0 和 source-v3 算法保持一致。事前从输入中取结点数为众数 7、一个入口和一个 final 的 Workflow，再按 ID 字典序选定 `00065f204bddb94d`，不按故障收益选例。

该 Workflow 的 A1 是前置 Agent，A2–A6 是五个并行分支，A7 是最终汇合 Agent。一次 F1 只注入一次 GPU 故障：当固定请求首次跨过输入 prefill 与输出 decode 总 token 的 80% 时，使其实际宿主 GPU 不可用 120 s。各策略按自身执行进度触发，不固定绝对时刻或附带受害集合，也不等备份完成。阈值在调度步内按既有模拟器插值解析；A7 的 378 个输入与 61 个输出 token 对应 351.2-token 阈值，仍处于 prefill，且短于一个 4K 保护 chunk。

图 {{ref:eval-agent80-workflow-wct}} 在 A7 触发故障时保留全部 160 个同 ID 对象，纵轴为同系统 WCT(F1)−WCT(F0)。横轴沿用本组 Mooncake 单轮 F0 的固定排序；阴影标出焦点。实心标记表示有 active 请求直接受害，空心表示仅排队请求受害；底部叉号表示没有这两类直接受害请求、但 WCT 发生变化的对象。

{{fig:eval-agent80-workflow-wct}}

按 Mooncake、DRAM-only AegisKV、AegisKV 的顺序，实际触发位置分别为 198.247 s/gpu-4、198.255 s/gpu-4、199.727 s/gpu-4；焦点 Workflow 的故障增量为 -15.886 s、-15.883 s、-10.226 s。无直接受害请求但 WCT 改变的 Workflow 分别有 81、81、82 个。此分类按同系统 F0/F1 的精确差值形成，包含容量、排队和后续入场变化；不是仅凭故障时仍活跃就认定受影响。完整数据同时保留释放 R、完成 C 和 WCT W，并逐行核对 ΔC=ΔW+ΔR，不能将释放延后造成的较短 WCT 等同于更早完成。

A7 案例中，三者都从 GPU4 重路由至 GPU2，各从 DRAM 恢复 64 tokens、重算 314 tokens，焦点 Peer 恢复量均为零。焦点 Workflow 的释放时刻与 F0 相等，因此这里的负增量确实对应完成提前；它包含恢复后的排队与组批变化，不能直接当作 Peer 保护收益。全部七个位置的 21 次焦点恢复也都没有使用 Peer tokens。

### 恢复机制：已有副本是否减少了重算

图 {{ref:eval-fault-paired-wct}} 对每个预选故障实例，同时展示同一个焦点 Workflow 的 F0 和 F1 WCT。每一行的空心与实心点属于同一系统、同一对象；跨系统比较 F1 终点，行内比较故障前后的增量。这样既保留故障代价，也不会将一个系统正常时已经较慢的部分隐藏在归一化分母中。

{{fig:eval-fault-paired-wct}}

这三个历史实例在基准完成进度附近选定焦点请求，并在同一请求总 token 进度约 60% 时触发。三系统的焦点 Workflow 和源 GPU 相同，但完整受害请求集合并不相同，因而它们是自然混部下的配对诊断，尚不满足隔离直接受害者的新协议。负的 F1−F0 反映故障后调度发生变化，不能解释为故障本身有益。当前实例也没有展示一致的 AegisKV 完整 WCT 优势。

{{fig:eval-fault-token-source}}

图 {{ref:eval-fault-token-source}} 解释为何不能将这些结果归因于 Peer：三例焦点请求的 Peer 恢复 token 全部为零，故障前也没有焦点 Peer 准入事件。前两例故障前最近的 50 ms 控制采样中，八张 GPU 的备份硬上限、额度和物理备份均为零；第三例只有一张 GPU 存在非零硬上限，但当时物理备份仍为零。冻结实现从实际空闲字节扣除前台保留量后计算可借空间，不把可复用的正常 HBM cache 自动当成空闲容量。

因此，当前图表暴露的是“这三个焦点未形成可用于恢复的 Peer 副本”的条件；DRAM 保护已经参与恢复，不能把 Peer 缺位扩大为全部保护路径失效。后续单故障主实验应按输入预选短/长上下文及关键/非关键分支，固定焦点请求、故障域与 decode 边界，并逐例报告故障前连续已提交前缀、保护覆盖率、Peer 容量和被丢失 token。资源条件应同时覆盖无借用余量与有借用余量，不删除未形成保护或恢复无收益的案例，也不能等 AegisKV 复制完成后才注入。

### 故障频率扩展

频率扫描使用外部时钟预定干预，固定观察窗口 $H=480$ s、默认并发 16。四个负载点为 $K=0,1,2,4$ 次故障，依次取嵌套事件表的前 $K$ 个事件：(60 s, GPU0)、(180 s, GPU2)、(300 s, GPU4)、(420 s, GPU6)。每次故障不可用 120 s，三系统的时刻、目标和停机时长完全相同，不因副本是否完成或目标是否空闲而延后。

横轴为预定 $K/H$，换算为 0、7.5、15、30 次/集群小时。该高频范围用于压力测试，不是生产可靠性假设。窗口内停机暴露分别为 0、120、240、420 GPU·s，最后一次故障在窗口内覆盖 60 s，其修复发生在 540 s。固定窗口完成速率为窗口内完成 Workflow 数除以 480 s，未完成数量同时记录。

保护在低故障率下主要体现常态成本，在故障更频繁时可能获得更多恢复机会；若存活容量、复制带宽或完整副本不足，恢复收益又可能被抵消。故障频率曲线用于找出这种条件变化，不预设两系统之间必有交叉点。有限输入和调度重排还可能使相邻点不单调，因而保留实际窗口完成数。

### 与相关恢复方案的比较

三系统对照可以识别 DRAM 准入和 Peer 借用的内部作用，却不足以回答相对其他恢复策略的优势。外部比较需要先对齐故障范围、恢复语义和资源成本。[DéjàVu](https://proceedings.mlr.press/v235/strati24a.html) 的状态复制提供相关的恢复参照，但它的执行并行方式不能直接等同于当前 TP1 模拟。若仅移植一种复制策略，应以“机制移植”命名；只有运行原系统并匹配服务条件，才按原系统名称报告端到端比较。

### 机制消融与适用边界

算法 2 消融回答“保护谁”：Slack 是否使有限容量优先服务那些恢复时间会暴露到 Workflow 终点的请求？算法 3 消融回答“借用多少”：在变化的前台需求下，自适应额度是否比固定预算保留更多有用副本，同时限制正常服务的损失？P7 对各变体保留同输入的 F0/F1；P8 主图采用 F0 的预定前台突发，故障覆盖复用 P3 的日程。各组逐次只改变所考察的机制。

### 结论边界与可复现性

当前观测支持分支异质性这一动机，预测曲线揭示了长前缀重算可能具有较高代价；两者尚不是完整系统收益。冻结原型暴露出正常重访下降、抢占停顿及部分场景没有 Peer 副本的问题，固定故障与扩展实验也未显示统一优势。因此，“近零正常开销”和“稳定故障收益”仍是待检验主张，不能由更换指标或绘图方式获得。

后续验证还需要覆盖不同 DAG 宽度与共享比例、重访间隔和长短上下文分层，并将 Slack 预测训练与评估 Workflow 分离。它们首先作为 P1、P3 和 P7 的预定分层报告，不为每个条件新增重复图。独立完整重复用于估计运行间变异；有限窗口未完成、复制失败和没有可借空间的情况均保留。原生执行还需核对输出语义，而当前模拟的输出位置一致性检查不能替代真实模型与工具链验证。
