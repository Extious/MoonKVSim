## 三部分的论证如何连接

| 动机 | 设计回应 | 当前证据 | 尚缺的直接检验 |
|---|---|---|---|
| 分支执行不均衡 | 请求携带当前可见 DAG 导出的 Slack 快照 | 124 个符合重叠筛选的轨迹对象 | P7：预测误差、关键/非关键分支与有限容量的消融；不能把分支长度差当作在线预测准确率 |
| 重算时长排序不等于 Workflow 损失排序 | 当前 Agent 估值与共享物理块容量竞争 | 五分支、其余条件不变的离线反事实 | P3/P7：在同一故障对象和预算下，保护选择能否改变真实终点 |
| 长前缀重算昂贵 | 兼容、连续、已提交的分层前缀 | 八个历史预测点；现有故障中 DRAM 参与恢复、Peer 为零 | P3/P5：实际形成副本、重建至共同 token 进度、分片恢复及完整 WCT |
| 保护与前台共享资源 | 物理计费、授权退让及独立传输约束 | 正常复用下降与抢占停顿 | P1/P2/P8：有效 prefill、原生 CPU/DMA 干扰与回收/排队；不增加第四条 Motivation 图 |

三类动机证据来自不同轨迹与预测配置，不能合并成一个部署的定量收益。正文集中说明这一界限；三条 Observation 后补充设计要求，再进入对象、所有权和资源约束。

## 对系统叙述的实质修正

- 明确当前设备 fail-stop 范围，以及应用、Router 和元数据存活的前提；跨 GPU 副本不自动提供主机掉电保护。
- 区分“可以向两层复制”与“已拥有两份副本”；每层独立准入、确认和失效。
- 请求只触发当前 Agent 的估值/续租，其他引用者可以结租但不自动重新授信；一次决策使用固定请求快照。
- 说明信用聚合不是完整 DAG 期望损失的精确解，不引入另一版本的联合分账公式或最优性保证。
- 发布需身份和分片核验；撤销先于新读取，物理释放等待读取/DMA 完成。执行失败不能假定已释放副本回滚。
- 额度用 B、容量上限用 C_HBM、实际占用用 U，避免与算法 2 的队列 Q 混淆；明确 U 可在回收期间暂时超过新额度。
- 区分副本正确性、容量可行性与性能干扰；模拟输出位置检查也不替代真实模型输出或工具事务恢复。

本地算法说明存在版本差异，故本稿只采用请求流程中明确的稳定接口，不拼接不同版本。核对来源与原有歧义见 [系统与论述审查](../../../output/aegiskv-revision-20260909/draft-refinement/story-review.md)。

第二轮规划修正了 P3 的比较终点：各系统自身已备份前缀可能长短不同，不能用这些不同完成条件的就绪时刻直接比较。主稿规格改为恢复到共同的 consumed-token cursor（已消费位置），缺失段重建也计入状态就绪时间。

第二轮还统一了 P1 的 revisit-1 统计范围、P2b 的源 GPU 与传输拓扑、P7 的 Slack 置零边际成本定义，以及 P8 静态额度/AIMD 的同等调优预算。P8 队列明确计入首次和抢占后的 HBM/GET/CPU 资源等待，并伴随入口前等待及准入/完成计数；独立完整规格已同步。故障图 C1–C3 的 Workflow/GPU 对应和恢复所需的已确认输出 token 序列也已补回。

## 投稿前仍需解决的证据缺口

这些问题不能通过改写文字完成：有效 prefill 与全生命周期等待计量；原生 DMA 干扰与 CPU 开销；预定条件下非零且可恢复的 Peer 前缀；严格故障对象对照；最终算法的消融、兼容基线与分片实验；与目标硬件的逐负载校验及独立重复。

因此，本文现在更清楚地提出研究问题、说明设计取舍，并解释现有负结果，但尚不能把“近零开销”和“稳定故障收益”写成已实现贡献。待绘位置是可执行的证据计划，不是预填的成功结论。原生采集前还需冻结硬件、参数、重复因素和服务退化边界；本次文稿修订未执行这些实验。
