## Abstract

多智能体（multi-agent）应用把一个用户任务展开成由多个 LLM 请求组成的依赖图（workflow），用户感知的是整张图的完成时间（Workflow Completion Time，WCT），而不是某一个请求的时延。GPU fail-stop 故障会让该卡上所有请求的 KV cache 一起丢失；随着 agent 上下文越来越长，重算这些 KV 需要数秒到数十秒。现有 KV 备份把每个请求当作同等重要、把请求内部每个 KV 块当作同等重要，而 Peer GPU 的空闲 HBM 远不足以容纳全部 KV。

本文提出 AegisKV，一个面向多智能体工作流、适用于原生稀疏注意力模型的 KV 备份与恢复系统。它采用两级保护优先级：请求之间，用 workflow 的 Slack（最多可以晚多久而不推迟 workflow 的完成）区分不备份、只备份到 DRAM、Peer HBM + DRAM 三层，优先给低 Slack 请求分配有限的 Peer HBM，并按该请求仍能减少的恢复等待限制配额；请求内部，以 `(layer, block)` 为单位，用层序与稀疏热度选择驻留块，恢复时按热度预取、按选择器的实际需求补取。请求可以并行 retry，H2D 与计算可以重叠，AegisKV 不规定请求级串行恢复队列。系统只读取稀疏 kernel 已有的选块索引，不改变模型的注意力选择。

在 124 个真实多智能体工作流中，91% 的并行分支持续时间差超过 128K 前缀重算的线性外推参考值 23 s，说明不同分支的执行时间显著不均衡；恢复是否被吸收仍取决于具体请求的 Slack，而非持续时间差本身。在两个公开的原生稀疏注意力模型（MiniCPM4-8B 的 InfLLM-v2、NOSA-1B）的真实选块轨迹上，最热 20% 的 `(layer, block)` 字节分别承担 66% 和 90% 以上的访问，而重放一个 64-token 未密封块只需一层 44%–77% 的字节经过恢复路径。闭式流水线模型表明，在拥塞的 6.25 GB/s 路径上，这一顺序把 32K 上下文的装载等待从 115 ms 降到 77 ms（MiniCPM4-8B）或 20 ms（NOSA-1B），MiniCPM4-8B 再将前 17 层的 Top-k 热块驻留 Peer HBM 后，计入预测未命中的按需补取，等待约为 20 ms。这些测量与解析结果支撑两级保护的动机；并行恢复下的端到端 WCT 收益、前台干扰与备份流量仍需通过配对的无故障/故障实验验证，本文不沿用旧串行队列模型的收益数字。

## 1 Introduction

LLM 正在从单次问答走向多智能体工作流：规划、检索、写代码、评审等角色各自发出 LLM 请求，请求之间有数据依赖，形成一个 DAG。用户等待的是 DAG 的汇合点，因此服务系统的目标从单请求时延变成 WCT。与此同时，agent 的上下文持续变长：每一轮调用都把工具输出、历史对话和检索结果追加到 prompt 中，单请求上下文达到 32K–128K tokens 已属常见；为了承受这样的上下文，原生稀疏注意力（native sparse attention）模型——MiniCPM4 的 InfLLM-v2、NOSA、NSA、DeepSeek 的 DSA 等——正在成为长上下文推理的主流：每个 query 只对被选中的一小部分 KV 块做注意力。

在这样的负载上，GPU 故障既不罕见，代价也与以往不同。大规模 GPU 集群的运维报告表明，GPU 及其 HBM 是非计划中断的最大来源（Llama 3 训练在 54 天里遇到 419 次非计划中断，其中 58.7% 与 GPU 相关）；服务集群运行同样的硬件，单卡 fail-stop 是每天都会发生的事件。执行 GPU fail-stop 后，该卡 HBM 中所有请求的 KV cache 一起丢失；如果没有备份，请求必须在别的 GPU 上重新 prefill 整段前缀。我们测得 MiniCPM4-8B 重建 32K 前缀需要 5.8 s，重建 128K 前缀至少 23 s（§2.2）。KV 备份（把已生成 KV 复制到 DRAM 池或其他 GPU）可以避免这段重算，但备份容量与带宽有限：Peer GPU 能借出的空闲 HBM 通常只有几 GiB，而一张卡上活跃请求的 KV 合计可达数十 GiB；故障后这些请求还要共享同一条 H2D 路径恢复。于是核心问题变为：**在多智能体工作流中，哪些请求的哪些 KV 值得占用最稀缺的备份介质？**

我们的回答建立在两个观察上。第一，请求之间不平等。在 124 个真实多智能体工作流中，并行分支的执行时间差中位数为 141 s，91% 的 workflow 的时间差大于 128K 前缀重算的线性外推参考值（§2.3）。持续时间差本身不等于 Slack；只有恢复代价不超过请求的 Slack 时，重算才不推迟汇合，而关键路径上的请求多等 1 s，WCT 就多 1 s。用调度理论中的 Slack 度量这种差别，可以把有限容量集中到真正会暴露给 WCT 的请求。第二，请求内部也不平等。原生稀疏注意力模型在每个 query 只读取少数历史 KV 块：在 NOSA-1B 和 MiniCPM4-8B 的真实选块轨迹上，最热的 20% `(layer, block)` 字节分别承担 90% 和 66% 的访问（§2.4）。这一集中性在 256/512 个后续 query 的窗口中都可检验，说明有限的 Peer HBM 不应均匀保护全部 KV。访问频次不直接等于恢复收益：§3.3 再区分历史热度、重算尾部所需的去重块并集和在线预取，以保证未预测到的必要块仍能到齐。

基于这两个观察，我们设计了 AegisKV。它把每张源 GPU 的备份目标固定为一个 Retry DP（其 Peer HBM 与主机 DRAM 池），用 Slack 把请求分为三层：recompute（不备份）、DRAM-only、Peer + DRAM。有限的 Peer HBM 优先分给低 Slack 请求，但每个请求只分配到其有用配额 $B_{use}$，超过该配额后转向下一请求（§3.4）。请求内部，AegisKV 按块密封（64 tokens），以 `(layer ↑, hotness ↓)` 的顺序选择进入 Peer HBM 的块；故障后 Recovery Loader 按层预取，当重放到达第 $l$ 层、选择器给出该层的确切需求时，再补取缺失块（§3.3）。不同请求的 retry、H2D 与计算由引擎并发推进，不要求一个请求装载或重放完成后才开始另一个。热度来自稀疏 kernel 已有的块索引，AegisKV 不改变选择器，也不引入第三张恢复 GPU。

本文的贡献：

1. 用真实轨迹和实机测量指出多智能体长上下文服务中的三个事实：重算代价随上下文超线性增长；工作流结构使同样的恢复延迟对 WCT 的影响相差数量级，且这一结构在真实轨迹中普遍存在；在真实原生稀疏注意力轨迹的 256/512-query 窗口中，请求内部 KV 的访问并不均匀，少量字节承担大量选块事件（§2）。
2. 设计基于 Slack 的请求间保护优先级、基于层序与稀疏热度的请求内优先级，以及用有用配额限制 Peer 占用的三层放置算法；通过"预取 + 按需补取"恢复装载器支持并行 retry，不改变模型的注意力选择（§3）。
3. 设计以 WCT 为中心的评估方法：配对无故障/故障运行、按逻辑进度对齐的注入、故障位置扫描、恢复来源与关键路径时间分解、两级优先级消融及带宽/并发度敏感性（§5）。端到端结果待并行恢复实现验证；旧串行队列模型输出不再用于本文结论。

## 2 Background and Motivation

### 2.1 场景、故障模型与备份介质

**多智能体工作流。** 一个 workflow 是一个 DAG $G=(V,E)$，节点是 agent 发出的 LLM 请求，边是数据依赖（父节点的输出进入子节点的 prompt）。WCT 定义为从首个请求释放到最后一个请求完成的时间。对节点 $v$，定义 Slack $\sigma_v$ 为 $v$ 最多可以推迟多久而不推迟整个 workflow 的完成，即关键路径法中的总时差（total float）：$\sigma_v=\mathrm{LF}_v-\mathrm{EF}_v$，关键路径上的节点 $\sigma_v=0$。在线系统只能用估计值（同一 agent 角色的历史持续时间、当前进度）计算 $\sigma_v$，因此 Slack 是一个随时间变化的快照（§3.2）。一个 workflow 的请求通常散布在多张 GPU 上，单卡故障一般只命中一个 workflow 的一个请求，因此该请求超过 Slack 的部分就是这个 workflow 的 WCT 损失。

**服务系统与模型。** 我们考虑分离式或数据并行的 LLM 服务集群：每个 DP 组（一张或一组 GPU）独立执行请求，前缀缓存以块（block，本文取 64 tokens）为单位管理，密封（sealed）块可以被复制到主机 DRAM 池以支持前缀复用，这和 Mooncake 等 KV 中心架构一致。模型是原生稀疏注意力模型：每层、每个 query 由选择器从压缩键（compressed keys / block summaries）算出 top-$k$ 个历史块，注意力只读这些块的 KV。选择器的输出——每个 `(layer, query)` 的块索引——是 kernel 本来就要产生的中间结果，AegisKV 只读取它。

**故障模型。** 我们关注执行 GPU 的 fail-stop（Xid 错误、HBM 不可纠正错误、掉卡、进程崩溃）：该卡上的 primary KV 和本地备份同时不可用，进程重启或替换需要几十秒到几分钟。主机、路由器/控制面、主机 DRAM 池和同机其他 GPU 存活；故障检测（心跳，默认 3 × 100 ms）、路由切换和重新准入的固定开销合记为 $R_{floor}$，本文取 0.5 s。整机故障（主机掉电、多卡同时失效）不是主要目标，但 AegisKV 的 DRAM 副本可以放在远端池中，此时恢复带宽被多张恢复 GPU 分摊（§2.1 末尾的 6.25 GB/s 场景）；Retry DP 与源 GPU 同时失效时，DRAM 副本仍是覆盖底线，恢复退化为 DRAM-only。网络分区、静默数据损坏和 agent 运行时自身的故障不在本文范围。

**备份介质。** Peer GPU HBM：读取零拷贝、可直接计算，但可借出的空闲容量只有几 GiB，且需要给前台服务让路。空闲容量来自 KV 池按峰值预留、占用随负载波动这一事实：以本文的模型配置（每 token 32 KiB KV，每卡 8 个活跃请求，中位 48K 上下文）计，前台 KV 占用不到 80 GB 卡上 KV 池的四分之一；本文默认只借 4 GiB，并在没有余量时退化为不用 Peer（§3.5、§5.6）。主机 DRAM 池：容量大（TB 级），但恢复时需要经过共享的 H2D 路径——单卡故障、本机池约 25 GB/s（PCIe 4.0 ×16）；整机故障、远端池被 4 张恢复 GPU 分摊时约 6.25 GB/s。重算：不占容量，但代价随上下文增长。AegisKV 的任务是在三者之间放置 KV。

### 2.2 长上下文使故障重试的重算代价很高

Agent 在多轮调用中积累上下文。执行 GPU 故障后，未备份的前缀只能重新 prefill。图 1 在 RTX 4090 上测量两个原生稀疏注意力模型完整前缀 prefill 的时延：MiniCPM4-8B 从 8K 的 1.28 s 增至 32K 的 5.76 s，每翻一倍上下文时延增至 2.1 倍（选择阶段与压缩键随上下文线性增长，注意力本身还要读 top-$k$ 块）；按 32K 的每 token 代价线性外推，重建 128K 前缀至少 23 s。NOSA-1B 更小，但 96K 前缀仍需 15.8 s。这段代价还会被两件事放大：接管 GPU 同时在服务自己的前台请求，重算只能分到部分算力；同卡其他请求也可能并行重算，共享算力使有效恢复速度下降。绝对时延与增长形态同时取决于模型、kernel、硬件和并发负载，因此部署时必须重新校准，不能把 RTX 4090 的曲线直接当作数据中心 GPU 的时延。备份已生成 KV 的目的，是避免把这段代价重新付一遍。

### 2.3 多智能体场景关心 WCT，故障下的保护优先级因此不同

用户等待的是汇合结点，而不是某个 agent 先算完。我们用一份公开的编码 agent 会话轨迹（CC/Weka，393 条会话）检验并行分支的不均衡：保留其中含有子 agent 扇出、且各分支在时间上严格重叠的 124 个 workflow（扇出宽度 2–10，中位 3），每个 workflow 取最长与最短分支的持续时间差。图 2 给出这一差值的分布：中位 141 s，P90 1,570 s，最慢与最快分支的持续时间之比中位为 2.2。把图 1 的重算代价参考画在同一坐标上：97.6% 的 workflow 的时间差大于 32K 前缀重算的实测 5.8 s，91.1% 大于 128K 的线性外推参考值 23 s。该分布说明分支持续时间存在显著差异，为差异化保护提供动机；但分支起点不同时，持续时间差不等于汇合处的 Slack，超过外推参考值也不代表一定能吸收实际重算。能否避免 WCT 损失，仍需比较故障请求的 Slack 与实际恢复代价。

恢复代价本身也不等于 workflow 的损失。图 3 在同一轨迹的一个五分支 workflow 上，于 349.5 s 分别假设各支路故障，用图 1 的 MiniCPM4-8B 代价估算重算时间，暴露延迟为 $J_i=\max(0,T_i-\sigma_i)$。A3 的前缀最长（112K，重算 19.8 s），却被 52.4 s 的余量完全吸收；A4 前缀更短（91K，15.9 s），却处于关键路径，全部暴露给 WCT；A5 的 14.5 s 中只有 3.7 s 越过 10.8 s 的余量。按 KV 大小或重算时间排序，会把容量分给不改变完成时间的分支。

### 2.4 稀疏注意力下，同一请求内不同位置的 KV 保护优先级也不同

原生稀疏注意力并不均匀消费全部历史 KV：有的块被后续 query 反复选中，有的很少被需要。因此，同一请求内部的 KV 也不应获得相同的保护优先级。我们读取 MiniCPM4-8B（InfLLM-v2）与 NOSA-1B（带训练局部性门控）在三份 PG19 长文本上的实际选块索引，固定 32K 历史，分别统计其后 256 与 512 个 query；256-query 窗口取自同一次因果前向的前半段，并非额外独立运行。

**少量 KV 承担大量访问（图 4）。** 以包含全部 KV head 的 `(layer, 64-token block)` 为对象，按当前窗口的选中次数降序排列。横轴是热块占全部历史 KV 字节的比例；纵轴是这些块覆盖的历史选块事件比例，同一块被不同 query 或 KV head 反复选中时重复计数。在原有两模型中，最热 20% 字节的覆盖中位数在 256/512-query 窗口分别为 NOSA-1B 92.2%/90.3%、MiniCPM4-8B 69.6%/66.0%。因此，集中性并非只出现在 512-query 窗口；但更短窗口不是新的模型或独立样本。

### 2.5 设计要求

综合 §2.2–2.4，一个面向多智能体工作流的 KV 备份系统需要：(R1) 保护决策以 WCT 为目标，用 Slack 区分请求，把最稀缺的介质留给会推迟汇合的请求；(R2) 请求内部按 `(layer, block)` 排序，优先保护恢复流水线先用到、且被稀疏注意力频繁选中的块，并且只使用任何原生稀疏选择器都会产生的块索引，不绑定特定算法；(R3) 放置与恢复解耦：允许请求并行 retry、H2D 与计算重叠，不为保护优先级引入请求级串行屏障；(R4) 备份流量不能挤占前台服务，Peer HBM 配额要随前台压力收缩；(R5) 恢复路径简单可预测：不引入额外的恢复 GPU，不做二次拷贝，恢复后的 KV 与从同一前缀重算得到的 KV 一致，模型的注意力选择不受影响。

## 3 AegisKV Design

### 3.1 架构概览

图 5 给出 AegisKV 的三层架构。**应用层**是现有的 agent 运行时（LangGraph、AutoGen 等）：它为 DAG 的每个节点发出一个 LLM 请求，并在请求元数据中携带 ⟨workflow id, node id, 依赖边⟩；AegisKV 不要求应用提供 Slack 或持续时间，只要求能识别请求属于哪个工作流的哪个节点、以及它的后继是谁（静态声明的图，或运行时在派生子 agent 时增量声明的边）。**Router/Controller 层**是 AegisKV 的控制面，四个模块：Workflow Tracker 维护每个工作流的 DAG 进度和持续时间估计，产出每个活跃请求的 Slack 快照 $\sigma_r$（§3.2）；Placement Planner 按窗口为每张源 GPU 决定请求层级和 Peer HBM 配额（§3.2–3.4）；Failure Detector 通过心跳检测 GPU fail-stop，并维护固定的 Retry-DP 映射 $g\mapsto p(g)$；Recovery Manager 在故障后向 $p(g)$ 提交受影响请求及其恢复计划，由引擎按资源可用性并发准入与执行（§3.5）。**引擎层**是每个 DP 一个的 vLLM 风格引擎，AegisKV 加入四个模块：源端的 Hotness Counter 从稀疏注意力 kernel 已经产生的块索引中累计每个 `(layer, block)` 的选中次数和每层的并集大小，并按窗口把摘要上报控制面；Backup Agent 按块密封，把密封块复制到 Peer HBM 与 DRAM 池并在 ACK 后提交；接管端的 Peer Region 是 Peer HBM 中借给备份的区域，其大小由 Peer Budget 按前台 KV 的高水位线动态给出；Recovery Loader 在故障后按层、热块优先地预取 DRAM 中的块，按选择器的实际需求补取，并重放尾部。

**正常路径。** 每个放置窗口（默认 1 s，或在请求到达/完成、Slack 变化超过阈值时触发），Planner 对源 GPU $g$ 上的活跃请求执行 §3.4 的算法 1，产出两个集合：需要 DRAM 副本的密封块和需要进入 Peer Region 的密封块。Backup Agent 只复制上一窗口之后新增或升级的对象，通过低优先级拷贝流发送；两条路径各自确认。放置计划连同最近一个窗口的热度摘要保存在控制面，源 GPU 失效后仍然可用。

**故障路径。** $g$ 失效后，Recovery Manager 向 $p(g)$ 提交所有受影响请求，沿用引擎的并发调度；放置时的 Slack 排序不变成恢复时的完成顺序约束。每个请求的恢复流水线：Peer Region 中的块直接参与计算；DRAM 中的块由 Recovery Loader 按层、热块优先预取，重放到达某一层时按该层的实际选择补取缺失块，冷块后台补齐；未密封的活跃块和缺失的后缀重算。不另加恢复 GPU，也不把 Peer 状态拷到第三张卡（R5）。

**为什么固定 Retry DP。** 备份目标在故障前就确定，Peer 副本才能是零拷贝可读的；映射采用环形 $p(g)=g+1 \bmod n$，每个 DP 只为一张源 GPU 保存 Peer 副本，Peer Region 的容量竞争只发生在同一源 GPU 的请求之间。多对一映射只需在算法 1 中把预算按源 GPU 划分；把一张卡的请求分散到多个 Retry DP 则相当于把 $g$ 的请求集合切分后分别运行算法 1，每份有自己的路径与预算。

### 3.2 请求之间：Slack 与三层

**Slack 估计。** Workflow Tracker 为每个 agent 角色（由运行时的节点类型标识）维护最近完成的持续时间样本（滑动窗口，默认最近 200 次或 1 小时），以其 P90 作为该角色未完成节点的持续时间估计 $\hat T_\rho$，正在运行的节点取 $\max(\hat T_\rho-\text{已运行时间},\ \tau_{min})$；没有历史的角色回退到全局分布。对当前已知的 DAG 做一次关键路径法的前向/后向遍历，得到每个活跃请求的总时差 $\sigma_r=\mathrm{LF}_r-\mathrm{EF}_r$。动态 workflow（运行时才决定是否再派生子 agent、循环几轮）只在派生时声明边：尚不知道后继的节点被视为处在关键路径上（$\sigma_r=0$），这是保守方向的误差。为了避免乐观估计把关键请求错分到低层，估计使用 P90 而不是均值，并对分层阈值施加 20% 的滞回；Slack 在节点完成/派生事件和每个放置窗口更新（§3.6 讨论误差的后果）。

**恢复代价估计。** 记请求 $r$ 的历史上下文长度为 $L_r$，$T_{rc}(L_r)$ 为完整历史前缀重算时间，$T_{rp}(r)$ 为未密封尾部的纯重放时间。二者按模型、GPU 与代表性并发负载校准，不取其他请求代价的前缀和。记 $R_{base}(r)=R_{floor}+T_{rp}(r)$，$W_0(r)$ 为没有 Peer 副本、从 DRAM 按 §3.3 装载时超出纯重放的暴露等待，则重算与 DRAM 恢复的估计分别为 $R_R(r)=R_{base}(r)+T_{rc}(L_r)$、$R_D(r)=R_{base}(r)+W_0(r)$。这里 $R_{floor}$ 包含检测、重路由与准入开销；并发带来的资源竞争由校准代价与有效带宽反映，不假定每个请求独占峰值带宽。

**三层。** 每个请求独立比较当前 Slack 与恢复代价：

- **Tier R（recompute）：** $\sigma_r\ge R_R(r)$。估计完整重算可被 Slack 吸收，不要求备份 KV。
- **Tier D（DRAM-only）：** 不满足 Tier R，但 $\sigma_r\ge R_D(r)$。DRAM 恢复已能被 Slack 吸收，只保留 DRAM 副本。
- **Tier P（Peer 候选 + DRAM）：** 前两者均不满足。保留 DRAM 副本，并按低 Slack 优先竞争 Peer HBM；能否实际获得 Peer 字节取决于有用配额、预算和复制是否提交。

这些是在线估计下的放置类别，而不是三条串行恢复队列，也不保证每个请求必然在 Slack 内恢复。预算不足时 Tier P 仍可从 DRAM 恢复；负载或 Slack 变化时重新分层。

### 3.3 请求内部：层序 × 热度，预取 + 按需补取

**尾部重计算（tail recomputation）。** 故障后，接管端利用已恢复的历史 KV，对故障前已经生成、但 KV 尚未备份的已知尾部 token 再执行前向计算，重建这些 token 的 KV。它不重新采样生成 token，也不重新计算整个历史前缀。图 6(b–e) 将这部分计算标为 `Tail recompute`；图 6(a) 新增无 KV 备份时的 `Full recompute`，从头重建完整历史及相同尾部的 KV，以区分两种恢复路径。

**保护单位与密封粒度。** 保护单位是 `(layer, block)`，使各层可以选择不同的 token 位置。保留的同轨迹粒度对照显示：32K 历史、512-query 窗口下，若每个 token 段必须携带全部层，同样 20% 字节只能覆盖约 53%–59% 的选块事件；这支持分层保护，但不等价于恢复字节减少一半。一个 64-token 块写满即密封并进入复制队列，decode 时未密封尾部小于一个块，分析保守取 64 tokens；在故障相位均匀的假设下约为 32 tokens。尚未提交的密封块可能进一步扩大实际重算后缀，必须以提交前沿为准。每次密封产生 64 tokens × 全部层的 KV（MiniCPM4-8B 为 2 MiB）；以 50 token/s 解码时，100 个请求持续产生约 160 MiB/s 的原始 KV。这是复制流量的量级估计，不含初始 prefill、元数据、重复复制及 Peer 副本，也不证明无前台干扰。

**恢复需求不等于访问频次。** 对第 $l$ 层，重放 $n$ 个已知尾部 token 所需的历史块为 $U_l(n)=\bigcup_{q=1}^{n}\bigcup_g S_{l,q,g}$，其中 $g$ 为选择组；重复选中的同一块只传一份。它沿同一轨迹随尾部增长而不减，但不能由图 4 的访问覆盖率推算。在原有两模型的 32K 轨迹中，64-query 并集占每层历史字节的均值为 NOSA-1B 37%、MiniCPM4-8B 68%；512-query 时分别为 58% 与 90%。这些恢复参数保留在 `needed_fraction_models.csv`，原所需比例图不再占用 Motivation 篇幅。16K 到 32K 的并集比例下降是当前固定预算配置下的观察，不是所有上下文、文本或自适应选择器的单调保证。

**选择预算与热度的来源。** 计数使用真实选择索引，不假设所有模型具有相同或固定的 $k$。本次 MiniCPM4-8B 的配置 `topk=64` 加上 2,048-token 局部窗口，实际总预算为 $64+2048/64=96$ 块；NOSA-1B 总预算为 64 块，已含强制局部/起始块，两者每块 64 tokens。Hotness Counter 将各层/选择组的索引累计到 `[layers × blocks]` 计数表。以 MiniCPM4-8B 的 32 层、2 个 KV head、32K 历史为例，每步最多 6,144 个计数增量；16 位计数表为 32 KiB，在每组索引去重且每 512 步清零时，单块最多计数 $2\times512=1,024$，不会溢出。额外 kernel 与聚合开销需测量，不能仅凭增量次数宣称可忽略。窗口结束后上报块排名和去重并集摘要；源 GPU 失效后，控制面保留最近已提交的摘要。

**在线装载器：预取 + 按需补取。** 恢复前无法精确知道重放的 query 会选中哪些块，但有两个可用的信号：前一窗口每个块的选中次数，以及前一窗口的并集大小。Recovery Loader 对第 $l$ 层的做法是：按 `hotness ↓`（并列时更新的块优先）预取该层最热的 $h_l$ 比例的块，$h_l$ 取前一个同长窗口的并集比例；当重放到达第 $l$ 层时，选择器基于压缩键或块摘要（体积按模型核算，随第一批对象驻留）算出这一层的确切需求，装载器立刻以高于预取流的优先级补取尚未到达的所需块；预取流随后继续搬运剩余的冷块。于是第 $l$ 层重放前经过路径的字节是"预取字节 + 补取字节"，记其占一层的比例为 $\tilde u_l$。图 7 用轨迹度量这一顺序的质量：预取一层最热的 40% 字节，NOSA-1B 的所需块已有 82% 驻留，MiniCPM4-8B 有 55%（最近优先分别为 60% 和 53%）；同轨迹的预取/补取集合复算表明（不是实测 DMA 流量），重放一个 64-token 尾部时 $\tilde u$ 为 NOSA-1B 0.44、MiniCPM4-8B 0.77，比理想并集只多 5–10 个百分点。在当前固定选择预算和文本中，较长上下文观察到更低的 $\tilde u$，但不保证跨模型单调：16K 历史下 MiniCPM4-8B 的 $\tilde u$ 为 0.96，稀疏优先级几乎没有可省的字节，而 NOSA-1B 为 0.69。稠密模型或 prefill 阶段的故障（未密封部分是整个 in-flight chunk）下 $\tilde u\to 1$，装载器退化为逐层稠密装载，正确性不受影响。

**层流水线。** 恢复是一条按层推进的流水线：第 $l$ 层的尾部重计算需要该层的所需历史块，而后续层的预取可以与当前层计算重叠。记每层完整历史 KV 的装载时间为 $D=L_r\cdot s/\beta$（$s$ 为每 token 每层的 KV 字节，$\beta$ 为请求在代表性并发下的有效 H2D 带宽；这里只分析单请求流水线），每层尾部重计算时间为 $C$，模型有 $N$ 层。若把每层的有效装载量 $\tilde u D$ 看作可提前排队的连续传输任务，暴露等待的理想流体近似为

$$W_0 = \tilde u D + (N-1)\,[\tilde u D-C]^+ .$$

Peer HBM 驻留的是前若干层中按历史热度排序的 **Top-$K_l$ KV 块**，不是这些层的全部 KV。$K_l$ 由上一同长重放窗口的并集大小估计（$h_l=K_l/B_l$，$B_l$ 为该层历史块数），不等于选择器对单个 query 的预算（本次 MiniCPM4-8B 总计 96 块）。因此，前 $k$ 层即使已保护，预测集合之外的所需块仍需补取；只有所需集合被完全覆盖且后续传输及时到达时，才能做到零暴露等待。图 6 使用同质层近似：对三份文档先逐层平均、再跨层平均，得到 $h=0.658$、$\tilde u=0.775$；固定这一热块比例后，遍历保护的前层数 0–32，达到按需补取等待平台的最小值为 17：前 17 层仅这约 66% 的 Top-k 热块驻留 Peer HBM，共约 358 MiB，而不是整层备份的 544 MiB。16 层时等待约 20.22 ms，17 层时约 19.99 ms；继续增加前层数不再减少本例尾部重计算的 KV 等待。17 是当前同质参数下、固定热块比例与前层优先策略的解析拐点，不是任意块放置的全局最优，也不是部署中固定的层数。对这些层，每层仍有 $\tilde u-h\approx0.116$ 的块必须从 DRAM 补取。

图 6 的其余参数为 MiniCPM4-8B、32 层、32K 历史（每层 32 MiB）、拥塞路径 $\beta$ = 6.25 GB/s（$D$ = 5.37 ms），以及 RTX 4090 上重计算已知 64-token 尾部的每层校准计算 $C$ = 1.82 ms。(a) 无 KV 备份，从头重建 32,768 个历史 token，再重计算相同的 64-token 尾部：32K prefill 的实测中位数为 5.759 s，叠加与其余组相同的约 58 ms 尾部计算，组成约 5.817 s 的成本参考；这不是一次性 32K+64 prefill 或端到端故障恢复的实测。(b)/(c) 分别是“按 token 块传输且等全部历史到齐”的基线（等待 172 ms）和逐层完整装载（等待 115 ms；模型仍使用稀疏注意力）。(d)/(e) 显式将补取任务推迟到上一层计算完成、当前层需求可知后释放，并赋予其高于预取的优先级：无 Peer 时等待 77 ms；前 17 层的 Top-k 热块驻留 Peer 后约 20 ms，而不是 0。后者的主要残余等待为逐层补取，$N(\tilde u-h)D\approx20$ ms。计入相同的纯尾部计算，(b–e) 到尾部 KV 重建完成的总时间依次约为 230/174/135/78 ms，不含其后补齐冷块的时间。图中的浅蓝色流在尾部重计算后补齐所有仍未驻留的冷块，包含前 17 层的冷块。为保留毫秒级流水线细节，(a) 使用独立的秒轴，(b–e) 共用放大的毫秒轴，不能跨这两种尺度直接比较条形长度。该解析例子采用可抢占的单复制流，未计入选择器计算、DMA 启动和资源干扰；$C$ 来自 HF eager 实现，生产引擎需重新校准。

图 8 保留流体近似 $W(x)=[W_0-x/\beta]^+$，用来估计提前驻留字节的收益；它假设这些字节直接消除已可调度的传输任务，不包含图 6 显式表示的逐层按需补取释放约束，因而不能用于保证 Top-k 预测下的零等待。给定 Slack $\sigma$，该近似下的单请求有用配额为

$$B_{use}(r)=\beta_r\cdot\min\{W_0(r),\,[R_{base}(r)+W_0(r)-\sigma_r]^+\},$$

其中 $R_{base}=R_{floor}+T_{rp}$ 包含无法由减少历史 KV 装载而消除的固定开销与纯重放时间。

在这一近似内，超过 $B_{use}$ 的驻留字节不再改变该请求自身的 WCT 贡献；实际恢复仍可能受预测未命中的补取约束。同一 20 ms 余量下，稠密装载需要 569 MiB，MiniCPM4-8B 的在线装载器需要 338 MiB，NOSA-1B 的 $W_0$ 已低于余量、不需要 Peer 字节。

### 3.4 Peer HBM 分配：Slack 优先，有用配额封顶

**放置优先级，而非恢复顺序。** 请求间按 $\sigma_r$ 升序分配 Peer HBM；相同 Slack 使用稳定请求 ID 打破并列，不引入装载时长调度规则。每个请求分配到 §3.3 的 $B_{use}(r)$、可备份候选字节或剩余预算中的最小值，再处理下一请求。这个策略直接实现"高优先级请求的高优先级块进入 Peer HBM"，不需要预测故障后的请求级完成顺序。

**请求内块选择。** 只考虑已密封的块，按 `(layer ↑, hotness ↓, block position ↓)` 排序，每层候选为前一窗口估计的预取集合（$h_l$ 比例）。$h_l$ 是预取比例，$\tilde u_l$ 还包含预测未命中的补取量，二者不能混用。Peer 配额向下取整到完整块，未用完的字节继续给下一请求；DRAM 保留 Tier D/P 的完整密封前缀。选择器必需的压缩键/块摘要先于所保护的 KV 提交，其 Peer 空间同样计入预算；若元数据和至少一个 KV 块都放不下，则不在 Peer 中保留孤立元数据。

**算法 1。** 下列算法只计算放置计划。它用单请求代价估计限制无效复制，不声称在任意并发调度下全局最优；恢复并行度、批处理与流调度仍由引擎管理。

```text
Algorithm 1  Place(g): Slack-first placement with useful quota caps
Input : requests on g with Slack, calibrated costs, and per-layer hotness; Peer budget B
Output: desired DRAM objects and Peer objects
 1  DRAM ← ∅; Peer ← ∅
 2  for r in requests sorted by (Slack ↑, stable request id ↑):
 3      if σ_r ≥ R_base(r) + T_rc(L_r): continue                  # Tier R
 4      DRAM ← DRAM ∪ sealed_blocks(r) ∪ selector_state(r)        # Tier D/P coverage
 5      if σ_r ≥ R_base(r) + W_0(r): continue                    # Tier D
 6      candidates ← preload_set(r) sorted by (layer ↑, hotness ↓, position ↓)
 7      meta ← required_selector_state(candidates) \ Peer
 8      quota ← min{B_use(r), bytes(candidates), max(0, B − bytes(meta))}
 9      chosen ← longest whole-block prefix of candidates fitting quota
10      if chosen is empty: continue
11      Peer ← Peer ∪ meta ∪ chosen; B ← B − bytes(meta) − bytes(chosen)
12  reconcile desired and committed objects under the physical Peer watermark
13  copy new objects asynchronously; publish only after completion; reclaim safely
```

请求排序为 $O(n\log n)$；候选块可在热度窗口结束时排序并缓存。共享前缀按物理对象去重，只扣除实际新增字节。算法中的 $B$ 是目标总预算；执行差量计划时，copying、committed 与 reclaiming 对象都计入物理水位，不能把尚未释放的容量再次借出。配额上限是近似代价模型下的停止条件，不是零等待保证；实际就绪条件由 Recovery Loader 检查。

**并行与竞争。** 多个 retry 可以同时在途，H2D 与计算可以重叠，但总链路带宽与算力仍有限。Planner 使用代表性并发下校准的有效带宽与重算/重放代价，不逐个累加其他请求的传输时间；§5 用并发度与带宽扫描验证估计的适用范围，而不把跨请求的排队传播作为算法贡献。

### 3.5 机制：复制、提交、前台保护与恢复

**两条独立的复制路径。** Backup Agent 把密封块分别发往 Peer Region（NVLink/P2P）和 DRAM 池（D2H）；两条路径各自分配、传输、确认，一条失败不影响另一条已提交的对象。DRAM 副本是覆盖的底线，Peer 副本只用来减少等待；若 Peer 副本是某块唯一有效副本，降级前先完成 DRAM 提交。共享前缀（多个 agent 复用的系统提示或检索结果）只计一份物理容量，并与前缀缓存的 DRAM 层合用同一份副本。压缩键等选择器状态与第 1 层一起复制，恢复时最先到达。

**提交语义。** 试算不改变可读集合；复制完成并核对模型、布局、分片信息后才发布。配额下降不等于地址已空：copying / committed / reclaiming 状态的字节仍计入占用，直到释放完成。

**前台保护（Peer Budget）。** Peer Region 是可被前台收回的借用容量：Peer Budget 用 $p(g)$ 前台 KV 占用的高水位线预留余量，其余作为预算 $B$ 交给 Planner；前台压力上升时先回收高 Slack 请求中优先级较低的对象，回收的对象在 DRAM 中仍有副本。复制流量使用低优先级拷贝流，并限制在链路带宽的固定比例内（默认 20%）；Peer 写入消耗接管端的 HBM 带宽，同样受这一比例约束。

**接管端的负载。** $g$ 失效后，$p(g)$ 还要服务自身的前台请求。所有 retry 沿用引擎的并发准入、连续批处理和计算/复制资源限制，不设置请求级完成屏障；重算任务可使用低优先级执行配额，但不能据此声称没有前台干扰。Peer Region 的借用量、复制速率和恢复准入数均受水位线约束，额外负载的代价由 §5 的前台 WCT、吞吐和并发扫描测量。若单个 Retry DP 容量不足，按 §3.1 在故障前将请求及其备份目标分散到多个 Retry DP。

**恢复（Recovery Manager 与 Recovery Loader）。** Recovery Manager 提交并行 retry，Loader 为每个请求维护预取与补取任务：预取按 `(layer ↑, hotness ↓)` 搬运每层预测集合并跳过已驻留块；选择器给出确切需求后，缺失块以高于预取任务的优先级提交，是否能抢占在途 DMA 由引擎实现决定。某请求第 $l$ 层所需 KV 就绪后即可计算，不等待其他请求完成；后续层的预取可与当前层计算重叠。预测未命中的补取仍可能产生等待。冷块在后台补齐，未密封或未提交的后缀重算；Tier R 直接重算前缀。恢复后的 decode 如仍选到未驻留块，同样补取，不为了启动 retry 而等待全量 KV 到齐。

**正确性。** AegisKV 只决定备份位置和装载顺序，不改变稀疏选择器的输出；补取保证所需块在注意力执行前到齐，因此恢复后的 KV 与在同一前缀上重算得到的 KV 一致（同一权重与 kernel），请求的后续输出与无故障执行在数值上等价，差别只来自批次组成引起的浮点顺序差异，这与任何重算恢复相同。

### 3.6 讨论

**Slack 估计误差。** 在线 Slack 可能过于乐观（把关键请求放进 Tier R）或过于悲观（把太多请求放进 Tier P、稀释预算）。AegisKV 用 P90 持续时间、阈值滞回、未知后继按 $\sigma=0$ 处理和事件触发的重新规划限制后果；Tier R 不保证有副本，乐观误差可能导致完整重算并暴露给 WCT。可以在空闲时机会式复制到 DRAM，但只有已经提交的副本才提供这一额外保障。Slack 误差的敏感性实验列入 §5.7 的待补项。

**热度陈旧与窗口长度。** 图 4 只展示同窗口离线集中度，不验证在线预测。保留的前窗排序统计（`budget_coverage_models.csv`，512-query 窗口）在 20% 字节预算下有约 55%–88% 的访问次数覆盖；真正的所需块覆盖由图 7 单独验证，不能把两者混为命中率。默认热度排名窗口为 512 个 decode 步，预取比例 $h_l$ 用与实际重算尾部同长的窗口估计（默认分析为 64 步），§5 扫描窗口长度。

**对不同稀疏选择器的适用性。** 接入条件是能够观察选择索引、恢复选择器状态与所有必需的注意力分支，并按模型校准成本。InfLLM-v2/NOSA 输出块索引；DSA 输出 token 索引，需要映射到实际复制块，分散 token 可能显著放大块级传输；NSA 的压缩/局部分支也必须计入，不能只备份 Top-k 分支。选择器元数据体积和驻留代价必须按实现核算，不假设统一压缩比。AegisKV 依赖真实索引及块并集，不依赖 $k$ 固定或随上下文增长的特定规律；是否节省等待取决于热度稳定性、复制粒度、尾部长度及并发资源。不满足时退化为逐层完整装载，Slack 分层仍适用。稠密注意力模型下 $\tilde u=1$，请求内部只剩层序这一维。无 workflow 的独立请求可取 $\sigma=0$，按稳定 ID 打破保护优先级的并列，恢复仍然并行；当前策略不对此情形声称最优公平性。

**更快的恢复路径。** 更高的有效 H2D 带宽降低 $D$ 和 $W_0$，因而缩小有用 Peer 配额；若 DRAM 恢复已被 Slack 吸收，就不需要 Peer。即使 $\sigma=0$ 的请求仍是 Tier P 候选，也不能靠 Peer 消除固定检测与纯重放开销。PCIe、远端池与高速 CPU–GPU 互连下的实际收益由 §5 的带宽扫描验证，不预设某条路径一定是瓶颈。张量并行下一个 TP 组是"GPU $g$"的单位，Retry DP 是另一个 TP 组，每层字节按分片计。

**局限。** 图 4、7 和 §3.3 的恢复参数来自书籍文本；agent 负载中的代码与工具输出可能有不同的选择模式。同一轨迹的所需并集随重放窗口增长而不减，但其占比不保证随上下文增长而下降；访问集中程度与恢复收益需要在 agent 轨迹和不同选择预算下重新测量。prefill 阶段的故障可能丢失整个 in-flight chunk，需要按其实际后缀长度校准重算代价，不能沿用 64-token decode 尾部的收益估计。

## 4 Implementation

实验平台采用 MoonKVSim（以 Mooncake 为原型、以 KV 块为一等对象的离散事件模拟器），复用块级复制/提交、Peer 容量管理和故障注入接口。新版接入点是 §3.4 的放置策略与 §3.5 的逐请求异步就绪条件；不向调度器添加请求级串行屏障。GPU 原型需提供选块索引观测、异步块复制与逐层就绪事件。MiniCPM4-8B 和 NOSA-1B 的选块轨迹、完整 prefill 与尾部重放测量已完成；新版放置与并行恢复的端到端实现尚待验证，本节不把旧示意模型视为其实现证据。

## 5 Evaluation

本节保留实验设计，尚不报告新版端到端结果。旧图 9 的串行队列示例及旧图 10–14 的示意模型输出已撤出正文；原文件保留用于历史追溯，不能作为并行 retry 设计的结果。评估围绕正常开销、故障位置、恢复来源与时间分解、两级保护消融及敏感性展开。

### 5.1 方法

**平台与参数。** 目标配置为 MiniCPM4-8B BF16、DP=8、1 TB DRAM 池、每个 Retry DP 借用 4 GiB Peer HBM，默认单卡故障与 8 个受影响请求。链路总可用带宽分别设为 25 GB/s 与 6.25 GB/s；多个 H2D 任务共享这一总量，不能给每个并发请求各计一次完整带宽。所有策略使用相同的 retry 并发度、计算调度器、前台负载与传输共享规则，允许请求间传输交错及计算/复制重叠。部署代价按实际 GPU 和并发负载校准，RTX 4090 的图 1、图 6 参数只用于当前动机与解析图。

**工作负载。** 主实验使用 CC/Weka 导出的 124 个 workflow，保留请求依赖、上下文与逻辑进度；缺失字段与重建假设需显式报告。合成的 160 个七节点 workflow 仅用于可控机制扫描，不冒充真实 trace 运行。故障在指定请求的 80% 逻辑进度注入，源 GPU 不可用 120 s；对照间固定故障身份、逻辑进度、备份前的请求到 GPU 映射和预期受害集合，并在运行日志中核对实际受害请求，不能只对齐墙钟时间。

**基线。** Recompute 不备份；DRAM-only 备份全部密封 KV；Peer-uniform 在完整 DRAM 副本之上平均分配 Peer 配额、按 token 位置选择块；AegisKV 使用 §3 的两级保护。除明确的放置/请求内顺序差异外，所有基线均可并行恢复，不能用串行基线制造收益。补充一项层序装载的 DRAM-only 强基线，以分离层流水线与 Peer 放置的贡献。

**协议与指标。** 每个策略的无故障 F0 与故障 F1 按 workflow ID 配对，WCT 惩罚为 $\mathrm{WCT}(F1)-\mathrm{WCT}(F0)$；备份的正常开销相对相同负载的无备份运行。至少五次完整配对重复，报告 workflow 数、每策略运行数及重复单位；不能将同一批 workflow 的多次注入视为独立 workflow。一个 workflow 多请求同时受影响时直接测量 DAG 完成时间，不把请求迟到相加当作 WCT。

画每个 workflow 的配对 WCT 增量 ECDF，保留负值与长尾，报告均值、P95 及吞吐；另报 DRAM/Peer 复制字节和 Tier R/D/P 比例。检验 Slack 是否减少无效复制，以及计数、备份和 Peer 写入是否干扰前台，而不预设“近零开销”。

在同一 workflow 的关键路径与不同 Slack 分支分别注入，画各位置的 WCT 惩罚中位数与四分位距，同时标注故障时估计 Slack 和离线实际 Slack。所有位置沿用相同恢复并发配置；低 Slack 请求是否获得更多有效保护、较大 Slack 是否吸收恢复延迟，由实际配对运行验证。

### 5.4 恢复的 KV 来源与时间分解

来源图将历史 KV 划分为 Peer 已驻留、DRAM 恢复前装载、DRAM 后台补齐和重算，按同一 token/层口径去重核算。时间图记录检测、准入、H2D、补取、重放与首次恢复 decode 的事件；用时间线展示重叠，或只堆叠关键路径上互斥的时间区间。不能把全部 H2D 服务时间与计算时间直接相加，也不能将其他请求的总传输量当作本请求等待。另报不受故障直接影响的前台请求变慢。

### 5.5 消融

保留相同并行调度器，每次只移除一项保护机制：

- **无 Slack 优先级：** 所有请求保留 DRAM 副本，Peer 配额平均分配，保留请求内层序与热度。
- **无稀疏热度优先级：** 保留 Slack 与层序，块按最近位置选择，恢复仍使用原模型的真实选择器与补取；不能通过改成稠密注意力替代这一消融。
- **无层序优先级：** 保留 Slack 与热度，改为 token 段优先，以分离层就绪顺序的作用。
- **无 Peer 层：** 保留 Slack 分层与在线装载器，只使用 DRAM/重算。
- **无有用配额上限：** 保留两级排序，但不在 $B_{use}$ 处停止，检验是否过度保护少数请求。

分别在两种带宽下报告 WCT 惩罚、Peer 驻留量与复制流量。预算充足或带宽很高时，差异可能很小；不要求每项机制在所有条件下均显著获益。

### 5.6 敏感性

扫描 Peer 预算 0–16 GiB、总 H2D 带宽 6.25–50 GB/s、同时 retry 的请求数 1/2/4/8，以及固定 retry 数下低 Slack 请求的比例。改变并发度时保留总带宽约束，并报告实际传输/计算重叠率，而不引入固定串行恢复顺序。另扫描 Slack 估计误差（乐观/悲观 ±30%）、密封尾部长度和热度窗口；跨模型分别校准 KV 大小、计算代价与选块轨迹，只有明确标为机制扫描时才单独替换 $\tilde u$。

### 5.7 结论边界

图 1–4 与图 7 支撑动机和选块特征，原有两模型覆盖三份文档及 16K/32K 历史，图 4 增加 256/512-query 窗口对照；仍需更长上下文、更多选择器家族与 agent 类文本。图 6、8 是单请求解析机制图，不证明请求间串行关系，也不证明端到端收益。旧串行模型的数值结论已撤回，当前不声称新版降低 WCT 或备份开销已被验证。下一阶段需完成并行恢复的模拟器/原型对齐、补取时延微基准及上述配对实验。更早的结果见 [逐图审查](PAPER_FIGURE_REVIEW.md) 与 [旧图](Old_Figures.md)，不进入当前结论。

## 6 Related Work

**GPU 故障与训练侧的快速恢复。** 大规模集群的运维报告（Llama 3、MegaScale、Acme 的集群特征研究）一致指出 GPU 与 HBM 故障是非计划中断的主要来源。Gemini、CheckFreq、Oobleck、Bamboo、ReCycle 等利用内存检查点或冗余计算缩短训练故障的恢复时间。训练的状态是全局同步的，而服务的状态是每请求独立、生命周期短、价值随工作流位置变化的，这使得优先级放置成为核心问题。

**KV cache 系统。** PagedAttention/vLLM 把 KV 以块为单位管理；Mooncake、LMCache 等把 KV 提升为跨节点共享的一等对象，并用 DRAM/SSD 池支持前缀复用。AegisKV 复用这类块级密封与复制机制，但决定"复制什么、复制到哪"的依据是故障恢复对 WCT 的影响，而不是复用命中率。

**LLM 服务的容错与迁移。** DéjàVu 把 KV 流式复制到 CPU 以容忍 fail-stop；Llumnix、ServerlessLLM 通过请求迁移或快照缩短中断。AegisKV 的区别是结合 workflow 级 Slack 与请求内稀疏热度，为有限的备份介质分配两级保护优先级；它不要求替换引擎的并发恢复调度器。

**多智能体与工作流调度。** Parrot、Autellix 等把应用级依赖信息暴露给服务系统以优化端到端时延。AegisKV 使用关键路径法的总时差衡量请求能吸收的恢复延迟，将应用信息用于备份放置，而不是设计新的请求执行顺序。

**稀疏注意力与 KV 卸载。** NSA、InfLLM-v2/MiniCPM4、NOSA、DSA 等原生稀疏注意力通过可训练的块选择降低长上下文注意力的代价；Quest、DuoAttention、MInference 等在推理时选择部分 KV；NOSA、InfiniGen 等进一步利用选择的局部性做 KV 卸载与预取。AegisKV 不改变这些方法的选择器，只把它们已经产生的块选择信息用作备份优先级与恢复装载顺序，并处理它们都无法回避的"重放需要的是并集"这一事实。

## 7 Conclusion

AegisKV 面向多智能体长上下文服务，以 WCT 为保护目标：Slack 决定请求之间的保护优先级，层序与稀疏热度决定请求内部保护哪些块，有用配额限制 Peer HBM 的无效占用。故障后，各请求沿用引擎的并行 retry 与计算/传输重叠能力，按自身 KV 就绪条件推进，缺失的必要块按需补取。测量与单请求解析图支持这一设计的动机；新版端到端收益、前台干扰及估计误差下的鲁棒性仍需 §5 的实验验证。
