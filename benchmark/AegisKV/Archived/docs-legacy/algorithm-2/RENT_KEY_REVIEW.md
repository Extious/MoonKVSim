# SlackLandlord：是否继续采用历史租值键

> 历史评审，已由 [Agent 子租约与尾块收租设计](AGENT_LEASE_DESIGN.md) 接续。下文保留当时“暂不恢复 H”的结论及其理由；当前版本按 Agent 单独授信、仅对可释放尾块收租，并在推进 L 前检查全部尾块，不再采用下文建议的无 H 主流程。三个冲突的处理与边界见新设计第 1、4–8 节。

2026-09-08。本文评审旧专利的 H/L 租值键与当前单块恢复收益模型的兼容性，不修改专利或运行实现。[当前流程图](../drawio/slacklandlord-patent-revised/algorithm-2-patent-revised.drawio)继续按 P 选择合法尾块、按实际回收损失判断准入。

**建议：不原样恢复旧租值键作为当前算法的主决策依据。** 租值键作为扣租状态的表示是合理的，但不能与“按最新输入重算收益”混为同一个操作。若继续保留真正的租金机制，需要先定义共享信用的续租规则和尾块排序保证。当前 D_Y 是容量回收的机会成本，不是已经实现了累计租金；名称 SlackLandlord 沿用研究方案，不据此声称具备经典 Landlord 的全部机制或保证。

## 1. 租值键合理的含义

经典 Landlord 为缓存对象授予信用，容量不足时按对象大小统一扣租，信用耗尽后淘汰；真正访问对象时可以补充信用。其分析对象是具有给定大小和读取成本的文件，原文明确没有处理读取成本随时间改变的问题。见 Young, [On-Line File Caching](https://www.cs.ucr.edu/~neal/publication/Young02Online.pdf)，图 1 与脚注 3。

GreedyDual-Size 用累计量 L 和对象键 H 代替逐项减法：插入或命中时设置 H=L+cost/size，回收时推进 L；对象没有新访问时不自动补充信用。见 Cao & Irani, [Cost-Aware WWW Proxy Caching Algorithms](https://www.usenix.org/legacy/publications/library/proceedings/usits97/full_papers/cao/cao.pdf)，图 5。

按照这个扣租规则，可推导出下面的等价表示。令 ℓ_x 为 x 上一次获得信用时的 L，P_x 为该次授予的单位字节信用，则：

\[
H_x=\ell_x+P_x,\qquad
c_x(L)=b_x\max(H_x-L,0).
\]

c_x 是该租约的剩余信用，区别于当前流程中的净收益 Credit_x。L 增长时，只读取 H_x 与 L 的差就能得到剩余信用，不需要遍历所有块逐项扣减。这个“延迟扣租”是历史租值键本身的价值；它与“收益输入变动后延迟计算 W/G/P”是两项不同的优化。

## 2. 不能把 Lazy Refresh 写成无条件续租

假设只有 L 推进、x 没有获得新信用，P_x 也没有变化。如果此时因为索引刷新而执行 H_x←L+P_x，那么：

\[
c_x(L)=b_x\max(\ell_x+P_x-L,0)
\quad\longrightarrow\quad b_xP_x.
\]

已经消耗的租金被补回了。若触发原因只是成为堆顶、成为新尾块或者收益缓存版本检查，这种补回没有对应的新请求授权。

另一种做法是在每次比较时，把所有候选都重算为同一当前 L 加上最新 P。此时：

\[
\arg\min_y(L+P_y)=\arg\min_yP_y.
\]

共同的 L 完全不改变这次排序，H 也就没有保留历史扣租的作用。以上两点是针对当前设计的代数推导，不是经典算法在原问题设定中的缺陷。

## 3. 当前 KV 场景还缺少的条件

| 当前要求 | 直接套用 H=L+最新 P 的问题 |
|---|---|
| 一个 Agent 新请求只更新自己的权益 | 整块重新授信会同时补回其他 Agent 已消耗的信用，违背分 Agent 续租要求 |
| 同一工作流存在共享块和并行分支 | 联合 WCT 收益通常不能唯一拆为可相加的每 Agent 信用；先相加后分账可能重复计价 |
| 保持可恢复的连续前缀 | 内部块即使信用归零也不能直接删；只从尾块推进租金不再是经典全池扣租规则，需重新论证 |
| Slack 在新请求时可升可降 | 陈旧键可能高于最新键；只刷新旧堆顶可能漏掉另一个已经降价的尾块 |
| 按当前恢复收益分配有限容量 | 历史 H 混入授信时间；即使所有最新 P 相同，H 也可能不同，这需要一个明确的跨时间优化目标 |

尾块后插入、初始租值键较高的问题，也不会因为写出 H=L+P 就自动解决。必须明确是在保护历史租约，还是在比较当前删去尾块会损失多少 WCT 收益。前者不是后者的同义表达。

## 4. 如果继续研究租值键，必须分开的操作

| 操作 | 应有语义 |
|---|---|
| 新请求登记 | 更新该 Agent 的输入与轮版本，登记一次续租事件；其他 Agent 不自动获得信用 |
| Lazy Refresh | 读取最新输入、重估收益并验证版本；本操作不自动重置整块剩余信用 |
| 兑现续租 | 按明确的共享收益归属规则替换该 Agent 的贡献；同一事件只能兑现一次 |
| 容量扣租 | 推进 L；已有租约的信用由 H 与 L 的关系消耗 |
| 选择尾块 | 使用有效键或经过证明的排序下界；不能假定任意陈旧键都是下界 |

仅增加这些事件名称并不构成已完成的算法。共享 WCT 收益如何归属、被前缀保护的零信用块如何处理、租值键下降如何修复索引，仍要给出可执行规则和验证。直接另加一套 Agent 账本会增加复杂度，不应在这些语义未确定时塞回主流程。

因此，当前主流程继续使用准确的模型收益、条件回收损失和按需计算；历史租金方案保留为待验证的设计方向。若未来重引入 H，需要与当前方案比较恢复 WCT、准入/回收结果及控制开销，不能仅凭经典算法的名字移植其竞争保证。
