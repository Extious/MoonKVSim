# Algorithm 2 参考模型验证

验证日期：2026-09-08。机器可读结果及被测源码 SHA-256 见 [VALIDATION.json](VALIDATION.json)。

**结果：28 项检查通过。** 这是 Python 3.8.17 上、精确有理数运算下的 CPU 元数据/合成代价验证，不是 MoonKVSim 正式 E2 实验或 Mooncake 实机性能结果。

## 1. 复现

在仓库根目录运行：

~~~bash
python benchmark/AegisKV/docs/algorithm-2/validate.py
~~~

脚本先运行本目录的测试，再生成计算量示例和源码指纹。任何失败都会记录并以非零退出码结束。时间数值随机器负载变化，精确值、分配和计数由固定输入/随机种子决定。

测试文件：

- [test_reference.py](test_reference.py)：目标、反例、精确求解与区间。
- [test_policy.py](test_policy.py)：事件更新、有限预算模式、回收和事件合并。
- [test_protocol.py](test_protocol.py)：复制、实际释放、版本和迟到通知。

## 2. 正确性检查覆盖什么

| 检查 | 规模或关键断言 |
|---|---|
| 前缀选择 | 尾部边际收益最高时仍可保留短前缀；缺口非法 |
| 组合收益 | 单块收益为 0 的前缀不能阻止整个有价值组合被考虑 |
| Slack | 同样恢复时间减少，在不同 Slack 下收益为 4、2、0 |
| 共享容量 | 一份共享物理副本只占一次容量 |
| 工作流合并 | 两个独立工作流可合计 8；同一并行工作流仅为 4 |
| 非次模反例 | 单独备份两个分支分别为 0，一起备份为 4 |
| 场景 | 归一化权重和场景特定恢复时间表 |
| 随机精确对照 | 240 个 1–8 块的森林/共享路径/工作流/可变字节实例 |
| 四种求解一致性 | 穷举、完整刷新搜索、Lazy 搜索、组件整数 DP 的值和分配相同 |
| 跨轮有效区间 | 24 个随机模型，各连续更新 3 轮且不逐项刷新；所有合法状态的新值都在区间内 |
| 搜索超时证据 | 25 个随机模型，各测试 0、1、3、9 次搜索预算，满足“可行值 ≤ 穷举最优值 ≤ 上界” |
| 固定引用和可读性 | 非法固定集合、容量不足或前缀缺失被拒绝 |
| 缓存隔离 | 不相关工作流的值/场景成员更新不会补算其他工作流 |
| 正常在线替换 | 候选必须被精算为严格改善；未闭合差距不会被标成 exact |
| 容量下降 | 即使收益降低也执行必要回收；固定引用超额时延后 |
| 物理释放 | 释放 ACK 前不扣除占用，不开始占用所需空间的复制 |
| 复制提交 | 每个必需分片都确认后才可恢复，重复 ACK 不充当其他分片 |
| 迟到通知 | 旧事务 copy ACK、旧分配代次 free ACK 都不能修改新副本 |
| 失败处理 | 不会把已删除的旧备份当作回滚成功 |
| 事件持续到达 | 纯价值更新合并到合法复制完成之后；源失效立即撤销，不能合并延后 |

穷举独立枚举所有物理集合，与搜索和 DP 的枚举方式不同；三者共享模型的目标函数。模型公式另由手算例子和 [PROOFS.md](PROOFS.md) 检查。随机对照不是一般正确性的数学证明。

## 3. 解决尾部问题的最小例子

A 的累计前缀收益为 0、1、3、6，B 的一块收益为 4，容量为 3。

| 结果 | 值 |
|---|---|
| 原有 A 完整三块 | 6 ms |
| 最优保留 | A1、A2、B1 |
| 最优收益 | 7 ms |
| A 删最后 1 / 2 / 3 块的损失 | 3 / 5 / 6 ms |

这说明“删尾换来更大收益”不等于“前面也应全部过期”。此例没有用位置保护分数或人为分摊 Credit。

## 4. Lazy 的两种效果分别报告

### 4.1 冷启动搜索：没有普遍收益

24 个独立的双块 Agent，共 48 个物理块、容量 24：

| 模式 | 工作流精算次数 | 搜索弹出次数 | 本次耗时 |
|---|---:|---:|---:|
| 完整刷新 | 24 | 73 | 约 41 ms |
| Lazy | 24 | 73 | 约 43 ms |

二者得到相同精确结果。这个例子中 Lazy 没有少算，反而有区间管理开销。此输入以 \(4^j\) 设置合成收益尺度，目的是避开大量等值解造成的枚举，不代表真实恢复代价分布。

另外使用固定种子 90210，生成 80 个各含 8 块的随机模型：

| 指标 | 结果 |
|---|---:|
| 所有分配结果一致 | 80 / 80 |
| 完整刷新总工作流精算次数 | 410 |
| Lazy 总工作流精算次数 | 408 |
| Lazy 少算 / 相同 / 多算的实例数 | 2 / 78 / 0 |

这组数据只减少约 0.5% 的精算，不能声称冷启动 Lazy 已显示明显优势。

### 4.2 跨轮组件复用：局部更新可以明显少算

24 个相互独立组件，每个包含一个双块 Agent。完成一次求解后，仅改变一个工作流下一轮的 Slack：

| 指标 | 全部重新构建 | 复用未变组件 |
|---|---:|---:|
| 重建组件数 | 24 | 1 |
| 复用组件数 | 0 | 23 |
| 工作流精算次数 | 48 | 2 |
| 结果与完整重建一致 | 是 | 是 |

精算次数减少 95.8%，来自**组件候选表复用**。全局整数 DP 仍执行 1332 次状态转移；并没有减少为只处理该 Agent 的两块 KV。

本次冷构建约 33 ms，局部更新路径约 20 ms。二者输入状态不同，且计时不包含 Model 构造；没有进行重复采样或系统负载控制，因此不以这两次耗时推导生产加速比。

## 5. 共享规模压力：必须保留的负面结果

构造一个有 20 个并行 Agent 的工作流：它们共用一块前缀，各有一块独有后缀，共 21 块；Pool 容量为 10。

| 项目 | 结果 |
|---|---|
| 完整组件表预算 | 128 个配置，触发超预算 |
| 后续搜索预算 | 100 次弹出 |
| 找到的可行收益 | 1 ms |
| 仍未排除的收益上界 | 73 ms |
| 报告的差距 | 72 ms |
| exact | false |

根据这个专门构造的并行结构，可以手算最优值其实是 1；但求解器在该预算内未能证明它。这揭示当前上界在强并行互补场景下很松。

两种运行模式分别处理：

- 精确模式：DEFER，不冒充已经证明最优。
- 有限预算模式：已有该共享前缀时 KEEP；从空 Pool 开始时可选择收益 1 的前缀并复制，仍记录 exact=false、gap=72。

这个结果不能被写成“已解决任意共享规模的实时分配”。它说明上界收紧、组件结构利用和真实负载上的求解预算仍然重要。

可以报告：

目前不能报告：

- Mooncake 或 MoonKVSim 正式运行路径已经采用本算法。
- 实测 WCT 改善、Peer HBM 对前台推理无影响、控制器生产尾延迟。
- 保留旧累计 L 与 Agent 分账续租的行为等价性。
- 通用 Lazy 加速比、已证明的新在线竞争比或已确认的首创性。
