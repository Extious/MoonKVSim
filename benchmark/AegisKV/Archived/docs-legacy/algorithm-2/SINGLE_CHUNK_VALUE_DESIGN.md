# SlackLandlord：单个 KV chunk 的备份决策

2026-09-08 更新。[当前 Draw.io](../drawio/slacklandlord-patent-revised/algorithm-2-patent-revised.drawio) 每次只决策一个物理 KV chunk **x**，不再枚举候选集合 X。符号说明放在流程开头；图件使用黑线、黑字和白底。

[chunk_slacklandlord.py](chunk_slacklandlord.py) 提供相应 CPU 元数据参考 `decide_chunk`。它检查连续前缀、评估 x、试算尾块回收并返回准入方案，尚未接入 Mooncake 或 MoonKVSim 的实际复制执行路径。

## 1. 决策对象和引用记录

- x 必须已完整生成、源端可读，且其所有祖先已提交备份。缺少前缀时返回 `WAIT_FOR_PREFIX`，不隐式补充其他 chunk。
- x 已有提交副本时，仅更新逻辑引用并返回 `REUSE`，不重复分配物理空间。
- 每个 chunk 保存父块、物理字节数和引用 Agent 的 ID。Slack、当前轮版本、恢复代价保存在对应 Agent/工作流记录中；图里的 `Agent1: Slack1` 是展开显示这些引用，不要求把 Slack 值复制到每个 chunk 中。
- 图中 `Size:4096 tokens` 表示 token 数；容量判断中的 b_x 使用真实 KV 布局对应的 HBM 字节数，不能把 4096 tokens 当成 4096 bytes。

## 2. 恢复收益和 Priority

当前图的 ③a–③d 直接给出公式，不再以数值算例代替计算规则。W_x 表示额外备份一个物理 chunk x 能使受影响工作流提前完成的时间，单位为 ms。

### ③a 连续前缀的恢复代价

令 k 为当前可用的连续备份块数，n_a 为 Agent a 已生成的总块数。t_a^load(j) 是加载前 j 块的时间；t_a^rec(j,n_a) 是重算第 j+1 至 n_a 块的时间。加载和重算串行时：

\[
T_a(k)=\min_{0\le j\le k}
\{t_a^{\mathrm{load}}(j)+t_a^{\mathrm{rec}}(j,n_a)\}.
\]

j=0 表示全部重算。允许回退到更短的可用前缀，使 T_a(k) 不随可用备份增加而增大。代价从对应模型、KV 布局和恢复路径的测量/代价表读取；若加载和重算重叠，则使用该恢复调度的完成时间替代括号内的串行加和。公式针对给定故障情形；不受影响的节点恢复耗时为 0。

### ③b 单 Agent 的 Slack 收益

候选 x 是已有前缀后的第 k+1 块：

\[
\Delta T_{a,x}=T_a(k)-T_a(k+1),
\qquad
W_{a,x}=\min\{\Delta T_{a,x},\max(T_a(k)-s_a,0)\}.
\]

一个工作流只有 Agent a 额外受恢复影响时，该式直接给出 x 对它的 WCT 收益。s_a 是该 Agent 的本轮 Slack，在本轮请求中不变。只有超过 Slack 的恢复延误会推迟工作流，因此时间收益由 min 限制。若 x 只服务这一个受影响工作流，W_x=W_{a,x}。

### ③c 共享块按工作流联合计算

同一工作流有多个受影响 Agent 时，不能直接相加上面的 W_{a,x}。令 d_v 为 DAG 节点的正常耗时，T_v 为该节点的恢复耗时，t_v 为完成时间；对给定的各节点恢复耗时向量 T，按拓扑顺序计算：

\[
t_v=d_v+T_v+\max_{u\to v}t_u,
\qquad
\mathrm{WCT}_w(\mathbf T)=\max_{v\in w}t_v.
\]

无前驱时最大值取 0。受影响的 Agent 节点取 T_v=T_a(k_a)，其他节点取 0。向量 T^x 只把引用 x 的受影响 Agent 节点改为 T_a(k_a+1)，其他节点维持当前恢复耗时。于是共享物理块的总收益为：

\[
W_x=\sum_{w\gets x}
\big[\mathrm{WCT}_w(\mathbf T)-\mathrm{WCT}_w(\mathbf T^x)\big].
\]

w←x 表示工作流 w 引用 x；每个工作流只出现一次。T 和 T^x 是两组节点恢复耗时，不是两个候选块集合，准入对象仍是单个 x。这一表达直接使用 DAG 完成时间，不引入 J 或中文“加入前/加入后”下标。

同一工作流内部的等待与汇合由 max 递推计算，隐含在 s_a 中的工作流结构没有丢失；也没有在生成请求的过程中修改 s_a。单 Agent 公式是这个 DAG 模型的特殊情形。代价表有多种故障情形时，逐情形计算上述收益，再按固定情形权重汇总；不据此声称已测得真实故障概率。

### ③d 备份收益与单位字节优先级

\[
G_x=W_x,\qquad P_x=\frac{G_x}{b_x}.
\]

本版只计故障恢复收益，不包含命中复用或 LRU 奖励。b_x 是本池中的实际物理字节，P_x 的单位为 ms/byte。尾块 y 的保留收益按当前试算状态计算：暂移去 y 后，把 y 作为该前缀的下一块代入同一组收益公式。试算状态已经包含本次候选 x，因此同时引用 x/y 的工作流不会被分别按错误的固定分数计算。

## 3. 单块准入与尾块回收

1. 对本次 x 建立临时回收记录：Y 为空、D_Y=0、f 为可用字节。
2. f<b_x 时，只比较可释放的物理尾块。候选 x 的祖先及固定读取前缀不能回收；仍有保留后继的内部块不能单独删除。
3. 每个参与比较的尾块 y 按当前试算状态计算保留收益 W_y，令 G_y=W_y、P_y=G_y/b_y，选择 P_y 最小者；并列按稳定 ID 决定。此时的状态已包含候选 x，因此不会忽略 x 与 y 在同一工作流中的依赖。
4. 每次只试删一块：

   \[
   Y\leftarrow Y\cup\{y\},\quad D_Y\leftarrow D_Y+G_y,\quad f\leftarrow f+b_y.
   \]

   新暴露的尾块重新检查输入和收益；f≥b_x 后立即停止。D_Y 累计的是各次试删当时的损失，不能累加陈旧的固定分数。
5. 计算 \(\mathrm{Credit}_x=G_x-D_Y\)。只有 Credit_x>0 才准入；找不到合法尾块或净收益不正时返回 `BYPASS`，保留现有备份。
6. 执行层重验版本、容量和固定读取引用，等待 Y 的物理释放后才给 x 分配空间并复制。全部必要分片确认后发布 `COMMITTED`；失败则回收新分配，不能假装已恢复被释放的旧副本。

一次成功准入最多新增 **一个**物理 chunk。淘汰集合 Y 可以有多块，例如 chunk 字节大小不同；它不是候选集合。容量缩小时暂停新准入，先完成回收；正在复制、释放的分配仍占实际容量。

容量租金仍指实际回收损失 D_Y；Credit_x 是本次净收益。此版没有恢复旧的累计 L、历史租值键 H 或 Agent 分账扣租余额。

## 4. Lazy Refresh 更新什么

**新请求更新输入；实际决策才更新计算结果。** 如果新请求到来后马上遍历全部已备份 chunk 并重算每个键，就不存在这里的 Lazy Refresh。引用了 Agent 的 chunk 不必各自保存一份权威 Slack：只保存 Agent ID，图中显示的 Slack 从 Agent 表读取。

| 时机 | 更新的内容 |
|---|---|
| Agent1 新请求 | 只登记 Agent1 的 Slack、轮版本和对应恢复输入；不重算已有块的 W/G/P；Agent2 的当前记录保持原值 |
| 复用已经备份的共享块 | 登记新增或解除的 Agent 引用；已有副本不重新准入，不因命中而重算整段 KV 的键 |
| 新引用、引用解除、恢复代价或前缀变化 | 更新对应输入记录/版本；之后读取时版本失配表示缓存陈旧，不要求逐块写 dirty 标记 |
| 新块 x 待准入 | 计算 x 的当前 W/G/P；这是新块的首次计算 |
| 已备份尾块 y 参与回收比较 | 检查引用/工作流输入和当前试算前缀；变化时才重算该块的 W/G/P，并记录对应版本 |
| 输入和前缀均未变 | 使用已缓存的值 |
| 试删后暴露新的物理尾块 | 重新检查其当前收益，不沿用上一尾块的过期键 |

例如 Agent1 的 Slack 从 8 改为 4 ms、版本从 7 改为 8，引用它的一个已备份块仍保留按版本 7 算出的 P。块参与回收比较时发现 `已算版本7 ≠ Agent当前版本8`，才重新计算该块并记下版本 8；尚未参与比较的内部块继续保留旧结果。共享块重新计算时同时读取 Agent2 的当前输入，但不会给 Agent2 增加一份历史信用。本版没有这种信用账本。

假设一条没有分叉、没有固定读取限制的链有 100 个已备份 chunk。新请求到来时只改 Agent 输入，100 个 chunk 都不立即重算。容量足够、也没有回收事件时，已有块可以一直不算；需要比较这条链时，先计算可释放的第 100 块，只有它被试删后，第 99 块才进入比较。期间多次新请求还可合并为按最新输入计算一次。这是延迟计算的收益来源；若每次事件恰好都需要所有合法尾块的最新值，能省下的重算就会减少。

**比较范围和排序正确性。** 当前简单实现检查所有可释放尾块的输入版本，而非全池内部 chunk 的收益。选择最小 P 时必须使用相同试算状态下的有效值。Slack 可以在新请求时增大或减小，陈旧键并不总是最新键的下界；只刷新旧堆顶可能漏掉已降价的其他尾块。因此本版不声称实现了旧专利的“只弹出堆顶即可保证正确”的懒堆。

**与旧专利的区别。** 旧专利把持久租值键写成 H_x=L+P_x；当前简化版没有 L/H，而是当前回收损失 D_Y 和本次净收益 Credit_x。因此图中的 Lazy Refresh 准确指恢复收益及优先级的按需计算，不能直接称为已经完成了旧版租值键刷新。恢复 H 还涉及累计租金、共享 Agent 信用和排序保证，是另一项算法设计，不能只把 P 改名为 H。

[租值键评审](RENT_KEY_REVIEW.md)给出经典来源、剩余信用公式和续租/刷新混淆的代数推导。当前建议是不原样恢复旧 H 主决策；真实累计租金方案仍保留为待验证方向。

**参考代码的实现边界。** 调用方跨事件保留一个 `LazyValue` 实例，通过 `decide_chunk(..., values=...)` 使用。`LazyValue.update(model)` 登记并扫描工作流输入签名，但不计算工作流收益；`__call__` 首次读取相关工作流与前缀组合时才计算。CPU 参考缓存保存工作流收益，按 chunk 操作求出 W/G/P；它没有每个物理 chunk 的 P 缓存和租值键最小堆。图中按块显示的已算版本表达部署接口，不是现有 GPU 实现。版本登记也没有被证明为 O(1)，Lazy 的性能收益尚未实测。

## 5. 单块版本的边界与验证

在输入模型固定且方案成功提交的条件下，普通准入保持前缀合法、共享空间只计一次，并严格改善模型内的 WCT。它没有全局最优保证。

**改为单块 x 后，不再解决“前几块各自零收益、只有多块一起备份才有收益”的组合准入。** 如果第一块的 G_x=0，本次会 BYPASS；未来新请求/恢复输入变化可以重试，但不能声称总能进入那段有价值的长前缀。多个互不共享的 Agent 需要同时备份才有收益时也可能漏解。这是严格单块决策的实际限制，没有用隐式集合或额外奖励隐藏它。

[CHUNK_VALIDATION.json](CHUNK_VALIDATION.json) 记录 7 项行为检查和 160 个随机小实例：成功计划恰好新增 x、缺少前缀时不补块、共享副本不重复分配、固定引用与容量约束、条件回收损失、Slack 直接公式、Lazy 输入失效，以及联合收益的负面用例。都是 CPU 模型验证，不是部署或性能结果。
