# SlackLandlord：从最小模型到可执行的容量分配算法

更新日期：2026-09-08。本文对应本目录的独立 CPU 参考实现。

这次推导得到的核心结论是：**物理管理对象仍然是 KV chunk，但优先级必须针对一个合法的备份状态变化计算。** 对有前缀依赖的 KV，不能先给每个 chunk 分配一个固定 Credit，再假定这些 Credit 可以独立相加、独立淘汰。共享引用和工作流并行还会进一步破坏这种假定。

本目录给出了完整的目标函数、容量租金推导、精确基准、带误差上界的在线求解、跨轮缓存，以及复制与释放的元数据执行流程。它在明确的恢复时间模型内可验证；它尚未替换 MoonKVSim 或 Mooncake 中的运行路径。

**一个必须明确的设计变化：本版的“租金”是容量约束导出的单位容量价格，不是旧版累计 \(L\) 扣减历史余额的租金。** 因而，本版不实现“只有 Agent A 补充自己的余额，B/C 保留已扣租余额”的旧账本语义。新一轮只替换 A 的模型输入，但这不能被称为已经实现分账续租。这里按“允许调整租金数学定义”的工作假设推进；两个语义不能混写成同一个算法。

## 1. 本次固定的范围

1. 算法 3 提供一个 Peer HBM Pool 的可用容量 \(C\)，算法 2 不重新评价前台推理的显存代价。
2. 算法 2 的容量消耗是实际备份字节数。同一个物理 chunk 被多个 Agent 引用，仍然只占一份容量。
3. 暂不把备份复制占用带宽、复制耗时、复制能耗加入收益函数。复制仍然必须完成后才能用于恢复。
4. 收益只来自故障后 WCT 的减少；没有命中次数、复用频率、LRU、年龄奖励或人为设置的前缀保护分数。
5. 恢复只使用连续且已提交的备份前缀，后续 KV 重算。不使用“重算前面、读取后面”的恢复路径。
6. Agent 的本轮 Slack 不因本轮生成一个 chunk 而重新估计。新请求到来才发布新一轮的工作流输入。新 chunk 完整生成后，恢复时间表可以扩展。
7. 优化使用当前可见的数据和预测。它不读取未来真实生成长度、未来实际运行时间或未来真实故障。

容量约束并不意味着“把容量成本删除”。这里将其保留为硬约束，并由这个约束导出容量的竞争价格。恢复时的读取和重算时间仍在收益模型中；用户暂时省略的是**备份复制对系统的带宽干扰**。

## 2. 最小模型：一个 Agent 的连续前缀

设已经生成的完整 chunk 是 \(x_1,\ldots,x_n\)。可选备份状态只有前 0、1、…、n 块。

- \(T(k)\)：保留前 k 块备份时，恢复当前已生成 KV 所需的时间，单位 ms。
- \(s\)：该 Agent 在当前工作流中的 Slack，单位 ms。
- \(U(k)\)：这段备份减少的工作流完成时间，单位 ms。

\[
U(k)=[T(0)-s]_+-[T(k)-s]_+,\qquad [z]_+=\max(z,0).
\tag{1}
\]

恢复时间表应来自可测量的恢复路径：

\[
T(k)=\min_{0\le j\le k}
\{\text{读取前 }j\text{ 块的时间}
+\text{重算其余已生成 KV 的时间}
+\text{必要的恢复同步时间}\}.
\tag{2}
\]

取最短可用前缀路径使 \(T(k+1)\le T(k)\)。这不是要求所有备份都必然加速，而是允许恢复器忽略没有带来加速的备份。实际重算时间可随上下文长度、批大小和 TP 配置变化，不能默认每块相同，也不能凭位置直接设一个权重。

**Slack 没有被做差消掉。** 只有当两个恢复时间都超过 Slack 时，局部收益才等于两者时间差；此时两条恢复路径本来都在拖慢关键路径。

例如，\(T(0)=12\)、\(T(1)=8\)：

| Slack | 不备份的 WCT 损失 | 备份的 WCT 损失 | 备份收益 |
|---:|---:|---:|---:|
| 2 ms | 10 ms | 6 ms | 4 ms |
| 10 ms | 2 ms | 0 ms | 2 ms |
| 15 ms | 0 ms | 0 ms | 0 ms |

这张表给出了请求/Agent 级 Slack 如何影响 chunk 决策，而不需要把低 Slack 转成所有 chunk 都很高的统一分数。

### 2.1 前缀扩展和截短应该如何计价

从前 k 块扩展到前 k+m 块，收益为：

\[
\text{扩展收益}=U(k+m)-U(k).
\tag{3}
\]

从前 k 块截短到前 k-m 块，损失为：

\[
\text{截短损失}=U(k)-U(k-m).
\tag{4}
\]

这里不是取消 chunk 管理。实际分配和释放仍按 chunk 执行，但一个决策可以包含多块，且必须保持连续前缀。

### 2.2 “尾部收益最高”并不意味着删尾后整个前缀都应删除

使用参考实现中的例子：Agent A 的前缀累计收益是 0、1、3、6 ms；Agent B 的一块备份收益为 4 ms。每块占一个容量单位，Pool 容量为 3。

| 可行备份 | 占用 | 总收益 |
|---|---:|---:|
| A1、A2、A3 | 3 | 6 ms |
| A1、A2、B1 | 3 | **7 ms** |
| A1、B1 | 2 | 5 ms |
| B1 | 1 | 4 ms |

虽然 A3 的新增收益为 3 ms，高于 A1 的 1 ms 和 A2 的 2 ms，仍然应删 A3 换 B1，保留 A1、A2。原因是容量只需要腾出一块；删更多会额外损失收益。

从 A 的完整前缀依次删除最后 1、2、3 块，真实损失是 3、5、6 ms。**一次截短成立，不能推导下一次截短也成立。** 本版没有“尾部的历史期限到期，所以前面也全部到期”的规则。

同样，只看下一块也会漏解。若累计收益为 0、0、0、3 ms，前两块单独没有收益，但三块一起有收益。求解器必须能评价合法扩展的组合，不能遇到一块零收益就永久停止该 Agent 的备份。

## 3. 完整模型：共享物理 KV 与工作流 WCT

### 3.1 三种对象各负责什么

| 对象 | 保存的核心信息 | 用途 |
|---|---|---|
| 物理 chunk | 内容与模型/布局绑定、父 chunk、字节数、目标 Pool、提交状态 | 去重、容量核算、复制和回收 |
| Agent 的当前执行分支 | 工作流、Agent/分支身份、本轮输入、KV 路径、各前缀的恢复时间 | 找出该 Agent 能恢复到哪里 |
| 工作流 | 当前剩余 DAG、节点时间、Agent 所在节点 | 计算故障是否真正推迟工作流完成 |

Agent 身份可以跨请求保持；本轮数据用版本替换。同一个 Agent 并发的不同分支必须拆开登记，不能共用一个可变的本轮记录。一个共享 chunk 对应多条 Agent 路径，但只对应一个物理对象。

### 3.2 可行备份集合

用 \(S\) 表示拟保留的物理 chunk 集合，用 \(b(S)\) 表示其实际总字节数。必须同时满足：

- 父 chunk 不在 S 中时，子 chunk 也不能在 S 中。
- 已被恢复读取固定的 chunk 及其祖先必须保留。
- 新增块已完整生成，源端可读，内容/模型/布局兼容。
- \(b(S)\le C\)。

每条 Agent 路径在 S 中的连续长度就是它的备份前缀长度。删除内部共享 chunk 需要同时处理仍依赖它的后继；不能只释放一个内部物理块，然后继续宣布这些后继可恢复。

### 3.3 同一工作流内不能直接把各 Agent 的收益相加

对于一个给定故障场景，在本轮参考 DAG 的受影响节点加入对应前缀的恢复延迟，再按依赖关系计算节点结束时间：

\[
\text{finish}(v)=\max_{u\to v}\text{finish}(u)
+\text{正常剩余时间}(v)+\text{恢复延迟}(v,S).
\tag{5}
\]

无前驱节点的最大值取 0；整个 DAG 的最大结束时间记为 \(D_w(S,f)\)。f 是故障场景，w 是工作流。这个计算也覆盖并行分支在恢复后切换关键路径的情况。

为遵守“本轮 Slack 固定”的设定，正常执行时间与 Slack 的参考 DAG 在本轮沿用；新生成 chunk 的事件只扩展恢复代价输入。真实执行中的剩余 Slack 是否适合保持不变，是需要校准的建模假设，不能把这张参考 DAG 直接等同于任意故障时刻的实测调度结果。

以同一场景下完全不保留本 Pool 备份的结果作基线，目标为：

\[
F(S)=\sum_f\omega_f\sum_w
\bigl[D_w(\varnothing,f)-D_w(S,f)\bigr].
\tag{6}
\]

\[
\boxed{\max_{S\text{ 满足前缀、可读性和固定引用约束}}F(S)
\quad\text{s.t. }b(S)\le C.}
\tag{7}
\]

这里不再重复从 DAG 算出的结果中减一次 Slack。只有一个受影响 Agent 时，式 (6) 退化为式 (1)。

最小验证可以固定一个故障场景，令其权重为 1。多个场景的权重必须非负、和为 1，并由实验/部署的故障模型明确提供；参考代码中的合成权重不是测得的故障概率。该目标是**给定这些故障场景的条件恢复收益**，不能直接宣称是全年平均 WCT 收益。

不同工作流的 WCT 可以在式 (6) 中相加，同一工作流的并行 Agent 需要一起算。例如两个并行 Agent 都从恢复 6 ms 降到 2 ms，同一工作流缩短 4 ms；如果它们属于两个独立工作流，总缩短时间才是 8 ms。共享物理副本在两种情况都只计一次容量。

### 3.4 一个 Agent 的新请求如何影响共享块

Agent A 的新请求只替换 A 的本轮路径、恢复时间输入，以及由这次事件改变的 DAG 数据。B/C 的输入不因 A 的事件被重新初始化。

随后，重新评价受影响工作流的**整体 WCT**。A 和 B 在同一工作流时，A 的变化可能改变关键路径，因而 B 对 WCT 的边际贡献也可能改变；这是一项实际的 DAG 依赖，不是给 B “续租”。

本版没有可消耗的 Agent 余额，因此也没有“把 B 已经花掉的余额加回来”这一操作。若必须保留旧分账语义，需要另行定义和验证在线账本目标；不能把式 (6) 的当前价值称为剩余历史信用。

## 4. Priority、Credit 与租金的严格定义

### 4.1 Priority 对应合法操作的收益

给定当前 S 和另一个合法状态 S'：

\[
\Delta F=F(S')-F(S),\qquad
\Delta b=b(S')-b(S).
\tag{8}
\]

如果只是新增一块且它的前缀已经存在，\(\Delta F\) 就是这块当前的备份收益。若需要新增多块前缀，或删除共享子树，则计算整个操作。对于 \(\Delta b>0\)，可以报告 \(\Delta F/\Delta b\) 作为收益密度，但**不能仅按这个比值贪心宣称得到最优解**。

固定一个单位容量租金 \(\lambda\)，操作的 Credit 定义为：

\[
\boxed{\operatorname{Credit}(S\to S';\lambda)
=\Delta F-\lambda\Delta b.}
\tag{9}
\]

F 的单位为 ms，b 的单位为 byte，\(\lambda\) 的单位为 ms/byte。Credit 也以 ms 计，可正可负。

式 (9) 是精确的模型收益减去容量价格；没有额外的风险系数、保护权重或分摊系数。它是当前状态下的净值，不是随着墙钟时间或累计 L 消耗的余额。对于等容量替换，租金项自然抵消，需要比较的就是 WCT 净改善。

### 4.2 租金如何确定，而不是拍一个阈值

完整整数问题不能一般地靠单个租金价格解决。本版从一个可证明的上界推导价格，并让整数求解负责最终分配。

首先，由恢复时间表得到每个物理 chunk 的最大可能贡献：

\[
u_x=\sum_f\omega_f
\sum_{\substack{a\text{ 在 }f\text{ 中受影响}\\x\text{ 位于 }a\text{ 的第 }k\text{ 块}}}
\bigl[T_a^f(k-1)-T_a^f(k)\bigr].
\tag{10}
\]

**\(u_x\) 是上界，不是该 chunk 的真实 Priority/Credit。** 同一工作流的并行收益在这里可以被高估，但不会被低估，所以适合剪枝；真正决策仍使用式 (6) 的 DAG WCT。

搜索过程中，I 表示已决定保留的前缀，待定块集合为 X，剩余空间 \(R=C-b(I)\)。忽略待定块的整数性和依赖性，仅用于求上界：

\[
\overline F(I)+
\min_{\lambda\ge0}
\left\{\lambda R+\sum_{x\in X}[u_x-\lambda b_x]_+\right\}.
\tag{11}
\]

\(\overline F(I)\) 是 I 的已验证价值上界。式 (11) 是一个分数背包上界，按 \(u_x/b_x\) 排序即可得到它的最小值和对应租金。这里的价格是**这个松弛问题**的最优价格，不能称为原整数问题唯一、精确的影子价格。

这也说明租金在程序中具体起什么作用：它帮助给未探索的方案计算上界、决定先验证哪个分支、以及安全排除不可能更优的分支。实现并不以 Credit 的正负独立淘汰 chunk。组件动态规划能直接求解时，无需调用这个租金上界；所以租金并不是本版所有路径上的唯一决策机制。

## 5. Lazy Refresh：延后计算，但保留正确的比较依据

这里把两个效果分开评价：**带界的延迟重算**和**未变组件的计算结果复用**。二者都能避免逐块重算，但不是同一个加速来源。

### 5.1 同一请求内

Slack 不变，不发布“Slack 随生成下降”的事件。新 chunk 完整生成或恢复代价输入发生实际变化时，登记新模型版本。只更新有关 Agent/工作流的数据，不遍历 Pool 中所有物理块去改租值键。

同一个备份状态在未变的工作流下使用缓存的 WCT 收益。缓存键由工作流版本与相关 Agent 的备份前缀长度构成；共享物理块不会因此产生多份容量记录。

### 5.2 新请求到来后

收益可能升高，也可能降低，旧精确值不能无条件充当新下界或新上界。

对于 DAG 拓扑、Agent 路径、故障场景结构都未改变的更新，计算一个保守扰动量：

\[
E_w=\sum_{v\in w}
\left(
|\Delta\text{正常剩余时间}(v)|
+\max_{f,k}|\Delta T_v^f(k)|
\right).
\tag{12}
\]

工具节点的恢复项为 0。从某个缓存值上次计算到现在，把这些扰动量累加。由于无备份和有备份的 DAG 完成时间分别至多变化这个累加量，缓存收益满足：

\[
F_w^{\rm new}(S)\in
\left[
\max(0,F_w^{\rm cached}(S)-2\sum E_w),
\ \min(\text{当前可证上界},F_w^{\rm cached}(S)+2\sum E_w)
\right].
\tag{13}
\]

该区间只用于延迟判断，**不取区间中点作为真实收益**。若一个方案的上界已经低于当前已验证方案，可以直接跳过；否则到它真正影响选择时再计算当前 DAG。

拓扑、路径或场景结构变更时，不沿用式 (13)。相关工作流进入新缓存代次，使用新的保守上界；其他工作流仍可以复用。Lazy 的正确性不要求收益单调变化，也不要求 WCT 收益具有次模性。

### 5.3 共享与工作流组成的独立组件

将以下依赖连接起来：

- chunk 的父子关系；
- 共享的物理 chunk；
- 同一个工作流中各 Agent 使用的所有 chunk。

形成不同组件后，各组件之间既不重复占用物理容量，也不共享 WCT 目标项。每个组件可以建立“合法备份集合、所占字节、收益”的完整候选表，然后用整数动态规划分配总容量。

某个工作流下一轮更新时，只重建受影响组件的候选表；完全未变的组件直接使用缓存。**跨组件的全局容量分配仍须重新检查**，不能据此声称总决策是 O(1)。

若所有 Agent 共用一个系统前缀，或者位于同一巨大工作流中，组件可能退化为一个大组件。这是本方法的明确计算瓶颈，不通过截断候选表再声称“精确”来掩盖。

## 6. 完整 Algorithm 2 执行过程

输入：算法 3 的容量 C、当前已提交前缀、完整且可复制的候选块、固定读取引用、当前 Agent/DAG/恢复代价版本、计算预算。

~~~text
Algorithm 2: SlackLandlord（容量租金版）

收到新请求、完整 chunk、引用变化或容量变化：
  1. 更新本次事件涉及的 Agent、DAG 和源可读性。
     仅影响价值的更新可合并到当前合法复制完成之后再发布。
     源失效、布局、固定读取引用或容量变化立即使旧事务失效。
  2. 若仍有复制或实际释放未完成：记录后续事件，暂缓新事务。
  3. 构造合法候选：连续前缀、固定引用、可读源、实际字节容量。
     若固定引用已超过容量：停止新分配，等待读取结束或完成回收。
  4. 优先复用未变组件的候选表；在预算内完整计算变化组件，
     用整数 DP 选出最佳合法组合。
  5. 组件计算超预算：转入有上界的有限预算搜索。
     用租金松弛上界组织搜索；只有需要比较时才刷新 WCT。
     保留当前找到的可行方案，以及仍可能存在的最高收益上界。
  6. 正常容量下：
       精确模式要求完整最优性证明，否则 DEFER。
       有限预算模式只采用已验证比当前方案收益更高的可行结果。
       没找到更好结果则 KEEP，并记录是否仍有未闭合差距。
     容量缩小时：
       只从现有备份中选择合法子集；即使收益下降也执行必要回收。
  7. 复核版本；撤销受害后缀的恢复可见性，发起实际释放。
     RETIRING 仍计入物理占用。
  8. 所有必要释放 ACK 到达后才申请新块空间并复制。
     COPYING 计入占用，但不计入恢复收益。
  9. 同一已发布版本下所有必需分片 ACK 成功，才发布 COMMITTED 前缀。
     失败/安全相关版本变化则撤销待提交方案并等待实际释放。
     随后发布合并的价值更新，重新决策。
~~~

有限预算模式不是“选到什么就叫最优”。每次求解都返回：

\[
F(S_{\rm found})\le F(S^*)\le UB,\qquad
\text{gap}=UB-F(S_{\rm found}).
\tag{14}
\]

未搜索完但 gap=0，可以证明目标值最优；仍可能未完成确定性平局选择。本实现的 exact 标志要求连平局选择也完成。有限预算模式在 gap>0 时仍可提交严格改善的方案，但必须保留“尚未证明最优”的状态。

默认平局顺序是：先最大化 F，再最小化改变的物理字节，再最小化新增复制字节，再最小化占用。平局规则没有被加到 WCT 收益中，也不奖励最近访问。正常执行时没有严格收益改善就保留当前状态。

事件合并是避免复制反复被无关新 chunk 打断的执行规则。它允许价值输入暂时滞后一个在途事务；收益保证针对决策时已发布的快照。源地址失效、故障、布局、固定读取引用和容量变化不能这样延后，必须立即失效处理。调用 policy.py 的适配器应将这些事件标记为 hard；发生物理内容变化时保留旧分配对象，直到对应实际释放完成。

### 6.1 每类事件具体做什么

| 事件 | 处理 |
|---|---|
| 新请求开始 | 以 Agent/分支身份替换本轮输入，更新相关工作流缓存代次或扰动量 |
| 复用共享前缀 | 绑定到已有物理 ID，新增/修改 Agent 路径；重新评价有关工作流 |
| 新 chunk 生成完整 | 加入可复制候选；不把未完整 chunk 当作备份 |
| 请求尚未结束且容量不足 | 可以停止当前扩展；后来容量、共享关系或本轮结束后的输入变化可再次使其有价值 |
| 新轮不再引用旧 KV | 删除相应当前引用；未来未知的复用不会自动获得收益 |
| 工具阶段暂时无请求 | 只保留已知仍需保护的 Agent 状态；未知未来请求不虚构为受益者 |
| 恢复读取开始/结束 | 获取/释放固定引用；固定集合包含前缀依赖 |
| 源/目标失效或布局变化 | 先撤销不再有效的副本与事务；按新的故障域/可读性发布模型 |
| 算法 3 缩小 C | 停止新分配，执行已有前缀的合法回收；容量不能在 ACK 前假装已释放 |

某个 chunk 新生成不意味着它必须准入。它加入可行候选后，由整体恢复收益与容量竞争共同决定。

## 7. 实现位置与部署边界

参考实现只依赖 Python 标准库，使用有理数验证比较关系。执行：

~~~bash
python benchmark/AegisKV/docs/algorithm-2/validate.py
~~~

| 层 | 本次实现 | 尚需运行系统提供 |
|---|---|---|
| Agent/物理对象/工作流 | 显式对象、共享路径、前缀检查、DAG WCT | 从真实调度状态构建无未来信息的输入 |
| 恢复成本 | 按场景与前缀长度输入单调时间表 | 读取、重算、同步的实测与预测校准 |
| 求解 | 穷举基准、精确组件 DP、有界搜索、缓存 | 生产规模上的计算预算及尾延迟验证 |
| 事务 | 版本、实际字节核算、分片 ACK、释放代次 | CUDA/RDMA 复制、DMA fence、目录发布、故障处理 |
| 算法 3 接口 | 外部发布容量，必要时回收 | 前台保留量与每个目标设备可用容量的证明 |

当前 [slack_landlord.py](../../../../python/moonkvsim/aegiskv/slack_landlord.py) 的累计租金执行路径没有被替换。[prefix_frontier.py](../../../../python/moonkvsim/aegiskv/prefix_frontier.py) 已有的 Pool/事务对象也没有自动切换到本目录求解器。这些文件的既有仿真结果不能当作本版的实验结果。

部署时需遵守以下模型边界：

- 本目录是一个 Pool 的容量模型。多设备的放置必须预先确认各设备容量，不能只凭聚合总字节合法就宣布每张 GPU 都可放下。
- 恢复时间表可以区分故障场景，但假定给定场景下，各 Agent 的恢复延迟由自己的备份前缀决定。若并发恢复带宽/调度竞争令某个 Agent 的时间依赖其他 Agent 选择的备份集合，应扩展时间模型及上界证明。
- 当前场景模型直接表示受影响 Agent 及其时间表。候选副本需位于该规划所考虑的可用恢复目标；任意目标副本同时失效、按场景出现不同可存活 chunk 子集的模型尚未实现。
- 从当前备份切换到新备份时，可能有一段旧备份已删除、新备份尚未提交的时间。目标函数评价提交后的状态；它未优化切换期间故障的期望损失。
- Python 时间表构造、校验与组件签名仍会扫描输入。不能用“减少 DAG 精算次数”替代控制器总耗时和元数据内存开销。
- 参考事务采用单事务串行执行；真实运行系统还需持久化/清理事务记录、处理进程重启和实际设备隔离。

## 8. 旧租金语义为什么不能悄悄保留在这些公式里

经典 Landlord 在访问对象时给信用，并在需要空间时按对象大小扣租，耗尽信用后淘汰。这是有历史的在线缓存策略。[Young, On-Line File Caching](https://www.cs.ucr.edu/~neal/Young98Online.pdf)

式 (7) 则在当前快照下比较恢复收益。它不把历史上付过多少租金当作当前恢复收益。举例：容量只能放一块，A 过去信用高、当前收益 1；B 当前收益 2。旧账本可能继续保护 A；当前价值最优化会选 B。这只能说明两种策略目标不同，不能证明所有历史租金方案都无效。

若继续要求累计 L、按 Agent 分账、只补充发起者余额，应在共同的式 (1)–(7) 基准之外，另外定义在线历史目标、分账规则与保证。本版既没有证明这条路线不可能，也没有完成它。**不能为了保留旧符号，把当前价值、历史余额、容量影子价格三个不同概念混为一谈。**

## 9. 可支持的研究贡献与目前结论

“租金”“带依赖的容量优化”“用上界延迟精算”都有已有研究基础，不能仅凭这些词声称创新：

| 相关基础 | 与本问题的关系 |
|---|---|
| [On-Line File Caching](https://www.cs.ucr.edu/~neal/Young98Online.pdf) | 固定文件取回代价下的历史信用/租金；原竞争性结论不能直接搬到动态工作流和共享前缀 |
| [Online Compression Caching](https://www.cs.utexas.edu/~plaxton/pubs/2008/swat.pdf) | 对象不同表示的容量/恢复代价与租金；其分析有专门的问题条件，不等同于共享 KV 的任意前缀收益 |
| [Precedence Constrained Knapsack](https://repositorio.uchile.cl/handle/2250/135687) | 选择物品需满足前驱约束；前缀容量分配具有这类依赖 |
| [Fast Multi-Stage Submodular Maximization](https://proceedings.mlr.press/v32/wei14.pdf) | Lazy greedy 利用次模收益的界；这里的并行 WCT 存在互补性，需另证安全上界 |

本次可以明确提出并检验的研究方向是：**把 Agent 工作流的故障恢复收益、共享物理前缀和容量选择放在同一模型中；跨轮使用可验证的收益界减少重算；对在线选择报告可行性与剩余最优性差距。** 这是候选贡献定位，不是已经确认的首创或可专利性结论。

当前已经有可执行定义和模型内正确性证据。尚不能把它称为完成实机验证、解决任意规模共享负载、保留旧累计扣租语义的最终部署版本。后续论文应先分别检验模型校准误差、有限预算决策损失、共享规模下的控制开销和复制过渡窗口，再确定最终可支持的算法声明。
