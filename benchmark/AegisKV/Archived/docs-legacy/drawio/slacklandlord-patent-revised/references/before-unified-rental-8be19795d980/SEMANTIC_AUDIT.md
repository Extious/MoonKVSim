# 两张 SlackLandlord 流程图的语义审计

审计对象是第 2 页新 chunk 准入、第 3 页 Cache hit 续租。用户本次手动源图已保存为 [06f9e9e4d5ea 基线](references/before-gain-credit-audit-06f9e9e4d5ea-algorithm-2-patent-revised.drawio)。第 1 页保持原样。

本次将“总收益评估”“Agent 授信分账”“剩余信用更新”拆为不同执行阶段，同时修正不变版本路径漏更新租值键等问题。下表区分具体修正与已有规则的核对，不将所有条目都声称为新发现的漏洞。

| 审计项 | 原问题或必须保持的边界 | 当前处理 |
|---|---|---|
| 收益与分账混合 | 原收益框先按 Agent ID 构造分账，再汇总得到准入收益，容易把记账约定当作收益定义 | 直接按每个工作流的两个 WCT 端点计算 G；固定顺序的 W 公式移到独立 Credit 分账框 |
| 符号角色混合 | W 同时被称为独立收益和授信依据，P 使用 Agent 下标，Credit 又容易被理解成当前 G | P_x=G_x/b_x；W 只表示授信额度；Credit 是各 Agent 剩余余额之和。仅新副本首次授信时 Credit=G |
| 共享工作流计益 | 不能因“分账分开”就把多个 Agent 的单独收益直接相加；共同瓶颈使这种求和失真 | 联合计算受影响工作流，每个工作流只计一次；单 Agent Slack 式保留为明确的特例 |
| 不变版本 Cache hit | 原路径在输入不变时结束；块暂停收租期间 L 可能已增长，重入 Q 后旧 H 失效 | “不变”分支直接到统一租值键更新框，使用当前 L；不重算收益、不新增信用 |
| 全 Q 的租值键 | 只刷新价值变化的尾块，仍会漏掉暂停后重入队列的未变块 | 检查全部 Q；按需重算额度，但全部 H 均以当前 L 和余额重建，然后才计算租金增量 |
| 续租与首次授信 | 必须防止给其他 Agent 退款、同轮重复补信，以及解除再引用被视为“首次” | 新轮只重置对应 Agent 的份额；已兑现份额只保留或下调；兑现时记录轮号，解除引用仍保留记录；旧轮不覆盖当前输入 |
| 删除损失与租金 | 已付完 Credit 不代表删除损失为零；静态旧损失不能用于连续试删 | 保留真实 WCT 条件损失公式；每删一块更新临时前缀，逐次累加 D_Y；不从租金或余额推导删除损失 |
| 前缀与副本状态 | “已准入”可能包含仍在复制的前缀；重复事件、旧 ACK、部分分片成功不应产生新信用 | 必要前缀须已提交；相同物理复制合并事件；仅本代次全部分片成功后分账，同代次只发布一次；失效走清理分支 |
| 计算与提交之间的变化 | 先核验后另行写入会留下竞争窗口；复制完成前算出的额度也可能过期 | 新块发布时按实际前缀重算额度；两页最终原子核验并写账本和 Q；输入变化重算，副本失效清理 |
| 失败前后语义 | 未执行的回收试算可以丢弃，但已完成物理释放不能回滚 | 图中分别保留“丢弃临时计划”和复制后的清理路径，不把已经释放的备份当作仍存在 |

## 反例检查

使用既有 CPU 参考模型的精确有理数运算，未实现新的运行时路径。数值是示意时间单位，不是硬件测量。结果见 [SEMANTIC_AUDIT.json](SEMANTIC_AUDIT.json)，脚本为 [audit_semantics.py](audit_semantics.py)。

1. **收益不依赖分账函数。** 禁止调用分账函数后，仍能直接求得共享块的总收益 4；同样两名 Agent 位于不同工作流时，总收益为 8。
2. **分开计算不等于独立相加。** 同一工作流的两条并行分支均从 6 降到 2：仅改善任一分支的收益为 0，共同改善的收益为 4。固定 A→B 分账为 0/4，反向为 4/0，二者总额相同。这验证了联合收益的必要性，也暴露了额度的顺序依赖。
3. **单 Agent 续租不会补回他人信用。** 当前 G=8，剩余 A/B 为 3/1；A 新轮续租后为 4/1，Credit=5。再次扣租后重放同轮事件，余额不增长。
4. **价值未变时旧 H 仍可能失效。** 块余额为 4，暂停前 L=2、H=6；暂停期间其他块使 L 升到 9。重入 Q 时旧 H 会产生 −3 的租金增量，正确重建为 H=13，剩余密度为 4；无需任何 WCT 计算。
5. **删除损失必须逐次计算。** 新块收益为 4，两次条件删除损失分别为 3、2，D_Y=5，实际净收益为 −1。用零余额替代损失会错误准入。

另运行 [DESIGN_CHECKS.json](DESIGN_CHECKS.json) 中 8 项已有核算检查，包括比例收租、共享计价、单 Agent 续租、同轮去重、待兑现轮合并、内部块余额保留、全部尾块检查及试算回滚；并核对两组恢复范围和 44 个单 Agent Slack 等价式条件。图结构检查验证了收益框不含分账公式、新块授信位于准入和复制确认之后、Cache hit 未变分支也经过 H 更新，以及本次新增的清理路径。

## 保留的设计选择与证据边界

- **固定 Agent ID 是可执行的分账约定，不是唯一或公平的贡献分配。** 本次按用户范围将其移到 Credit 阶段，未替换分账策略。它不改变本次真实 G，但可能影响日后的单 Agent 续租和回收选择。
- **Lazy Refresh 延迟的是受影响块的收益重算与续租兑现。** 新请求只更新 Agent 记录；内部块暂停收租；可释放尾块在访问或收租前按需结算。全部 Q 的廉价版本检查仍不可省略，也不声称总是 O(log n)。
- **免费容量允许零收益块，替换必须严格正净收益。** 保留用户指定的分段准入条件；它没有为未知后续收益预付信用，也不能保证满池时发现必须同时准入多个块才能获益的全局最优方案。
- **恢复模型沿用当前已生成 KV 与完整前缀。** 不加入未来长度；单 Agent 简式要求 Slack 与固定其他路径的 DAG 基线一致。成本模型校准、真实复制故障、并发容量收缩等仍需运行实现验证。
- **此次完成的是图中语义、控制路径、公式核算和导出审查。** 未修改专利或 Mooncake/MoonKVSim 运行代码。原子发布与分配代次是图中明确的实现要求，CPU 算术检查不构成并发协议验证或性能结论。
