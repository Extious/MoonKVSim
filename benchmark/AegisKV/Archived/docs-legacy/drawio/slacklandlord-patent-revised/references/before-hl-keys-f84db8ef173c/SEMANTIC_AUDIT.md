# SlackLandlord 流程简化与核对

2026-09-09。[当前流程 PDF](algorithm-2-rental-management.drawio.pdf) · [可编辑源](algorithm-2-patent-revised.drawio) · [阅读说明](README.md)

## 简化了什么

| 原流程 | 当前流程 | 保留的条件 |
|---|---|---|
| 输入、读取状态两个框 | 合成①读取事件与状态 | 每次等待或冲突后仍重新读取 |
| 操作进行中、请求去重两个判断 | 一个事件状态判断，三个明确出口 | 优先检查进行中操作，否则跳过重复/过期事件，其他事件继续 |
| 操作等待与前缀等待分别处理 | 共用等待框，条件满足后返回① | 各自的等待原因由入边标明，不提前授信 |
| 算收益后才检查能否建立前缀 | 将新副本就绪检查移到收益之前 | 已有备份的续租不受新副本条件限制 |
| 当前 Agent 信用更新、全块汇总两个框 | 合成③，先更新 a，再求和 | 其他 Agent 的租后余额保持原样 |
| 单独的 Q 更新框 | 初始化放入④；试删后更新 Q | 前缀、读取、其他操作保护与释放中块仍被排除 |
| 核验、重试、执行、结果判断分别展开 | ⑤核验并执行，三种结果直接出边 | 未执行冲突可丢弃；执行失败不能回滚实际释放；全部成功才发布 |

## 当前主线

**事件筛选 → 新副本就绪检查 → 当前 Agent 独立收益 → 该 Agent 续租并汇总 Credit → 已有副本保存 / 新副本容量竞争 → 核验、执行与发布。**

事件筛选三个结果互斥：先判断 x 是否有进行中的操作；没有时，再判断当前请求是否重复或过期；其余进入后续处理。共用等待框在对应条件变化后重读，不作忙等。

“需要新副本，且前缀或源未就绪？”为真才等待。因此，已有副本即使当前源不可读、或该块正在被其他恢复读取，仍可按有效新请求续租。

新块从空分账开始，只为实际触发本次事件的 Agent 授信。A 的新请求不重算 B，也不补回 B 已付租金。容量收租仍扣除每个块的全部 Agent 份额。

## 逻辑检查

- 19 个执行节点均可从入口到达；事件筛选和核验执行各有三个标注出口，其他判断各有两个。
- 不就绪的新副本在收益计算前等待；已有保护副本仍可立即续租。
- 只有新副本进入容量竞争；空闲容量允许零信用候选。
- Q 在循环前初始化，每次试删后更新；候选先归零或同时归零均被拒绝。
- 失败试算不修改实际信用或“本请求已处理”标记。
- 执行前冲突返回①；实际执行后失败按已发生的扣租/释放/分配处理。
- 发布成功保存租后余额，不能重新补满。
- 专利原文、算法三源文件哈希保持不变。

检查见 [DESIGN_CHECKS.json](DESIGN_CHECKS.json) 和 [SEMANTIC_AUDIT.json](SEMANTIC_AUDIT.json)。17 组事件与算术检查包含原有共享分账、重复事件、多尾块试删、失败隔离，以及新增的“就绪检查提前但不阻止已有副本续租”检查；2040 个单 Agent Slack 恒等式组合保留。
