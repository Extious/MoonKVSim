## 主流程

1. **请求复用或生成 x。** 记录有效请求的 Slack、请求号和引用关系。本轮生成过程中 Slack 不变。已有复制任务则合并事件，不重复分配。
2. **已有备份：立即刷新信用。** 用新 Slack 和当前已生成 KV 重算收益、分账并续租。内部块和读取中的块也可立即刷新，不等待成为尾块；物理副本仍只占一份空间。
3. **缺少备份：判断新块准入。** 必要前缀必须已提交，源完整可读。先计算新块的总恢复收益 G，再检查空间。
4. **空间不足：收租并试删尾块。** Q 只含可释放的物理尾块。按当前恢复前缀重算授信上限，只下调已有余额；然后按字节收租，试删归零块并累计真实删除损失。
5. **通过条件后复制并授信。** 无需淘汰时允许 G=0；需要淘汰时必须 G>D_Y。复制成功后按当前输入分账，原子保存余额与本轮处理记录并更新 Q。

只有新备份首次授信、或 Agent 的新请求实际复用该块，才能补充该 Agent 的信用。新请求仅出现但没有复用 y，不会在 y 的回收检查中自动续租。没有新请求的 Agent 无须结束事件：不再续租，已有信用随容量竞争消耗。没有容量压力时，保留备份不必主动删除。

## 收益、授信与剩余余额

| 量 | 含义 |
|---|---|
| G_x | 连续备份前缀增加 x 后的总 WCT 改善，单位为时间 |
| W_a,x | 从当前总收益分配给 Agent a 的授信额度，单位为时间 |
| c_a,x | Agent a 对块 x 的剩余信用，单位为时间 |
| Credit_x=Σ_a c_a,x | 物理块的剩余信用 |
| b_x | 物理字节数，共享块只计一份 |
| δ | 本次每字节收取的租金，单位为时间/字节 |
| D_Y | 回收计划造成的真实 WCT 删除损失，单位为时间 |

收益直接按每个受影响工作流的两个恢复状态计算：

\[
G_x=\sum_{w\gets x}[\mathrm{WCT}_w(\mathbf T)-\mathrm{WCT}_w(\mathbf T^x)].
\]

同一工作流只计算一次；不能将多个 Agent 单独计算的 Slack 收益直接相加。只有同一工作流中一个恢复节点变化、其他路径固定且 Slack 来自一致基线时，图中的单 Agent 简式才等价。

分账单独进行：按固定 Agent ID 顺序逐个切换到“使用 x”的恢复状态，以相邻两次 WCT 差作为 W_a,x，各份额和等于 G_x。该顺序是一种确定性记账约定，额度分配和之后的单 Agent 续租可能受顺序影响，不宣称唯一公平。Agent 重复出现的恢复节点一起切换，不重复授信。

### 内部块为什么也能算收益

对任意 x，比较“备份前缀到 x 之前”与“备份前缀到 x”为止的恢复时间。只包含已生成的 KV，不引入未知未来长度；备份前缀之后已生成的内容计入重算。

当 x 是内部块，这两个估值状态都暂不使用 x 后面的备份。这样计算的是 x 作为前缀末端的增量收益，不是在仍保留后继的情况下挖掉内部块。物理备份布局不改变。等 x 真正成为可释放尾块时，该估值与其实际保留/删除收益一致。

没有 Agent 结束信号时，系统只能根据最近登记的请求信息估计恢复价值。历史引用不表示对应请求仍在运行，也不能保证 Agent 以后一定再来；本算法不为未知未来工作预付信用。这是信息条件的边界，不能用虚构的结束事件掩盖。

## 复用如何刷新 Credit

先用本次实际请求的 Slack 更新恢复收益与 W，再处理余额：

\[
c_{a,x}\leftarrow
\begin{cases}
W_{a,x},&\text{新备份，或 a 实际复用且该请求尚未授信};\\
\min(c_{a,x},W_{a,x}),&\text{其他已有份额}.
\end{cases}
\]

新备份初始化全部当前份额；之后只有本次实际复用的 Agent 可以在新请求中续租。其他 Agent 已花掉的信用不补回；收益下降时允许下调其上限。初次授信也记录本轮已处理，因此同一请求中的首次复制、重复命中和重试不能各获得一次额度。旧请求不能覆盖更新的 Slack 或处理记录。

记录以“物理分配代次、Agent、请求号”为范围；记录与余额一起提交。常规尾块检查只执行 min 下调，不能因为看见新轮号就补信用，也不能提前把一次并未发生的复用标为已处理。

## 收租与淘汰

不再单独保存 H 和 L。直接使用剩余信用密度计算最小收租步长：

\[
\delta=\min_{y\in Q}\frac{\mathrm{Credit}_y}{b_y},\qquad
c_{a,y}\leftarrow c_{a,y}\left(1-\frac{b_y\delta}{\mathrm{Credit}_y}\right).
\]

每个物理块支付 b_y δ，一块的多个 Agent 按剩余余额比例分摊。零余额时跳过除法；至少一个候选尾块归零。选一个归零块试删，同值使用稳定的物理块 ID 顺序。内部前缀不参与此次收租，保留余额；新暴露尾块下一轮重新评估上限并参与竞争。因此高信用尾块被淘汰，不会使整条前缀同时到期。

每次试删都从当前临时前缀计算真实 WCT 损失，加入 D_Y，再更新前缀与 Q。Credit=0 不意味着删除损失为零。准入条件为：

\[
Y=\varnothing:\ G_x\ge0;\qquad
Y\ne\varnothing:\ G_x>D_Y.
\]

试算将 x 看作已备份，必要前缀受保护；G 在加入 x 前后计算，D_Y 在加入 x 后逐次删除时计算。在同一输入模型下，G−D_Y 正好是最终替换的净收益。失败试算不扣真实信用，也不删除真实备份。

## 必要的执行约束

同一 Pool 的计划、信用更新和发布串行提交；计算所用请求输入、恢复代价和容量状态需一致，冲突则重新计算。缓存命中读取期间固定对应物理分配，保护其所需前缀；更新信用不解除读取保护。Q 排除全部共享后继依赖、读取保护、释放中分配和本次候选前缀。

执行回收计划时，释放 ACK 到来后才减少占用；原子检查容量后开始新复制。复制中、释放中的分配仍计入容量。复制结果核验分配代次和所有必要分片，成功后以当前前缀重算额度，再原子写入信用与发布状态。失败或旧 ACK 不能生成信用；已释放的旧备份不能回滚成仍然存在。简图把这些条件合并在“核验并执行计划”及最终提交框中。

算法 3 缩小可用容量的强制回收属于独立容量控制入口，可复用尾块收租与删除逻辑，不受新块正净收益门槛阻止；读取保护可能使回收等待。该控制入口未增加到本次请求事件图中。
