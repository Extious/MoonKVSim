## 1. 图要回答什么

算法 3 需要支持三项可检验的判断：故障风险是否改变合适的 checkpoint 间隔；间隔改变后，更多 Peer 层是否仍值得保存；正常推理的内存需求升高时，Peer 占用是否应减少。

现有 Figure 5 固定为 MiniCPM4-8B、32K 历史、64-token 尾部和一组带宽/热集画像，比较四种恢复流水线。它解释“为什么 Peer 可能减少暴露等待”，但没有扫描 Z、L 或前台压力，也没有评价窗口控制。仅将四条时间线画得更漂亮，不能补足这些证据。

建议将正文 Figure 5 改为跨双栏三联机制图，分别对应算法 3 的三个控制依据；原四行时间线保留为补充说明。另在 Evaluation 用闭环对照验证自适应是否优于固定配置，避免用算法自己的输出证明算法有效。

### (a) 风险与 Z：从完整配对运行得到代价

对每个 Z，使用同一组 workflow 做无备份无故障运行、开启备份的 F0 运行，以及故障条件下的 F1 运行。先计算每个 workflow 的正常备份代价，再计算该 workflow 的 F1−F0 恢复惩罚；随后按预先指定的故障场景概率组合，最后跨 workflow 汇总。

所有项保持同一个 workflow 集合、同一个风险暴露区间和相同的时间单位。直接测量 workflow 完成时间，不将多个请求超出 Slack 的延迟相加当成 WCT。算法 3 的请求评分只是控制代理，图中的 WCT 是独立评价。

风险场景应定义为固定暴露区间内的一次源故障概率及故障时刻分布，避免把“每小时故障数”直接乘到“每请求延迟”上。若概率来自人为配置，图注称为风险场景，不称为生产故障率测量；若采用 Poisson 多故障过程，则单列完整多故障运行，不能沿用单故障混合近似。

曲线属于“配对实测代价 + 声明的风险模型”，与实际长期运行在多种故障率下的结果区分。最低点标为该扫描集合中的最佳点，不标为全局最优。若正常风险范围内最佳 Z 不变，保留这一结果，不通过挑选极端故障率强行制造移动的最低点。

在正式 F0/F1 workflow 运行尚未完成时，单请求 checkpoint/replay 微基准只能作为校准素材，不能填入 WCT 纵轴。

### (b) Z 与 L：不把 N=Z 当作故障状态

主图比较不同 checkpoint 间隔下的层数收益，而不是只比较几个给定尾长。每种 Z 都运行真实的异步 checkpoint 流，在其周期内按墙钟时间分层采样故障状态，记录生成前沿、决策前沿、有效提交前沿和实际 N。采样包含刚提交后的短尾、提交前的长尾、以及在途备份造成的超 Z 尾部。

先做固定状态的恢复微基准：冻结同一历史、已知尾部、热块集合和必要选择器状态，改变 L，与 L=0 逐点配对。这隔离初始驻留的作用。随后再测真实 checkpoint 运行中各 Z/L 配置的状态分布和恢复结果，检验复制竞争是否改变提交滞后。不能直接把一个配置的 N 分布套给所有 L。

主图用平均等待减少量解释边际收益；同时保留绝对恢复延迟、P95 恢复延迟、各 L 的实际驻留字节和实际 N 分布。只看“消除了多少等待”可能掩盖大 Z 的重算更慢。

所有曲线使用同一个逐层恢复调度：前 L 层初始热集驻留不改变计算批大小；缺失块的 H2D 与此前层的计算按真实就绪条件重叠，不人为增加整批屏障。同 Z 的基线与被比较配置使用相同输入和故障状态。单请求微基准为每个候选提供足够容量，以便隔离 L；容量不足、覆盖不完整及已有引用占用另由容量实验和闭环实验评价。

h 按所选稀疏方法固定，物理热块数按密封块计数取整，并包含强制块；不能为了得到预期曲线随 Z 调整 h。N 变化时重新记录真实的选择需求和未命中，不沿用 64-token 画像中的需求并集比例。建议保留 40% 热集与当前 Figure 5 使用的约 65.8% 画像作为分别冻结的敏感性配置，主配置在正式采样前依据方法确定。

预期“较小 Z 的有效层数范围更大”只是一项假设。在高有效带宽、较小热集或较慢重放计算下，各 Z 都可能在一两层内饱和，这种情况应保留。

### (c) Peer 容量：测前台影响，不重画预算公式

单独画“前台需求增加，计算出的 B 减少”，只能复述算法，不能证明减少 B 对推理有价值。这个面板必须改变真实 Peer 占用，并测量同一前台负载的响应。

预算初始候选为管理 KV 池的 0%、12.5%、25%、37.5%、50%；横轴最终使用实际达成的驻留量，未填满的预算不能当作已占用容量。每个预算点从相同初态独立运行，避免前一个配置留下的 pinned 副本污染下一个点。

先用静态驻留副本、关闭新增复制测量容量竞争；再在相同 Z/L 下开启 checkpoint 复制，报告完整运行中的内存与带宽干扰。前台压力档在校准集上按 KV 水位和内存准入等待定义，不按最终曲线是否出现性能恶化选择。各档内配对输入、到达序列、推理设置和设备，另外记录吞吐、KV 水位、准入等待、GPU 利用率及复制流量。

若高压状态中请求因可用 KV 空间不足而排队，要报告未完成、超时或 OOM，不能只画已完成请求的较低 P95；低压状态下曲线平坦也是有效结果。若没有既定延迟 SLO，就不在图中人为画一个“安全阈值”。

## 3. 闭环验证放在 Evaluation

Figure 5 解释控制依据；闭环实验检验这些选择组合后是否有效。至少包含四种变化：风险单独上升/下降，前台内存需求单独上升/下降，两者同时升高，以及预算下降时所有 Peer 副本仍被引用。

对照配置为：

- 完整算法 3。
- 固定 Z、L、B：参数只在独立校准负载上选择，然后冻结。
- 仅调整 Z：L、B 固定。
- 调整 Z 和 L：B 固定。
- 仅调整 B：Z、L 固定。

控制过程图的横轴使用时间窗口编号。风险变化实验分别显示风险输入/估计、Z 和 L；容量变化实验在同一 GiB 纵轴上显示前台 KV 需求、Peer 目标预算、实际 Peer 占用及仍被引用的字节。不要将不同量纲强塞到一条纵轴，也不要把目标下降画成瞬间物理释放。

效果用同 workflow 配对的 WCT、前台 P95、吞吐、复制字节、Peer 拒绝率和回收滞后评价。请求结束、tool 返回、热块更新和 L/B 下调都应记录引用变化。长期风险实验使用相同外生故障过程和负载种子；记录因调度变化产生的真实受害请求。固定请求身份及逻辑进度的故障注入继续用于阶段比较，不能与长期随机故障协议混为一项结果。

若需要离线逐状态最佳配置作为参考，明确标为离线参照，不归入在线算法，也不使用它选择正式测试条件。

A100 数据中，32K 历史下 N=1/64/512 的整模型缓存前向中位数分别为 69.91/91.83/124.27 ms。它们来自一次作业内每个形状的五次重复，不是五个独立 workflow，也不是三种 checkpoint 策略。除以 32 得到的量只是同质层模型使用的平均成本，不是逐层实测时序。

另一次 RTX 4090 预检发现缓存尾部与从空缓存处理整段输入的输出不同，原因尚未定位。正式恢复实验先区分稀疏 prefill/decode 的合法语义差异和状态恢复问题；不能仅因 KV 长度正确就宣称恢复正确，也不应把不同 chunk 规则下的输出差异直接归为缓存损坏。

## 5. 实测顺序与首轮范围

### P0：恢复契约与传输路径

先在同一模型、精度、native kernel 和相同 chunk 规则下，核对相同历史与已知尾部的 HBM、DRAM、部分 Peer 三条路径。验证 KV、选择器/辅助状态、已知 token 重放及后续一步 decode；说明浮点容差和随机采样控制。定位上面的诊断差异后再计时。

记录真正的数据路径和有效带宽：GPU→Peer GPU、GPU→故障后仍存活的 DRAM，以及该 DRAM→接管 GPU。微基准可在准备好的接管设备上比较起始驻留；涉及故障前复制、前台干扰和引用生命周期时，需要两个实际 DP，且接管 DP 同时承担普通推理。原型故障作用于指定 worker/进程，不将存活同机 DRAM 的实验泛化为整机故障容忍。

### P1：先做最关键的 Z/L 微基准

| 项目 | 首轮拟定范围 |
|---|---|
| 模型和设备 | MiniCPM4-8B，固定原生 revision，A100 80GB PCIe；相同组内不混入 4090 计时 |
| 历史 | 主实验 32K；64K 作为独立敏感性 |
| checkpoint 间隔 | Z=64、256、1024 tokens；均为 64-token 块的整数倍 |
| 层数 | L=0、1、2、4、8、16、32；只在校准阶段决定是否加密转折区 |
| 输入 | 至少五份预先固定的文本/Agent 历史；每份记录 token 哈希 |
| 故障状态 | checkpoint 周期内按墙钟时间分层采样，保留提交刚完成和在途复制状态 |
| 技术重复 | 每个固定状态/路径各自预热后，交错顺序重复三次；不将重复计时当独立输入 |
| 输出 | 等待、重放、绝对恢复时延、真实 N、Peer/DRAM 字节、必要状态就绪时间 |

三种 Z、七种 L 共 21 个主配置，输入数、阶段样本数和技术重复数分别报告。采样量根据首轮稳定性预检确定后冻结；不根据最终收益大小扩缩样本。若 1024-token 路径不受支持，记录原因，不通过线性外推补成实测点。

### P2：补 checkpoint 开销与容量竞争

对 P1 的 Z 测无故障复制开销及实际提交滞后；对两种预先校准的前台压力、五个预算档测容量曲线。分开记录物理驻留、申请预算、在途预留和可淘汰量。此阶段得到 Figure 5(c) 及 (a) 的正常开销素材。

### P3：配对 workflow 与完整控制器

控制器接入真实复制、提交和引用逻辑后，运行对应 F0/F1 及固定配置消融。完成这一阶段后才能绘制 Figure 5(a) 的 WCT 曲线和闭环效果图。先用受控少量请求检查行为，再运行完整 workload；短微基准不能替代 workflow 结果。

## 6. 统一记录与作图口径

每次运行记录模型/内核/脚本版本、设备与拓扑、输入和 workload 标识、种子、Z/L、目标与实际容量、请求源/接管目标、故障和提交时间戳、生成/密封/决策/提交前沿、逐层读写与计算事件、引用变化、正确性和失败原因。

固定状态微基准以输入为外层单位：先汇总同输入的技术重复，再按声明的阶段权重汇总；阶段样本与层不能冒充独立 workload。完整服务实验以完整运行和 workflow 配对，重采样区间按运行/输入层次处理。图注说明独立单位、次数、区间含义，以及是否为实测代价的风险模型组合。

Figure 5 暂定通栏三个面板，字体沿用正文 Linux Libertine，按最终插入宽度检查，不通过缩小字号塞入配置。相同 Z 跨图保持同色，L 为整数点，零 Peer 基线保留。图注写明路径、尾部采样和计时边界，完整矩阵放方法说明。

预先保留以下反例：较大 Z 可能减少 Peer 可消除的等待，但增大总恢复时间；高带宽下不同 L 几乎无差别；小热集下很少层即饱和；低前台压力下不同 B 几乎无差别；引用释放滞后导致目标预算暂时无法实现；完整自适应的迁移开销可能抵消收益。

当前交付是可供确定测量范围的设计稿。确认图的比较关系和首轮范围后，再安排对应实测；本稿不意味着测量作业或新控制器已经完成。
