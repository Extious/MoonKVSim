本图中的成本定义为**初始 Peer HBM 中的历史 KV 容量**，另一个目标是**累计加载等待**，两者都越小越好。每批层数与初始驻留前层数相同；在固定 32K 历史下，每层主 KV 为 128 MiB。保留下方层数轴，并在上方增加容量轴，使成本增长能直接读出。

如果存在另一个配置，初始占用和累计等待都不更差，且至少一项严格更好，当前配置就被支配。蓝色实心圆表示帕累托点，灰色叉号表示被支配点；浅灰线保留原始扫描顺序，仅连接离散候选，不表示中间批大小可选或已测量。

本例的帕累托配置为 **1、2、3、4、5、7、8、10、13、19、20 层**，共 11 个；剩余 25 个被支配。不能仅凭曲线形状或之前代表点的高亮来选择它们，也不能将 20 层称为唯一最优配置。

| 比较 | 初始容量 | 累计等待 | 结论 |
|---|---:|---:|---|
| 5 层 | 640 MiB | 18.6818494464 ms | 支配六层配置 |
| 6 层 | 768 MiB | 18.6818494464 ms | 同等等待，多占 128 MiB |
| 8 层 | 1024 MiB | 14.94547955712 ms | 支配九层和十二层配置 |
| 9 层 | 1152 MiB | 16.81366450176 ms | 占用更大，等待也更长 |
| 12 层 | 1536 MiB | 14.94547955712 ms | 与八层同等等待，占用更大 |
| 19 层 | 2432 MiB | 1.09441974272 ms | 较低占用与少量等待的取舍点 |
| 20 层 | 2560 MiB | 0 ms | 零等待配置中占用最小 |
| 21–36 层 | 2688–4608 MiB | 0 ms | 均被二十层配置支配 |

选择哪一个蓝点还需要容量预算、允许等待、成本权重或其他业务约束。本图没有任意归一化两个目标或自动挑选所谓“拐点”。固定请求下所有配置的重放计算量相同，因此以累计等待或以“计算加等待的执行时间”为性能目标，帕累托集合一致。

成本仅计初始 HBM 容量，不代表生命周期内 HBM 占用积分、故障前复制流量、备份维护、货币成本或对前台请求的干扰。如果增加这些目标，必须取得相应成本数据后重新判定；本图的前沿仅适用于扫描的 36 个配置和当前两个目标。

证据仍为 Qwen3-8B 结构下的解析估算：历史 32768 token、重放 512 token、假设有效带宽 25 GB/s、有效算力 100 TFLOP/s。沿用仅预取下一批、整批历史 KV 就绪后切换、末批保留实际层数的规则。已加载历史保留，初始驻留量不是整个执行期间 HBM 容量的上限；不计故障检测和接管排队，没有 GPU 实验或性能校准。

复现命令：

```bash
python3 output/pdf/batched-layer-pareto-20260914/build_pareto.py
```

脚本使用精确分数时间和整数容量做完整两两支配判断，再用按容量递增的历史最小等待扫描独立核对。36 个输入点逐一匹配上一版 `batch-size-sweep.csv`；额外核对五层与六层、八层与十二层的精确相等等待，以及所有超过二十层的零等待点被二十层支配。没有使用图中四舍五入的数值决定分类。
