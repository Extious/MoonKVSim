# 原生稀疏恢复：固定配置与机制图的采集规格

这是待执行的实验规格，不是真实稀疏轨迹或性能结果。当前没有下载权重、运行模型或验证恢复输出。先完成下面的执行路径检查，才能将该配置冻结为实验配置。

## 模型与固定状态

候选采用作者发布的 [NOSA-1B](https://huggingface.co/openbmb/NOSA-1B)，固定修订 `7bdc33fbc1bc80b76b29689ba35ff6a7991b7dee`。[作者仓库](https://github.com/thunlp/NOSA)和[论文](https://arxiv.org/html/2510.13602v2)提供方法依据。配置和源码已读取；运行行为尚未验证。

| 项目 | 配置草案 |
|---|---|
| 模型几何 | 28 层，16 个 Q 头，2 个 KV 头，head dimension 128，BF16 |
| 请求状态 | 同一个固定输入的 token IDs；16384 个有效历史 token，512 个需要前向的后缀 token |
| 原生策略 | 保持模型的选择器、权重和窗口不变；源码中的 block size 64、window size 1024、topk 64、compressed kernel 32 / stride 16 |
| 细粒度统计单元 | `(layer, KV group, 64-token block)`，主 K/V 有效载荷 32 KiB |
| 历史主 KV | 每层每组 256 块；全模型 448 MiB |
| HBM 初始主 KV 预算 | 每层每组 32 块，全模型 56 MiB；另计且统一放置必需的辅助状态 |
| 备份覆盖 | 相同有效历史、相同提交进度；全部主 KV 在 Peer HBM 或 DRAM 中有有效备份 |
| 接管路径 | 固定接管 DP；权重就绪；Peer HBM 就在该 DP 上 |

`topk` 是源代码参数，不能直接等同于所有 query、窗口和分支去重后读取的历史块总数。初始块、本地窗口、压缩表示、选择器/CIS 等辅助数据，以及新生成的因果可见 KV 都必须单独追踪。56 MiB 不是完整 HBM 开销。若真实分配器将两个 KV 组绑定在同一页面，需改用实际可独立放置的页面单位，重新核算预算。

待完成的路径检查：

1. 确认执行的是稀疏 prefill。论文区分 dense-prefill 的 NOSA-F 和 sparse-prefill 的 NOSA-S，不能只凭模型名称断言。
2. 确认 16K+512 输入的实际上下文支持；配置的 LongRoPE 字段不能替代一次正确执行验证。
3. 实现并检查历史 KV、压缩状态和选择器状态的恢复。保存配置 `use_cache=false`，不能假设即插即用。
4. 检查已有缓存时 512-token 后缀的执行路径；源码包含按末 token 更新的增量分支，不能直接假设它支持任意 cached multi-token prefill。
5. 对相同 token 输入，验证恢复后的输出与该原生稀疏模型不中断执行一致，允许明确定义的浮点误差；精确恢复的参考不是 dense 模型。

## 对照放置与调度

固定相同主 KV 和辅助状态字节预算，对照随机、故障前访问计数、故障前最近访问，以及离线已知恢复轨迹的参考放置。在线方案只能使用故障前已获得且在故障后可用的信息。离线方案必须标成参考上限，不得作为在线选择器输入。第一轮的历史访问频率不等于未来多轮 Agent 请求的稳定热点，需按实际同一请求的恢复窗口检验。

各放置使用相同的合理预取、传输合并和驻留保留规则。已装入后未被逐出的 KV 再次命中，不能再次记作节省一笔 H2D。不能只允许选择 HBM 内的块。DRAM Pool 若还需要网络读取，应记录网络与 H2D 的独立依赖和耗时。

## 论文图：三个相互对齐的面板

**(a) 实际选择与初始放置。** 预先固定层 1、14、28，并固定 KV 组，避免只挑最有利层。每张矩阵横轴是 256 个历史块，纵轴是 512 个恢复 query；标出实际被选中的块，矩阵上方标出初始 HBM 成员。新后缀 KV 和辅助状态不混入历史块矩阵，但计入总事件和内存。没有真实模型选块日志时不绘制伪热点。

**(b) 所需时刻与到达时刻。** 对同一个真实恢复窗口，将选中块的首次消费需求、实际可用时间和拷贝区间画在共同时间轴上。首次需求时刻使用消费者上游依赖已就绪的时刻，不能把等待结束后的 attention 启动误记成无等待的需求时刻。多个缺块可共享一个等待区间；逐块迟到量不能直接求和当作关键路径时间。

**(c) 等容量恢复时间线。** 对两种放置分别绘制 selector/辅助状态、H2D、attention、FFN 的实际事件；突出计算流因依赖未就绪而空闲的区间。标注初始 HBM payload / 辅助状态 / 恢复新增装入 / 峰值驻留字节，以及被选历史 KV 的逻辑复用量。局部放大采用相同 query 窗口，同时保留全恢复窗口的统计，不能用一个有利 head 替代全模型结论。

建议日志字段包括：request ID、token IDs hash、恢复进度、layer、KV group、block ID、query 范围、初始驻留位置、payload bytes、辅助状态类型、选择器完成时间、复制排队/开始/完成、消费者依赖就绪/实际启动/完成、重计算范围、逐出与重新加载。主 KV 读取包含在 attention 内，复用 token/bytes 不另造一段可加总的“reuse time”。

## 如何作出方法决策

- 优化的 DRAM 恢复仍有可观且可定位的等待，并且等容量放置能改变这些等待：支持研究请求内恢复优先级。
- 某些块选择频率高，但总能提前加载或加载一次后一直保留：只支持访问集中性，尚不支持高 HBM 备份价值。
- 离线参考有收益，故障前规则选不中：说明有潜在机会，但在线优先级算法尚未成立。
- 前几层固定驻留已达到参考效果：优先采用简单层规则；复杂选块/租金机制需要另有跨请求、预算或动态状态的证据。
- 优化预取已隐藏全部加载，或不同放置没有稳定差别：保留该负结果，不将其写成普遍的请求内优先级优势。

机制图用于建立等待来源和因果关系。算法有效性还需在预先固定的一组请求、逻辑故障进度、同容量放置和相同调度器上检验在线选择效果，再连接 Slack/WCT；这不由单个有利解析例子证明。
