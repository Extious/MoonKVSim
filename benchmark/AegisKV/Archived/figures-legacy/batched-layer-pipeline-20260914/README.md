# 六层一批的流水加载：解析重算

2026-09-14。根据用户“这张图应该改为分批流水加载的结果”的要求，生成原驻留深度图的分批版本。当前采用的明确假设是：**初始前六层已驻留，每批六层，整批 KV 到齐后切换，计算当前批时仅预取下一批**。这是确定性解析时间线，不是 GPU 实测或经过硬件校准的模拟结果。

## 这张图回答什么

固定前六层驻留后，改变可复用历史长度、丢失并重放的 token 数、有效 H2D 带宽，观察六层一批的流水是否仍然暴露加载等待。原图的最少驻留层数是另一种调度模型下的指标；新版热力图改为**整个 36 层执行期间五次批间切换的累计加载等待，单位 ms**，不宣称六层是最优驻留深度。

- 面板 a：32K 历史下，每批六层的整层前向计算耗时与下一批六层的历史 KV 加载耗时。复制只搬运可复用历史，重放产生的新 KV 在计算中生成。
- 面板 b–d：相同的 20 个历史长度与重放长度组合，分别使用 12.5、25、50 GB/s 的假设有效带宽。三个面板共用 0–300 ms 的色标，格内保留一位小数；标为 0 的格子在精确计算中确实为零。
- 橙框：32K 历史、512 个重放 token、25 GB/s。六层计算 28.47588483072 ms，六层加载 32.21225472 ms；每次切换暴露 3.73636988928 ms，五次累计 18.6818494464 ms。计算合计 170.85530898432 ms，图中执行区间合计 189.53715843072 ms。

## 调度语义与适用边界

1. Peer 固定为接管 DP；计时起点前，其 HBM 已具备第 1–6 层的全部可复用历史 KV。
2. 开始计算第 1–6 层时，提交第 7–12 层加载；开始计算第 7–12 层时，提交第 13–18 层加载，依次进行。
3. 一个计算批必须等自身全部历史 KV 就绪。批内六层依次计算；这里的计算包括整层前向，不能解释为仅 attention kernel。
4. 每批计算开始时仅提交下一批，不提前提交再下一批。当前批计算提前结束，就等待下一批剩余加载完成；加载提前结束，则等待计算推进到批间切换后再提交后续批次。
5. 一条串行 H2D 流与一条串行计算流可以重叠；不计启动延迟、共享带宽争用、核函数相互干扰和其他请求。有效算力固定假设为 100 TFLOP/s，所有层使用相同的结构化耗时模型。
6. 已加载 KV 不逐出，并假定 HBM 容量充足。仅预取下一批是调度约束，不是总共只允许驻留十二层。32K 示例初始历史 KV 为 768 MiB，后续加载 3840 MiB，最终历史 KV 4608 MiB；重放 512 token 另产生 72 MiB 主 KV。不计权重、激活及辅助状态。
7. 图中时间不含故障检测、模型加载、接管排队。流水重叠本身也适用于正常推理，不能单独作为故障恢复专有创新的证据。

## 为什么没有沿用旧图的数字

旧源 `output/pdf/kv-motivation-20260913/build_motivation.py` 采用从计时起点连续预取、每层历史 KV 就绪即可消费的调度。它已经允许持续流水，并不要求在前六层计算期间传完所有后续层。

本次变化是增加明确的“整批就绪后切换”和“只预取下一批”规则，且把观察指标改为固定六层初始驻留的累计等待。因此旧模型在上述示例中等待为 0，而当前整批切换模型等待为 18.68 ms；这不是仅更改图中文字，也不是声称旧模型算错。若采用批内逐层就绪即可计算，必须使用相应事件调度重算，不能直接引用本图。

等待随重放长度增长而下降，仅表示计算给下一批加载提供了更多时间，不表示丢失更多 token 能改善总恢复时间。每批装载与计算的相对速度、批内就绪规则、提前预取范围需要在比较中保持明确。
