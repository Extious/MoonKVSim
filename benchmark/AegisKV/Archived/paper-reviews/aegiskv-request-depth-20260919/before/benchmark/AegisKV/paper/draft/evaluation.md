## 5 Evaluation

本节保留实验设计，尚不报告新版端到端结果。旧图 9 的串行队列示例及旧图 10–14 的示意模型输出已撤出正文；原文件保留用于历史追溯，不能作为并行 retry 设计的结果。评估围绕正常开销、故障位置、恢复来源与时间分解、两级保护消融及敏感性展开。

### 5.1 方法

**平台与参数。** 目标配置为 MiniCPM4-8B BF16、DP=8、1 TB DRAM 池、每个 Retry DP 的 Peer HBM 上限为其可管理 KV 内存池的 50%，实际预算按 §3.6 取该上限与扣除前台水位、预留空间后的可借用余量的较小值，默认单卡故障与 8 个受影响请求。链路总可用带宽分别设为 25 GB/s 与 6.25 GB/s；多个 H2D 任务共享这一总量，不能给每个并发请求各计一次完整带宽。所有策略使用相同的 retry 并发度、计算调度器、前台负载与传输共享规则，允许请求间传输交错及计算/复制重叠。部署代价按实际 GPU 和并发负载校准，A100 上的图 2、图 7 参数只用于当前动机与解析图。

**工作负载。** 主实验使用 CC/Weka 导出的 124 个 workflow，保留请求依赖、上下文与逻辑进度；缺失字段与重建假设需显式报告。合成的 160 个七节点 workflow 仅用于可控机制扫描，不冒充真实 trace 运行。故障在指定请求的 80% 逻辑进度注入，源 GPU 不可用 120 s；对照间固定故障身份、逻辑进度、备份前的请求到 GPU 映射和预期受害集合，并在运行日志中核对实际受害请求，不能只对齐墙钟时间。

**基线。** Recompute 不备份；DRAM-only 备份全部密封 KV；Peer-uniform 在完整 DRAM 副本之上平均分配 Peer 配额、按 token 位置选择块；AegisKV 使用 §3 的两级保护。除明确的放置/请求内顺序差异外，所有基线均可并行恢复，不能用串行基线制造收益。补充一项层序装载的 DRAM-only 强基线，以分离层流水线与 Peer 放置的贡献。

**协议与指标。** 每个策略的无故障 F0 与故障 F1 按 workflow ID 配对，WCT 惩罚为 $\mathrm{WCT}(F1)-\mathrm{WCT}(F0)$；备份的正常开销相对相同负载的无备份运行。至少五次完整配对重复，报告 workflow 数、每策略运行数及重复单位；不能将同一批 workflow 的多次注入视为独立 workflow。一个 workflow 多请求同时受影响时直接测量 DAG 完成时间，不把请求迟到相加当作 WCT。

### 5.2 无故障开销

画每个 workflow 的配对 WCT 增量 ECDF，保留负值与长尾，报告均值、P95 及吞吐；另报 DRAM/Peer 复制字节和 Tier R/D/P 比例。检验 Slack 是否减少无效复制，以及计数、备份和 Peer 写入是否干扰前台，而不预设“近零开销”。

### 5.3 故障位置与 WCT 惩罚

在同一 workflow 的关键路径与不同 Slack 分支分别注入，画各位置的 WCT 惩罚中位数与四分位距，同时标注故障时估计 Slack 和离线实际 Slack。所有位置沿用相同恢复并发配置；低 Slack 请求是否获得更多有效保护、较大 Slack 是否吸收恢复延迟，由实际配对运行验证。

### 5.4 恢复的 KV 来源与时间分解

来源图将历史 KV 划分为 Peer 已驻留、DRAM 恢复前装载、DRAM 后台补齐和重算，按同一 token/层口径去重核算。时间图记录检测、准入、H2D、补取、重放与首次恢复 decode 的事件；用时间线展示重叠，或只堆叠关键路径上互斥的时间区间。不能把全部 H2D 服务时间与计算时间直接相加，也不能将其他请求的总传输量当作本请求等待。另报不受故障直接影响的前台请求变慢。

### 5.5 消融

保留相同并行调度器，每次只移除一项保护机制：

- **无 Slack 优先级：** 所有请求保留 DRAM 副本，Peer 配额平均分配，保留请求内层序与热度。
- **无稀疏热度优先级：** 保留 Slack 与层序，块按最近位置选择，恢复仍使用原模型的真实选择器与补取；不能通过改成稠密注意力替代这一消融。
- **无层序优先级：** 保留 Slack 与热度，改为 token 段优先，以分离层就绪顺序的作用。
- **无 Peer 层：** 保留 Slack 分层与在线装载器，只使用 DRAM/重算。
- **固定窗口参数：** 分别固定 checkpoint 间隔、统一层数或 Peer 预算，其余控制与引用回收规则不变，区分风险适应、层数选择和容量适应的作用。

分别在两种带宽下报告 WCT 惩罚、Peer 驻留量与复制流量。预算充足或带宽很高时，差异可能很小；不要求每项机制在所有条件下均显著获益。

### 5.6 敏感性

另需验证 时间窗口的故障风险控制：记录风险估计、$Z$、共同 $L$、各目标预算、实际提交尾长、前台 KV 水位、候选热块数、Peer 准入/拒绝、引用数及复制/释放时延。检查窗口内参数固定、发布 $Z$ 不重置生成进度、引用归零前不驱逐、预算下调不提前计入空闲空间，以及增长失败后的 DRAM 回退。扫描风险估计误差、风险上下阈值、checkpoint 档位、层数切换余量和复制积压，特别测试风险与前台压力同时升高、所有 Peer 副本均有引用、热集持续增长和长 tool 等待。控制效果另用较长故障序列评估，固定各策略的故障域、工作负载和随机种子；§5.1 的 80% 进度注入只用于配对恢复比较，不能作为故障率估计或动态风险控制的验证。扫描 Peer 预算 0–16 GiB、总 H2D 带宽 6.25–50 GB/s、同时 retry 数 1/2/4/8 及低 Slack 请求比例，保留共享总带宽约束。报告实际重叠率、前台开销、请求与 Workflow 延迟，不把算法 3 的请求得分当作 WCT 实测。跨模型分别校准 KV 大小、尾部重放及选块轨迹。
