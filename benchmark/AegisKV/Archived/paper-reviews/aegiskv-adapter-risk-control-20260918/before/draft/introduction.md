## 1 Introduction

LLM 正在从单次问答走向多智能体工作流：规划、检索、写代码、评审等角色各自发出 LLM 请求，请求之间有数据依赖，形成一个 DAG。用户等待的是 DAG 的汇合点，因此服务系统的目标从单请求时延变成 WCT。与此同时，agent 的上下文持续变长：每一轮调用都把工具输出、历史对话和检索结果追加到 prompt 中，单请求上下文达到 32K–128K tokens 已属常见；为了承受这样的上下文，原生稀疏注意力（native sparse attention）模型——MiniCPM4 的 InfLLM-v2、NOSA、NSA、DeepSeek 的 DSA 等——正在成为长上下文推理的主流：每个 query 只对被选中的一小部分 KV 块做注意力。

在这样的负载上，GPU 故障既不罕见，代价也与以往不同。大规模 GPU 集群的运维报告表明，GPU 及其 HBM 是非计划中断的最大来源（Llama 3 训练在 54 天里遇到 419 次非计划中断，其中 58.7% 与 GPU 相关）；服务集群运行同样的硬件，单卡 fail-stop 是每天都会发生的事件。执行 GPU fail-stop 后，该卡 HBM 中所有请求的 KV cache 一起丢失；如果没有备份，请求必须在别的 GPU 上重新 prefill 整段前缀。我们在一张 A100 上测得 MiniCPM4-8B 重建 32K 前缀需要 4.7 s，重建 128K 前缀需要 22.3 s，稠密与 MoE 模型的估计值更高（§2.3）。KV 备份（把已生成 KV 复制到 DRAM 池或其他 GPU）可以避免这段重算，但备份容量与带宽有限：Peer GPU 能借出的空闲 HBM 通常只有几 GiB，而一张卡上活跃请求的 KV 合计可达数十 GiB；故障后这些请求还要共享同一条 H2D 路径恢复。于是核心问题变为：**在多智能体工作流中，哪些请求的哪些 KV 值得占用最稀缺的备份介质？**

我们的回答建立在两个观察上。第一，请求之间不平等。在 124 个真实多智能体工作流中，并行分支的执行时间差中位数为 141 s，91% 的 workflow 的时间差大于实测的 128K 前缀重算时间（§2.2）。持续时间差本身不等于 Slack；只有恢复代价不超过请求的 Slack 时，重算才不推迟汇合，而关键路径上的请求多等 1 s，WCT 就多 1 s。用调度理论中的 Slack 度量这种差别，可以把有限容量集中到真正会暴露给 WCT 的请求。第二，请求内部也不平等。原生稀疏注意力模型在每个 query 只读取少数历史 KV 块：在 NOSA-1B 和 MiniCPM4-8B 的真实选块轨迹上，最热的 20% `(layer, block)` 字节分别承担 90% 和 66% 的访问（§3.3）。这一集中性在 256/512 个后续 query 的窗口中都可检验，说明有限的 Peer HBM 不应均匀保护全部 KV。访问频次不直接等于恢复收益：§3.3 再区分历史热度、重算尾部所需的去重块并集和在线预取，以保证未预测到的必要块仍能到齐。

基于这两个观察，我们设计了 AegisKV。Recovery Manager 在请求到达时将其恢复目标与 Peer HBM 所在的 DP rank 绑定为同一目标（§3.4）；KV Master 在请求到达、KV 密封、Slack 变化及控制窗口决定采用 Recompute、DRAM-only 或 Peer + DRAM，并选择每层的候选热块（§3.5）。Adapter 每 5 秒更新所有请求共用的驻留前层数 $L_t$，窗口内固定；各目标 DP 根据前台压力更新 Peer 总预算。固定预取比例 $h$ 由模型及稀疏注意力方式的画像确定，每层热块数 $K_r=\lceil h n_r\rceil$ 随请求的密封历史块数 $n_r$ 增长，块身份随实际选择索引滚动。预算内按 Slack 优先级准入前 $L_t$ 层的完整请求足迹，未获 Peer 配额时保留 DRAM 路径。故障后按层预取并在选择器揭示确切需求时补取缺失块（§3.6）。不同请求的 retry、H2D 与计算由引擎并发推进，不要求一个请求装载或重放完成后才开始另一个。热度来自稀疏 kernel 已有的块索引，AegisKV 不改变选择器，也不要求额外的专用恢复 GPU。

本文的贡献：

1. 用真实轨迹和实机测量指出多智能体长上下文服务中的三个事实：重算代价随上下文超线性增长；工作流结构使同样的恢复延迟对 WCT 的影响相差数量级，且这一结构在真实轨迹中普遍存在；在真实原生稀疏注意力轨迹的 256/512-query 窗口中，请求内部 KV 的访问并不均匀，少量字节承担大量选块事件（§2、§3.3）。
2. 设计基于 Slack 的请求间保护优先级、基于层序与稀疏热度的请求内优先级，以及由 KV Master 做层级决策、Adapter 按 5 秒窗口控制 Peer 容量与统一层数的备份机制；通过"预取 + 按需补取"恢复装载器支持并行 retry，不改变模型的注意力选择（§3）。
3. 设计以 WCT 为中心的评估方法：配对无故障/故障运行、按逻辑进度对齐的注入、故障位置扫描、恢复来源与关键路径时间分解、两级优先级消融及带宽/并发度敏感性（§5）。端到端结果待并行恢复实现验证；旧串行队列模型输出不再用于本文结论。
