## 最影响接收论证的结论

1. **有限 Peer-HBM 相对优化 DRAM 的增量价值尚需证明。** 巨大的“重算→DRAM”收益不能归因给“DRAM→Peer”；必须计入前台 HBM、复制、争用与故障风险成本。
2. **恢复状态和容量回退必须形成可检查的合同。** 合法恢复前沿、存活 token 日志、selector 状态、独立副本提交、有限 DRAM 准入及安全缩容，不能仅靠“runtime contracts”一句完成论证。
3. **局部 slack 评分不等于同源故障下的真实工作流收益。** 并列关键分支、目标拥塞、批处理牵连、预测漂移都可能使局部收益失真。可以保留启发式，但需要明确边界、反例和可行 oracle 对照。
4. **动机证据应精确区分存在性与普遍性。** 选定反例可以证明两种排序不必相同；真实依赖、故障时刻抽样和总体分布才决定生产意义。
5. **当前实证边界和表达必须一致。** 摘要中未经端到端结果支持的显著收益/可忽略开销承诺应删除；图4原约5pt的普通标签必须修复。

## 已排除或降级的评审误读

- **量纲错误指控不成立。** 原稿的 memory occupancy cost 指其造成的前台延迟，不是直接把bytes加seconds。仍应补可执行换算、受影响集合与相同horizon。层级资格不带故障概率也不自动代表p=1；低风险选L=0可以合理，需break-even。
- **阈值方向须纠正。** 固定其余变量，P区域由 slack<R_base+W0 决定，低估W0会缩小P区域。真实剩余A=100、B=90，预测A=60、B=90，会把A的真实0 slack错估为30；Grok勘误中的“关键分支真实slack=8”仍不采用。
- **恢复顺序不能臆造。** D/P通常有完整DRAM历史，非Peer冷块可按需取回；独立Peer/DRAM commit不等于强制先DRAM后Peer。实际backing缺失必须按真实覆盖回退。工具副作用是否重复取决于runtime日志/去重契约，不能直接断言。
- **引用场景须符合原稿。** LLM请求以交给外部工具的响应结束时会释放请求引用；工具等待本身不是旧pin长期占用的例子。活跃长decode与在途复制才是有效压力场景。安全回收不得抢走未排空I/O正在使用的字节。
- **已有证据不能抹去。** 原稿已披露反事实/静态/文献/建模性质；Figure3c有native capture、Figure5含实测计算参数。它们尚不是整系统恢复实验，但不是“完全没有任何原生测量”。
- **存在性不要求总体低相关。** 单反例足以否定“两种排序必相同”。121/393覆盖率不能推出未保留的69%都串行。Figure1 A1重算35.2s不是最大，A4为38.9s。
- **测试条件不能违反资源预算。** 单80GiB源GPU同时存16×20GiB或24×12.5GiB历史的例子不可直接用；先核算权重、KV、激活、TP与offload。重算也争用算力，不能断言并发增加必出现曲线交叉。
- **不强制重写成另一套算法。** stable ID不等于FCFS；评价Peer排序应用D→P增量。slack保护排序不要求按slack串行恢复。局部启发式不必有通用近似比，但应有目标、反例和oracle对照。
- **不要求预设正结果。** “收益≥10%”“某基线必须输”“曲线必交叉”都不是合理验收。Peer无益、预测无益、某模型热集近乎无益均须保留。
- **保留时间和范围定义。** 同终点下slack与额外恢复延迟可以比较；跨硬件替换的外推仍需校准。replay尾不等于未来无限decode；集合并集扩大不自动保证任意覆盖率单调下降。
- **不按外部模型替用户决定投稿。** 仅凭这份章节预览，不接受“必须放弃本轮”结论；亦不因评审偏好覆盖用户既定图2单轴/紧凑/最大上下文要求。
