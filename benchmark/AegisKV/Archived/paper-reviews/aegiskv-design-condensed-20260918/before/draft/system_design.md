## 3 AegisKV Design

§2 提出的问题是在有限 Peer HBM 与复制带宽下减少故障对工作流完成时间（WCT）的影响。本节按三条线索引出设计：agent 剩余执行时间的估计，长上下文模型采用稀疏注意力，以及未提交尾部在 retry 时所需 KV 的预测。前者对应 Workflow Tracker 的 Slack 输入，后两者对应 Planner 的保护对象与预取顺序；随后再讨论层流水线、容量约束和并发恢复。

### 3.1 Insights 与设计启示

三张图作为一个跨双栏 Figure 并排排版，其余图均按单栏排版；预测隔离方式、来源范围和 Query 窗口只在正文/图注说明，不作为图内页脚。按“待验证的时间估计前提 → 目标模型的适用性 → KV 预测的直接证据”组织。**当前第一项还没有足够证据写成“agent 执行时间可以准确预测”**；图 3(a) 保留本次真实的预测核对结果，防止把待验证的前提写成已成立的实验结论。

**Insight 1：工作流感知的保护需要经过验证的 agent 剩余时间估计。** 角色固定、重复执行的 agent 为历史画像提供了可能性。[Pythia](https://arxiv.org/abs/2604.25899) 的角色相关输出长度分布提供了动机，但单次 LLM 输出长度不等于多轮 agent 的总执行时间，后者还包括工具执行与服务延迟。为检验当前数据能否支持该前提，我们对 [CC/Weka](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126) 中 174 个 workflow 的 1,688 个已完成 agent 进行按 workflow 隔离的五折预测；每次请求到达时只使用当时可见的进度、已完成请求与上下文特征。归一化误差先在每个 agent 内对各请求时刻的绝对剩余时间误差取均值，再除以该 agent 的真实总时长，每个 agent 在 CDF 中只占一个样本。诊断用进度 GBDT 的误差中位数为 **51.8%**，训练折持续时间中位数基线为 **49.3%**。所有原始角色标签均为 `Subagent`，故该数据无法验证当前按角色维护 P90 的算法。P90 本来就不是以最小化 MAE 为目标，图中全局 P90 回退结果也不能解释为角色画像算法失效。

**设计启示。** 把剩余时间估计与 DAG 上的 Slack 传播分开；当前仍采用 §3.3 的角色 P90、未知后继保守处理和阈值滞回，不因这张诊断图改成 GBDT。要把本段升级为“时间可预测”的正面 Insight，还需要保留角色/任务标识的重复执行时序，并在隔离的 workflow 上验证预测误差、P90 覆盖率与保护层级误判。不能用单例累计误差或单次 LLM 输出长度替代这项证据。

**Insight 2：稀疏历史访问已成为长上下文 agentic serving 需要面对的模型特性。** 图 3(b) 使用找回的“发布日期—原生上下文”旧图，按三联图宽度重排；保留十个模型条目，以 marker 区分 token、block 与 compressed-entry 选择。灰色阶梯仅为入选版本的最大上下文，不是总体采用率。日期采用官方发布公告或模型仓库记录；GLM-5 改为仓库记录的 2026-02-11（原图使用次日公告日期）。其中，[MiniCPM4](https://huggingface.co/openbmb/MiniCPM4-8B) 使用 InfLLMv2，图中取原生 32K 而非外推的 128K；[DeepSeek-V3.2](https://huggingface.co/deepseek-ai/DeepSeek-V3.2) 与 [GLM-5](https://huggingface.co/zai-org/GLM-5) 使用 DSA，报告了 128K/200K 上下文并面向 agentic 能力；[DeepSeek-V4](https://huggingface.co/deepseek-ai/DeepSeek-V4-Pro) 将 CSA 与 HCA 组合到百万 token 上下文。其余条目为 MiniCPM4.1、DeepSeek-V3.2-Exp、MiniCPM-SALA、MiniMax-M3、GLM-5.2 与 LongCat-Flash-Lite-Sparse；来源逐条保存在 `experiments/data/design-insights/sparse-releases.json`。SALA 的 block 标记只描述稀疏分支，其大部分层是线性注意力。这里支持“已有代表性模型采用”，不是对部署总体的普查，不能据此声称稀疏注意力已占据大多数市场。混合压缩架构也不等于每层都是普通 top-k KV。

**设计启示。** Planner 应接收原生选择器的逐层访问对象，按 `(layer, block)` 分配保护，而不是默认每个历史 KV 字节都同等重要。不同稀疏/压缩机制需要各自的恢复对象、选择器状态与校准；模型采用情况不等于 AegisKV 已支持图中全部模型。

**Insight 3：较早的选择记录能预测短 retry 尾部所需历史 KV 的一部分，效果取决于模型。** 故障后未提交的已生成 token 按原 token ID 重放，因此预测目标是“这些 Query 将需要哪些历史块”，而不是复述它们已产生的选择结果。对 NOSA-1B、NOSA-3B、MiniCPM4-8B 的原生轨迹，固定 32K 历史，仅用 Query 32,257–32,768 的选块计数排名，预测完全位于其后的 Query 32,769–32,832。两个策略都先在预算内保留起始块和局部窗口，再用历史频次或最近顺序填满相同的 **40% 历史 KV 字节预算**。按去重后的所需历史 `(layer, 64-token block)` 计算覆盖率，历史频次分别覆盖 **79.2%、77.8%、53.6%**，最近优先分别为 **59.7%、59.7%、50.9%**。NOSA 的改善较大，MiniCPM4 的改善仅约 2.6 个百分点，且均有预测未命中。每个模型使用 3 份 PG19 文档、各一次真实权重的因果前向；这是书籍轨迹上的假设 retry 需求分析，尚不是 agentic 故障恢复实测。

**设计启示。** 历史选择记录用于提前放置和预取，重放时的确切需求用于按需补取；重复读取同一块只计一份恢复字节。在权重、因果前缀、token ID 与选择器状态一致时，留出的后缀需求可作为 retry 需求的代理；仍需物理恢复验证两者的一致性。历史频次覆盖率不意味着完整恢复成功率，也不直接给出 WCT 收益。

### 3.2 System Overview

图 4 将 AegisKV 分为 Applications、Control plane 与 Inference engines 三层。按单栏等比缩放 v11 原图，保留原有宽高比；不再使用纵向拉长的重排版本。图上的黑底编号是附加的正文索引：① Workflow Tracker 对应 §3.3；② KV Placement Planner 对应 §3.4–3.5；③ Recovery Manager 对应 §3.6；④ Adapter 对应 §3.7。编号不表示执行顺序，各出现一次；Connector 是 Adapter 调用的传输接口，不单设算法小节。

**应用层。** Agent 运行时提交 LLM 请求，并声明 ⟨workflow id, node id, 依赖边⟩。静态 DAG 可以预先给出，动态派生的节点与依赖在运行时增量报告。应用不需要估计 Slack。

**控制面。** Router 按负载和 KV 局部性将正常请求分发到引擎。AegisKV Controller 维护工作流、保护计划和恢复状态：Workflow Tracker 生成 Slack 快照；KV Placement Planner 综合校准参数、上一窗口的块排名与可借用容量，决定保护层级、目标、层/块集合和传输计划；Recovery Manager 根据成员状态、引擎/GPU 进度及故障报告判定不可用实例，组织接管。KV 目录与复制提交元数据属于控制面共享状态，在源引擎失效后仍需可用。静态校准表是 Planner 的配置，不画成在线模块或独立数据流。

**引擎层。** DP0 与 DP1 拥有等价的 Adapter、Connector 和 HBM 分区。较大的 Local KV 区服务本 DP 的请求，较小的 Peer KV 区借给预先指定的对端；图中比例仅为示意。Adapter 汇总选择索引、报告可借用容量，管理密封/提交、前台回收与恢复装载。Connector 按计划执行 KV 传输。策略由 Planner 决定，数据直接在引擎与存储间移动，不经 Controller 中转。

### 3.3 Workflow Tracker：保护层级与竞争顺序 ①

**Slack 估计。** Workflow Tracker 为每个 agent 角色（由运行时的节点类型标识）维护最近完成节点的持续时间样本（滑动窗口，默认最近 200 次或 1 小时），以其 P90 作为该角色未完成节点的持续时间估计 $\hat T_\rho$；正在运行的节点取 $\max(\hat T_\rho-\text{已运行时间},\ \tau_{min})$，没有历史的角色回退到全局分布。对当前已知的 DAG 做一次关键路径法的前向/后向遍历，得到每个活跃请求的总时差 $\sigma_r=\mathrm{LF}_r-\mathrm{EF}_r$。动态工作流只在派生子 agent 时声明新边；尚不知道后继的节点视为处在关键路径上（$\sigma_r=0$），使未知拓扑的处理偏向保守。为避免乐观估计把关键请求错分到低保护层级，估计使用 P90 而不是均值，并对层级阈值施加 20% 的滞回；这仍是启发式估计，不保证 Slack 永不被高估。Slack 在节点完成/派生事件与每个放置窗口更新；§3.8 讨论估计误差的后果。

**恢复代价估计。** 记请求 $r$ 的历史上下文长度为 $L_r$，$T_{rc}(L_r)$ 为完整重算历史前缀的时间，$T_{rp}(r)$ 为未密封尾部的纯重放时间；二者按模型、GPU 与代表性并发负载离线校准。固定开销 $R_{floor}$ 包含故障检测、重路由与重新准入（§2.1）。记 $R_{base}(r)=R_{floor}+T_{rp}(r)$，$W_0(r)$ 为没有 Peer 副本、按 §3.4 从 DRAM 装载时超出纯重放的暴露等待（§3.4 给出闭式），则重算恢复与 DRAM 恢复的代价估计分别为

$$R_R(r)=R_{base}(r)+T_{rc}(L_r),\qquad R_D(r)=R_{base}(r)+W_0(r).$$

并发带来的资源竞争由校准代价与有效带宽反映；估计不假定请求独占峰值带宽，也不累加其他请求的传输时间。

**三个保护层级。** 每个请求独立比较当前 Slack 与恢复代价：

- **Tier R（recompute）：** $\sigma_r\ge R_R(r)$。完整重算可被 Slack 吸收，不备份 KV。
- **Tier D（DRAM-only）：** 不满足 Tier R，但 $\sigma_r\ge R_D(r)$。DRAM 恢复可被 Slack 吸收，只保留 DRAM 副本。
- **Tier P（Peer + DRAM）：** 两者均不满足。保留 DRAM 副本，并按 Slack 升序竞争 Peer HBM；进入 Peer 的对象是 §3.4 定义的足迹 $F(r)$，整体放入或整体不放（§3.5）。

层级是在线估计下的放置类别，而不是三条恢复队列：预算不足时 Tier P 的请求仍从 DRAM 恢复；负载或 Slack 变化时请求重新分层。

**Slack 只做分层与排序。** 它不直接缩放请求内部的 Peer 足迹。若以 $[R_{base}+W-\sigma_r]^+$ 近似该请求暴露的工作流延迟，部分驻留在 $\sigma_r<R_{base}+W_{floor}$ 时同样能减少延迟；不能宣称部分保护只有在 $W_{floor}$–$W_0$ 的窄区间内才有价值。AegisKV 选择整体足迹，是为了让保护对象、容量核算与计划切换可预测，并避免用有噪声的 Slack 精细分配毫秒级预取收益；它是明确的策略取舍，不是全局最优性的证明。图 6 中可消除的预取等待约为 24 ms，端到端收益仍取决于故障时 Slack、排队与资源竞争。

### 3.4 KV Placement Planner：选择块与层 ②

**保护单位与块大小（离线）。** 保护单位是 `(layer, block)`，各层可以保护不同的 token 位置。块大小与稀疏选择器的块一致——MiniCPM4-8B 与 NOSA 均为 64 个 token——使热度计数、密封与复制使用同一粒度：更大的块把冷 token 与热 token 绑在一起，稀释热度排名；更小的块增加对象数与元数据。写满即密封并进入复制队列。在 32K 历史、512-query 窗口的选块轨迹上，若每个 token 段必须携带全部层，同样 20% 的字节只能覆盖 53%–59% 的选块事件，而按 `(layer, block)` 选择可覆盖 66%（MiniCPM4-8B）与 90% 以上（NOSA-1B；原始集中度分析保留在 `figures/design-sparse-concentration.pdf`）。解码时未密封的尾部小于一个块，分析中保守地取 64 个 token（故障相位均匀时期望为 32 个）；尚未提交的密封块同样计入需要重算的后缀，以提交前沿为准。每次密封产生 64 token × 全部层的 KV（MiniCPM4-8B 为 2 MiB）；100 个请求以 50 token/s 解码时产生约 160 MiB/s 的新 KV，这是复制流量的量级，§3.7 对其限速。

**尾部重计算。** 故障后，接管端利用已恢复的历史 KV，对故障前已经生成、但 KV 尚未备份的尾部 token 再执行一次前向计算，重建这些 token 的 KV；它不重新采样 token，也不重算历史前缀。本节的恢复流水线以尾部重计算完成为终点，之后请求继续正常解码。

**恢复需要的是并集，而不是访问频次。** 对第 $l$ 层，重放 $n$ 个尾部 token 需要的历史块是 $U_l(n)=\bigcup_{q=1}^{n}\bigcup_g S_{l,q,g}$（$g$ 为选择组），重复选中的块只传一份。$U_l(n)$ 随 $n$ 单调不减，且不能由访问事件的频次覆盖率推出；图 3(c) 直接评估去重后的需求覆盖。在 32K 历史的轨迹上，64-query 并集占每层历史字节的均值为 NOSA-1B 37%、MiniCPM4-8B 68%；512-query 时为 58% 与 90%。因此保护与装载的目标不是"最常被访问的块"，而是"重放尾部所需块的并集"；热度只是预测这一并集的信号。

**$K_l$ 的大小离线校准。** 第 $l$ 层进入 Peer 的块数 $K_l$ 是该层所需并集大小的估计。它不在线估计，而是查表：按模型、层、上下文长度档与尾长，从选块轨迹统计并集比例 $h_l=|U_l(n)|/B_l$ 的均值（$B_l$ 为该层的历史块数），得到 $K_l(L_r)=\lceil h_l B_l\rceil$，并校验其至少容纳选择器强制的历史块；强制块已计入 $K_l$，不在 Top-k 之外重复追加。在当前三文档轨迹中，逐窗口重估的额外收益较小：用其他文档校准的逐层表与逐窗口的在线估计相比，图 6 配置下的补取地板只差 0.4 ms（逐层计算为 20.3 对 19.9 ms；图 6 的同质层近似给出 20.0 ms），相邻窗口的并集比例变化均值 0.03、P90 0.07。但表必须逐层：同一模型各层的并集比例在 0.44–0.87 之间，改用单一常数会把地板抬高 18%（23.5 ms）。表的第三维是上下文长度——16K 历史下 MiniCPM4-8B 的 $h_l$ 均值为 0.89，32K 为 0.66——第四维是尾长。部署中 Adapter 的索引计数器 仍按窗口上报并集大小，用于表的慢速滑动平均（跨请求、以小时计），不进入单个请求的放置决策。

**$K_l$ 个块的身份在线滚动。** 原生稀疏注意力的选择器为每层、每个 query 输出被选块的索引；Adapter 的索引计数器 只读取这些索引，把各层、各选择组的索引累计到一张 `[layers × blocks]` 计数表中。计数不假定各模型使用相同或固定的选择预算：MiniCPM4-8B 在 `top-k = 64` 加 2,048-token 局部窗口的配置下每 query 每层最多选择 96 块，NOSA-1B 为 64 块（含强制的局部块与起始块）。以 MiniCPM4-8B 的 32 层、2 个 KV head 与 32K 历史为例，每个解码步最多产生 6,144 次计数增量，16 位计数表占 32 KiB；每组索引去重且每 512 步清零时，单块计数不超过 1,024，不会溢出。每个排名窗口（默认 512 个解码步）结束时，第 $l$ 层的热集取被选次数最高的 $K_l$ 个密封块，并列时更新的块优先；选择器强制访问的局部块与起始块恒在集合内。身份更新带滞回：只有连续两个窗口跌出前 $K_l$ 的旧块才成为替换候选，新块占用释放出的名额；强制块优先，热集总大小仍受 $K_l$ 限制。进入热集的新块只触发增量复制，离开的块仍有 DRAM 副本。图 5 扩展图 3(c) 的预算比较：相同 40% 字节预算下，历史频次排名覆盖 NOSA-1B/NOSA-3B/MiniCPM4 所需 KV 的 79.2%/77.8%/53.6%，最近优先为 59.7%/59.7%/50.9%。两种策略均在预算内保留强制块。该实验隔离排名信号与固定逐层预算，不是对完整准入策略或两窗口滞回的评估。

**在线装载器：预取 + 按需补取。** 恢复前无法精确知道重放会选中哪些块。Adapter 的恢复装载器 对第 $l$ 层的做法是：按热度降序预取该层最热的 $h_l$ 比例的块（即 $K_l$ 个）；当重放到达第 $l$ 层，选择器基于随第一批对象到达的压缩键或块摘要算出该层的确切需求后，装载器立刻以高于预取流的优先级补取尚未到达的所需块，随后预取流继续搬运剩余的冷块。于是第 $l$ 层重放前经过恢复路径的字节为"预取 + 补取"，记其占一层历史 KV 的比例为 $\tilde u_l$。按同一轨迹复算预取与补取集合，重放 64-token 尾部时 $\tilde u$ 为 NOSA-1B 0.44、MiniCPM4-8B 0.77，比理想并集只多 5–10 个百分点。$\tilde u$ 取决于模型、上下文与选择预算：16K 历史下 MiniCPM4-8B 的 $\tilde u$ 为 0.96，NOSA-1B 为 0.69；稠密注意力或 prefill 阶段的故障（未密封部分是整个在途 chunk）下 $h=\tilde u\to1$，装载器退化为逐层稠密装载，正确性不受影响。

**层流水线、暴露等待与补取地板。** 恢复是一条按层推进的流水线：第 $l$ 层的尾部重计算需要该层的所需历史块，而后续层的传输可以与当前层的计算重叠。设每层完整历史 KV 的装载时间为 $D=L_r\cdot s/\beta$（$s$ 为每 token 每层的 KV 字节数，$\beta$ 为该请求在代表性并发下的有效 H2D 带宽），每层尾部重计算时间为 $C$，模型有 $N$ 层，各层用均值 $h$、$\tilde u$。预取任务可以提前排队，补取任务只能在前一层算完、本层需求可知后释放，因此没有 Peer 副本时的暴露等待为

$$W_0=hD+(N-1)\,[hD-C]^+ + W_{floor},\qquad W_{floor}=N(\tilde u-h)D.$$

第一项是第 1 层预取，第二项是计算掩盖不了的预取积压，$W_{floor}$ 是每层预测未命中的补取——在这一固定热集和按需释放的装载模型下，它们不能提前发出；增加被保护的前层数只能消除预取等待，不能消除热集之外的预测未命中。这个地板不是任意放置策略的下界：扩大或改变热集、乃至驻留全部所需块，都可能降低它。图 6 以 MiniCPM4-8B、32K 历史、拥塞路径 $\beta=6.25$ GB/s 为例比较四种恢复流水线。无备份的完整前缀重算代价已在图 2 说明。有 DRAM 副本后，若按 token 块顺序传输并等待全部历史到齐再计算（a），暴露等待为 172 ms；逐层完整装载（b）为 83 ms；逐层预取加按需补取（c）为 44 ms。把前 7 层各自的 $K_l$ 个热块预先驻留 Peer HBM（d）后，等待降至 20 ms，即 $W_{floor}$：残余等待全部来自每层 $\tilde u-h\approx0.12$ 的预测未命中，继续增加驻留层数不再减少等待。

**$L$ 与足迹：窗口内固定的闭式量。** 驻留在 Peer 的前层热集直接从预取积压中扣除。使等待到达地板所需的 Peer 字节为

$$F^\star(r)=\beta\,(W_0-W_{floor})=\beta\left(hD+(N-1)\,[hD-C]^+\right),$$

前层数 $L(r)$ 是热集累计字节首次达到 $F^\star$ 的最小层数，足迹 $F(r)=\sum_{l\le L(r)}K_l(L_r)\,b$（$b$ 为一个块的字节数）。当 $hD\le C$ 时计算掩盖全部预取，$F^\star=\beta hD$，只需第 1 层的热集。图 7 用图 6 的流水线扫描驻留层数：稠密逐层装载（$h=\tilde u=1$）需要 16 层、512 MiB 才把 83 ms 的等待清零；MiniCPM4-8B 画像需要 7 层、147 MiB 到达 20 ms 的地板；NOSA-1B 画像只需第 1 层、11 MiB。$F$ 不含 Slack：它是请求的上下文长度、模型画像与带宽的函数。在固定 $L$ 与画像的区间内，足迹随上下文近似线性变化；跨越前层数阈值时会发生离散跳变。例如，同一画像与带宽下，16K 历史只需 1 层、14 MiB，32K 需要 7 层、147 MiB，64K 与 128K 按 32K 的并集比例外推分别需要约 20 层、843 MiB 与 25 层、2.1 GiB；主机本地 DRAM 路径（25 GB/s）下 32K 只需 1 层、21 MiB。在这个配置下，尾长改变也会改变足迹：尾部从 64 缩到 32 个 token 时 $h$ 与 $C$ 同时下降，足迹从 147 MiB 降到 92 MiB，仍是 5–7 层的量级。在该解码速率、且不跨越层数阈值的窗口内，$L_r$ 增长几十个 token 引起的 $F$ 变化不到 1 MiB；因此 $L(r)$ 与 $F(r)$ 在准入时按闭式计算、每个窗口刷新一次，窗口内不变。

**请求内顺序。** 综上，请求内部进入 Peer HBM 的对象与顺序为：前 $L(r)$ 层，层序优先；同一层内先放选择器强制访问的块，再按前一窗口的被选次数降序放至 $K_l$ 个；只考虑密封块，活跃块由尾部重计算重建。热度来自选择器已经产生的块索引，不需要额外的注意力计算，也不修改选择器：未进入 Peer 的块在恢复时照常从 DRAM 装载，只是顺序靠后。

### 3.5 KV Placement Planner：有限预算内的整体准入

**窗口预算 $B$。** Peer Region 是可被前台收回的借用容量。每个放置窗口开始时，Adapter 取 $p(g)$ 前台 KV 占用在最近若干分钟内的高水位线，加上一个窗口内准入可能带来的增长作为余量，把 KV 池的其余部分作为预算 $B=\max\{0,\min\{B_{cap},\ \text{pool}-\text{watermark}-\text{headroom}\}\}$ 交给 Planner，默认上限 $B_{cap}=4$ GiB（§2.1）。$B$ 在窗口内不变；窗口内前台压力超过水位线时按 §3.7 回收，被回收的对象在 DRAM 中仍有副本。

**放置。** 请求间按 $\sigma_r$ 升序分配 Peer HBM，Slack 相同时按稳定的请求 ID 打破并列。每个 Tier P 请求的足迹 $F(r)$ 由 §3.4 的闭式给出，加上其选择器状态（压缩键或块摘要）的字节；足迹的新增物理字节能放进剩余预算就整体放入，否则跳过该请求继续处理下一个——被跳过的请求保留 DRAM 副本。算法 1 给出放置计划的计算过程。

```text
Algorithm 1  Place(g): Slack-ordered, whole-footprint placement
Input : requests on g; Slack snapshots; calibrated block/K/cost tables;
        cached block rankings; total Peer budget B for this window
Output: desired DRAM and Peer object sets
 1  DRAM ← ∅; Peer ← ∅
 2  for r in requests sorted by (Slack ↑, stable request id ↑):
 3      if σ_r ≥ R_base(r) + T_rc(L_r): continue             # Tier R
 4      DRAM ← DRAM ∪ sealed_blocks(r) ∪ selector_state(r)
 5      if σ_r ≥ R_base(r) + W_0(r): continue                # Tier D
 6      L ← smallest prefix reaching β·(W_0(r) − W_floor(r))
 7      A ← selector_state(r)
 8      for l in 1..L:
 9          A ← A ∪ select_K_sealed(r, l)   # forced blocks count within K_l
10      Δ ← bytes(A \ Peer)                # unique physical objects
11      if Δ > B: continue                 # skip; keep the DRAM plan
12      Peer ← Peer ∪ A; B ← B − Δ
13  return DRAM, Peer
```


请求排序为 $O(n\log n)$；第 6 行是对 $N$ 层的一次前缀和，每层的块排名在排名窗口结束时排好并缓存。共享前缀按物理对象去重，只扣除实际新增的字节。$B$ 是目标总预算；执行差量计划时，处于 copying、committed 与 reclaiming 状态的对象都计入物理水位，尚未释放的容量不会被再次借出。

**跨窗口的变化。** 相邻窗口之间只有三类变化：Slack 更新改变请求的层级或顺序；$L_r$ 增长与 $B$ 刷新改变足迹与可容纳的请求数；排名窗口结束改变各层 $K_l$ 个块的身份。三者都通过差量计划体现为有限的增量复制或回收，Adapter 不重复复制已提交的对象。后续评估需度量身份变化引起的复制量。

**并行与竞争。** 多个 retry 可以同时在途，H2D 与计算可以重叠，但链路带宽与算力仍然有限。Planner 使用在代表性并发下校准的有效带宽与重算/重放代价，不逐个累加其他请求的传输时间；并发度与带宽扫描需检验这一估计的适用范围。
### 3.6 Recovery Manager：故障判定与并行接管 ③

**故障判定的归属。** Recovery Manager 在控制面维护 DP 可用性和预定恢复映射；各 DP 的 Adapter 提供本地进度与错误信号。进程心跳、设备健康与 GPU 前向进度是不同信号，不能仅凭进程心跳推断 GPU 正常。具体超时、误报处置和代价计入 $R_{floor}$；本文的恢复路径以故障已经被确认、源实例不再提交写入为前提。

**恢复上下文。** Manager 从控制面取得受影响请求的 token 前缀、提交前沿、模型/布局标识和副本位置，向预定 $p(g)$ 提交 retry。只有完成提交的对象可以用于恢复；尚未提交的后缀重新计算。当前设计针对已隔离的单个引擎/DP fail-stop，控制面持久性、故障域隔离和重试去重是运行时契约；本文不把图中的 Controller 方框当作完整的高可用、故障仲裁或 fencing 协议。

**所有受影响请求均可独立进入恢复。** Manager 不按放置时的 Slack 顺序逐个等待 retry 完成；各请求由引擎按资源可用性准入，由 Adapter 依据本请求的 KV 就绪事件推进。保护层级只决定可用副本，不变成请求级串行队列。

**接管端的负载。** $g$ 失效后，$p(g)$ 仍在服务自己的前台请求。所有 retry 沿用引擎的并发准入、连续批处理与计算/复制资源限制，不设置请求级完成屏障；重算任务可以使用低优先级执行配额。Peer Region 的借用量、复制速率与恢复准入数均受水位线约束；若单个 Retry DP 容量不足，按 §3.2 在故障前把请求及其备份目标分散到多个 Retry DP。


### 3.7 Adapter：提交、前台保护与按需恢复 ④

**两条独立的复制路径。** Adapter 根据 Planner 的计划，通过 Connector 把密封块分别发往 Peer Region（P2P 或可用的设备传输路径）与故障域外的 DRAM 池。Connector 执行分配、传输和完成通知，不决定保护层级、目标或热集；具体协议由部署决定。两条路径各自分配、传输、确认，一条失败不影响另一条已提交的对象。DRAM 副本是覆盖的底线，Peer 副本只用于减少等待；若 Peer 副本是某块唯一有效的副本，降级前先完成其 DRAM 提交。共享前缀（多个 agent 复用的系统提示或检索结果）只占一份物理容量，并与前缀缓存的 DRAM 层共用同一副本。压缩键等选择器状态随第 1 层一起复制，恢复时最先到达。

**提交语义。** 放置计划的试算不改变可读集合；复制完成并核对模型、布局与分片信息后才发布对象。预算下降不等于地址已释放：copying、committed 与 reclaiming 状态的字节持续计入占用，直到释放完成。

**前台保护。** 窗口内前台 KV 占用超过水位线时，Adapter 的容量管理 按放置的逆序回收：先回收 Slack 最大的 Tier P 请求，同一请求内先回收层序最后的热集；回收以整个请求的足迹为单位，回收后该请求在下一窗口重新竞争。复制流量使用低优先级拷贝流，并限制在链路带宽的固定比例内（默认 20%）；Peer 写入消耗接管端的 HBM 带宽，同样受该比例约束。

**每个请求独立推进的装载器。** Recovery Manager 提交并行 retry，Adapter 的恢复装载器 为每个请求维护预取与补取任务：预取按 `(layer ↑, hotness ↓)` 搬运每层的 $K_l$ 个块并跳过已驻留的块；选择器给出确切需求后，缺失块以高于预取任务的优先级提交，是否抢占在途 DMA 由引擎实现决定。某请求第 $l$ 层的所需 KV 就绪后即可计算，不等待其他请求；后续层的预取与当前层的计算重叠。冷块在后台补齐，未密封或未提交的后缀重算，Tier R 请求直接重算前缀。恢复后的解码如再选到未驻留的块，同样按需补取；retry 不为等待全部 KV 到齐而推迟启动。

**正确性。** AegisKV 只决定备份位置与装载顺序，不改变稀疏选择器的输出；补取保证所需块在注意力执行前到齐。因此该设计不引入新的注意力近似：在相同权重、布局、已知 token 前缀与兼容算子下，恢复重建的是同一逻辑 KV 状态。浮点执行次序仍可能随批次变化，不能由这一机制直接推出后续随机采样输出逐 token 相同（R5）。
### 3.8 适用边界与待验证项

**Slack 估计误差。** 在线 Slack 可能过于乐观（把关键请求放入 Tier R）或过于悲观（把过多请求放入 Tier P）。AegisKV 用 P90 持续时间、阈值滞回、未知后继按 $\sigma=0$ 处理与事件触发的重新规划限制其后果。乐观误差的代价是 Tier R 请求没有副本，只能完整重算并暴露给 WCT；空闲时可以机会式地把 Tier R 请求复制到 DRAM，但只有已提交的副本提供这一保障。悲观误差不改变足迹，只让更多请求排队竞争 $B$，Slack 最小的请求仍然先得到 Peer。后续评估需量化 Slack 误差的影响。

**身份陈旧与校准表漂移。** 热集身份来自前一个排名窗口，与恢复时的实际需求之间存在时间差；图 5 度量的正是这种陈旧预测的覆盖质量，滞回把身份抖动限制在窗口边界。$K_l$ 表由轨迹校准并按小时级滑动平均更新；画像缓慢修正仍可能跨越离散的层数或准入阈值，不能保证窗口间没有跳变。默认排名窗口为 512 个解码步，表中并集比例按与尾长相同的窗口统计（默认 64 步）；后续评估需扫描窗口长度与表的过时程度。

**对不同稀疏选择器的适用性。** 接入条件是能观察选择索引、恢复选择器状态与全部必需的注意力分支，并按模型校准成本。InfLLM-v2 与 NOSA 输出块索引；DSA 输出 token 索引，需要映射到实际复制的块，分散的 token 会放大块级传输；NSA 的压缩分支与局部分支也必须备份，不能只保护 Top-k 分支。选择器元数据的体积与驻留代价按实现核算。AegisKV 依赖真实索引与块并集，不依赖 $k$ 固定或随上下文增长的特定规律；当热度不稳定或复制粒度不匹配时退化为逐层完整装载，Slack 分层仍然适用。稠密注意力下 $h=\tilde u=1$，$K_l$ 退化为整层，请求内只剩层序这一维（图 7 中 16 层、512 MiB 的足迹）。无工作流的独立请求取 $\sigma=0$，按稳定 ID 打破并列，恢复仍然并行。

**更快的恢复路径与张量并行。** 更高的有效 H2D 带宽降低 $D$，足迹 $F^\star=\beta hD+(N-1)[\beta hD-\beta C]^+$ 中只有第一项与带宽无关（它就是一层热集的字节），第二项随 $\beta$ 增大迅速消失：32K 历史在 25 GB/s 下只需 1 层、21 MiB。若 DRAM 恢复已能被 Slack 吸收，则不需要 Peer HBM。Peer 副本不能消除固定检测开销、纯重放时间与补取地板，因此即使 $\sigma=0$ 的请求也只在 $W_0-W_{floor}$ 范围内受益。张量并行下，一个 TP 组是"GPU $g$"的单位，Retry DP 是另一个 TP 组，每层字节按分片计算。带宽扫描应分别覆盖 PCIe、远端池与高速 CPU–GPU 互连的场景。

**模型近似。** 闭式 $F^\star$ 使用同质层近似；实际逐层代价、块数与带宽不同时，它是规划估计，不能保证达到同一个精确地板。异构层和不可抢占 DMA 的误差需用逐层递推与真实执行验证。

**局限。** 图 3(a) 的角色特定时间预测前提尚未验证；图 3(b) 是代表性采用实例，非市场份额。图 3(c)、图 5 与 §3.4 的恢复参数来自书籍文本的原生轨迹，未执行故障注入与选择器状态恢复；agent 负载中的代码与工具输出可能呈现不同的选择模式，访问集中度、并集比例与恢复收益需要在 agent 轨迹和不同选择预算下重新校准。所需并集的占比不保证随上下文增长而下降，64K 以上的足迹外推沿用了 32K 的并集比例。NOSA-1B 画像借用 MiniCPM4-8B 的层数、每层字节与重计算代价，只用于对比装载比例的影响。prefill 阶段的故障可能丢失整个在途 chunk，其重算代价需按实际后缀长度校准，不能沿用 64-token 尾部的估计。

**当前证据。** 本节的访问集中度与并集统计来自原生选择器轨迹；计算代价来自指定 GPU 的测量；恢复时间线与 Peer 足迹是受这些参数约束的模型结果。新的放置策略、并行接管与运行时开销仍需端到端验证，不能用旧的串行恢复或旧策略结果代替。正文中的不变式规定预期行为，不等于已经完成实现验证。
