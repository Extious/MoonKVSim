## 3 AegisKV Design

AegisKV 回答 §1 提出的问题：在多智能体工作流中，哪些请求的哪些 KV 值得占用最稀缺的备份介质。它把回答拆成两条彼此独立的线。请求之间，Slack 是唯一的优先级来源：它决定一个请求属于哪个保护层级，以及层级内竞争 Peer HBM 的先后（R1）。请求内部，进入 Peer HBM 的对象是"前 $L$ 层、每层 $K_l$ 个热块"：块大小与 $K_l$ 是离线校准的常量，$L$ 与 Peer 预算 $B$ 在一个放置窗口内固定，只有"是哪 $K_l$ 个块"这一身份在线随选择器的输出滚动（R2）。于是每个请求的 Peer 足迹是一个只取决于请求自身的确定数，放置退化为按 Slack 排序、按足迹整体装入预算的过程。放置与恢复解耦：故障后各请求并行 retry，装载器按每层的实际需求补取缺失块，不为保护优先级引入请求级串行屏障（R3）；备份流量与 Peer 容量受前台水位约束（R4）；恢复不引入额外 GPU 或二次拷贝，也不改变模型的注意力选择（R5）。表 1 列出各决策量及其变化的时间尺度。

**表 1：AegisKV 的决策量与时间尺度。**

| 时间尺度 | 决策量 | 来源 |
|---|---|---|
| 离线常量 | 块大小；每层热集大小 $K_l(L_r)$；每层尾部重计算代价 $C$ 与有效带宽 $\beta$ | 选择器的块粒度；轨迹与实测校准（§3.3） |
| 窗口内固定（默认 1 s） | 每个请求的保护层级与 Peer 竞争顺序；前层数 $L(r)$ 与足迹 $F(r)$；Peer 预算 $B$ | Workflow Tracker 的 Slack（§3.2）；闭式流水线模型（§3.3）；前台水位线（§3.4） |
| 在线连续 | 每层 $K_l$ 个热块的身份；块的密封、复制与提交；前台压力下的回收 | Hotness Counter（§3.3）；Backup Agent 与 Peer Budget（§3.5） |

### 3.1 架构概览

图 5 给出 AegisKV 的三层架构。**应用层**是现有的 agent 运行时（如 LangGraph、AutoGen）。它为 DAG 的每个节点发出一个 LLM 请求，并在请求元数据中携带 ⟨workflow id, node id, 依赖边⟩。AegisKV 不要求应用提供 Slack 或持续时间估计，只要求能识别请求属于哪个工作流的哪个节点以及它的后继是谁：依赖图可以静态声明，也可以在运行时派生子 agent 时增量声明。

**控制面**由四个模块组成。Workflow Tracker 维护每个工作流的 DAG 进度与持续时间估计，为每个活跃请求产出 Slack 快照 $\sigma_r$（§3.2）。Placement Planner 按放置窗口为每张源 GPU 计算放置计划：输入是 Slack 快照、离线校准表、上一窗口的块排名与本窗口的 Peer 预算，输出是每个请求的层级、前层数 $L(r)$ 与进入 Peer 的块身份（§3.3–3.4）。Failure Detector 通过心跳检测 GPU fail-stop，并维护固定的 Retry-DP 映射 $g\mapsto p(g)$。Recovery Manager 在故障后向 $p(g)$ 提交受影响的请求及其恢复计划，由引擎按资源可用性并发准入与执行（§3.5）。

**引擎层**是每个 DP 一个的 vLLM 风格引擎，AegisKV 在其中加入四个模块。源端的 Hotness Counter 从稀疏注意力 kernel 已经产生的块索引中累计每个 `(layer, block)` 的被选次数，按窗口给出每层的块排名。Backup Agent 按块密封 KV，把密封块复制到 Peer HBM 与 DRAM 池，并在收到确认后提交。接管端的 Peer Region 是 Peer HBM 中借给备份的区域；Peer Budget 按前台 KV 占用的高水位线在每个窗口开始时给出它的容量 $B$。Recovery Loader 在故障后按层、热块优先地预取 DRAM 中的块，按选择器的实际需求补取缺失块，并驱动尾部重计算。

**正常路径。** 每个放置窗口（默认 1 s；请求到达或完成、Slack 变化超过阈值时立即触发），Planner 对源 GPU $g$ 上的活跃请求执行算法 1（§3.4），产出两个集合：需要 DRAM 副本的密封块与需要进入 Peer Region 的密封块。Backup Agent 只复制相对上一窗口新增或升级的对象，通过低优先级拷贝流发送，两条路径各自确认。放置计划连同最近一个窗口的块排名保存在控制面，源 GPU 失效后仍然可用。

**故障路径。** $g$ 失效后，Recovery Manager 向 $p(g)$ 提交全部受影响请求，沿用引擎的并发调度；放置时的 Slack 排序不构成恢复时的完成顺序约束。每个请求的恢复流水线相同：Peer Region 中的块直接参与计算；DRAM 中的块由 Recovery Loader 按层、热块优先预取，重放到达某一层时按该层的实际选择补取缺失块，冷块在后台补齐；未密封的活跃块与缺失的后缀重算。不引入额外的恢复 GPU，也不把 Peer 状态拷到第三张卡。

**固定 Retry DP。** 备份目标在故障前确定，Peer 副本才能被接管端零拷贝读取。映射采用环形 $p(g)=g+1 \bmod n$：每个 DP 只为一张源 GPU 保存 Peer 副本，Peer Region 的容量竞争只发生在同一源 GPU 的请求之间。多对一映射只需在算法 1 中按源 GPU 划分预算；把一张卡的请求分散到多个 Retry DP，则等价于把 $g$ 的请求集合切分后分别运行算法 1，每份使用自己的路径与预算。

### 3.2 请求之间：Slack 决定层级与顺序

**Slack 估计。** Workflow Tracker 为每个 agent 角色（由运行时的节点类型标识）维护最近完成节点的持续时间样本（滑动窗口，默认最近 200 次或 1 小时），以其 P90 作为该角色未完成节点的持续时间估计 $\hat T_\rho$；正在运行的节点取 $\max(\hat T_\rho-\text{已运行时间},\ \tau_{min})$，没有历史的角色回退到全局分布。对当前已知的 DAG 做一次关键路径法的前向/后向遍历，得到每个活跃请求的总时差 $\sigma_r=\mathrm{LF}_r-\mathrm{EF}_r$。动态工作流只在派生子 agent 时声明新边；尚不知道后继的节点视为处在关键路径上（$\sigma_r=0$），使误差偏向保守。为避免乐观估计把关键请求错分到低保护层级，估计使用 P90 而不是均值，并对层级阈值施加 20% 的滞回。Slack 在节点完成/派生事件与每个放置窗口更新；§3.6 讨论估计误差的后果。

**恢复代价估计。** 记请求 $r$ 的历史上下文长度为 $L_r$，$T_{rc}(L_r)$ 为完整重算历史前缀的时间，$T_{rp}(r)$ 为未密封尾部的纯重放时间；二者按模型、GPU 与代表性并发负载离线校准。固定开销 $R_{floor}$ 包含故障检测、重路由与重新准入（§2.1）。记 $R_{base}(r)=R_{floor}+T_{rp}(r)$，$W_0(r)$ 为没有 Peer 副本、按 §3.3 从 DRAM 装载时超出纯重放的暴露等待（§3.3 给出闭式），则重算恢复与 DRAM 恢复的代价估计分别为

$$R_R(r)=R_{base}(r)+T_{rc}(L_r),\qquad R_D(r)=R_{base}(r)+W_0(r).$$

并发带来的资源竞争由校准代价与有效带宽反映；估计不假定请求独占峰值带宽，也不累加其他请求的传输时间。

**三个保护层级。** 每个请求独立比较当前 Slack 与恢复代价：

- **Tier R（recompute）：** $\sigma_r\ge R_R(r)$。完整重算可被 Slack 吸收，不备份 KV。
- **Tier D（DRAM-only）：** 不满足 Tier R，但 $\sigma_r\ge R_D(r)$。DRAM 恢复可被 Slack 吸收，只保留 DRAM 副本。
- **Tier P（Peer + DRAM）：** 两者均不满足。保留 DRAM 副本，并按 Slack 升序竞争 Peer HBM；进入 Peer 的对象是 §3.3 定义的足迹 $F(r)$，整体放入或整体不放（§3.4）。

层级是在线估计下的放置类别，而不是三条恢复队列：预算不足时 Tier P 的请求仍从 DRAM 恢复；负载或 Slack 变化时请求重新分层。

**Slack 只做两件事：分层与排序。** 它不缩放足迹。驻留部分足迹只在 $\sigma_r-R_{base}(r)$ 落在补取地板 $W_{floor}$ 与 $W_0$ 之间时才改变该请求对 WCT 的贡献；图 7 的配置下这是一个 20–44 ms 的区间，宽度低于在线 Slack 估计的分辨率（持续时间样本以秒计）。按 Slack 切分足迹得不到可靠的收益，却会让 Peer 中充满只覆盖前一两层的碎片。整体放入使每个请求的 Peer 占用可预测，预算能容纳的请求数在窗口开始时就已确定。

### 3.3 请求内部：块、$K$ 与 $L$

**稀疏选择集中在少量块上（离线轨迹）。** 稀疏注意力并不均匀地读取历史 KV：有的块被后续 query 反复选中，有的几乎不被需要。我们读取三个模型（MiniCPM4-8B、NOSA-3B、NOSA-1B，后两者带训练得到的局部性门控）在三份 PG19 长文本上的实际选块索引：固定 32K 历史，统计其后 256 与 512 个 query 的选择，以含全部 KV head 的 `(layer, 64-token block)` 为单位按被选次数降序排列。图 6 中最热 20% 的字节在 256/512-query 窗口下覆盖 NOSA-1B 92.2%/90.3%、NOSA-3B 91.5%/89.5%、MiniCPM4-8B 69.6%/66.0% 的选块事件；覆盖 90% 的事件，两个 NOSA 模型只需约 20% 的历史字节，MiniCPM4-8B 约需 40%。两个 NOSA 模型的曲线几乎重合，集中度不随规模变化；MiniCPM4-8B 没有局部性门控，集中度较低，但仍远高于均匀访问。因此有限的 Peer HBM 应优先容纳更常被选中的 KV，而不是按 token 位置或均匀比例备份。图 6 只回答“请求内是否存在优先级”；下面依次说明保护单位、恢复真正需要的集合与在线装载。

**保护单位与块大小（离线）。** 保护单位是 `(layer, block)`，各层可以保护不同的 token 位置。块大小与稀疏选择器的块一致——MiniCPM4-8B 与 NOSA 均为 64 个 token——使热度计数、密封与复制使用同一粒度：更大的块把冷 token 与热 token 绑在一起，稀释热度排名；更小的块增加对象数与元数据。写满即密封并进入复制队列。在 32K 历史、512-query 窗口的选块轨迹上，若每个 token 段必须携带全部层，同样 20% 的字节只能覆盖 53%–59% 的选块事件，而按 `(layer, block)` 选择可覆盖 66%（MiniCPM4-8B）与 90% 以上（NOSA-1B，图 6）。解码时未密封的尾部小于一个块，分析中保守地取 64 个 token（故障相位均匀时期望为 32 个）；尚未提交的密封块同样计入需要重算的后缀，以提交前沿为准。每次密封产生 64 token × 全部层的 KV（MiniCPM4-8B 为 2 MiB）；100 个请求以 50 token/s 解码时产生约 160 MiB/s 的新 KV，这是复制流量的量级，§3.5 对其限速。

**尾部重计算。** 故障后，接管端利用已恢复的历史 KV，对故障前已经生成、但 KV 尚未备份的尾部 token 再执行一次前向计算，重建这些 token 的 KV；它不重新采样 token，也不重算历史前缀。本节的恢复流水线以尾部重计算完成为终点，之后请求继续正常解码。

**恢复需要的是并集，而不是访问频次。** 对第 $l$ 层，重放 $n$ 个尾部 token 需要的历史块是 $U_l(n)=\bigcup_{q=1}^{n}\bigcup_g S_{l,q,g}$（$g$ 为选择组），重复选中的块只传一份。$U_l(n)$ 随 $n$ 单调不减，且不能由图 6 的访问覆盖率推出。在 32K 历史的轨迹上，64-query 并集占每层历史字节的均值为 NOSA-1B 37%、MiniCPM4-8B 68%；512-query 时为 58% 与 90%。因此保护与装载的目标不是"最常被访问的块"，而是"重放尾部所需块的并集"；热度只是预测这一并集的信号。

**$K_l$ 的大小离线校准。** 第 $l$ 层进入 Peer 的块数 $K_l$ 是该层所需并集大小的估计。它不在线估计，而是查表：按模型、层、上下文长度档与尾长，从选块轨迹统计并集比例 $h_l=|U_l(n)|/B_l$ 的均值（$B_l$ 为该层的历史块数），得到 $K_l(L_r)=h_l B_l$。轨迹表明在线估计几乎不含额外信息：用其他文档校准的逐层表与逐窗口的在线估计相比，图 7 配置下的补取地板只差 0.4 ms（逐层计算为 20.3 对 19.9 ms；图 7 的同质层近似给出 20.0 ms），相邻窗口的并集比例变化均值 0.03、P90 0.07。但表必须逐层：同一模型各层的并集比例在 0.44–0.87 之间，改用单一常数会把地板抬高 18%（23.5 ms）。表的第三维是上下文长度——16K 历史下 MiniCPM4-8B 的 $h_l$ 均值为 0.89，32K 为 0.66——第四维是尾长。部署中 Hotness Counter 仍按窗口上报并集大小，用于表的慢速滑动平均（跨请求、以小时计），不进入单个请求的放置决策。

**$K_l$ 个块的身份在线滚动。** 原生稀疏注意力的选择器为每层、每个 query 输出被选块的索引；Hotness Counter 只读取这些索引，把各层、各选择组的索引累计到一张 `[layers × blocks]` 计数表中。计数不假定各模型使用相同或固定的选择预算：MiniCPM4-8B 在 `top-k = 64` 加 2,048-token 局部窗口的配置下每 query 每层最多选择 96 块，NOSA-1B 为 64 块（含强制的局部块与起始块）。以 MiniCPM4-8B 的 32 层、2 个 KV head 与 32K 历史为例，每个解码步最多产生 6,144 次计数增量，16 位计数表占 32 KiB；每组索引去重且每 512 步清零时，单块计数不超过 1,024，不会溢出。每个排名窗口（默认 512 个解码步）结束时，第 $l$ 层的热集取被选次数最高的 $K_l$ 个密封块，并列时更新的块优先；选择器强制访问的局部块与起始块恒在集合内。身份更新带滞回：一个块要离开热集，须在两个连续窗口都跌出前 $K_l$；进入热集的新块只触发增量复制，离开的块仍有 DRAM 副本。图 8 用轨迹度量这一排名的质量：预取一层最热的 40% 字节时，NOSA-1B 的所需块已有 82% 驻留，MiniCPM4-8B 为 55%，而按最近优先分别只有 60% 与 53%。

**在线装载器：预取 + 按需补取。** 恢复前无法精确知道重放会选中哪些块。Recovery Loader 对第 $l$ 层的做法是：按热度降序预取该层最热的 $h_l$ 比例的块（即 $K_l$ 个）；当重放到达第 $l$ 层，选择器基于随第一批对象到达的压缩键或块摘要算出该层的确切需求后，装载器立刻以高于预取流的优先级补取尚未到达的所需块，随后预取流继续搬运剩余的冷块。于是第 $l$ 层重放前经过恢复路径的字节为"预取 + 补取"，记其占一层历史 KV 的比例为 $\tilde u_l$。按同一轨迹复算预取与补取集合，重放 64-token 尾部时 $\tilde u$ 为 NOSA-1B 0.44、MiniCPM4-8B 0.77，比理想并集只多 5–10 个百分点。$\tilde u$ 取决于模型、上下文与选择预算：16K 历史下 MiniCPM4-8B 的 $\tilde u$ 为 0.96，NOSA-1B 为 0.69；稠密注意力或 prefill 阶段的故障（未密封部分是整个在途 chunk）下 $h=\tilde u\to1$，装载器退化为逐层稠密装载，正确性不受影响。

**层流水线、暴露等待与补取地板。** 恢复是一条按层推进的流水线：第 $l$ 层的尾部重计算需要该层的所需历史块，而后续层的传输可以与当前层的计算重叠。设每层完整历史 KV 的装载时间为 $D=L_r\cdot s/\beta$（$s$ 为每 token 每层的 KV 字节数，$\beta$ 为该请求在代表性并发下的有效 H2D 带宽），每层尾部重计算时间为 $C$，模型有 $N$ 层，各层用均值 $h$、$\tilde u$。预取任务可以提前排队，补取任务只能在前一层算完、本层需求可知后释放，因此没有 Peer 副本时的暴露等待为

$$W_0=hD+(N-1)\,[hD-C]^+ + W_{floor},\qquad W_{floor}=N(\tilde u-h)D.$$

第一项是第 1 层预取，第二项是计算掩盖不了的预取积压，$W_{floor}$ 是每层预测未命中的补取——它们不能提前发出，因此无论 Peer 中驻留多少字节都不会消失。图 7 以 MiniCPM4-8B、32K 历史、拥塞路径 $\beta=6.25$ GB/s 为例比较五种恢复方式。无 KV 备份时需要重算 32K 历史前缀，耗时 4.8 s（a）。有 DRAM 副本后，若按 token 块顺序传输并等待全部历史到齐再计算（b），暴露等待为 172 ms；逐层完整装载（c）为 83 ms；逐层预取加按需补取（d）为 44 ms。把前 7 层各自的 $K_l$ 个热块预先驻留 Peer HBM（e）后，等待降至 20 ms，即 $W_{floor}$：残余等待全部来自每层 $\tilde u-h\approx0.12$ 的预测未命中，继续增加驻留层数不再减少等待。

**$L$ 与足迹：窗口内固定的闭式量。** 驻留在 Peer 的前层热集直接从预取积压中扣除。使等待到达地板所需的 Peer 字节为

$$F^\star(r)=\beta\,(W_0-W_{floor})=\beta\left(hD+(N-1)\,[hD-C]^+\right),$$

前层数 $L(r)$ 是热集累计字节首次达到 $F^\star$ 的最小层数，足迹 $F(r)=\sum_{l\le L(r)}K_l(L_r)\,b$（$b$ 为一个块的字节数）。当 $hD\le C$ 时计算掩盖全部预取，$F^\star=\beta hD$，只需第 1 层的热集。图 9 用图 7 的流水线扫描驻留层数：稠密逐层装载（$h=\tilde u=1$）需要 16 层、512 MiB 才把 83 ms 的等待清零；MiniCPM4-8B 画像需要 7 层、147 MiB 到达 20 ms 的地板；NOSA-1B 画像只需第 1 层、11 MiB。$F$ 不含 Slack：它是请求的上下文长度、模型画像与带宽的函数。$D\propto L_r$ 使足迹随上下文近似线性增长——同一画像与带宽下，16K 历史只需 1 层、14 MiB，32K 需要 7 层、147 MiB，64K 与 128K 按 32K 的并集比例外推分别需要约 20 层、843 MiB 与 25 层、2.1 GiB；主机本地 DRAM 路径（25 GB/s）下 32K 只需 1 层、21 MiB。尾长的影响很弱：尾部从 64 缩到 32 个 token 时 $h$ 与 $C$ 同时下降，足迹从 147 MiB 降到 92 MiB，仍是 5–7 层的量级。一个窗口内 $L_r$ 最多增长几十个 token，$F$ 的变化不到 1 MiB（0.2%），因此 $L(r)$ 与 $F(r)$ 在准入时按闭式计算、每个窗口刷新一次，窗口内不变。

**请求内顺序。** 综上，请求内部进入 Peer HBM 的对象与顺序为：前 $L(r)$ 层，层序优先；同一层内先放选择器强制访问的块，再按前一窗口的被选次数降序放至 $K_l$ 个；只考虑密封块，活跃块由尾部重计算重建。热度来自选择器已经产生的块索引，不需要额外的注意力计算，也不修改选择器：未进入 Peer 的块在恢复时照常从 DRAM 装载，只是顺序靠后。

### 3.4 Peer HBM 分配：Slack 排序，整体放入

**窗口预算 $B$。** Peer Region 是可被前台收回的借用容量。每个放置窗口开始时，Peer Budget 取 $p(g)$ 前台 KV 占用在最近若干分钟内的高水位线，加上一个窗口内准入可能带来的增长作为余量，把 KV 池的其余部分作为预算 $B=\min\{B_{cap},\ \text{pool}-\text{watermark}-\text{headroom}\}$ 交给 Planner，默认上限 $B_{cap}=4$ GiB（§2.1）。$B$ 在窗口内不变；窗口内前台压力超过水位线时按 §3.5 回收，被回收的对象在 DRAM 中仍有副本。

**放置。** 请求间按 $\sigma_r$ 升序分配 Peer HBM，Slack 相同时按稳定的请求 ID 打破并列。每个 Tier P 请求的足迹 $F(r)$ 由 §3.3 的闭式给出，加上其选择器状态（压缩键或块摘要）的字节；足迹能放进剩余预算就整体放入，否则跳过该请求继续处理下一个——被跳过的请求保留 DRAM 副本。算法 1 给出放置计划的计算过程。

```text
Algorithm 1  Place(g): Slack-ordered, whole-footprint placement
Input : requests on g with Slack σ_r; offline tables (block size b, K_l(L_r), C, β);
        previous-window block rankings; Peer budget B for this window
Output: desired DRAM objects and Peer objects
 1  DRAM ← ∅; Peer ← ∅
 2  for r in requests sorted by (σ_r ↑, stable request id ↑):
 3      if σ_r ≥ R_base(r) + T_rc(L_r): continue                     # Tier R: recompute
 4      DRAM ← DRAM ∪ sealed_blocks(r) ∪ selector_state(r)           # Tier D/P: DRAM copy
 5      if σ_r ≥ R_base(r) + W_0(r): continue                        # Tier D: DRAM only
 6      L ← smallest L with Σ_{l≤L} K_l(L_r)·b ≥ β·(W_0(r) − W_floor(r))   # closed form, no Slack
 7      F ← Σ_{l≤L} K_l(L_r)·b + bytes(selector_state(r))            # whole footprint
 8      if F > B: continue                                           # all or nothing
 9      for l in 1..L: Peer ← Peer ∪ forced_blocks(r, l) ∪ top_ranked_sealed(r, l, K_l)
10      Peer ← Peer ∪ selector_state(r); B ← B − F
11  reconcile desired and committed objects under the physical Peer watermark
12  copy new objects asynchronously; publish only after completion; reclaim safely
```

请求排序为 $O(n\log n)$；第 6 行是对 $N$ 层的一次前缀和，每层的块排名在排名窗口结束时排好并缓存。共享前缀按物理对象去重，只扣除实际新增的字节。$B$ 是目标总预算；执行差量计划时，处于 copying、committed 与 reclaiming 状态的对象都计入物理水位，尚未释放的容量不会被再次借出。

**跨窗口的变化。** 相邻窗口之间只有三类变化：Slack 更新改变请求的层级或顺序；$L_r$ 增长与 $B$ 刷新改变足迹与可容纳的请求数；排名窗口结束改变各层 $K_l$ 个块的身份。三者都通过差量计划体现为有限的增量复制或回收，Backup Agent 不重复复制已提交的对象。§5.6 度量身份变化引起的复制量。

**并行与竞争。** 多个 retry 可以同时在途，H2D 与计算可以重叠，但链路带宽与算力仍然有限。Planner 使用在代表性并发下校准的有效带宽与重算/重放代价，不逐个累加其他请求的传输时间；§5 用并发度与带宽扫描检验这一估计的适用范围。

### 3.5 机制：复制、提交、前台保护与恢复

**两条独立的复制路径。** Backup Agent 把密封块分别发往 Peer Region（NVLink/P2P）与 DRAM 池（D2H）。两条路径各自分配、传输、确认，一条失败不影响另一条已提交的对象。DRAM 副本是覆盖的底线，Peer 副本只用于减少等待；若 Peer 副本是某块唯一有效的副本，降级前先完成其 DRAM 提交。共享前缀（多个 agent 复用的系统提示或检索结果）只占一份物理容量，并与前缀缓存的 DRAM 层共用同一副本。压缩键等选择器状态随第 1 层一起复制，恢复时最先到达。

**提交语义。** 放置计划的试算不改变可读集合；复制完成并核对模型、布局与分片信息后才发布对象。预算下降不等于地址已释放：copying、committed 与 reclaiming 状态的字节持续计入占用，直到释放完成。

**前台保护（Peer Budget）。** 窗口内前台 KV 占用超过水位线时，Peer Budget 按放置的逆序回收：先回收 Slack 最大的 Tier P 请求，同一请求内先回收层序最后的热集；回收以整个请求的足迹为单位，回收后该请求在下一窗口重新竞争。复制流量使用低优先级拷贝流，并限制在链路带宽的固定比例内（默认 20%）；Peer 写入消耗接管端的 HBM 带宽，同样受该比例约束。

**接管端的负载。** $g$ 失效后，$p(g)$ 仍在服务自己的前台请求。所有 retry 沿用引擎的并发准入、连续批处理与计算/复制资源限制，不设置请求级完成屏障；重算任务可以使用低优先级执行配额。Peer Region 的借用量、复制速率与恢复准入数均受水位线约束；若单个 Retry DP 容量不足，按 §3.1 在故障前把请求及其备份目标分散到多个 Retry DP。

**恢复。** Recovery Manager 提交并行 retry，Recovery Loader 为每个请求维护预取与补取任务：预取按 `(layer ↑, hotness ↓)` 搬运每层的 $K_l$ 个块并跳过已驻留的块；选择器给出确切需求后，缺失块以高于预取任务的优先级提交，是否抢占在途 DMA 由引擎实现决定。某请求第 $l$ 层的所需 KV 就绪后即可计算，不等待其他请求；后续层的预取与当前层的计算重叠。冷块在后台补齐，未密封或未提交的后缀重算，Tier R 请求直接重算前缀。恢复后的解码如再选到未驻留的块，同样按需补取；retry 不为等待全部 KV 到齐而推迟启动。

**正确性。** AegisKV 只决定备份位置与装载顺序，不改变稀疏选择器的输出；补取保证所需块在注意力执行前到齐。因此恢复后的 KV 与在同一前缀上重算得到的 KV 一致（同一权重与 kernel），请求的后续输出与无故障执行在数值上等价，差别只来自批次组成引起的浮点顺序差异，这与任何基于重算的恢复相同（R5）。

### 3.6 讨论

**Slack 估计误差。** 在线 Slack 可能过于乐观（把关键请求放入 Tier R）或过于悲观（把过多请求放入 Tier P）。AegisKV 用 P90 持续时间、阈值滞回、未知后继按 $\sigma=0$ 处理与事件触发的重新规划限制其后果。乐观误差的代价是 Tier R 请求没有副本，只能完整重算并暴露给 WCT；空闲时可以机会式地把 Tier R 请求复制到 DRAM，但只有已提交的副本提供这一保障。悲观误差不改变足迹，只让更多请求排队竞争 $B$，Slack 最小的请求仍然先得到 Peer。§5.6 量化 Slack 误差的影响。

**身份陈旧与校准表漂移。** 热集身份来自前一个排名窗口，与恢复时的实际需求之间存在时间差；图 8 度量的正是这种陈旧预测的覆盖质量，滞回把身份抖动限制在窗口边界。$K_l$ 表由轨迹校准并按小时级滑动平均更新：负载的选择模式漂移时地板与足迹随之缓慢修正，不会在窗口之间跳变。默认排名窗口为 512 个解码步，表中并集比例按与尾长相同的窗口统计（默认 64 步）；§5.6 扫描窗口长度与表的过时程度。

**对不同稀疏选择器的适用性。** 接入条件是能观察选择索引、恢复选择器状态与全部必需的注意力分支，并按模型校准成本。InfLLM-v2 与 NOSA 输出块索引；DSA 输出 token 索引，需要映射到实际复制的块，分散的 token 会放大块级传输；NSA 的压缩分支与局部分支也必须备份，不能只保护 Top-k 分支。选择器元数据的体积与驻留代价按实现核算。AegisKV 依赖真实索引与块并集，不依赖 $k$ 固定或随上下文增长的特定规律；当热度不稳定或复制粒度不匹配时退化为逐层完整装载，Slack 分层仍然适用。稠密注意力下 $h=\tilde u=1$，$K_l$ 退化为整层，请求内只剩层序这一维（图 9 中 16 层、512 MiB 的足迹）。无工作流的独立请求取 $\sigma=0$，按稳定 ID 打破并列，恢复仍然并行。

**更快的恢复路径与张量并行。** 更高的有效 H2D 带宽降低 $D$，足迹 $F^\star=\beta hD+(N-1)[\beta hD-\beta C]^+$ 中只有第一项与带宽无关（它就是一层热集的字节），第二项随 $\beta$ 增大迅速消失：32K 历史在 25 GB/s 下只需 1 层、21 MiB。若 DRAM 恢复已能被 Slack 吸收，则不需要 Peer HBM。Peer 副本不能消除固定检测开销、纯重放时间与补取地板，因此即使 $\sigma=0$ 的请求也只在 $W_0-W_{floor}$ 范围内受益。张量并行下，一个 TP 组是"GPU $g$"的单位，Retry DP 是另一个 TP 组，每层字节按分片计算。§5.6 的带宽扫描覆盖 PCIe、远端池与高速 CPU–GPU 互连的场景。

**局限。** 图 6、图 8 与 §3.3 的恢复参数来自书籍文本的轨迹；agent 负载中的代码与工具输出可能呈现不同的选择模式，访问集中度、并集比例与恢复收益需要在 agent 轨迹和不同选择预算下重新校准。所需并集的占比不保证随上下文增长而下降，64K 以上的足迹外推沿用了 32K 的并集比例。NOSA-1B 画像借用 MiniCPM4-8B 的层数、每层字节与重计算代价，只用于对比装载比例的影响。prefill 阶段的故障可能丢失整个在途 chunk，其重算代价需按实际后缀长度校准，不能沿用 64-token 尾部的估计。
