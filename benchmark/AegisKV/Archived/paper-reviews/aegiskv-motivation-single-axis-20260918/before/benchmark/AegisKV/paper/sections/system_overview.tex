\subsection{System Overview}
\label{sec:system-overview}

Figure~\ref{fig:system-overview} separates applications, control, and
inference engines. Applications report request/workflow IDs and DAG
updates. The Router dispatches by load and locality; the AegisKV
Controller owns slack, placement, and recovery decisions. Each DP has
an Adapter and Connector; KV moves directly between engines and
storage. Badges index the mechanisms below, not execution order.

Peer destinations are assigned \emph{before} failure so takeover reads
the replica locally, e.g., $p(g)=(g+1)\bmod n$ for $n\ge2$ DPs.
A TP group restores compatible shards as one DP. Distributing requests
over several targets likewise requires assigning replicas in advance.
The Controller retains the KV directory and commit metadata outside
the source's failure domain. The Planner refreshes every 1\,s or on
significant request/slack events; static profiles size hot sets, while
Adapter counters update their identities.
