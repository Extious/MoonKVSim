# AegisKV 论文方法决策：Slack 与恢复等待共同决定分层备份

2026-09-13。本文是方法建议，未修改执行器、租金算法或论文正文，未启动硬件测量或性能实验。

**建议主线：精确恢复；以 Slack 映射 Workflow 损失，以真实恢复流水估计 HBM 的边际收益，自适应选择每个请求在固定接管 DP 上的驻留深度。** 原生稀疏的动态选段保留为扩展；租金作为在线维护策略及消融，不承担发现 KV 价值的职责。

依据是本次实际读取的两个任务：

- [Query tile 与逐 query 选块](codex://threads/01a08ef4-e86b-73a1-80ba-c3f1a3d553b8)。结论是 kernel 的批处理不意味着 query 共享选块；稀疏恢复必须考虑需求并集、因果可见性和辅助状态。
- [每层 Prefill/H2D 与驻留层数收益](codex://threads/01a08ef3-1763-7681-8419-f1287ffe5ae6)。最后一次回答比较了严格下一层预取与从起点连续预取，明确收益是等待减少，计算量不变。

两者提供的是模型机制与解析论证，尚未证明某种在线备份方法能够改善实际故障 WCT。

**两个探索对选题的影响**

| 探索结果 | 方法决策 |
|---|---|
| DRAM 副本也能避免已有前缀重算 | 比较 HBM 放置时固定有效备份覆盖；HBM 只领取它额外消除的等待收益 |
| DRAM 基线已经可以逐层预取 | 不把共同的 overlap 全部计为 HBM 驻留贡献；以优化后的 DRAM 恢复为基线 |
| C≥D 时，首层之后可能很快饱和 | 一个请求不应仅因为 Slack 小就不断获得更多 HBM |
| D≫C 时，多存层继续有收益 | 不预设少量 KV 必然覆盖大部分收益；允许请求需要较深驻留 |
| 不同 query 可以选择不同历史块 | 单 query 稀疏率不能作为整个恢复过程的 HBM 覆盖率 |
| 逐层预取、按计算/传输关系划分状态已有先例 | 论文贡献应集中于故障 WCT 目标下的跨请求分配及其在线实现 |

分层预加载与首层启动等待已有 [CachedAttention §3.2.1、Figure 6–7](https://www.usenix.org/system/files/atc24-gao-bin-cost.pdf#page=6) 的直接机制支撑。[LayerKV §3.1.1–3.1.2](https://arxiv.org/html/2410.00428v3) 已研究驻留层数、分层管理和异步 offload；[HCache §4.1](https://chenyoumin1993.github.io/papers/eurosys25-hcache.pdf) 已按计算与传输关系划分恢复方式。[DéjàVu](https://proceedings.mlr.press/v235/strati24a.html) 已提供 KV 状态复制容错。因此不能把单独的“KV 备份”“逐层 overlap”或“根据 C/D 调层数”作为尚无人研究的贡献。本次核对也不是穷尽性的新颖性检索。

**系统合同与两个不同的分配量**

Router 预先指定接管 DP；备份 Peer 就是该 DP。其 HBM 中兼容、已提交的 KV 可以直接读取，不额外添加故障时 Peer 到第三张 GPU 的复制。其余有效状态在故障域之外可访问的 DRAM，恢复方向为 H2D。

每个请求分别维护：

1. 有效恢复覆盖 M：跨 HBM 与 DRAM 的联合状态能恢复多新的逻辑进度。第一版采用所有必要层和分片均已提交的连续 token 前缀；缺失部分按依赖重建。未完成 Prefill 层的零散 KV 不自动等于可续算的隐藏状态检查点。
2. HBM 驻留深度 k：上述相同历史状态中，前 k 层在接管 DP 上预先就绪，其余层在 DRAM。物理对象可采用 `(request, layer, token_block, shard)`；第一版策略按完整层集合配置，暂不为同层等路径、等大小的 token 块制造语义差异。

M 决定避免多少状态重建，k 决定还需暴露多少装入等待。这两个量应分别核算。HBM-only 的有效副本降级时，需要完成 DRAM 提交再释放；已有有效 DRAM 副本则无需重复保存。主对照固定 M，避免把更鲜的备份带来的补算减少混入 HBM 放置收益。

前 k 层是一个容易解释和实现的候选族，不是异构层、异构路径和受限预取下的普遍最优定理。第一版无需解决任意 `(layer, token)` 子集优化。若真实执行中层间不均匀性显著，再用同一恢复时间估值接口比较其他合法放置方案。

**每个请求维护一条容量—恢复损失曲线**

在当前逻辑进度，用已知输入、已提交输出游标、备份提交进度及接管端资源状态，估计若现在失败需要执行的恢复计划。令：

- M：已有有效历史 KV 的 token 数；
- N：重试仍需前向的 token 数；其中可能包含故障丢失后的补算，也可能包含正常情况下尚未处理的输入；
- C_l：该实际执行批次在第 l 层的完整前向耗时；
- D_l：该层尚未驻留的历史 KV 的 H2D 耗时。

恢复计划显式包含复制、计算、就绪依赖、可用缓冲及目标端排队。不能把完整前缀重新 Prefill 的耗时当作可用于 overlap 的窗口。Prefill 分块执行时，也不能使用整个剩余输入的总计算时间替代实际一批的窗口。接近完整提交的 Decode 恢复可能只有很少的补算，须单独估计，不能外推大 N 的 FLOPs 模型。

简化事件递推为 `F_l = max(F_(l-1), A_l) + C_l`，A_l 是相应 KV 的实际就绪时刻。真实执行器可把等待门放在 attention 前并允许 QKV 投影提前执行；上述整层门模型只用于初始分析。

对于 L 层等时、单一串行复制流、传输与计算无相互减速、空间充足的模型，令单层计算为 C、单层全历史传输为 D，并令 `W = D + (L-1) max(D-C, 0)`。当 DRAM 在时间零开始依次预取未驻留层时：

```
T(0) = LC + W
B(k) = T(0) - T(k) = min(kD, W),  0 <= k <= L
```

若执行器严格只预取下一层，则 `B(k) = D + (k-1) max(D-C,0)`，适用于 k≥1；不能混用两种预取语义。推导及独立事件递推见[已有解析说明](/home/comp/zhanzhao/MoonKVSim/output/pdf/hbm-layer-benefit-20260913/README.md:21)。这些是解析结果，不是设备时延。

此处两个边界对论文尤其重要：

- C≥D：一层可以消除全部 W，但 W 只有 D。36 层、C=2 ms、D=1 ms 的假设例子只是 73→72 ms。捕获全部可消除等待与显著降低总 WCT 是两个不同命题。
- D≫C：W 接近 LD，B(k) 接近 kD。高收益可能需要较大的 HBM 比例，此时不能声称普遍的少量高价值块集中性。

正常备份越新，N 可能越小，可重叠窗口随之变短；这是值得验证的阶段变化，不应把它预先写成已观察事实。目标端排队期间若 DRAM 能提前装入，HBM 的额外收益还会降低。预取空间与故障接管后的完整工作集均须计入容量，备份起点只驻留少数层不代表恢复只需要那些层的显存。

**通过 Slack 把恢复收益换算为分配优先级**

令 R_r(k,t) 为请求 r 在当前状态发生故障后，驻留前 k 层所导致的额外延迟估计；其对照是同一逻辑状态的无故障执行。R 不是整个剩余请求执行时长，上述 T 是恢复流水中的一个时间段，只有正确扣除正常还需执行的工作后才能映射到 R。

令 s_r(t) 为已有的 Slack 估计，定义局部 Workflow 损失代理：

```
J_r(k,t) = max(R_r(k,t) - s_r(t), 0)
G_r(k -> k',t) = J_r(k,t) - J_r(k',t)
P_r(k -> k',t) = G_r(k -> k',t) / [HBM_bytes_r(k') - HBM_bytes_r(k)]
```

第一版在每个请求的合法驻留层数中，按下一次增加所带来的边际 G/byte 分配 HBM；收益饱和或已被 Slack 吸收就停止追加。允许不分配 HBM。一个很紧急但已饱和的请求不应继续压过尚有暴露收益的另一请求。同层块可以平局，无需为每块构造不同分数。

对撤销已有驻留，使用 `J_r(k-1)-J_r(k)` 这样的当前撤销损失；一般对象集合使用 `J(S\{x})-J(S)`，不能把向 S 添加已存在 x 的零增益当作保留价值。扩展到共享物理块或同时调整多个请求时，重新评估受影响集合，不能直接相加陈旧单块分数。

上述逐增量分配是一种工程算法建议；不同层大小、共享副本、拥堵与故障相关性存在时，不宣称贪心最优或继承 Landlord 的竞争比。小规模离线穷举/动态规划可用于检查候选族中的最优性差距。J 是单分支扰动下的局部代理；同一 GPU 失败会影响多个请求，最终指标应在实际故障事件及完整 Workflow 上计算，不能把多个 J 的和称作精确 WCT。

只有当前可观测的状态可以进入在线估值。未来故障位置或恢复后选块轨迹仅能用于离线参考上界，不能提前泄露给在线策略。

**租金应承担的职责**

建议先建立“显式价值更新 + 有限的迁移迟滞”的可解释版本，再保留租金版本对比。租金可表达资源持续被占用、旧租约逐渐失去保留资格，以及容量竞争；它本身不能感知 Slack、N、D_l 或接管队列变化。

Slack 更新、复制提交、请求阶段/逻辑进度变化、接管端负载或可借容量变化时，应使相关曲线失效并重估。价值上升必须能触发重新竞争，包括已被降级的候选；仅刷新待淘汰堆顶不够。估值更新与实际续租必须分开：重新估值不自动补回已经支付的租金。

若沿用当前 all-block-rent 设计，保留“全部仍占用资源的已提交备份支付租金；Q 仅限制安全淘汰资格”。不能因为某块刚进入 Q 就重发信用，也不能因前台额度下降便视为物理内存已释放。共享块的其他 Agent 份额不应因一个 Agent 的请求自动续租。

迟滞只控制不必要的升降级，不允许掩盖已经明显变化的恢复价值；阈值必须结合迁移字节、预计驻留时间或正常服务干扰，不能无单位地把迁移毫秒与“可能发生故障的收益毫秒”直接相减。第一版不需要未经支撑的逐请求故障概率模型，可明确采用 fail-now 价值作为分配代理。

**原生稀疏如何保留**

[NSA §3.4](https://arxiv.org/html/2502.11089v1#S3.SS4) 明确说明连续 query 可需要不相交的块；其 kernel 的共享单位是同一个 token 的 GQA query heads。因而小的逐 query 选择集，不能证明跨 query、层、组和恢复窗口的物理需求并集也小。

若后续验证表明故障前可观测的信息可以预测恢复中的阻塞读取，再把候选单位从整层集合扩展到具体块，用相同 J 的下降定价。原生选择仍在完整逻辑历史上进行，选到 DRAM 状态必须补载，压缩、indexer、窗口等状态均计费。主要指标是未被隐藏的等待，不是 attention 分数、累计访问次数或逻辑命中率。

当前不把这条路线作为主方法的必要条件，避免论文同时依赖特殊模型、访问预测、细粒度恢复执行器与足够大的 WCT 收益四项未证实前提。

**论文成立所需的最小证据**

先在方法层明确目标，再按条件推进验证。当前用户没有硬件和测量时间，本次仅整理可核对的分析与计划。

| 比较或观测 | 要回答的问题 |
|---|---|
| 同一有效覆盖下的优化 DRAM-only：逐层预取，允许可用排队窗口提前装入 | 还剩多少 HBM 能消除的等待？ |
| 固定首层、固定层数/比例、等预算按请求集中放置 | 自适应驻留深度是否优于简单规则？ |
| Slack 开/关 × 自适应驻留开/关 | 请求紧迫性与恢复收益曲线各贡献什么，组合是否有额外价值？ |
| 即时重排、重排加迟滞、租金版本 | 租金是否改善迁移量和正常干扰，并保留故障收益？ |
| 同一 Workflow/Agent、相同逻辑故障进度下的 F1−F0 | 等待减少是否传递到 WCT，还是被 Slack 或其他分支吸收？ |
| Prefill/Decode 进度、M/N、C/D、目标队列、带宽、备份预算变化 | 收益范围及反转条件是什么？ |

F0 为无故障对照，F1 为目标故障运行。分别报告恢复等待、补算量、首个可提交输出、故障引起的 WCT 增量以及无故障开销。以故障事件和完整运行为适当统计单位，不把共享故障中的请求视为独立重复。按实际场景检查多请求同时接管及缓存容量，而非只验证孤立的一条时间线。

“少量 HBM 获取大部分剩余等待收益”与“显著降低用户 WCT”应分别给证据。若在优化后的 DRAM 基线上，等待已大多被隐藏，或其量级远小于 Slack/其他恢复成本，应如实收窄 HBM 的贡献。可以保留跨请求保护与已提交覆盖的研究主线，但需要重新证明其价值；不能靠选择低效 DRAM 对照或未经验证的稀疏热块假设维持性能主张。

推荐的论文问题表述是：**在故障恢复代价与 Workflow Slack 随执行变化时，如何把有限备份容量分配给能够减少终点延迟的请求状态，并避免把昂贵的 Peer HBM 分配给已经能被计算或 Slack 隐藏的恢复工作？**
