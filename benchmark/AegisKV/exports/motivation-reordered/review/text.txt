AegisKV: Background, Motivation, and System Design
Anonymous Author(s)
Abstract
Multi-agent applications coordinate interdependent LLM
requests and accumulate long contexts across interactions.
Recovering lost or unavailable key–value (KV) state can
be costly, but its impact on workflow completion depends
on each request’s delay tolerance. We present AegisKV, a
workflow-aware KV fault-tolerance framework built on mul-
tilevel storage. AegisKV derives request slack from work-
flow dependencies and estimated remaining execution time,
then combines slack with recovery costs to choose protec-
tion levels and allocate limited backup resources. Within
each request, sparse-attention access patterns and layer ex-
ecution order guide KV block placement and recovery. By
coordinating request-level protection with block-level place-
ment, AegisKV focuses limited backup resources on reduc-
ing recovery delays that affect workflow completion. The
design separates fault-safe KV availability from limited Peer-
HBM residency, allowing request-local hot-set replacement
and capacity-driven demotion without changing the model’s
sparse selections. Native selection traces and a pipeline model
using measured forward latency and assumed transfer band-
width motivate these mechanisms; end-to-end workflow ben-
efits and normal-service overhead remain to be evaluated.

Background and Motivation
2.1
Background
Multi-agent workflows. Multi-agent workflows are be-
coming an important form of LLM application, including
coding assistants and research systems [1, 17]. An agent may
have a predefined role, such as a planner or reviewer, or be
instantiated as a subagent to complete a particular subtask.
Each agent may issue several LLM requests, invoke tools, and
incorporate their results before producing its output. These
interactions form a workflow with sequential dependencies,
parallel branches, and joins. Multiple requests using the same
role may share a compatible prompt prefix, while successive
tool interactions extend an individual agent’s history. Thus,
a request, an agent, and the complete user workflow describe
different units of execution and completion.
Failures at serving scale. LLM services distribute re-
quests across many GPU workers, with each model replica
potentially spanning several devices. As deployments grow,
failures become an operational concern even when individ-
ual devices are reliable: an unavailable device can interrupt
an entire replica and shift its work to the surviving fleet [2].
The interruption loses both serving capacity and access to the
failed worker’s GPU-resident KV cache. Recovery therefore
requires more than rerouting a request; it must also supply
the state needed to resume computation. KV replication and
checkpointing systems already address this state-recovery
problem [2, 6, 16]. We focus on fail-stop GPU/worker failures
with a compatible surviving replica, retained token history
and control state, and surviving backup storage. Under this
scope, the application-level consequences of the interruption
depend on both its workflow position and its recovery cost.
2.2
Motivation
Workflow completion requires different protection pri-
orities. The user waits for the complete task, so we use work-
flow completion time (WCT), from task release to completion
of all required results, as the primary objective. Minimizing
an individual request’s or agent’s completion time alone
does not capture the effect of its dependencies. Figure 1(a)
illustrates this distinction with a four-branch coding work-
flow. A2 completes last, 151.6 s after the fork, whereas A1
completes at 60.4 s. If the following Main stage needs all four
outputs, accelerating A1 alone does not advance the join,
while delaying A2 postpones downstream work. The same
distinction matters for fault protection: branches differ in
how much additional delay they can absorb. We call this
tolerance slack.
To characterize this heterogeneity beyond one example,
we analyze the public SemiAnalysis CC/Weka dataset col-
lected from Claude Code coding workflows [14]. Its filtered
release contains 393 sessions. We retain overlapping sub-
agent groups whose branches complete and are followed by
a Main request after the last branch finishes; Main may also
execute while the branches run. This yields 286 groups in 121
workflows. For each group, we compute the longest minus
the shortest branch duration; each workflow contributes its
maximum such difference. Figure 1(b) shows a median of
138 s and a 90th percentile of 1,173 s. These statistics show
branch-duration heterogeneity among workflow maxima.
The trace lacks explicit result-consumption edges, so fan-in
is inferred from timing and the gaps are not a distribution
of slack at failure time. The example and distribution to-
gether motivate assigning protection priorities according
to workflow impact, rather than treating all agent requests
equally.
Growing contexts make KV reconstruction increas-
ingly costly. An agent’s later requests often include earlier
reasoning, code, tool outputs, and other agents’ results. With-
out context reduction, this history grows across interactions.
KV caching avoids repeatedly processing that history during
normal execution. If a failure makes the active KV unavail-
able and no usable copy survives, recovery must rebuild
the missing state before continuing; longer histories can

These observations lead to AegisKV: a workflow-aware
KV protection system that allocates limited recovery state
according to its effect on WCT. The design connects request-
level delay tolerance to the recovery value of that request’s
KV, while accounting for the HBM, DRAM, and bandwidth
consumed by protection. Existing valid cache copies remain
usable for recovery; additional protection must justify its
cost to normal serving. The next section develops the corre-
sponding protection, placement, and recovery mechanisms.
3
AegisKV Design
AegisKV combines workflow delay tolerance with each re-
quest’s KV recovery demand. The Tracker estimates slack;
the Recovery Manager binds takeover destinations at arrival;
the KV Master chooses backup tiers, per-request layer depths,
and hot blocks at backup-policy events. The checkpoint in-
terval is configured, while Adapters update target-local Peer
budgets at window boundaries. The following design sepa-
rates these decisions from the evidence that motivates them.
3.1
Insights and Design Implications
Three premises motivate the design (Figure 3). The first
draws on published agent-prediction results; the other two
characterize selected sparse-attention releases and recovery
demand.
Insight 1: execution context predicts remaining agent
work. Existing predictors exploit task semantics and exe-
cution progress. Heddle [21] reports trajectory-length cor-
relations of approximately 0.72, 0.88, and 0.94 for coding,
search, and math agents after two steps, improving over
one-step predictions (Figure 3(a)). AgentDecarbonizer [18]
additionally estimates task durations and updates remain-
ing time from observed progress. AegisKV builds on these
capabilities: the Tracker converts remaining-time estimates
into workflow slack for KV protection. Trajectory corre-
lation supports predictability; runtime calibration remains
deployment-specific.
Insight 2: sparse attention changes the recovery ob-
jects. Long-context models use sparse mechanisms includ-
ing InfLLMv2, DSA, or compressed/hybrid attention [3–5,
8, 9, 11–13, 19, 20]. Figure 3(b) establishes release examples,
not deployment share. The KV Master therefore consumes
actual layer/block selections and model-specific recovery
state instead of valuing all KV bytes equally.
Insight 3: past selections predict part of retry demand.
With 40% of each model’s historical KV bytes, historical fre-
quency covers 77.8%, 53.6%, and 43.0% of distinct needed
KV for NOSA-3B, MiniCPM4-8B, and SeerAttention-Qwen3-
8B, versus 59.7%, 50.9%, and 42.0% for recency (Figure 3(c)).
Seer’s demand spans 92.5% of historical blocks after the head
union, limiting even oracle placement to 43.3% coverage.
Thus gains depend on the model and placement granularity.
These held-out book-text suffixes motivate advance place-
ment with exact demand fetches for misses; they do not
establish performance on agentic failure retries.
3.2
System Overview
Figure 4 separates applications, control, and inference en-
gines. Applications report request/workflow IDs and DAG
updates. The Router dispatches by load and locality; the
AegisKV Controller owns slack, recovery assignments, and
backup policy. KV Master sets each request’s depth and hot
blocks at checkpoints or policy changes. Each Adapter man-
ages its local Peer budget and invokes a Connector to copy
KV directly between engines and storage. Badges index the
mechanisms below, not execution order.
The Recovery Manager binds retry and Peer targets at
arrival (§3.4). KV Master uses a fixed checkpoint interval
and reviews each request’s depth at policy events (§3.5).
Adapters update budgets at window boundaries (§3.6). The
Controller retains directory and commit metadata outside
the source’s failure domain.

3.4
Recovery Manager: Preassigned Takeover
Recovery Manager (2) decides where each request will re-
sume before failure occurs. When request 𝑟arrives and the
Router selects source DP rank 𝑔𝑟, the Manager records a tar-
get assignment 𝑝𝑟≠𝑔𝑟in control state outside the source’s
failure domain. The same 𝑝𝑟is both the retry destination and
the DP rank that will hold any Peer-HBM backup of 𝑟. A sim-
ple mapping for𝑛≥2 DPs is 𝑝𝑟= (𝑔𝑟+1) mod 𝑛; per-request
assignments may distribute load across several targets. The
assignment does not reserve HBM: the KV Master chooses
whether to request Peer protection, and the target Adapter
controls its capacity. A TP group restores compatible shards
as one DP.
Activate the recorded route after failure. The Man-
ager combines membership, device errors, and GPU progress
reported by Adapters; a process heartbeat alone does not
prove GPU progress. After confirming and isolating a failed
source, it obtains request token prefixes, commit frontiers,
model/layout IDs, and replica locations from surviving con-
trol state, then submits retries to their recorded targets. Avail-
able Peer replicas are therefore local to takeover. DRAM or
recomputation supplies the remaining state. Control-state
survival, fencing, failure-domain separation, and retry dedu-
plication are runtime contracts. A failed target requires a
new valid assignment; copies on the old target cannot be
treated as local to the new target.
Recover a dependency-closed frontier. A surviving au-
thority assigns a monotonically increasing source epoch;
copies, directory commits, and output acknowledgements
reject stale epochs. Before acknowledging a generated to-
ken, persist its request ID, position, token ID, and epoch in
a surviving ordered log. Prompt and accepted tool inputs
are likewise recoverable. KV may lag this log; recovery re-
constructs the acknowledged suffix and suppresses duplicate
delivery. External tool side effects require the orchestrator’s
own idempotency contract.
Publish a checkpoint manifest only after its full depen-
dency closure is committed: compatible model, weights and
layout, all required layers and TP shards, sealed token in-
tervals, selector state, and the matching token-log prefix. A
frontier is the latest valid common manifest, not the maxi-
mum of independently updated object locations. Peer and
DRAM may commit in either order; each manifest entry
must resolve to a matching surviving replica. An incomplete
new manifest leaves the older one authoritative; without one,
replay from recoverable inputs. Recovery validates versions
and closure again after fencing. These checks define the min-
imum contract; their concurrent implementation remains to
be validated.
Share resources without serializing retries. Retries en-
ter independently and advance on their own layer-readiness
events. Slack determines protection, not a request-level com-
pletion barrier. The engine reserves a positive dispatch share
for feasible recovery work while continuing foreground
batching. Within that share, ready admitted retries receive
round-robin service in bounded prefill chunks or decode
steps; eligible waiting retries use oldest-first admission sub-
ject to physical space. Blocked layers yield rather than hold-
ing a request-level barrier. These are required scheduler in-
terfaces, not a claim of support in an unmodified engine.
Each retry moves through waiting-for-space, waiting-for-
data, ready, and running states. Reserve its bounded activa-
tion/KV workspace and transfer buffers before admitting an
execution chunk. The batch coordinator admits compatible
ready work and gives every TP rank the same batch, layer,
and collective order. A newly discovered miss parks that
work only at a legal kernel boundary, retaining and charging
its activation buffer; it can split from a batch only if the back-
end supports that split. Otherwise the whole batch waits
and the profile charges the resulting interference. Readiness
does not authorize arbitrary layer reordering or unmatched
collectives. Memory reservations precede I/O leases; release
queue/directory locks before waiting on a copy or collective,
and reserve demand-transfer progress space. Preassignment
reserves neither compute nor retry workspace. Profiles in-
clude target foreground batches, available KV/workspace,
readmission queues, shared links and failure domains. If the

3.5
KV Master: Request-Specific Backup Decisions
KV Master (3) selects recovery tiers, each request’s Peer
depth 𝐿𝑟, and layer-local hot sets. Recovery Manager fixes
the retry/Peer target; Adapter publishes its window-level
capacity 𝐵𝑝. Requests may use different depths within the
same capacity window.
Decision events. The Master establishes policy at arrival,
offers sealed state after prefill, and reviews a request every
additional 𝑍generated tokens. 𝑍is a block-aligned system
configuration, not an Adapter output. Significant slack, bud-
get, context, or copy-state changes can trigger an earlier
review. A decision does not imply a completed checkpoint:
the replay tail extends beyond the latest committed frontier
and can exceed 𝑍when copying lags. Copy queues have
configured byte and operation limits. Coalesce superseded
unstarted plans, retain dependencies of in-flight or commit-
ted versions, and skip a new backup attempt if it cannot
be reserved. Report the resulting commit lag; the trigger
interval supplies no durability bound. Sealing only updates
eligibility. Hot-block statistics use the preceding 512 decode
steps, independently of checkpoint and capacity windows.

Adapter: Windowed Peer Capacity Control
Adapter (4) sets the total Peer budget 𝐵𝑝on its target DP
at each control-window boundary. The target remains fixed
within the window; every allocation also checks physical
space. The Master owns fixed-𝑍backup decisions and per-
request 𝐿𝑟and hot sets. Adapter controls capacity, not a
common depth or an adaptive checkpoint interval.
Reserve memory for foreground inference. Subtract pre-
dicted foreground KV demand and admission headroom from
the managed KV pool, clamping the result to zero through
half the pool. The pool excludes weights and fixed runtime
state but includes existing Peer copies; 𝐵𝑝is total permitted
occupancy, not newly available space. KV watermarks and
memory-related admission stalls inform demand. Increased
pressure shrinks the budget; sustained relief allows expan-
sion. Report physical occupancy, ownership references, I/O
leases, pending copies, and safely reclaimable bytes sepa-
rately.
The migration steps are asynchronous and continue af-
ter the control tick; a later budget update reconciles their
outstanding reservations. Algorithm 3 does not wait for all
migrations before allowing unrelated ready requests to run.
Admit DRAM protection explicitly. Each backing pool
has a finite byte ledger charging committed objects, pend-
ing reservations, retiring buffers, and required metadata.
Shared objects are charged once. Reserve the missing depen-
dency closure before accepting a checkpoint; publish only
completed coverage. Live checkpoint and reader references
protect DRAM objects; zero-reference objects enter LRU
reclamation, with physical release delayed until I/O leases
drain. Newer valid manifests, request completion, or an ex-
plicit transition to recomputation release obsolete ownership.
An old manifest remains retained until its replacement is

committed or its recovery claim is withdrawn. If reservation
or commit fails, keep the earlier valid frontier and replay
its missing suffix, or use R from logged inputs. A Peer de-
nial does not imply DRAM admission, and partial copies
do not establish full D protection. DRAM exhaustion is an
operational limit, not hidden unlimited backing.
Protect ownership, not a permanent HBM address. A
request reference prevents other requests from taking its Peer
capacity, even when they have smaller slack. Normal ad-
mission uses free space or safely reclaimable zero-reference
copies; otherwise the new Peer increment is denied. An in-
ference request need not wait to obtain Peer protection. The
owner can replace its own hot set or reduce its depth. Com-
pletion, including a handoff to a tool, drops that request’s
references, while other owners of shared blocks retain theirs.
These ownership references differ from short-lived I/O
leases. A lease pins the physical buffer while a kernel, read,
or copy uses it. An owner update removes only its own
reference and cannot free a shared copy still protected by
another owner. Adapter contraction has explicit system-level
authority to demote even protected copies; it never overrides
an outstanding I/O lease or deletes the logical KV state.
Demote through a committed DRAM copy. The Con-
nector and directory expose four operations: reserve space,
commit a versioned replica, acquire/release an I/O lease, and
retire a location. A block ID includes model/weights/layout,
request-prefix identity, layer, shard, and sealed token in-
terval; a location generation prevents reuse of a stale ad-
dress. A pending copy is never readable. A checkpoint fron-
tier advances only when its required shards, layers, selector
state, and token log are recoverable in the declared failure
model. Independent Peer and DRAM transfers do not imply
an atomic joint commit.
Retiring a Peer location follows the same order for an
owner update and an Adapter contraction:
1. Reserve DRAM if needed, copy the immutable block,
and commit a complete matching replica outside the
failed source’s domain. A valid existing DRAM replica
avoids another writeback.
2. Atomically redirect the directory to DRAM and mark
the old Peer generation retiring. This transition closes
new lease acquisition on that address; a lookup racing
the transition must retry.
3. Wait for all old-generation readers, writers, and DMA
operations to release their leases. Existing holders may
finish; no fresh holder can enter through a cached stale
address.
4. Free the Peer buffer and then return its bytes to the
allocator.
Before the directory transition, an unsuccessful writeback
leaves the surviving Peer location authoritative; afterward
new readers resolve DRAM. If DRAM allocation, transfer,
or commit fails, retain the Peer copy and report the unful-
filled shrink. Fault detection fences stale writers and retries;
directory generations and metadata survive the source fail-
ure. These are required runtime interfaces, not claims of a
verified implementation.
Bound replacement and contraction. For old and new
hot sets, retain their intersection, retire departing owned
blocks, and fetch only new arrivals. With no spare space, safe
retirement precedes admission; overlapping copies require
explicit temporary reservations. Thus changing {𝐴, 𝐵,𝐶, 𝐷}
to {𝐶, 𝐷, 𝐸, 𝐹} can retain four blocks after migration, without
pinning every historical hot set until request completion.
Shared replicas and incomplete transfers remain separately
charged until physically releasable.
When occupancy exceeds a new 𝐵𝑝, stop new Peer reser-
vations and reclaim zero-reference copies first. If insufficient,
Adapter requests protected demotions in the Master’s order:
larger slack first, then deeper layer, lower recent selection
count, and stable object ID. A shared object’s priority uses
the smallest slack of its remaining owners. This ordering
chooses victims; it does not serialize independent migra-
tions or retries. Publish the reduced coverage to the Master,
and do not re-admit it beyond the new budget. The Master
subsequently reassesses request-specific 𝐿𝑟.
Contraction waits for bounded transfers and leases, not
for the LLM request to finish. Actual usage may temporarily
exceed the target; foreground admission can still wait for
physical space if headroom is exhausted. The scheduler re-
serves progress for required writeback, and the controller
reports pending bytes rather than claiming an instantaneous
shrink. Insufficient backing capacity remains an explicit op-
erational limit.
Scope and validation. Sparse integration needs native
selection indices, recoverable selector state and all attention
branches, physical-block mapping, and the directory/ lease
interface above. Poor predictions can use exact demand fetch
or full-layer loading; dense attention uses the full historical
set. Standalone requests use zero slack. Prefill failures require
profiles for the lost chunk, not a universal 64-token tail.
The present evidence consists of native selection traces,
attributed prediction results, and a single-request pipeline
model using measured forward latency and assumed trans-
fer bandwidth. It does not validate the depth-score profiles,
failure-risk calibration, checkpoint sensitivity, active hot-set
migration, concurrent retry fairness, or foreground inter-
ference. End-to-end tests must include recovery during de-
motion, stale-location races, DRAM exhaustion, copy back-
logs, and shared bandwidth pressure. The specified inter-
faces and fallbacks make those claims testable; they do not
establish performance or a completed implementation. Val-
idation must also replay common source failures through
the dependency DAG, compare the local policy with fea-
sible small-DAG allocations, and report regret, including
