# AegisKV：跨 HBM、DRAM 与共享存储的工作流感知 KV 检查点

> 完整中文译稿，对应 [英文论文 main.pdf](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/main.pdf)。章节、图、公式、算法及参考文献编号与英文稿一致；图像沿用原图，正文和图注逐段翻译。

## 摘要

多 Agent 应用在执行相互依赖的 LLM 请求时会不断积累可复用的上下文。一个 worker 故障可能导致这些状态丢失，并同时延迟多个分支，而将所有上下文都保护在快速内存中的成本很高。我们提出 AegisKV，一种面向工作流的 KV checkpoint 管理系统，跨 Peer HBM、共享 DRAM 和共享存储管理状态。系统在 DRAM 或存储中保留完整 checkpoint，并在预先指定的接管 DP 上复制选定层与热块。AegisKV 分别评估 Peer 加速、完整 checkpoint 降级和最终淘汰的价值，将正常复用与恢复对工作流的影响相结合。它联合评估受同一次故障影响的请求，利用稀疏访问需求与层间重叠评估快速层驻留价值，并在有界决策开销和迁移阈值约束下，直接重新评估完整替换方案。带版本的状态转换在迁移和显式回退过程中保持恢复有效性。每个 DP 的 Adapter 限制 Peer 容量，Master 则为各请求选择层深度和热块，保持原生注意力语义不变。我们将从 trace 得到的工作流观察和已有的重建微基准，与可复现的分析研究及完整实验协议结合起来。在 36 个明确声明且禁用 Peer 的场景中，放置模型在 17 个场景中优于 LRU，在 19 个场景中与其持平。匹配条件的分析调度展示了 Peer 带来的额外重叠收益；这两类模型均不是对三层系统的实测。历史故障时序驱动一个独立的恢复负载模型，其中平均延迟下降与尾延迟恶化同时存在。机制消融揭示了层放置与重叠之间的交互，并考察了一种被否决的租金替代方案。本研究明确了资源竞争、预测误差和提交滞后何时会限制收益。要确立所提系统的性能，仍需端到端故障注入和正常服务测量。

## 1　引言

当多 Agent 应用的必要结果就绪时，应用才算完成：结果可能是经过测试的代码补丁、一份报告，或由并行搜索汇总而成的答案。因此，一个 LLM 请求的价值取决于它在工作流中的位置。关键分支上的延迟会推迟完成时间，另一个分支则可能在汇合前吸收这段延迟。面向应用的服务系统已在正常执行中利用这种结构[[17]](#ref-17)、[[22]](#ref-22)、[[27]](#ref-27)。故障提出了进一步的问题：当一个 worker 故障同时中断多个请求时，哪些历史应当保持快速可恢复？

长上下文使这一选择的成本变得高昂。Agent 会积累推理、代码和工具结果；丢失其驻留在 GPU 上的 KV 后，可能需要大量重建工作。Checkpoint 可以避免这些工作[[14]](#ref-14)、[[33]](#ref-33)，负载感知的恢复机制则将中断请求分配到不同位置[[4]](#ref-4)。分层缓存提供 DRAM 和存储容量[[28]](#ref-28)、[[34]](#ref-34)，但将每段历史都保留在较快层中的成本很高。

仅凭最近访问情况和恢复延迟无法决定放置。一段较长且最近使用过的历史，可能属于能够容忍存储访问延迟的分支，而较短的历史却可能位于关键路径上。较大的 slack 不能成为删除可复用历史的充分理由：后续正常调用可能反复重建该历史。同一 worker 的故障还会通过 DAG 和共享恢复资源耦合多个请求。只加速两个延迟分支中的一个，可能不会改变其汇合时间。最后，降级迁移是异步的：在存储层替代副本提交之前释放 DRAM，会使保护失效。

AegisKV 跨 Peer HBM、共享 DRAM 和共享存储管理 checkpoint。Tracker 估计工作流剩余时间；Master 在正常复用与共同故障域内的故障情景下比较完整方案。在 DRAM 或存储中的完整 checkpoint 基础上，因果稀疏访问需求与层间重叠指导逐请求的 Peer 层／块复制；直接价值重评则在有界决策开销和迁移阈值约束下比较当前替换方案。Router 在请求到达时绑定兼容的接管 DP；Adapter 限制 Peer 容量，Connector 执行安全传输。带版本的 manifest、资源预留和 reader lease 在完整 checkpoint 降级及 Peer 副本替换期间保持恢复有效性。

我们提出的贡献包括：一种区分 Peer 加速、完整 checkpoint 降级和最后副本删除的工作流目标；一个有界在线控制器和安全状态转换协议；以及具有匹配实机实验计划的可复现分析场景。模型展示了收益、持平结果、预测敏感性，以及相对于可行 oracle 的遗憾值。Trace 驱动的恢复模型和独立机制模型揭示了队列尾部退化，以及一种效果不利的租金替代方案。这些结果为所提系统提供动机并限定其适用范围，但并非对其实现的测量。核心经验假设是：在计入正常服务和迁移成本后，面向工作流的保护可以改善有限资源分配。

## 2　背景

**多 Agent 执行。**

随着 LLM 应用的发展，越来越多的任务需要通过多 Agent 协作完成。这些应用将用户任务划分为多个子任务，并分派给若干 Agent 并行执行。每个 Agent 维护自己的对话，通过 LLM 请求和工具调用推进任务：模型生成响应或发起工具调用，返回结果成为后续请求的输入。**请求**是一次模型调用；一个 **Agent** 可以发起多个请求以完成子任务；**工作流**则通过串行依赖、并行分支和汇合点连接这些任务。应用负责编排工作流，推理服务层负责执行模型请求。

[图 1](#fig-agent-workflow-examples)展示了这种结构。在代码生成中，主 Agent 将 CSV 导出功能分派给 API、UI、测试编写和文档 Agent。各分支并行执行，交替进行模型请求与文件读取、编辑或检查。主 Agent 随后集成修改并运行测试。在深度研究中，牵头 Agent 分派技术、成本、安全和供应调查，再将收集的证据综合为报告[[1]](#ref-1)。各分支需要的请求次数和工具调用次数可能不同。因此，一个模型请求完成后，其所属 Agent 和整个工作流都可能仍未完成。

![图 1](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/agent-workflow-examples.png)

**图 1：** 多 Agent 工作流示例。每行代表一个 Agent：$R_i$ 表示该 Agent 的第 $i$ 次 LLM 请求，中间的工具结果进入下一次请求。各分支的请求次数可能不同。协调者在各分支结果汇合后继续执行。

**工作流完成时间。**

令 $w$ 表示一个工作流，$a_w$ 表示该工作流到达系统的时刻，$c_w$ 表示其全部必要输出就绪的时刻。我们将工作流从到达到完成的总耗时定义为*工作流完成时间*（WCT），即 $\mathrm{WCT}_w=c_w-a_w$。它包括模型执行、工具执行、排队和依赖等待。在代码示例中，集成需要等待所有必要修改。最后一个未完成分支上的延迟会推迟集成，而较早完成的分支可能在汇合前吸收同样的延迟。请求延迟通过这些依赖关系影响 WCT。

**多 Agent 工作流中的 KV 复用。**

这些分支中的模型请求会反复使用先前步骤积累的上下文。代码 Agent 将源文件、修改记录和测试输出带入后续请求；研究 Agent 则不断积累检索文档、中间结论和工具结果。若每次请求都从头处理这些持续增长的历史，就会重复已经完成的计算。在*预填充*（Prefill）阶段，LLM 为输入 token 计算逐层 key 和 value（KV）；*解码*（Decode）随输出 token 的生成继续扩展这些状态。保留这些 KV 后，只要模型与位置语义兼容，具有匹配 token 前缀的后续请求就只需计算新增后缀[[11]](#ref-11)、[[41]](#ref-41)。

这种复用既发生在同一 Agent 内，也发生在不同 Agent 之间。同一 Agent 的连续请求可以复用共同对话历史的 KV；不同 Agent 则可以继承共同提示，再追加各自的任务。例如，[图 1](#fig-agent-workflow-examples)中的 API、UI 和测试 Agent 可以共享公共项目说明与代码仓库上下文的 KV，前提是这些内容构成相同的起始 token 序列。不同的角色提示或上下文修改可能缩短可复用的前缀[[41]](#ref-41)。

因此，KV 缓存是 Agent 执行或 LLM 推理请求过程中的重要中间状态。

**图 2：** 根据 InfiniteHBD 生产训练集群 trace 重建的 GPU 服务器可用数量[[32]](#ref-32)：以 400 台减去处于记录不可用区间内的服务器数。记录包括 GPU、网络、电源与散热以及软件故障，同时保留未知原因、测试、排障和变更记录。同一服务器的重叠区间合并，可用性按节点统计。

**故障与 KV 重建。**

这些复用收益依赖缓存状态持续可用。在大规模 LLM 部署中，硬件故障和软件崩溃可能中断 serving worker，并使其 GPU 中的 KV 不可用[[4]](#ref-4)、[[14]](#ref-14)。[图 2](#fig-gpu-server-availability)使用公开的 InfiniteHBD 训练集群 trace 提供生产集群背景：约 349 天内的 584 次不可用事件涉及 400 台 GPU 服务器中的 231 台，重建得到的可用服务器数量最低为 365 台[[32]](#ref-32)。该 trace 同时包含故障和运维中断，具体类别见图注。

如果没有可复用的 KV 存活，接管请求的 worker 就必须重放保留的 token 来重建这些状态，即使它已加载模型权重、应用也保留了对话历史[[33]](#ref-33)。对于长时间执行的 Agent，这意味着重新处理先前多轮请求积累的上下文，而不只是最新输入[[14]](#ref-14)。一个 worker 故障还可能同时中断多个部署在其上的 Agent，使存活 worker 在处理正常流量的同时重建多份历史[[4]](#ref-4)。这些延迟会通过工作流依赖传播：最后一个未完成分支上的重建会推迟汇合，并可能增加 WCT。

**跨存储层级备份 KV。**

为减少重建工作，*KV checkpoint* 保留已经计算完成的前缀。如果该前缀在故障后仍然可用，恢复时即可取回它，只重放尚未保存的尾部[[14]](#ref-14)、[[33]](#ref-33)。KV 可以保存在 GPU HBM、主机 DRAM 或共享存储中[[11]](#ref-11)、[[28]](#ref-28)。这些层级的存储成本与恢复延迟不同。HBM 访问快，但容量成本高，且备份会与前台推理竞争 GPU 内存；DRAM 和使用存储设备作为后端的共享服务可以提供更低成本的容量，但会增加读取延迟。

[图 3](#fig-motivation-recompute)展示重建历史与复用已保留 KV 之间的延迟差异。在 1,010,000 tokens 处，即使采用稀疏注意力，完整 Prefill 仍需 571.21 s；HBM、DRAM 和共享存储复用分别需要 1.305、2.663 和 10.156 s。该历史在两个 rank 上共占用 57.92 GB。所有路径均以同一输入的 KV 就绪为终点：复用路径在需要时取回已有历史，再计算一个新 token。可以看出，KV 复用能够大幅降低 KV 重建延迟。但存储本身存在成本，如何存储以及存储哪些 KV 已成为不可忽视的问题。

![图 3：KV 重建与复用成本](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/recovery-cost.png)

**图 3：** 在两张 A100 PCIe 40 GB GPU 上实测 Qwen2.5-7B-Instruct-1M 的 KV 重建与复用成本（TP2、BF16、batch 为 1），超过 32K 后使用稀疏注意力。完整 Prefill 从空 KV 开始；复用从 $(C-1)$ 个缓存 token 开始，再计算一个 token。KV 重建时间包括所需的读取与计算，直到全部 $C$ 个 token 的 KV 就绪。

## 3　动机与挑战

由此产生的管理问题是：应保留哪些 KV，并将其放在哪个层级。对于多 Agent 服务，这些决策的收益取决于保留的状态如何同时支持正常执行与故障后的工作流完成。现有容错服务与工作流感知的 KV 管理提供了有用机制，但各自的目标尚未解决这一联合决策问题。

**局限 1：容错机制缺少面向工作流的优先级。**

容错服务系统为中断请求保留状态并协调恢复。DéjàVu 流式传输 KV checkpoint，GhostServe 使用主机内存中的校验冗余减少重建工作[[33]](#ref-33)、[[14]](#ref-14)。LUMEN 进一步根据 worker 负载协调 checkpoint 放置、恢复路由和容量恢复[[4]](#ref-4)。这些机制处理了状态丢失与恢复竞争，但没有利用多 Agent 依赖关系，判断哪些请求更快恢复能够提前工作流完成。仅凭请求恢复成本和 worker 负载，无法表达这种收益。

[图 4(a)](#fig-motivation-workflow)说明工作流位置为何重要。A2 最晚完成，在 fork 后 151.6 s 结束，而 A1 在 60.4 s 结束。若后续 Main 阶段需要全部四个输出，A1 可以吸收 91.2 s 的额外延迟而不推迟汇合，A2 上的任何延迟则都会推迟汇合。这个例子来自 Claude Code trace[[31]](#ref-31)，其中的工作流与[图 1(a)](#fig-agent-workflow-examples)所示结构十分相似。我们把一个分支在不推迟必要输出的情况下能够吸收的额外延迟称为 *slack*。

并行执行的 Agent 在不同时间完成的情况，在多 Agent 应用中十分常见，而且时间差可能很大。我们分析 Claude Code trace[[31]](#ref-31)，并在[图 4(b)](#fig-motivation-branch-gap)中展示这种时间差。该图报告各工作流的最大分支时长差，即最长与最短分支的时长差在该工作流中的最大值，中位数为 138 s，90 分位数为 1,173 s。当 Main Agent 等待全部必要分支时，分支完成时间的差异可以为较短分支留下 slack。处于该 slack 范围内的额外延迟不会推迟汇合，也不会增加 WCT。

这些 slack 差异会影响故障后的 KV 重建如何延迟工作流完成。[图 4(c)](#fig-motivation-recovery-exposure)展示了使用稀疏注意力的 Qwen2.5-7B-Instruct-1M 完整 Prefill 实测重建时间[[29]](#ref-29)、[[15]](#ref-15)，及其对 WCT 的计算影响。我们分别考虑每个 Agent 的中断，保持其他执行不变，并假定 Main Agent 等待全部四个分支。A1 的 33.2 s 重建时间处于其 91.2 s slack 之内，因此 WCT 不变。相比之下，A2 没有 slack，其 32.6 s 重建会使 WCT 增加同样的时长。因此，相近的重建成本可能对工作流完成产生截然不同的影响。恢复优先级不仅应考虑请求的重建成本，还应考虑它在工作流中的位置。

**局限 2：工作流感知的 KV 管理没有考虑故障。**

工作流感知的服务系统已经在利用上述依赖关系，但目的是加速正常执行。一类工作把工作流结构交给调度器：Parrot 暴露请求间依赖以支持应用级调度[[17]](#ref-17)，Ayo 以原语级数据流图编排整个应用[[46]](#ref-46)，Autellix 和 SAGA 把整个 Agent 程序而非单次调用作为调度单位[[45]](#ref-45)、[[50]](#ref-50)，Cortex 和 Murakkab 据此池化并配置资源[[26]](#ref-26)、[[47]](#ref-47)。另一类直接用它管理 KV：InferCept 和 Continuum 决定工具调用期间的 KV 是保留、换出还是丢弃，以及保留多久[[44]](#ref-44)、[[43]](#ref-43)；TokenCake 在工具停顿时卸载 KV、在调用临近前预取，并为关键路径上的 Agent 预留 GPU 内存[[42]](#ref-42)；KVFlow、CacheScout 和 PBKV 按预测的后续 Agent 调用安排淘汰与预取[[27]](#ref-27)、[[48]](#ref-48)、[[49]](#ref-49)；Pythia 预测后续步骤和提示内容以提前准备 KV[[37]](#ref-37)；TOPAS 则根据剩余路径推进、复用收益以及迁移或抢占成本，联合选择驻留前缀与准入请求[[22]](#ref-22)。这些策略按“哪些请求接下来会读取”来评估已保留 KV 的价值，并默认持有这些状态的 worker 会一直运行。

但正如[图 2](#fig-gpu-server-availability)所示，真实集群中故障并不罕见：约 349 天内的 584 次不可用事件波及 400 台服务器中的 231 台。一台服务器故障时，其上正在运行的 Agent 请求连同 GPU 中的 KV、以及换出到本机主存的副本一起失效[[44]](#ref-44)、[[27]](#ref-27)、[[42]](#ref-42)；留在其他 worker 或共享存储里的，是按下一次预期读取挑选出来的固定提示和共享前缀[[27]](#ref-27)、[[37]](#ref-37)、[[48]](#ref-48)，被中断请求到故障时刻为止的历史并不在其中。Claude Code trace 给出了这些幸存前缀最多能帮多少：同 Agent 前缀覆盖了全部请求输入的 97.9%（主 Agent 请求 98.7%，子 Agent 请求 93.9%），其他 Agent 的前缀最多覆盖 10.1%（分别为 4.4% 和 36.2%），且绝大部分与前者重叠（[图 5](#fig-agent-prefix-reuse)）。也就是说，被中断请求的输入绝大部分是它自己 Agent 的历史，而这部分历史正随该 Agent 驻留在故障 worker 上；它只能根据提示和 token 日志重建，代价如[图 3](#fig-motivation-recompute)和[图 4(c)](#fig-motivation-recovery-exposure)所示，而它落在哪个 Agent 上，决定了这段时间是被 slack 吸收还是直接加到 WCT 上。根本原因是，故障不在这些系统的模型里：一份 KV 值不值得留、留在哪、留多久，都建立在 worker 不会故障的前提上。换出到主存是为了腾出 GPU 容量而不是躲过故障，共享存储里放的是供后续复用的已完成上下文而不是运行中请求的历史，一份只在故障后才会被读到的副本在它们的保留评分里价值为零。于是，尽管判断“哪个 Agent 丢不起这段重建”所需的信息它们已经掌握——依赖图、下一步调用和剩余路径正是推导 slack 的原料，TokenCake 甚至据此为关键路径 Agent 预留了 GPU 内存[[42]](#ref-42)——这些信息从未被用来回答：故障前应为哪个 Agent、在哪一层、保留多久一份能续跑的副本。

![图 5](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/agent-prefix-reuse.png)

**图 5：** Claude Code trace[[31]](#ref-31) 中按 token 加权的潜在前缀覆盖率：全部 98,827 个请求，拆分为 56,798 个主 Agent 请求和 42,029 个子 Agent 请求。每个请求的覆盖率是其输入与同一工作流、同一模型下更早完成的请求之间的最长公共前缀，按 token 数汇总。同 Agent 与其他 Agent 的柱状存在重叠：其他 Agent 在最佳同 Agent 前缀之外仅额外覆盖 0.37%、0.01% 和 2.05%。这些值表示复用机会，而非运行时缓存命中。

这两项局限互为镜像。容错 serving 决定*如何*保存与恢复状态，但按恢复成本和 worker 负载对中断请求排序；工作流感知缓存决定工作流接下来会读取*哪些*状态，但假定持有状态的 worker 不会故障。两者都没有回答多 Agent 服务在 worker 故障时面对的问题：哪些 Agent 的历史必须能被快速恢复，其工作流才能按时完成；这种保护又可以从有限的 HBM、DRAM 和存储中，从正常复用手里拿走多少。将二者结合，不是给恢复路由器加一个 slack 特征、或给缓存加一条 checkpoint 路径那么简单：两个目标争用同一批层级，各自看重的状态不同，而且都随 Agent 运行而变化。AegisKV 以这一联合决策为问题。它沿用上述系统中的 checkpoint 传输与分层存储，贡献的是放置策略——每个层级持有哪些 KV 对象、为谁持有、何时迁移——以及让该策略在线保持正确的有界控制器与安全转换。实现它需要应对三个挑战。

### 3.2　设计挑战

**挑战 1：计算 slack 需要在线预测每个 Agent 的剩余执行时间。**

Slack 是一个关于未来的判断：一个 Agent 所在的分支还能再运行多久，才会取代最慢的兄弟分支成为决定汇合的那一个。[第 3.1 节](#sec-motivation-limitations)中的示例是从已完成的 trace 中读出它的。在线时，一次保护决策需要的是决策那一刻每个正在运行的 Agent 的剩余执行时间——还剩多少次模型调用与工具等待、每一次要花多久——而这些都无法直接观测。工具耗时不受 serving 系统控制，后续还有多少轮取决于尚未生成的输出，决定汇合的分支也会随兄弟分支完成而变化，因此一个 Agent 的 slack 会随另一个 Agent 的推进而改变。待预测的量跨度也很大：工作流最大时长差从数秒到上千秒（[图 4(b)](#fig-motivation-branch-gap) 中位数 138 s、90 分位数 1,173 s），因此没有固定规则能区分紧迫分支与可容忍分支，recency 或重建成本也不能代替这一预测：A1 与 A2 的重建时间相近，却只有 A2 会推迟汇合。因此，系统必须仅凭部分执行的因果特征估计剩余时间，随 Agent 推进不断刷新估计，并由此推导出在预测误差下仍然可用、在估计无效时能安全回退的优先级。

**挑战 2：KV 优先级必须同时考虑复用价值与恢复收益，再据此决策放置。**

现有系统只按一种标准给 KV 排序：工作流感知缓存按接下来会读取它的请求，容错 serving 按重建它的代价（[第 3.1 节](#sec-motivation-limitations)）。二者都不是多 Agent 服务所需的价值。一份 KV 值得保留有两个并存且可能相互冲突的理由。正常复用能在该 Agent 的下一次调用中省去 prefill，无论其 worker 是否故障。恢复收益只在故障发生时才省去重建，并且只有在节省的时间超过挑战 1 中该 Agent 的 slack 时才对 WCT 有意义。因此，高 slack 不能成为删除那些后续正常调用会重算的历史的理由，低重建成本也不能让那个重建恰好落在关键路径上的 Agent 被降级。恢复收益也不可相加：一次 worker 故障会同时中断多个共置 Agent，它们的恢复共享 reader、链路和目标 GPU；只加速两个延迟分支中的一个，汇合时间不变。重新定义的优先级接着要决定存储管理。在任何层级保留历史都能消除重建：在 1M tokens 处，571.21 s 变为从共享存储读取的 10.156 s（[图 3](#fig-motivation-recompute)）。更快的层级只是缩短读取——DRAM 为 2.663 s，HBM 为 1.305 s——代价却截然不同：这份历史占用 57.92 GB，超过两张 A100 HBM 总量的 70%；而由于被中断 Agent 的历史大多是独有的（[图 5](#fig-agent-prefix-reuse)），共享无法缩减这一成本。不过，历史不必作为一个整体移动。长上下文模型越来越多地按 Query 选择块、token 或压缩条目（[图 6](#fig-sparse-releases)），且其访问是集中的：在 NOSA-8B、NSA-8B 和 MiniCPM4.1-8B 中，约 20% 的历史块承载了 87.64%、74.76% 和 56.54% 的访问（[图 7](#fig-design-insights)）。只要热子集仅凭因果历史选出、未命中的块仍可取回，快层中的一个小热子集就可以服务大部分读取，而完整历史留在更便宜的层级。因此，放置必须把这一合并后的优先级转化为按层、按块的决策——每一层为谁持有哪些对象、持有多久——把避免重建的“保留”与缩短读取的“加速”分开，并受限于有限的层级预算。

**挑战 3：额外的保护不能干扰正常推理。**

每一份超出正常 serving 本会保留范围、专为恢复而保留的副本，都是 serving 路径上的额外工作。写入 checkpoint 和在层级间移动它们，消耗的是正常复用与并发恢复所读取的 DRAM 与存储带宽；放在 HBM 中的副本占用的是推理 batch 所需的内存——每一个用于保护的 HBM 字节都是从 serving 中拿走的。决定保护什么本身也并非免费。每生成一个 token 都会延长未保存的尾部，每次工具返回和新请求都会改变 slack，每个 batch 都会改变推理所需的 HBM，因此在块粒度上对每个事件重新评估所有驻留对象代价过高，而陈旧的分数又会把错误的状态留在快层。保护还不能反过来损害自身：传输是异步的，而其所防范的故障可能恰好发生在中途；在存储替代副本提交之前释放 DRAM 副本，或在 owner 故障后仍将对象视为本地，都会悄无声息地让一个 checkpoint 失去可恢复的副本。因此，控制器需要每个事件有界的工作量、在前台需求上升时向推理让位、需求回落时再回涨的保护容量、控制在带宽预算之内的迁移节奏，以及让每个已提交 checkpoint 始终拥有可达 owner 的状态转换。

这些挑战组织了整个设计。Workflow Tracker 预测剩余执行时间并由此推导 slack，应对挑战 1（[第 4.2 节](#sec-workflow-protection)）；感知 slack 的请求优先级、块级需求与逐 Agent 可续租信用定义合并后的优先级及其放置，应对挑战 2（[第 4.4.1 节](#sec-placement-value)–[第 4.4.3 节](#sec-sparse-placement)）；惰性事件循环、调节 Peer 容量的 AIMD Adapter 与带版本传输让保护远离推理路径，应对挑战 3（[第 4.4.4 节](#sec-placement-plan)与[第 4.5 节](#sec-adapter)）。

## 4　AegisKV 设计

AegisKV 分配有限 KV 存储以减少工作流完成时间（WCT），同时保留正常缓存复用。本节先介绍架构，再按[第 3.2 节](#sec-motivation-challenges)中三个挑战的顺序介绍各组件。

### 4.1　系统总览

AegisKV 将工作流优先级与三层 KV 层级结合起来（[图 8](#fig-system-overview)）。Peer HBM 将选定层与热块保留在另一个数据并行（DP）副本上，以支持快速恢复；共享 DRAM 和存储保留其余状态，用于复用与恢复。三个层级共同覆盖每个已提交 checkpoint，传输完成后每个对象只有一个受管 owner。这种划分使系统能够保留长历史，同时以有界的逐请求配额，将稀缺 HBM 用于零 slack 请求的状态。

Application 向 Controller 提供请求和工作流进度。**(1)** Workflow Tracker 估计每个 Agent 能吸收多少延迟，**(2)** Recovery-aware Router 选择其执行 DP 和接管 DP。**(3)** KV Master 利用紧迫性与位置信息，决定每个 KV 对象的保留位置，以及哪些热块值得使用 Peer 空间。在 Engine 内部，**(4)** Adapter 随服务需求变化调整可用 Peer 容量。Connector 执行 Master 的传输计划并报告结果。Worker 故障后，Router 将请求重定向到接管 DP；Connector 结合 Peer 命中与下层读取，恢复执行。

![图 8](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/system-overview.png)

**图 8：** AegisKV 架构。编号 (1)–(4) 与正文对应；DP1 具有与 DP0 对称的 Adapter／Connector。图中在 DP1 展示 Master 与 Connector 的通信：计划向下发送，传输状态向上返回。DP0 执行请求；DP1 保存选定的 Peer 对象并负责接管。蓝色实线传输 KV，深色虚线传输控制信息，红色虚线表示重试；橙色块为尚未封闭的尾部。其余 checkpoint 对象位于共享 DRAM／存储中，处于两个 DP 故障边界之外。

### 4.2　Workflow Tracker：剩余时间与 Slack

为在线提供工作流优先级，Tracker 先估计剩余执行时间，再计算 slack。它维护残余 DAG，节点对应已暴露的 fork／join 边界或任务完成边界之间的 Agent segment。一个 segment 可以跨越多次 LLM 调用与工具等待。子任务执行计入子路径，不在父路径重复计入；未知的未来分叉不包含在图中。

GBDT 根据因果特征预测 segment 剩余秒数 $d$：角色／模型、当前输入长度、已耗时、已完成调用数，以及此前调用的长度、耗时和上下文增长。缺失历史使用 mask 标记；训练、校准与评估以完整工作流为单位划分。标签终点位于 segment 边界，未来调用结果绝不作为特征。

[算法 1](#alg-workflow-tracker)以残余 DAG $G$ 和特征 $X$ 为输入。前向／后向关键路径遍历[[16]](#ref-16)以预测的工作流完成时刻为基准，计算最早完成时间 $EF$ 与最晚完成时间 $LF$。两者之差为名义 slack。Guard $g$ 取自校准工作流中 slack 正向高估误差的经验上分位数；扣除它得到建议 slack $s$，而非逐请求保证。同一 segment 中的请求共享该余量。

**算法 1：剩余时间与 Slack**


| 行   | 操作                                                                        |
| --- | ------------------------------------------------------------------------- |
| 1   | $(G,X)\gets\operatorname{SnapshotProgress}()$                             |
| 2   | $\nu\gets\operatorname{NextVersion}()$                                    |
| 3   | **if not** `Supported`$(G,X)$ **then**                                    |
| 4   | &emsp;`PublishInvalid`$(\nu)$; **return**                                 |
| 5   | $d\gets\max(0,\operatorname{GBDT}(X));\quad g\gets\operatorname{Guard}()$ |
| 6   | $EF\gets\operatorname{Forward}(G,d)$                                      |
| 7   | $LF\gets\operatorname{Backward}(G,d,\max_v EF_v)$                         |
| 8   | **for** $v\in V(G)$ **do**                                                |
| 9   | &emsp;$s_v\gets\max(0,LF_v-EF_v-g_v)$                                     |
| 10  | `Publish`$(\nu,G,d,g,s)$                                                  |


`Supported` 检查输入、依赖、校准与时效性；无效估计不提供正 slack 额度。进度事件与周期刷新向 Master 发布带版本的时长 $d$、guard 和 slack，并使旧优先级估计失效。DAG 遍历开销为 $O(|V|+|E|)$；预测质量在[第 5.12 节](#sec-eval-prediction)评估。

### 4.3　恢复感知的 Router

Router 确定正常执行与恢复执行的位置。正常分派兼顾负载和兼容前缀的局部性。[图 5](#fig-agent-prefix-reuse)显示，主 Agent 和子 Agent 请求的同 Agent 潜在 token 覆盖率分别为 98.7% 和 93.9%。Agent 亲和仅是一种偏好：其他 Agent 的前缀同样可以提供复用机会，对子 Agent 的首个请求尤其如此。

请求到达时，Router 记录一个带版本的接管绑定，目标是源故障域之外且布局兼容的 DP。该 DP 中对应的张量并行（TP）分片可以持有选定 Peer 对象。确认故障后，Router 隔离旧 epoch，并在满足工作区和准入约束的条件下激活目标。新目标不能将旧目标的 Peer 对象计为本地对象：重新绑定时需要取回仍可达的对象；若唯一 owner 已丢失，则使用较旧 checkpoint／重放回退。该绑定为 Master 提供具体访问路径和目标负载，以支持恢复性能估计与 Peer 放置。

### 4.4　KV Master：面向工作流的分层放置

Master 首先将请求紧迫性与请求内部的 KV 需求结合，再将这一优先级延伸到重复使用与共享使用。可续租信用管理下层保留；固定大小的请求级策略分配 Peer 加速。事件循环将两类策略与实际传输和可用容量连接起来。

#### 4.4.1　感知 Slack 与访问需求的 KV 优先级

两个因素决定一个请求对 KV 块的需求价值：恢复对其工作流的影响程度，以及执行需要该块的可能性。令 $R_r$ 为请求当前放置下估计的恢复延迟，包括下层读取、重放和排队，$s_r$ 为扣除 guard 后的 slack。我们使用暴露比例：

$$
u_r=\frac{[R_r-s_r]^+}{\max(R_r,\varepsilon)},
 \qquad P_{r,l,b}=u_r\,\widehat p_{r,l,b}, \tag{1}
$$

其中，$\varepsilon>0$ 用于避免除零。因此，当恢复需要时间时，零 slack 对应完全紧迫；若 slack 足以覆盖恢复，则消除的是这一恢复紧迫性，而非普通复用价值。无效的 Tracker 估计使用零 slack。$P$ 是排序信号，不是可相加的 WCT 节省量估计。

在一个 dense-attention 层内，后续 Query 需要每个因果可见的历史块，因此这些块的访问因子均为 1。仅仅创建得更早，并不意味着未来价值更高。稀疏注意力则使用最近一段已完成 Query 的窗口：

$$
\widehat p_{r,l,b}=
 \frac{\text{选择块 }b\text{ 的 Query 数}}
      {\text{块 }b\text{ 因果可见时的 Query 数}}. \tag{2}
$$

对每个 Query，同一物理块跨 head 只计一次。可见性在稀疏选择之前定义，而不是在候选剪枝之后定义。在 200 次机会中被选择 40 次的块，其估计需求低于在 30 次机会中被选择 15 次的块；原始次数会颠倒这一排序。经过校准的逐层先验对小分母进行平滑。该因果估计在不修改原生 selector 的情况下预测需求；必需的辅助状态无论测得频率如何，都仍然是依赖项。正是[图 7](#fig-design-insights)所示的访问集中度，使按块估计需求有价值；该估计保持因果性，快层中缺失的块从其 owner 取回。

优先级与保留成本不同。对于同一 dense 层中大小相同、成本相同的块，访问贡献相等；但对象大小、传输路径和重建成本仍可能不同。[图 9](#fig-retention-value)说明了单位字节成本为何同样重要。这为下层采用成本感知的信用提供动机，而下文 Peer 策略则有意使用更简单的紧迫性规则。

**图 9：** 仅凭 slack 无法对保留价值排序。在这个独立故障示例中，A 使用两个容量单位，将恢复时间从 4 s 降到 2 s；B 使用一个容量单位，将恢复时间从 18 s 降到 8 s。Slack 为 0 的 A 节省 1 s/unit，slack 为 6 的 B 则节省 10 s/unit。正常使用价值为零。这个构造示例为成本感知的下层保留提供动机，并揭示仅按紧迫性进行 Peer 准入的局限；它不是策略加速结果。

#### 4.4.2　带惰性更新的可续租信用

前述优先级针对单个请求。跨请求来看，共享前缀可以服务多个 Agent，同一个 Agent 也可能在工具等待后再次使用它。Master 为每个有需求的 Agent 分配对象信用中的独立份额。不同 Agent 增加一个份额；同一 Agent 的新使用刷新其原有份额，而不是再累积一份相同价值。Agent 身份包含所属工作流实例，物理容量只计费一次。

对于下层对象 $x$，当前授予信用由正常复用项与恢复优先级共同组成：

$$
g_{a,x,j}=v^{\mathrm{reuse}}_{a,x,j}
                +\lambda_f c_{a,x,j}P_{a,x}. \tag{3}
$$

其中，$j$ 表示 DRAM 或存储；$\lambda_f$ 对统一决策时间范围内的故障风险加权。估计成本 $c$ 衡量对象离开 $j$ 后增加的服务工作：DRAM 降级后需要访问存储，或最后一份存储副本被移除后需要重建。复用项将因果的下一次使用估计与相应避免的服务工作相乘，且独立于 slack。这样可以为 slack 较大的多轮 Agent 保留有用状态。当恢复需要一个存在依赖的对象组时，其估计成本按字节分摊，而不是向每个块重复赋予整个组的成本。Agent 份额之和表达竞争需求，不等于精确的联合 WCT：工作流汇合点上的同时延迟不能相加。

一次性授予的信用会过时；每次 checkpoint 都重新授予信用，又可能无限期保留未使用的状态。受 Landlord 与 GreedyDual-Size 启发[[3]](#ref-3)、[[36]](#ref-36)，Master 将当前授予信用 $g$ 与已付租金 $d$ 分开：

$$
C_{x,j}=\sum_a[g_{a,x,j}-d_{a,x,j}]^+,
 \qquad H_{x,j}=\rho_j+C_{x,j}/b_x. \tag{4}
$$

存储池压力时钟 $\rho_j$ 按字节数 $b_x$ 计费，而非按经过的时间计费。时钟增加 $\delta$ 时，扣除 $\min(C_{x,j},b_x\delta)$，并在仍为正的 Agent 份额之间按比例分摊。所有已提交的驻留对象都会老化，包括有 lease 的对象；是否允许淘汰另行判断。实际复用或恢复使用只续租发起使用的 Agent，并以对象与 request/use ID 为单位去重。注意力观察更新需求；checkpoint 增长、分数更新和迁移保留已付租金。过期的 Agent 需求被移除。[图 12](#fig-renewable-credit)展示了这些不同事件。最近使用情况通过续租体现，需求通过选择概率与复用历史体现，工作流紧迫性通过 $u_r$ 体现；这些都是明确的信号，并不意味着该机制涵盖所有 LRU／LFU 变体。

**避免逐 token 更新信用。**

引擎为每层推进一个 Query 计数器，并且只记录被选中的块 ID。块的创建序号和窗口边界决定其访问机会数，无需为每个块递增分母。数量有界的 Query bucket 使旧的选择计数过期；dense attention 不需要这些计数器。统计信息在 checkpoint 事件中批量提交。Slack 变化只更新请求标量与版本，不触碰其各个块。

Master 仅在实际使用、候选检查或轮转扫描时具体更新一个块。它先结算该块自上次时钟以来产生的租金，再读取当前请求／需求版本，并在保留已付金额的同时刷新授予信用。两次具体更新之间，授予信用保持固定；因此，共享压力时钟可以避免每次计费都扫描全部驻留对象。如果尚未查看的 key 可能降低，只刷新过时堆顶是不够的。每轮在固定工作预算内刷新 $q$ 个低 key 候选和 $q$ 个轮转候选，然后选择受害对象。这是近似选择，[第 5.10 节](#sec-eval-rental)将其与立即全面刷新比较；它不是精确的全局最小值。工作量随观测到的选择、检查的候选及其 Agent 份额增长，而非每生成一个 token 就更新整个缓存。

#### 4.4.3　贪心 Peer 保护

Peer 加速恢复，但不参与租金机制。由于访问集中于部分块（[图 7](#fig-design-insights)），固定的热集即可服务选定层的大部分读取。对于每种受支持的模型／布局，校准阶段固定 checkpoint 间隔 $Z$、前缀层深度 $L$ 和每个选定层的块数 $K$。在线策略改变热块身份与请求成员，而不改变这三个参数。一个 Peer slot 最多预留 $LK$ 个块，并为必需状态单独分配预算。短历史使用更少的块；共享物理对象只计费一次。这是固定配额，并不意味着每个请求的实际物理占用都相同。引擎 block size 与 $Z$ 独立配置；某项测量中的 64-token 单位不具有普适性。

[图 10](#fig-sparse-recovery)展示了相应放置。每个已封闭的层／块／TP 对象只有一个受管 owner，与执行侧工作 KV 区分开来。Peer、DRAM 和存储共同覆盖已提交 checkpoint；对象迁入 Peer 后，待交接完成再释放其下层副本。未选中的块留在下层，需求未命中时从实际 owner 取回。

![图 10](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/sparse-recovery.png)

**图 10：** 跨三个互斥层级的 checkpoint，Peer 配额固定为 $L=2$、$K=2$。每个格子表示一组层／块对应的 TP 对象；四个格子位于 Peer，其余位于 DRAM／存储。第 1 层需要 B0/B1/B2：B0 在本地，B1 需要 H2D，B2 需要存储读取加 H2D。虚线尾部尚未提交。热块身份可以在配额内变化；被淘汰的 Peer 对象必须先向下迁移，其空间才能再次使用。

只有经过截断、扣除 guard 后 slack 为 $s_r=0$ 的请求，才能进入 Peer 候选队列，包括运行期间 slack 降到零的请求。已准入请求按 $\widehat p$ 为每层选择 $K$ 个块，依次以最近使用时间和块 ID 打破平局。请求完成或交接给工具后，该请求的 slot 可被淘汰。准入或缩减配额时，Master 先回收已结束请求，再按 slack 从大到小回收活跃请求。普通准入在 slack 相等时保留已有请求；新的同值请求等待 Peer，同时保留下层保护。必要的缩减使用最久未发生请求使用的顺序打破活跃请求间的平局。因此，活跃请求具有策略上的保留偏好，而非绝对淘汰锁；物理 read/copy lease 始终必须遵守。只有不再有保留的 slot 需要共享对象时，才能释放该对象。不同接管 DP 不能同时将其唯一 owner 计为本地。

**为何固定保留前若干层？**

令 $M$ 为已提交历史，$N$ 为其后已确认但尚未提交的尾部。恢复需要重放 $N$，这部分计算可以与后续层读取重叠。下层状态已经避免了重建，Peer 额外消除的仅是暴露出的传输等待。[图 11](#fig-design-pipeline)在同一时间轴上包含存储读取、H2D 和重放。在该示例中，需求未命中使稀疏加载比完整层流水线更慢；相对于相同稀疏需求，Peer 减少约 15 ms。该对比展示部分驻留，而不说明某个 $L$ 普遍最优。校准在已声明的历史／尾部与负载配置上扫描固定配额，在 HBM 预算下选定一个配置，然后在其他工作流上评估之前冻结它。不同请求可能适合不同深度；自适应深度和小规模 oracle 对比用于测量这种简化的代价。

#### 4.4.4　在线三层管理

Prefill 提供已封闭块；Decode 每固定 $Z$ 个 token 复核一次，完成／工具交接时提供最终快照，也包括短轮次。实际使用、Slack 变化、容量更新和传输结果也会调用[算法 2](#alg-placement)。新块获得创建该块的 Agent 的初始信用；未变化的前缀对象不获得新信用。

**准入与容量压力。**

下层存在空闲空间时接纳新状态，包括零信用状态。有容量压力时，Master 刷新候选受害对象，并试算按字节比例收费的租金，直到耗尽一个已检查且可安全移除的对象组的信用。新对象支付相同试算租金；信用归零的新对象在该层被延后准入。DRAM 拒绝后，可以将状态直接送入存储。已提交的零信用对象在需要空间前仍可使用；DRAM 受害对象迁往存储，存储的独立账目根据避免重建的价值来评估保留。删除最后副本前，必须为每个受影响的 manifest 发布有效的较旧 checkpoint 或输入／日志重放回退。依赖关系和物理 lease 约束所有受害对象选择。

Peer 准入／缩减遵循上述请求顺序。热集变化在同一 slot 内替换对象身份。两者都可能需要 Peer→DRAM 和 DRAM→存储的级联迁移。如果无法预留安全目的地，迁移就等待，源位置继续被占用。下层各 pool 的已付金额在往返迁移后仍保留，离开期间不收租。经过 Peer 的迁移和仅更新价值的刷新，都不会触发续租。

### 4.5　Adapter：带保护条件的 AIMD Peer 容量调节

Master 在配额内选择内容；Adapter 随前台推理需求变化调整配额。它在压力下进行乘法减小，在稳定窗口后进行加法增加[[5]](#ref-5)。Peer 总授权容量受物理上限约束：

$$
C=\max\{0,\min(B_{\mathrm{cap}},
 B_{\mathrm{pool}}-B_{\mathrm{serve}}-B_{\mathrm{reserve}})\}. \tag{5}
$$

Pool 不包含权重／固定分配；服务高水位不包含 Peer，预留空间覆盖增长／工作区。已有 Peer 字节不会被重复扣除。$B_{\rm cap}$ 可以配置为 pool 容量的一定比例。

当前配额 $B$ 和稳定窗口计数 $z$ 均从零开始。压力信号（分配停顿、预留空间不足或内存相关准入等待）使 $B$ 乘以 $0<\gamma<1$。连续 $m$ 个稳定窗口的等待低于较低阈值后，如果存在被延后的零 slack Peer 需求，则允许按字节步长 $\Delta$ 增加配额；该需求在配额过滤之前计数。处于中间状态的窗口重置 $z$；遥测缺失时禁止增长。每次更新均受容量上限截断；紧急情况下可以在窗口内减小，但增长必须等待完整稳定窗口。参数和窗口长度均可配置。

**算法 3：按窗口调整 Peer 配额**


| 行   | 操作                                                            |
| --- | ------------------------------------------------------------- |
| 1   | $C\gets\operatorname{SafeCeiling}();\quad B'\gets B$          |
| 2   | **if** `Pressure`() **then** $(B',z)\gets(\gamma B,0)$        |
| 3   | **else if** `Stable`() **then**                               |
| 4   | &emsp;$z\gets z+1$                                            |
| 5   | &emsp;**if** $z\ge m$ **then**                                |
| 6   | &emsp;&emsp;**if** `PeerDemand`() **then** $B'\gets B+\Delta$ |
| 7   | &emsp;&emsp;$z\gets0$                                         |
| 8   | **else** $z\gets0$                                            |
| 9   | $B\gets\operatorname{RoundDownPage}(\min(C,B'))$              |
| 10  | `PublishBudget`$(B)$; `EmitCapacityEvent`()                   |


Adapter 设置总预算；Master 准入固定 $L/K$ 的请求 slot，并在固定 $Z$ 间隔及其他放置事件中刷新对象身份。如果占用加预留超过缩减后的配额，Master 暂停 Peer 准入并选择对象降级。其 DRAM 目的端可能先需要向存储降级。只有这些传输和正在进行的读取结束后，服务才可复用该内存；新配额是授权目标，而不是瞬时空闲空间的声明。

## 5　评估

评估回答五个问题：面向工作流的放置是否改善一次故障后的完成时间；哪些恢复与依赖机制产生这种改善；该收益是否在记录的故障时序下仍然存在；哪些在线机制的收益足以支撑其复杂度；以及这些机制伴随哪些正常服务、资源和正确性成本。我们评估从保留字节到 KV 就绪、再到分支完成和工作流完成的完整论证链，而不以缓存命中率作为终点。

**证据状态。**

本扩展研究稿包含可复现的分析结果、公开 trace 的描述、trace 驱动的模型结果，以及详细实机实验规格。本文未报告已经实现并执行的端到端故障恢复实验。每张图都标明其证据层级。Motivation 中的实测微基准保留各自适用范围；其耗时没有被不加说明地替换为下文的通用速率。现有 DRAM／存储放置结果使用早期的完整 checkpoint、禁用 Peer 的策略；它们没有评估互斥三层控制器。独立层模型研究部分 DRAM payload 驻留与 I/O 重叠，而非集成策略。Design 中的流水线复用已有 MiniCPM4-8B 校准，并明确传输假设；其 Peer 案例在相同独特状态覆盖下，将选定对象从 DRAM／存储移出。需求集合与传输速率均是显式分析假设。静态价值、独立租金和层模型分别检验不同机制，不是完整控制器运行。

### 5.1　实验约定与基线

**部署。**

主要实机实验使用故障域分离的服务副本，以及可独立访问的后备存储。将 DP=2/4/8 和 TP=1/2 设为不同实验配置；TP2 主机故障测试至少需要两个位于不同主机、兼容的双 GPU 副本。GPU 进程、整个副本、主机和存储主机故障分别测试。报告存活容量与执行／暂存 HBM，而不是假定接管目标具有无限内存。本地 NVMe、远程 NVMe 和共享文件系统后端分别配置。同机 SSD 无法抵御主机丢失。实机实验必须固定模型权重、注意力 kernel、引擎和控制器 commit、TP 布局、block size、驱动、网络拓扑、文件系统配置以及故障注入器版本。

**工作负载与负载水平。**

使用可执行的 coding-agent 与 FanOutQA 工作流，以及受控的串行、平衡 fork/join 和异构 fork/join DAG。原始图只执行一次，保持相同工作流 ID 与到达顺序；不能通过重复 DAG 人为制造正常复用。每个工作负载族从 30 个不同工作流开始，公开其 ID 与输入哈希。主要对比重放冻结的工具响应；实时工具调用作为独立有效性检查。使用受支持的 dense 和原生 sparse 模型路径，包括 Qwen3-8B 与 Qwen2.5-7B-Instruct-1M，并在可执行时使用 32K/128K/512K/1.01M 上下文。对不支持的配置保留缺失并说明原因。到达 trace 使用一个固定基线可持续正常吞吐的 30/60/85%，各策略的绝对到达序列相同。报告失去一个副本后的实际负载。

**相同资源下的基线。**

Recompute 保留持久化的已接受输入／输出日志，但不保留额外的故障安全 KV 历史。Storage-only 在容量层保留完整 checkpoint。Hierarchical LRU 与 reuse-only 共享 AegisKV 的传输、manifest、安全机制和 checkpoint 前沿实现。LRU 是使用同一基础设施的主要基线；reuse-only 用于分离依赖与故障信息的收益。所有策略都计入已提交、预留、待释放、元数据和暂存字节，以及 checkpoint 与迁移流量。匹配的在线基线使用相同互斥所有权规则。共享对象在稳态下只占一份容量；迁移期间两份物理副本都计费。All-DRAM 放宽容量约束，是参考而非同成本竞争者。穷举的可行 oracle 限于小候选集合和相同目标；它不是在线系统 oracle。

外部对比应在兼容时使用固定版本的 DéjàVu、GhostServe 和 LUMEN 实验材料，以及经过调优的 Mooncake／SGLang 或 Strata 风格层级[[4]](#ref-4)、[[14]](#ref-14)、[[28]](#ref-28)、[[33]](#ref-33)、[[34]](#ref-34)。计入复制／校验容量、编码工作、写流量和实际前沿滞后。复现的机制应标为重新实现；当前曲线中没有为这些具名系统编造结果。TOPAS／KVFlow 对比必须使用相同的故障安全后备基础设施，之后才能将恢复差异归因于工作流策略。

**结果指标与样本集合。**

对于策略 $p$ 和工作流 $w$，配对的故障惩罚为：

$$
D_{w,p}=\mathrm{WCT}^{\mathrm{fault}}_{w,p}
          -\mathrm{WCT}^{\mathrm{healthy}}_{w,p}. \tag{6}
$$

每个策略都有自己的正常运行配对实验。$D_{w,\mathrm{LRU}}-D_{w,p}$ 为正表示有利于 $p$，但我们同时报告正常与故障状态下的绝对 WCT、完成情况和 SLO goodput。区分直接中断的工作流、共享恢复资源的其他工作流，以及隔离的对照组。只有明确实际共享的链路、队列或 GPU，第二组才能用于确立干扰。仅在已完成样本足够时报告 p50/p95/p99，并同时报告超时与统一观察时间范围。命中率、状态恢复延迟和工作流延迟的分母不同，不能互相替代。

**明确声明的分析实例。**

四个分支 A0–A3 的状态大小为 4/8/12/16 GiB，剩余时长为 12/10/5/1 s，下一次使用权重为 0.15/0.35/0.60/0.85。速率分别为：DRAM 20 GiB/s、存储 4 GiB/s、共享网络 12 GiB/s、每个目标的 H2D 20 GiB/s，并有两个存活目标。共同恢复固定开销为 0.25 s，重放为 0.4 s，重建成本为 8 s/GiB。DRAM 限于 16 GiB，存储限于 160 GiB。事件日历按请求轮转顺序调度 0.25 GiB 块，依次通过共享 reader、共享网络，以及目标本地 H2D／计算。所需状态到达后才开始尾部重放。传输存在重叠，但这个特定模型没有逐层重放重叠或在线重估控制器。静态准入以贪心方式最大化单位字节边际价值，采用 60 s 决策范围内 0.05 的故障事件概率和 0.02 的下一次使用概率。这些是敏感性分析输入，而非观测到的生产系统发生率。

### 5.2　一次故障：端到端收益

**受控干预。**

主要实验在指定工作流、Agent 和请求达到冻结逻辑 token 进度的 80% 时，终止同一个源副本。样本集合包含该源上所有被中断请求，而不仅是触发注入的请求。基线与候选策略保持相同输入、token 历史、到达 trace、目标资源与故障身份。原始日志分别记录检测固定开销、路由／准入、checkpoint 查询、状态恢复、重放与恢复后的执行。按统一墙上时间终止会将进度与策略速度混淆。机制归因实验冻结故障前源分配和已提交覆盖。完整系统实验允许策略改变路由和实际前沿，并使用固定原始到达集合进行意向处理对比；同时报告哪些工作流被直接中断发生了变化。这两类实验回答不同问题。

分析网格覆盖状态大小因子 0.5/1/2、slack 因子 0/0.3/1/3，以及存储速率 1/4/12 GiB/s，共 36 个配置。该网格中的 DRAM 容量随状态大小同比缩放。[图 13](#fig-eval-workflow-outcomes)展示其分布。我们还为每个配置计算匹配差值。Workflow value 在 17 个配置中改善，在 19 个配置中持平；该网格中没有出现损失并不构成最坏情况保证。在这一明确声明的实例中，LRU 与 reuse-only 恰好选择相同顺序，因此两者一致不能作为否定所有复用策略的独立证据。实机对比必须包括其他最近访问／复用顺序，并分别考察各工作负载族。

![图 13](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/eval-workflow-outcomes.png)

**图 13：** 36 个明确声明的状态大小、残余分支 slack 和存储带宽配置中的单次故障惩罚。每个策略使用相同配置。CDF 对配置等权，不是实测工作流的分布。分配 oracle 搜索相同的完整对象组候选空间。

在基准实例中，storage-only 为工作流完成增加 5.5583 s，LRU 增加 3.6208 s，workflow value 增加 1.6125 s。相对 LRU 减少 2.0083 s，即*故障惩罚*降低 55.5%；这不是端到端 WCT 降低 55.5%。正常状态下的剩余汇合时间为 12 s，因此故障后的剩余完成时间分别为 15.6208 s 和 13.6125 s。重建路径的 190.65 s 惩罚说明可靠覆盖的价值，而与 LRU 的比较则隔离了在已有覆盖基础上快速层放置的收益。实机实验应测量完整工作流生命周期，不应以这个剩余时间窗口示例替代。

### 5.3　一次故障：收益来源

**依赖暴露。**

对于一个剩余时长为 $d_i$、恢复就绪时间为 $R_i$ 的 fork/join 实例，精确的局部汇合惩罚为：

$$
D=\max_i(d_i+R_i)-\max_i d_i. \tag{7}
$$

基准汇合 slack 为 0/2/7/11 s。LRU 保留 16 GiB 的 A3 历史；workflow value 保留 A0 和 A1，共 12 GiB。[图 14](#fig-eval-branch-exposure)说明这两种选择为何不同。A3 较长的恢复仍可能处于可用余量内，而 A0 无法隐藏任何延迟。完整对象组粒度使 4 GiB 未被使用；这是候选限制的一部分，并不是暗中分配给其他策略的免费容量。

![图 14](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/eval-branch-exposure.png)

**图 14：** 基准实例收益的来源。A0–A3 的汇合 slack 分别为 0、2、7 和 11 s。条形将这些 slack 与共同故障后模型中实际算出的恢复完成时间比较。此处加速最大历史 A3 的工作流价值很小；延迟 A0 则直接推迟汇合。

**关键路径核算。**

通过有顺序的反事实干预，将最终汇合惩罚归因于各项成本。固定放置，先将读取／网络／H2D 服务时间设为可忽略，并将固定开销／重放设为零，然后依次恢复检测固定开销、读取、网络、H2D 和重放成本。相邻步骤的汇合差值相加等于最终惩罚。如果改变干预顺序，这种分解可能将交互效应分配给不同阶段。因此，它是解释性模型分解，而不是唯一的因果归因。在硬件上，还需根据事件时间戳记录由依赖关系连接的关键路径：仅累加该路径上不重叠的区间，另行报告 GPU／I/O 总工作量。两种方法都不能将所有 SSD、H2D 和 GPU 时长相加后称为墙上时钟恢复时间。

**优先保护的代价。**

资源核算揭示优先保护的代价。Workflow value 从存储读取 28 GiB，而 LRU 为 24 GiB；前者占用完整恢复池 7.6833 s，后者为 6.6833 s。它更早完成当前工作流，却更长时间地占用资源。除关键路径外，还应采集有效字节、未使用预取字节、重复读取、checkpoint 写入和重建工作量。对该示例声称存储流量、GPU 成本或所有恢复完成所需的总历时更低，均不成立。

### 5.4　一次故障：连带延迟与恢复积压

**共享资源实验。**

将 1/2/4/8 个中断工作流、30/60/85% 的故障前负载，以及一／二／四个兼容恢复目标交叉组合。固定故障发生时的逻辑状态和正常到达流。报告直接受影响工作流延迟、连带工作流延迟、重试队列占用、存储／NIC 积压，以及回到预先声明延迟区间的时间。通过为目标提供独立通道，分别移除公共 reader／链路。如果连带影响消失，则支持资源共享这一解释。如果物理上没有共享瓶颈，就不能从强行设置了共享瓶颈的模型中声称存在跨目标级联效应。

![图 15](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/eval-burst-interference.png)

**图 15：** FIFO 恢复池压力模型：一批同时突发的相同中断工作流共享一个具有两个目标的恢复池。每个工作流最后一次状态恢复结束前，恢复池持续为其保留。排队延迟加入汇合惩罚。这一刻意限制并发的策略揭示了独立故障对比会遗漏的外部影响。

[图 15](#fig-eval-burst-interference)中的 FIFO 压力模型持续占用一个恢复池，直至四个分支的状态恢复全部结束。对于 $n$ 个同时到达的相同工作流，平均惩罚为 $D+(n-1)S/2$，其中 $S=\max_i R_i$ 为恢复池占用时间。当额外的恢复池等待占主导时，workflow value 在独立案例中的优势消失：$n=8$ 时，workflow value 的平均惩罚为 28.5042 s，LRU 为 27.0125 s。这反驳了将独立放置结果推广到任意突发负载的做法，并不是对所提负载感知 Router 的测量。当正常 I/O 使用 4 GiB/s reader 的 70% 时，流体积压模型显示，更大的恢复字节量需要更长时间排空。该计算针对 I/O 积压，并非实测 TTFT 或连带 WCT。实机测试必须包含并发调度，以及受影响与连带工作流的联合价值。

### 5.5　故障位置与 Checkpoint 新鲜度

在 20/50/80/95% 逻辑进度，以及 Prefill、Decode、工具等待和降级提交前后，重复相同 ID 的实验。明确进度统计的是已接受总 token 还是已生成 token，绝不混用分母。分析扫描按逻辑进度缩放 checkpoint 字节数，同时保持剩余工作不变。真实阶段扫描还会改变剩余图、原生需求和 checkpoint 前沿，必须从实际运行中获得这些信息。

对于 $Z=64/256/1024$，在展示分析平均值时枚举所有理想 checkpoint 相位，并在相同 $Z$ 和相位下配对策略。实机实验记录触发、复制开始、已提交前沿、已确认前沿和重试开始时刻。报告丢失／未提交尾部长度、重放时间、提交失败和写积压。背压下实际尾部长度可能超过 $Z$。较短触发间隔若使写路径拥塞，反而可能恶化恢复。固定总保留预算，扫描读写干扰、写速率和队列容量。

### 5.6　真实 Trace：来源与事件语义

**历史节点中断。**

LANL 记录了节点中断的开始／结束时间、节点／系统 ID 和原因类别[[18]](#ref-18)、[[30]](#ref-30)。由于准备期间原始 FTP 档案不可用，我们使用固定修订版本的公开再分发副本。其 CSV 有 23,739 条记录，而官方页面描述为 23,741 条；字节一致性与两条记录的差异尚未解决。此限制已记录在实验材料中，在将该副本称为经认证的原始版本之前必须解决。当前结果明确针对所提供的再分发 CSV，并不声称它与原始档案完全相同。

我们保留 purpose 精确等于 `compute` 的行，排除 1,648 条其他行和 122 条零时长行，并按节点合并重叠或首尾相接的区间，进一步移除 231 个区间边界。未出现负时长或无法解析的 compute 区间。最终 21,738 个区间覆盖 22 个系统中 3,542 个被观测节点。保留所有记录的原因类别，包括可能涉及维护的中断；这不是仅由硬件崩溃组成的样本。原始行 ID 及每次排除／合并都可从清洗结果中恢复。

记录的开始时间具有分钟级分辨率。相同时间戳表示*记录上的*开始时刻重合，并不能证明具有共同物理原因。系统内部共有 19,561 个开始时间组，其中 568 个涉及多个节点，最多为 45 个节点。各系统有独立观察日历，绝不将它们叠加为一个集群。这些历史 CPU／HPC 中断用于检验时间聚集性，不能估计 2027 年 GPU 集群的故障率、维修延迟或工作负载构成。缺失的暴露信息也使我们不能将观测到的故障节点数用作整个集群可用率估计的分母。

**现代 GPU 告警的独立检查。**

Reflex 发布版本包含 98 个 LLM 训练作业、344,175 条告警和 144 个故障节点／作业标签[[2]](#ref-2)、[[9]](#ref-9)。我们将这些标签与中断日历分开审计。在故障标签中，有 108 个在标记节点上没有告警。此外，各作业的时间戳被独立平移，且没有维修时间。因此，我们既不将作业拼接为日历，也不把首次告警视为故障时刻。该数据集可以支持作业内告警模式或诊断研究，但无法为本文提供无需限定的 fail-stop／修复日程。具有明确事件语义的现代服务系统中断 trace，仍是外部有效性的重要验证目标。

### 5.7　Trace 驱动的恢复：收益与尾部退化

**可复现的条件重放。**

每个清洗后的 LANL 节点中断开始时刻，都释放一个假定需要恢复的四分支工作流。每个原始系统有独立 FIFO 恢复池，包含两个存活目标。服务占用 $S_p$ 与固有汇合惩罚 $D_p$，使用前文从字节与速率推导出的基准值。对于到达时刻为 $a_i$ 的连续请求，恢复池等待为 $q_i=\max(0,q_{i-1}+S_p-(a_i-a_{i-1}))$，工作流惩罚为 $q_i+D_p$。相同时刻按节点 ID 排序。开始时刻保持原始间隔。不对服务时间进行 trace 拟合，也不为各策略单独调节到达日程。

这一重放以存在可用的独立恢复容量和完整已提交历史为条件。它不重放正常服务、不为故障节点配置资源、不建模有限备用资源耗尽，也不推断哪些历史节点实际承载了活跃 Agent。结束时间用于描述中断，而不被当作实测 GPU 维修时间。因此，该结果是恢复负载实验，并非运行中集群的可用率或 SLO goodput 测量。

![图 16](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/eval-trace-penalty.png)

**图 16：** 由 LANL 开始时刻驱动的 FIFO 恢复模型：每个清洗后的节点中断对应一个假定四分支工作流，保留各系统原速率的开始时刻。曲线包含 21,738 次条件恢复事件。观测输入是中断日历；恢复时长与工作流惩罚来自模型。

[图 16](#fig-eval-trace-penalty)报告条件恢复分布。在原始时间间隔下，LRU 的模型平均惩罚为 10.4533 s，workflow value 为 9.4673 s，降低 9.4%。平均排队等待从 6.8324 s 上升至 7.8548 s。P95 惩罚从 37.0375 s 恶化至 40.0292 s，P99 从 204.1208 s 恶化至 232.1125 s。因此，这组输入支持有条件的平均收益，同时反驳笼统的尾延迟改善声明。逐系统聚合也保留损失，包括 System 2 的负平均收益。数千次事件或很小的算术误差条，都不能将一条历史 trace 变成独立服务实验。

**对照与完整系统扩展。**

均匀间隔对照保留每个系统的事件数量和日历跨度，同时移除原始聚集性。时间戳压缩与分钟内展开用于区分负载和时间戳分辨率的敏感性。将同分钟开始的事件展开到 59 s 内，LRU／workflow value 的均值为 8.0997/7.0224 s，P99 为 163.8936/191.8852 s；不利尾部仍然存在。这些构造时间戳不是推断出的真实值。压缩因子 10/100/1000 显式增加负载；只有因子 1 保留原始速率。完整服务重放应在比较策略前冻结工作负载到故障域的映射，公开随机种子，并使用原始开始／结束区间移除和恢复容量。即使中断期间也重放到达，允许尚未恢复完成时再次故障，并在统一时间范围结束时保留未完成工作流。固定每个源 1/2/4 个活跃工作流，在不同备用比例以及独立／共享后备域下重复映射。映射到较少机器时保留相关事件组；绝不将 45 节点事件悄悄串行化到一个注入器上。超出容量的组必须报告为不支持，或在声明规模下仿真。Trace 放大和合成修复时间假设应放在敏感性分析图中，而非主要的原速 trace 结果中。

### 5.8　完整价值与依赖消融

每项消融只改变一个明确机制，保持相同的故障安全后备、候选预算、工作负载和物理资源。实机矩阵包括：去掉 DAG／Slack 信息；去掉正常复用项；去掉故障项；固定放置；无租金的直接重估；去掉实际使用续租；去掉压力老化；去掉共享 Agent 聚合；用立即全面刷新替代惰性刷新；用原始次数替代按访问机会归一化的选择；用串行执行替代逐层重叠；用仅考虑局部性的路由替代负载感知路由。开销更大的联合 DAG 与自适应深度参考用于量化可分离优先级和固定 Peer slot 的损失。移除一个价值项绝不会禁用底层安全协议或普通缓存资格。正确性机制通过注入交错事件测试，而不是将不安全变体作为有效基线进行性能比较。

![图 17](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/eval-value-ablation.png)

**图 17：** 在相同 12 个状态大小／slack 场景、4 GiB/s 存储带宽下进行静态价值消融。每个策略包含故障惩罚条和正常下一次使用成本条；它们是不同成本，不是可相加的阶段。六个策略采用相同权重、容量和候选对象组。同时展示两种结果可以揭示恢复优先保护对正常复用的代价。这是静态放置模型，而非完整在线系统。

[图 17](#fig-eval-value-ablation)在 4 GiB/s 存储带宽、12 个状态大小／slack 子集场景上，同时报告相同六个策略的故障成本与正常下一次使用成本；这些均值不同于结果 CDF 中混合带宽的 36 场景均值。每次真实实验还需记录驻留对象变化、预测计划价值、被接纳／拒绝的迁移、实际关键路径分支、移动字节和控制器耗时，以区分有用信号与偶然相同的放置。共同故障示例说明为何仅累加独立损失不够：互补的必要分支可能使对象组的边际价值不同于各单对象价值之和。将因子化策略与有界成对搜索和完整 DAG 参考比较，再枚举小实例以量化近似损失。所选在线策略不执行这种搜索。

对相互作用的机制采用因子实验：Slack $\times$ 共享 Agent 聚合；需求归一化 $\times$ 逐层重叠；租金筛选 $\times$ 惰性刷新；负载感知路由 $\times$ 共享链路竞争。保留每个 $2\times2$ 设计的全部四种组合。交互效应是配对差值之差，而不是各项加速比之和。持平或负向消融同样具有信息价值，不能仅因它削弱所提论述就将其移除。

### 5.9　稀疏需求与逐层重叠消融

**受控机制模型。**

一个八层示例在完整选定需求下，每层 SSD payload 成本为 4 ms，H2D 成本为 1 ms，必需计算为 3 ms/layer。DRAM 保留两个 payload，可位于早期或后期；瞬时工作区只能容纳当前层与下一层。串行与流水线模式使用相同需求和资源。Payload 密度对所有策略的 I/O 等比例缩放，并不改变原生注意力算法。[图 18](#fig-eval-layer-factorial)隔离了放置与调度的交互。另一项预取正确性扫描固定必需需求，以隔离预测误差。

![图 18](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/eval-layer-factorial.png)

**图 18：** 在八个合成层 payload 上进行同预算的 $2\times2$ 层放置／调度实验。早期／后期策略均保留两个 payload；串行／流水线调度使用相同的选定需求、速率和两层瞬时工作区。横轴对全部策略等比例改变选定 payload 密度，而不是改变注意力语义。

完整需求下，两种串行放置都需要 56 ms；采用流水线后，后期放置需要 34 ms，早期放置需要 32 ms。必需计算始终为 24 ms。剩余的 10 ms 与 8 ms 是暴露等待，而不是被避免的历史 Prefill。预测误差消耗额外读取，并使执行因等待需求揭示而停顿；完美预测只是一个敏感性分析点。

**匹配条件的三层扩展。**

固定相同跨层 checkpoint 覆盖、故障 ID、原生需求和恢复调度器，比较禁用 Peer、相同字节预算的 recency／frequency Peer、固定配额 Slack 准入，以及自适应 L/K 参考。通过校准工作流选定并冻结 L/K/Z，再在留出工作流和上下文上测试。在相同固定 slot 下，比较 FCFS、recency、Slack 和估计恢复收益的请求排序。将 Peer 位置 $\times$ overlap 作为四组合对比。Peer 使用同一物理 HBM pool 计费，包括被挤出的正常执行、跨 DP 流量、实际 Peer→DRAM 降级和临时副本。另在相同物理预算下比较互斥所有权与重复后备。扫描历史 $M$、实际尾部 $N$、配置的 $Z$、热集漂移和目标重新绑定。联合报告 WCT 收益、移动字节和正常吞吐。历史 HBM 复用微基准是本地已驻留参考，不是 Peer 放置测量。这些匹配实验配置目前仍是实验规格。

**原生实现实验。**

从固定版本的原生 kernel 采集重试尾部实际逐层需求并集，以及选择元数据和需求揭示时间戳。只用历史 Query 预测，以更晚的留出重放窗口评估；按文档／工作流划分，而非按单个块划分。在相同物理字节、必需 sink／window 预留和完整 checkpoint 覆盖下，对比 recency、历史访问频率与所提因果 profile。将每种策略分别与串行恢复及有界流水线恢复组合。报告全部层覆盖率、有效／未使用预取字节、未命中需求、从揭示到就绪的等待、暴露 GPU 停顿、工作区峰值、总重放时间和 WCT。较高的早期层命中率不能证明总覆盖率较高。Dense 需求是对照，不代表实现失败。不能为加速卸载策略而减少原生选择、遗漏辅助状态，或将近似答案算作精确恢复。

### 5.10　租金诊断与直接重估对照

所提控制器将下层可续租信用与惰性刷新，同固定配额、零 slack 的 Peer 准入结合。我们将早期租金筛选策略的负面结果保留为回归案例，而不是将其当作新控制器改善 WCT 的证据。这个独立的可加模型包含八个 slot、24 个等字节对象，以及价值平滑漂移的 512 次确定性候选机会。所有策略获得相同候选流、下一次使用流、移动成本和替换阈值。原始筛选策略在候选再次被检查时续租，而不在计入分数的下一次使用命中时续租，并且只检查一个最低信用受害对象。被拒绝的预演不改变租金。该模型没有多 Agent 份额、前缀依赖、三层降级、物理 lease 或服务调度器。

![图 19](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/eval-rental-cost.png)

**图 19：** 保留的历史租金回归结果，单位为抽象延迟成本。早期只检查一个受害对象的试租筛选迁移略少，但未命中加移动成本高于直接重估。这些曲线没有实现修订后的三层控制器。

[图 19](#fig-eval-rental-cost)报告直接重估成本 462.96，原始租金策略成本 506.39。两者分别迁移 108 次和 106 次，各执行 396 次标量替换检查；这不是完整 DAG 遍历次数或 CPU 测量。去掉滞回后迁移次数增加到 121；去掉续租后迁移次数减少到 77，但成本上升到 526.05。在原始租金策略轨迹中，104 次被拒绝的机会实际上存在另一个驻留对象，能够满足当前价值增益阈值。这些是诊断观察，而不是总差距的可加因果分解。

有界修复保持输入和阈值不变。仅改为按实际计分命中续租，会将成本提高至 512.67。在不退还已付租金的情况下刷新当前价值，将成本降至 477.86；进一步检查两个低信用受害对象，成本降至 466.76。最后一种修复弥合原始差距的 91.26%，但仍比直接重估高 0.82%。在四个相位、三个漂移周期和三个容量构成的固定网格中，它在全部 36 个案例中优于原始租金策略，但仅在九个案例中优于直接价值策略。这些构造的敏感性案例既不是独立重复，也不是留出工作负载验证。基准实例中，该修复还需要 747 次替换检查和 4,088 次驻留对象 key 更新；结果不能证明控制器开销更低。

这些诊断支持两个明确的设计选择：价值变化时保留已付租金，以及检查其他合法受害对象链。它们没有测量修订后的逐 Agent、分层控制器。其匹配对比包括普通 GDS／Landlord 与使用相同估值的直接策略。直接重估、原始筛选和修订机制应使用相同价值模型、候选机会、工作预算、安全协议和资源。分别消融续租、压力老化、价值刷新、共享 Agent 聚合和替代受害对象探索。在相同工作预算以及不限制工作量的立即全面刷新参考下，比较惰性与立即全面刷新；报告受害排序误差、扫描陈旧时间、WCT 和 CPU 时间。在匹配字节、块年龄和新块样本集合下，使用未来 Query 检验归一化选择概率与原始计数。必须保留小分母和未见阶段上的误差。重放多轮工具等待、增长上下文、同角色共享前缀、阶段变化、下层满载和 Adapter 缩减。记录授予信用、已付租金、试算／已提交时钟、快照失效、DAG 遍历、控制器 CPU 时间、迁移、实际前沿、未命中和 WCT。负面基准实例继续保留在该回归集合中。

### 5.11　容量、存储与恢复覆盖

扫描 DRAM／独特 checkpoint 工作集比例 0/0.1/0.25/0.5/1，以及存储比例 0.5/1/2。统计独特物理字节，并记录随时间变化的工作集。有限存储配置必须实际触发最后副本删除和有效回退前沿；不能悄悄将 DRAM 降级变成无限后备存储。在相同预算下交叉比较上下文长度与源并发度。明确报告不受支持的内存／kernel 配置。[图 20](#fig-eval-capacity-frontier)展示容量敏感性；实验包还保留带宽扫描。基准模型假定后备容量充足，因此不能验证最后副本淘汰的性能。

价值目标并非仅考虑故障 WCT。在 16 GiB 和 28 GiB 预算下，可行 oracle 的联合得分从 0.15049 s 改善到 0.14383 s，但故障惩罚从 1.6125 s 增加到 1.9458 s，因为正常复用也受益于保留，而且传输共享资源。因此，原始容量表同时记录两个目标与所选对象。仅故障曲线非单调，并不说明额外容量使 oracle 优化的联合目标变差。

![图 20](/home/comp/zhanzhao/MoonKVSim/benchmark/AegisKV/paper/figures/preview/eval-capacity-frontier.png)

**图 20：** 固定存储容量、速率和逻辑故障下的单次故障 DRAM 容量扫描。Value 与 oracle 策略优化正常使用／故障的联合得分；其仅故障惩罚不一定单调下降。可部署策略之间的比较必须使用相同 DRAM 容量。

对每个真实后端，测量读写带宽、对请求大小的依赖、并发读写竞争、提交持久性，以及端到端 GPU 就绪时间。客户端冷缓存、客户端热缓存和有记录的服务端缓存状态分别设为不同配置。Direct I/O 只控制客户端路径；无法控制的共享文件系统服务端缓存必须标为未知。各策略读取相同 payload，使用相同传输调度。增加共享存储降速或丢失实验，以区分存活 checkpoint 覆盖与名义上的低延迟放置。状态不可用时，即使期望价值很高，系统也无法恢复它。

### 5.12　预测、陈旧 Profile 与缺失信息

已有诊断使用 170 个 CC/Weka 工作流中的 1,443 个第二次请求处的 Agent 样本，目标是整个 Agent 的剩余时间。五个工作流互斥划分的折，得到训练折中位数、基础 GBDT 和加入历史的 GBDT 的 MAE 分别为 438.6、406.7 和 407.1 s。基础模型减去中位数基线的配对区间 $[-80.9,4.9]$s 跨越零；六个特征相关区间也跨越零。这些结果既不能证明可靠的均值改善，也不能验证残余 segment 的 Slack。原始预测、完整误差尾部与相关图保留在实验材料中。

在较早的完整工作流上训练剩余时间预测，在互斥验证划分上调参，在较晚的工作流上评估。特征必须在决策时点可见。报告原始剩余时间误差、误判的正 slack、关键路径排序、回退频率，以及推理／更新开销。相关系数或聚合 WAPE 不能决定逐 Agent 的误差 CDF。将训练模型与时长中位数、零 slack 回退和 oracle 时长参考比较。

当前扰动模型在各分支间交替改变符号；在 $-25$ 处，其 4.5583 s 惩罚劣于 LRU 的 3.6208 s。实机鲁棒性矩阵包括独立与相关的 $\pm10/25/50/100$ 时长误差、缺失依赖边、工具延迟完成、陈旧带宽 profile、冷启动、模型变化和故障概率校准偏差。应重新计算决策并对照实际结果，而不是给名义曲线加一根误差条。包含保守回退，并比较失去机会的成本与错误 slack 的成本。若较高预测准确率不能改变有用的放置决策，则仅有准确率仍不够。

### 5.13　正常服务与保护何时值得

在每个由固定基线定义的负载下，无故障运行相同工作流。分母包括首次调用、工具等待以及每个 Agent 请求。报告正常 WCT、TTFT、token 间延迟、SLO goodput、GPU 秒数、控制器 CPU／内存、checkpoint 写入量，以及逐层请求／token 命中。区分 trace 中观测到的前缀共享与实际运行时命中。在相同存储限制下比较无新增 checkpoint 保护、LRU、reuse-only、完整价值和去掉复用项的价值策略。

一个独立的、服务时间恒定的 M/D/1 计算仅建模 I/O 排队；它不测量 TTFT 或 GPU 干扰。对于独立基准实例，决策时间范围内的简单收支平衡计算为 $p_f\Delta D-C_h$，其中 $C_h$ 包含按相同目标单位计量的正常服务和迁移成本。在该模型下，固定成本 0.05 s、假定收益 2.0083 s 时，需要 $p_f>0.0249$。该阈值随工作负载、时间范围和队列外部影响变化。示意概率 0.05 与历史中断 trace 都不能确立生产环境中的 $p_f$。实机研究必须分别报告条件恢复收益与摊销净收益。即使恢复更快，故障罕见也可能使整个系统的价值主张不成立。

### 5.14　正确性、安全性与压力下的状态转换

测试零 slack Peer 准入、请求结束／工具交接后的淘汰资格、按 slack 降序淘汰活跃请求、稳定的准入平局处理、强制缩减平局处理，以及固定 slot 热集替换。物理 lease 仍然具有约束力。检查对象迁移期间，三个持有层级共同提供完整覆盖。重新绑定的目标必须取回仍可达 owner 的状态，或在唯一 owner 丢失后发布有效的较旧 checkpoint／重放回退；不能将旧 Peer 字节称为本地。测试 Peer→DRAM→存储级联、目的端满载、临时双份占用，以及跨层往返后保留已付租金。配额下降时不能将尚未完成降级的空间报告为空闲内存。

在预留、部分复制、校验和完成、存储提交、目录重定向、token 确认和最后读者排空的前后立即注入故障。包括重复完成通知、过时 epoch、目标丢失、TP 分片／selector 状态缺失、写超时和层级满载。已发布 manifest 必须标识完整兼容状态；PENDING 字节不能满足状态恢复。验证已接受 token 的持久性、所有层的重放状态、在声明数值容差下的下一个贪心输出，以及不存在重复确认输出。工具侧副作用需要单独提供应用幂等性证据。

24→16 GiB 的压力示例中，即使目标更早改变且复制已经完成，物理字节仍保留到 5.5 s。通过重叠 lease、反向压力、复制失败和最后副本淘汰复现该轨迹。在每次转换中检查物理、预留、已提交、待释放和真正空闲字节；较低目标不等于空闲内存。穷举小规模状态机，并在实现中对每类转换至少运行 100 次随机交错。报告不同注入交错、失败和未解决案例的数量。分析不变量不能替代协议执行。

### 5.15　规模与控制器成本

扫描 DP=2/4/8、DAG 大小 10/100/1,000、活跃组数 $10^2/10^3/10^4$ 和候选上限 16/64/256。独立改变源故障域并发度与存活目标数量。在固定 CPU 预算下，记录决策时间 p50/p95/p99、profile 调用、图节点访问、边访问、锁持有时间、元数据字节、计划陈旧时间和前台停顿。小实例 oracle 对比仅在穷举可行时测量解的质量；大规模时没有 oracle 不意味着差距为零。

分析操作成本估算将假设的单次节点访问成本乘以声明的遍历／事件次数。在纳入候选枚举和共享对象 owner 后，它既不能确立实际控制延迟，也不能确立完整算法复杂度。有用的扩展性结果必须展示队列有界、陈旧决策率可接受，以及工作流结果得到维持，而不仅是独立打分器很快。报告饱和与失败配置，不能将其从对数轴上省略。

### 5.16　统计、复现与执行顺序

主要实机配置从十次独立启动的配对实验开始。随机化策略顺序，保留相同工作流／故障 ID，并记录每个 seed 改变什么。每次实验内部，按工作流 ID 计算各策略的故障减正常结果，再计算相对于 LRU 的配对差值。先在实验内部聚合，再对实验进行 bootstrap（10,000 次重采样，固定分析 seed）；对单个 token 或相关故障重采样，不能创造独立重复。重复 trace 窗口采用不重叠日历块，并同时报告按事件加权和按系统／窗口加权的汇总。这里展示的确定性模型和有限公开 trace 描述，物理重复次数为零，也不编造置信区间。

对每个输入工作流报告统一时间范围内的完成情况与 deadline goodput，包括超时。仅完成案例的延迟必须使用各策略相同的合格样本集合，并展示排除项。如果使用受限平均完成时间，应声明估计器与删失假设；不能为超时分配虚构完成时刻，也不能让仅成功样本的 P99 在更多工作流失败时看似改善。公开原始 manifest、到达、故障、工作流／请求结果、依赖关联事件、预测快照，以及所有制表命令与哈希。固定单栏图画布与独立视觉规格，使替换数据可以沿用相同坐标轴、字体和布局。

先执行正确性与后端校准，再执行相同 ID 的单次故障矩阵及其分解，然后进行正常开销和四组因子消融，最后进行连续真实 trace 重放与压力／规模测试。在提出普遍的集群结论之前，解决 LANL 再分发差异，并获得事件语义可信的现代中断 trace。当前尾部与租金退化结果，是细化或简化设计的明确决策依据。只有对应的匹配实验真实存在，经验声明才获得支持；完成实验规格并不意味着其预期优势已成为实测结果。

### 5.17　可复用图像与实测数据替换

所有评估图使用独立单栏画布、固定物理字号、独立视觉规格和长格式 CSV 表。PDF、SVG 和 PNG 导出保留稳定文件名。Manifest 记录源码与表格哈希、证据类型、单位、聚合命令和独立运行次数。实测替换仅接受关联到已声明实机原始日志、且具有实验级样本核算的表；仅更换证据标记会被拒绝。部分实测发布只替换已经完成的图中配置，其他图保留原始标签。数据范围扩展以包含负面结果与尾部。改变指标，例如以 TTFT 替换 I/O 响应时间，需要单独明确其语义规格，不能只改坐标轴名称。数值论述和图注必须随新结果修订；稳定的绘图配置不会自动验证此前的分析解释。

## 6　相关工作

**容错 LLM 服务。**

DéjàVu 对 KV 进行流式传输与复制[[33]](#ref-33)；GhostServe 通过主机内存中的纠删码校验保护 KV[[14]](#ref-14)。RaidServe 使用循环放置、混合注意力与恢复路由处理 TP 韧性和负载不均衡[[35]](#ref-35)。LUMEN 在负载降低的条件下协调 checkpoint、请求重新分配与容量恢复[[4]](#ref-4)。放置对比必须使用同样强的恢复调度器。

**分层上下文缓存。**

Mooncake 将 KV 池化并围绕局部性进行调度[[28]](#ref-28)；其 SSD offload 在内存压力下将状态溢写到 SSD[[21]](#ref-21)。CachedAttention 使用分层缓存、逐层预加载与异步保存[[11]](#ref-11)。Strata 处理碎片化 I/O、延迟命中和缓存感知调度[[34]](#ref-34)。HCache 在平衡 I/O 与计算的同时恢复中间激活[[12]](#ref-12)。我们提出的区别在于共同故障下的工作流价值，以及安全降级与显式最后副本回退。

**工作流感知的服务与预测。**

Parrot 优化应用级执行[[17]](#ref-17)；KVFlow 使用未来调用距离进行前缀淘汰[[27]](#ref-27)。Pythia 与 Cortex 利用工作流语义[[26]](#ref-26)、[[37]](#ref-37)。TOPAS 使用剩余路径、复用和移动成本调度状态保留与执行[[22]](#ref-22)；因此，仅为缓存加入关键路径分数不足以构成新颖性。本文拟议的区别是在同一 worker 故障后，处理陈旧 checkpoint 和有限层级转换下的恢复。Heddle 预测执行轨迹[[40]](#ref-40)，但这不能确立 AegisKV 对剩余墙上时间的预测准确率。

**放置机制。**

关键路径分析[[16]](#ref-16)与基于成本／大小的缓存[[36]](#ref-36)提供了基础组成部分。AegisKV 的价值依赖 DAG、共享队列和对象位置，因此 Landlord 的竞争界不能直接迁移。小实例可行 oracle 用于测量近似损失。AegisKV 结合带惰性刷新的下层可续租信用、因子化请求／块优先级，以及固定配额 Peer 准入。在匹配资源与控制工作预算下，必须通过相对于直接重估的独立消融，确立租金、实际使用续租和价值刷新，以及稀疏排序与重叠各自的收益。

## 7　结论

AegisKV 结合正常复用、工作流紧迫性与块需求，管理有限的 Peer HBM、DRAM 和共享存储。互斥所有权使完整 checkpoint 分布于这些层级；固定配额的热集加速恢复。在线控制器结合惰性下层信用与贪心 Peer 准入，区分迁移与最后副本删除，并在每次转换中保持已提交覆盖。分析场景识别了潜在收益与局限。历史中断时序表明，平均恢复改善可以与尾部退化同时存在；独立消融指出尚未验证的在线策略成本。这些先前的模型结果并未验证互斥三层控制器。详细协议与单栏图支持后续实机正确性和性能实验，而这些实验仍是确立系统级收益所必需的。

**AI 辅助。**

生成式 AI 辅助了文稿撰写、实验规划和实验材料代码编写；作者仍对验证负责。

## 附录 A　Motivation 测量协议

**范围与配置。**

[图 3](#fig-motivation-recompute)与[图 4(c)](#fig-motivation-recovery-exposure)使用相同的固定 Qwen2.5-7B-Instruct-1M 权重、SGLang 0.5.10rc0、PyTorch 2.9.1/CUDA 12.8，在两张 A100 PCIe 40 GB GPU 上以 TP2、BF16 权重／KV 和 batch 为 1 执行。两组实验分别申请同型号 GPU，使用由模型 tokenizer 编码的同一固定重复合成文本。Trace 提供工作流位置与长度代理，不提供基准测试 prompt。我们的 adapter 使用固定 MInference vertical/slash 配置与 DCA 位置处理，在超过 32,768 tokens 后采用稀疏注意力，包括最后一个 token 的 EXTEND。SM80 稀疏 kernel 构建和模型／注意力源码均附哈希存档。GQA 的 K/V 共享；前缀执行每组最多包含两个 Query head，单 Query 则将全部 head 一起批处理。这些是插桩 worker 测量，而非未修改服务前端的吞吐测量。

**统一终点。**

对于 $C=M+1$，完整 Prefill 从空 KV 开始，以最多 8,192 tokens 的块计算 $M$ 个 token，再单独执行一个 token。复用消耗完全相同的稀疏计算所得 $M$-token 状态，包括不完整页，并执行最后那个 token。同步墙上时间在各 TP rank 间取最大值，在模型主体完成、全部 $C$ 个 token 的 KV 驻留时结束，早于输出词表投影。模型加载、备份创建和正确性检查不计入时间。不包含检测、重新路由、服务排队延迟或注入故障。

**状态恢复路径。**

HBM 从已驻留 KV 开始。DRAM 在计算前从 pinned 主机缓冲区复制全部历史层。共享存储在计算节点的 DPC 共享文件系统上打开、读取并关闭逐 rank KV 文件，然后执行相同的 H2D 复制与计算。这些阶段不重叠；没有压缩或选择性加载。1,010,000-token 案例在两个 rank 上共恢复 57,917,382,656 个逻辑历史字节；文件另外包含已记录的对齐填充。Direct I/O 与页驻留检查排除了 Linux 文件页命中，但 DPC 服务端和内部缓存不受控制。该曲线是共享存储路径测量，而非冷设备延迟或已确认 SSD 的测量。测量后删除 KV 文件。

**计时样本。**

[图 3](#fig-motivation-recompute)在一次资源分配中测量 8,192、65,536、262,144 和 1,010,000 tokens。HBM／DRAM 每个长度预热一次、计时三次；完整 Prefill 与共享存储各计时一次。计时前执行短前向与算子检查；64K 还执行完整的原始全 head 稀疏参考。256K/1.01M 没有额外的完整 Prefill 预热，也没有存储读取预热。因此，这些完整 Prefill／存储数据点描述单次运行，而非稳定延迟分布。[图 4(c)](#fig-motivation-recovery-exposure)使用两次资源分配，在 $C=100{,}865$、$105{,}921$、$108{,}865$ 和 $113{,}665$ 处测量，每个长度完整预热一次并进行三次完整 Prefill 计时。首次分配完成了三个长度；最后一个长度在提前终止信号后恢复测量。其不完整计时保留在实验材料中，但整组排除。图中报告中位数与 min–max。重复是同一输入的计时样本，不是独立工作流或置信区间。原始计时与全部样本都保留在实验材料中。

**校验与工作流映射。**

在重建／复用路径之间检查完整历史哈希、最终 hidden state、所有层的新 KV 和贪心输出。重复完整 Prefill 额外检查输出一致性，CUDA 事件时间线检查串行复制。这些检查验证所比较稀疏状态执行的一致性，不验证其与 dense attention 等价或长上下文任务质量。对于[图 4(c)](#fig-motivation-recovery-exposure)，四个历史长度是活跃请求 trace hash-block 数乘以 64。它们是大小代理，不是原模型准确 token 数或故障时观测到的 KV 前沿。该示例按四个并行分支和约 100 s 的差值选取；它不是该工作流的最大差值组。每个反事实分别在 fork 后 29.5 s，将一段实测完整 Prefill 时长作为额外分支暂停插入。全分支汇合假设、其他执行与队列保持固定。因此，只有重建成本是实测；图中的 WCT 增量是条件计算，而非 Claude Code 工作流中实际观测的故障恢复。
