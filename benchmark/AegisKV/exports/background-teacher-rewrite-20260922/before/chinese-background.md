## 2　背景

**多 Agent 执行。**

随着 LLM 应用的发展，越来越多的任务需要通过多 Agent 协作完成。这些应用将用户任务划分为多个子任务，并分派给若干 Agent 并行执行。每个 Agent 维护自己的对话，通过 LLM 请求和工具调用推进任务：模型生成响应或发起工具调用，返回结果成为后续请求的输入。**请求**是一次模型调用；一个 **Agent** 可以发起多个请求以完成子任务；**工作流**则通过串行依赖、并行分支和汇合点连接这些任务。应用负责编排工作流，推理服务层负责执行模型请求。

[图 1](#fig-agent-workflow-examples)展示了这种结构。在代码生成中，主 Agent 将 CSV 导出功能分派给 API、UI、测试编写和文档 Agent。各分支并行执行，交替进行模型请求与文件读取、编辑或检查。主 Agent 随后集成修改并运行测试。在深度研究中，牵头 Agent 分派技术、成本、安全和供应调查，再将收集的证据综合为报告[[1]](#ref-1)。各分支需要的请求次数和工具调用次数可能不同。因此，一个模型请求完成后，其所属 Agent 和整个工作流都可能仍未完成。

**工作流完成时间。**

令 $w$ 表示一个工作流，$a_w$ 表示该工作流到达系统的时刻，$c_w$ 表示其全部必要输出就绪的时刻。我们将工作流从到达到完成的总耗时定义为*工作流完成时间*（WCT），即 $\mathrm{WCT}_w=c_w-a_w$。它包括模型执行、工具执行、排队和依赖等待。在代码示例中，集成需要等待所有必要修改。最后一个未完成分支上的延迟会推迟集成，而较早完成的分支可能在汇合前吸收同样的延迟。请求延迟通过这些依赖关系影响 WCT。

**多 Agent 工作流中的 KV 复用。**

这些分支中的模型请求会反复使用先前步骤积累的上下文。代码 Agent 将源文件、修改记录和测试输出带入后续请求；研究 Agent 则不断积累检索文档、中间结论和工具结果。若每次请求都从头处理这些持续增长的历史，就会重复已经完成的计算。在*预填充*（Prefill）阶段，LLM 为输入 token 计算逐层 key 和 value（KV）；*解码*（Decode）随输出 token 的生成继续扩展这些状态。保留这些 KV 后，只要模型与位置语义兼容，具有匹配 token 前缀的后续请求就只需计算新增后缀[[11]](#ref-11)、[[41]](#ref-41)。

这种复用既发生在同一 Agent 内，也发生在不同 Agent 之间。同一 Agent 的连续请求可以复用共同对话历史的 KV；不同 Agent 则可以继承共同提示，再追加各自的任务。例如，[图 1](#fig-agent-workflow-examples)中的 API、UI 和测试 Agent 可以共享公共项目说明与代码仓库上下文的 KV，前提是这些内容构成相同的起始 token 序列。不同的角色提示或上下文修改可能缩短可复用的前缀[[41]](#ref-41)。

因此，KV 缓存是 Agent 执行或 LLM 推理请求过程中的重要中间状态。

**故障与 KV 重建。**

这些复用收益依赖缓存状态持续可用。在大规模 LLM 部署中，硬件故障和软件崩溃可能中断 serving worker，并使其 GPU 中的 KV 不可用[[4]](#ref-4)、[[14]](#ref-14)。[图 2](#fig-gpu-server-availability)使用公开的 InfiniteHBD 训练集群 trace 提供生产集群背景：约 349 天内的 584 次不可用事件涉及 400 台 GPU 服务器中的 231 台，重建得到的可用服务器数量最低为 365 台[[32]](#ref-32)。该 trace 同时包含故障和运维中断，具体类别见图注。

如果没有可复用的 KV 存活，接管请求的 worker 就必须重放保留的 token 来重建这些状态，即使它已加载模型权重、应用也保留了对话历史[[33]](#ref-33)。对于长时间执行的 Agent，这意味着重新处理先前多轮请求积累的上下文，而不只是最新输入[[14]](#ref-14)。一个 worker 故障还可能同时中断多个部署在其上的 Agent，使存活 worker 在处理正常流量的同时重建多份历史[[4]](#ref-4)。这些延迟会通过工作流依赖传播：最后一个未完成分支上的重建会推迟汇合，并可能增加 WCT。

**跨存储层级备份 KV。**

为减少重建工作，*KV checkpoint* 保留已经计算完成的前缀。如果该前缀在故障后仍然可用，恢复时即可取回它，只重放尚未保存的尾部[[14]](#ref-14)、[[33]](#ref-33)。KV 可以保存在 GPU HBM、主机 DRAM 或共享存储中[[11]](#ref-11)、[[28]](#ref-28)。这些层级的存储成本与恢复延迟不同。HBM 访问快，但容量成本高，且备份会与前台推理竞争 GPU 内存；DRAM 和使用存储设备作为后端的共享服务可以提供更低成本的容量，但会增加读取延迟。

[图 3](#fig-motivation-recompute)展示重建历史与复用已保留 KV 之间的延迟差异。在 1,010,000 tokens 处，即使采用稀疏注意力，完整 Prefill 仍需 571.21 s；HBM、DRAM 和共享存储复用分别需要 1.305、2.663 和 10.156 s。该历史在两个 rank 上共占用 57.92 GB。所有路径均以同一输入的 KV 就绪为终点：复用路径在需要时取回已有历史，再计算一个新 token。可以看出，KV 复用能够大幅降低 KV 重建延迟。但存储本身存在成本，如何存储以及存储哪些 KV 已成为不可忽视的问题。
