@@U055
在 1,010,000 tokens 处，即使采用稀疏注意力，完整 Prefill 仍需 571.21\,s。HBM、DRAM 和共享存储复用分别需要 1.305、2.663 和 10.156\,s。保留历史可以避免大部分重建工作；其位置决定额外读取延迟。本次运行中，共享存储比 DRAM 多 7.49\,s，而该历史在两个 rank 上共占用 57.92\,GB。这区分了保留可复用状态的价值，以及使其能够快速访问的额外价值。HBM／DRAM 各数据点报告三次计时，完整 Prefill 和共享存储各数据点则各报告一次。结果描述这一固定输入与串行实现中的成本；存储缓存和 I/O 重叠可能改变差异。它们并未测量某种保护策略对整体服务性能的净收益。
@@U056
挑战 2：平衡快速恢复、复用与资源消耗。
@@U057
有限容量使每段长历史都留在执行端附近成为不可能。保护机制既要决定哪些历史保留可复用状态，也要决定哪些状态值得快速访问。这些决策需要综合恢复对工作流的影响、未来正常复用、容量占用和数据移动。特别是，恢复紧迫性低并不等于复用价值低；更快的恢复路径只有在推进必要工作时才有相应价值。挑战在于，如何随这些需求变化分配保护资源，同时避免保护本身损害前台服务。
@@U059
AegisKV 针对这两个挑战：利用工作流进度指导恢复优先级，并在保持正常复用的同时，跨存储层管理有限 KV 容量。下一节介绍支撑这些决策的观察与机制。
@@U060
AegisKV 设计
@@U062
AegisKV 分配有限 KV 存储以减少工作流完成时间（WCT），同时保留正常缓存复用。两条观察将工作流级优先级与恢复所需状态联系起来。

@@U074
系统总览
@@U076
AegisKV 将工作流优先级与三层 KV 层级结合起来（图\ref{fig:system-overview}）。Peer HBM 将选定层与热块保留在另一个数据并行（DP）副本上，以支持快速恢复；共享 DRAM 和存储保留其余状态，用于复用与恢复。三个层级共同覆盖每个已提交 checkpoint，传输完成后每个对象只有一个受管 owner。这种划分使系统能够保留长历史，同时以有界的逐请求配额，将稀缺 HBM 用于零 slack 请求的状态。
@@U077
Application 向 Controller 提供请求和工作流进度。\textbf{(1)} Workflow Tracker 估计每个 Agent 能吸收多少延迟，\textbf{(2)} Recovery-aware Router 选择其执行 DP 和接管 DP。\textbf{(3)} KV Master 利用紧迫性与位置信息，决定每个 KV 对象的保留位置，以及哪些热块值得使用 Peer 空间。在 Engine 内部，\textbf{(4)} Adapter 随服务需求变化调整可用 Peer 容量。Connector 执行 Master 的传输计划并报告结果。Worker 故障后，Router 将请求重定向到接管 DP；Connector 结合 Peer 命中与下层读取，恢复执行。

@@U080
Workflow Tracker：剩余时间与 Slack
@@U082
为在线提供工作流优先级，Tracker 先估计剩余执行时间，再计算 slack。它维护残余 DAG，节点对应已暴露的 fork／join 边界或任务完成边界之间的 Agent segment。一个 segment 可以跨越多次 LLM 调用与工具等待。子任务执行计入子路径，不在父路径重复计入；未知的未来分叉不包含在图中。
@@U083
GBDT 根据因果特征预测 segment 剩余秒数 $d$：角色／模型、当前输入长度、已耗时、已完成调用数，以及此前调用的长度、耗时和上下文增长。缺失历史使用 mask 标记；训练、校准与评估以完整工作流为单位划分。标签终点位于 segment 边界，未来调用结果绝不作为特征。
@@U084
算法\ref{alg:workflow-tracker}以残余 DAG $G$ 和特征 $X$ 为输入。前向／后向关键路径遍历\cite{kelley1959cpm}以预测的工作流完成时刻为基准，计算最早完成时间 $EF$ 与最晚完成时间 $LF$。两者之差为名义 slack。Guard $g$ 取自校准工作流中 slack 正向高估误差的经验上分位数；扣除它得到建议 slack $s$，而非逐请求保证。同一 segment 中的请求共享该余量。
@@U086
\textsc{Supported} 检查输入、依赖、校准与时效性；无效估计不提供正 slack 额度。进度事件与周期刷新向 Master 发布带版本的时长 $d$、guard 和 slack，并使旧优先级估计失效。DAG 遍历开销为 $O(|V|+|E|)$；预测质量在第\ref{sec:eval-prediction}节评估。
@@U087
恢复感知的 Router
@@U089
Router 确定正常执行与恢复执行的位置。正常分派兼顾负载和兼容前缀的局部性。图\ref{fig:agent-prefix-reuse}报告，同 Agent 潜在 token 覆盖率为 97.90\%，额外跨 Agent 覆盖率为 0.37\%。Agent 亲和仅是一种偏好：共享前缀仍可能帮助另一个 Agent 的首次调用。
@@U090
98,827 个请求、2,090 个 Agent 和 393 个 CC/Weka 工作流中的潜在前缀复用。覆盖率基于同一工作流中、使用相同记录模型且更早完成的请求。同 Agent 与其他 Agent 的覆盖存在重叠；只有额外跨 Agent 覆盖能扩展同 Agent 复用范围。这些值表示 token 前缀复用机会，而非运行时缓存命中。
@@U092
请求到达时，Router 记录一个带版本的接管绑定，目标是源故障域之外且布局兼容的 DP。该 DP 中对应的张量并行（TP）分片可以持有选定 Peer 对象。确认故障后，Router 隔离旧 epoch，并在满足工作区和准入约束的条件下激活目标。新目标不能将旧目标的 Peer 对象计为本地对象：重新绑定时需要取回仍可达的对象；若唯一 owner 已丢失，则使用较旧 checkpoint／重放回退。该绑定为 Master 提供具体访问路径和目标负载，以支持恢复性能估计与 Peer 放置。
@@U093
KV Master：面向工作流的分层放置
@@U095
Master 首先将请求紧迫性与请求内部的 KV 需求结合，再将这一优先级延伸到重复使用与共享使用。可续租信用管理下层保留；固定大小的请求级策略分配 Peer 加速。事件循环将两类策略与实际传输和可用容量连接起来。
