结论
@@U277
AegisKV 结合正常复用、工作流紧迫性与块需求，管理有限的 Peer HBM、DRAM 和共享存储。互斥所有权使完整 checkpoint 分布于这些层级；固定配额的热集加速恢复。在线控制器结合惰性下层信用与贪心 Peer 准入，区分迁移与最后副本删除，并在每次转换中保持已提交覆盖。分析场景识别了潜在收益与局限。历史中断时序表明，平均恢复改善可以与尾部退化同时存在；独立消融指出尚未验证的在线策略成本。这些先前的模型结果并未验证互斥三层控制器。详细协议与单栏图支持后续实机正确性和性能实验，而这些实验仍是确立系统级收益所必需的。

Motivation 测量协议
@@U283
范围与配置。
@@U284
图\ref{fig:motivation}(\subref{fig:motivation-recompute})与图\ref{fig:motivation-recovery-exposure}使用相同的固定 Qwen2.5-7B-Instruct-1M 权重、SGLang 0.5.10rc0、PyTorch 2.9.1/CUDA 12.8，在两张 A100 PCIe 40\,GB GPU 上以 TP2、BF16 权重／KV 和 batch 为 1 执行。两组实验分别申请同型号 GPU，使用由模型 tokenizer 编码的同一固定重复合成文本。Trace 提供工作流位置与长度代理，不提供基准测试 prompt。我们的 adapter 使用固定 MInference vertical/slash 配置与 DCA 位置处理，在超过 32,768 tokens 后采用稀疏注意力，包括最后一个 token 的 EXTEND。SM80 稀疏 kernel 构建和模型／注意力源码均附哈希存档。GQA 的 K/V 共享；前缀执行每组最多包含两个 Query head，单 Query 则将全部 head 一起批处理。这些是插桩 worker 测量，而非未修改服务前端的吞吐测量。
@@U285
统一终点。
@@U286
对于 $C=M+1$，完整 Prefill 从空 KV 开始，以最多 8,192 tokens 的块计算 $M$ 个 token，再单独执行一个 token。复用消耗完全相同的稀疏计算所得 $M$-token 状态，包括不完整页，并执行最后那个 token。同步墙上时间在各 TP rank 间取最大值，在模型主体完成、全部 $C$ 个 token 的 KV 驻留时结束，早于输出词表投影。模型加载、备份创建和正确性检查不计入时间。不包含检测、重新路由、服务排队延迟或注入故障。
@@U287
状态恢复路径。
@@U288
HBM 从已驻留 KV 开始。DRAM 在计算前从 pinned 主机缓冲区复制全部历史层。共享存储在计算节点的 DPC 共享文件系统上打开、读取并关闭逐 rank KV 文件，然后执行相同的 H2D 复制与计算。这些阶段不重叠；没有压缩或选择性加载。1,010,000-token 案例在两个 rank 上共恢复 57,917,382,656 个逻辑历史字节；文件另外包含已记录的对齐填充。Direct I/O 与页驻留检查排除了 Linux 文件页命中，但 DPC 服务端和内部缓存不受控制。该曲线是共享存储路径测量，而非冷设备延迟或已确认 SSD 的测量。测量后删除 KV 文件。
@@U289
计时样本。
@@U290
图\ref{fig:motivation}(\subref{fig:motivation-recompute})在一次资源分配中测量 8,192、65,536、262,144 和 1,010,000 tokens。HBM／DRAM 每个长度预热一次、计时三次；完整 Prefill 与共享存储各计时一次。计时前执行短前向与算子检查；64K 还执行完整的原始全 head 稀疏参考。256K/1.01M 没有额外的完整 Prefill 预热，也没有存储读取预热。因此，这些完整 Prefill／存储数据点描述单次运行，而非稳定延迟分布。图\ref{fig:motivation-recovery-exposure}使用两次资源分配，在 $C=100{,}865$、$105{,}921$、$108{,}865$ 和 $113{,}665$ 处测量，每个长度完整预热一次并进行三次完整 Prefill 计时。首次分配完成了三个长度；最后一个长度在提前终止信号后恢复测量。其不完整计时保留在实验材料中，但整组排除。图中报告中位数与 min–max。重复是同一输入的计时样本，不是独立工作流或置信区间。原始计时与全部样本都保留在实验材料中。
@@U291
校验与工作流映射。
@@U292
在重建／复用路径之间检查完整历史哈希、最终 hidden state、所有层的新 KV 和贪心输出。重复完整 Prefill 额外检查输出一致性，CUDA 事件时间线检查串行复制。这些检查验证所比较稀疏状态执行的一致性，不验证其与 dense attention 等价或长上下文任务质量。对于图\ref{fig:motivation-recovery-exposure}，四个历史长度是活跃请求 trace hash-block 数乘以 64。它们是大小代理，不是原模型准确 token 数或故障时观测到的 KV 前沿。该示例按四个并行分支和约 100\,s 的差值选取；它不是该工作流的最大差值组。每个反事实分别在 fork 后 29.5\,s，将一段实测完整 Prefill 时长作为额外分支暂停插入。全分支汇合假设、其他执行与队列保持固定。因此，只有重建成本是实测；图中的 WCT 增量是条件计算，而非 Claude Code 工作流中实际观测的故障恢复。
