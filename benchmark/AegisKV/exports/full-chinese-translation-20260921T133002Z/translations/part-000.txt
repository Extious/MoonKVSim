@@U000
摘要
@@U001
多 Agent 应用在执行相互依赖的 LLM 请求时会不断积累可复用的上下文。一个 worker 故障可能导致这些状态丢失，并同时延迟多个分支，而将所有上下文都保护在快速内存中的成本很高。我们提出 AegisKV，一种面向工作流的 KV checkpoint 管理系统，跨 Peer HBM、共享 DRAM 和共享存储管理状态。完整 checkpoint 分布于三个层级，每个对象有且仅有一个受管 owner：选定层和热块位于预先指定的接管 DP，其余状态保留在下层。请求 slack 与按访问机会归一化的块需求共同构成因子化的恢复优先级；正常复用独立贡献保留价值。可续租的逐 Agent 信用管理 DRAM 与存储，惰性刷新将需求更新和由实际使用触发的续租区分开来。Peer 采用固定的层／块配额，并对零 slack 请求进行贪心准入。AIMD Adapter 限制 Peer 总容量，带版本的传输在迁移与显式回退过程中保持 checkpoint 覆盖。这些具有有界决策开销的策略保持原生注意力语义。我们将从 trace 得到的工作流观察和已有的重建微基准，与可复现的分析研究及完整实验协议结合起来。在 36 个明确声明且禁用 Peer 的场景中，放置模型在 17 个场景中优于 LRU，在 19 个场景中与其持平。匹配条件的分析调度展示了 Peer 带来的额外重叠收益；这两类模型均不是对三层系统的实测。历史故障时序驱动一个独立的恢复负载模型，其中平均延迟下降与尾延迟恶化同时存在。机制消融揭示了层放置与重叠之间的交互，以及早期租金筛选策略的负面结果。有界修复缩小了该模型的差距，但不能确立新控制器的性能。本研究明确了资源竞争、预测误差和提交滞后何时会限制收益。要确立所提系统的性能，仍需端到端故障注入和正常服务测量。
@@U002
引言
@@U004
当多 Agent 应用的必要结果就绪时，应用才算完成：结果可能是经过测试的代码补丁、一份报告，或由并行搜索汇总而成的答案。因此，一个 LLM 请求的价值取决于它在工作流中的位置。关键分支上的延迟会推迟完成时间，另一个分支则可能在汇合前吸收这段延迟。面向应用的服务系统已在正常执行中利用这种结构\cite{lin2024parrot,pan2025kvflow,ni2026topas}。故障提出了进一步的问题：当一个 worker 故障同时中断多个请求时，哪些历史应当保持快速可恢复？
@@U005
长上下文使这一选择的成本变得高昂。Agent 会积累推理、代码和工具结果；丢失其驻留在 GPU 上的 KV 后，可能需要大量重建工作。Checkpoint 可以避免这些工作\cite{strati2024dejavu,jayakody2026ghostserve}，负载感知的恢复机制则将中断请求分配到不同位置\cite{cao2026lumen}。分层缓存提供 DRAM 和存储容量\cite{qin2025mooncake,xie2026strata}，但将每段历史都保留在较快层中的成本很高。
@@U006
仅凭最近访问情况和恢复延迟无法决定放置。一段较长且最近使用过的历史，可能属于能够容忍存储访问延迟的分支，而较短的历史却可能位于关键路径上。较大的 slack 不能成为删除可复用历史的充分理由：后续正常调用可能反复重建该历史。同一 worker 的故障还会通过 DAG 和共享恢复资源耦合多个请求。只加速两个延迟分支中的一个，可能不会改变其汇合时间。最后，降级迁移是异步的：在存储层替代副本提交之前释放 DRAM，会使保护失效。
@@U007
AegisKV 跨 Peer HBM、共享 DRAM 和共享存储管理 checkpoint。Tracker 估计工作流剩余时间；Master 将请求紧迫性与按访问机会归一化的块需求相结合。不同 Agent 为共享对象贡献信用，而一个 Agent 的实际复用只续租其自身份额。下层租金使容量占用随压力老化，惰性价值更新保留已支付的租金。Peer 为零 slack 请求采用固定层／块配额；热块身份和已准入请求在线变化。迁移结束后，每个对象只有一个受管 owner。有界事件循环连接保留、准入与级联降级。Router 在请求到达时绑定兼容的接管 DP；AIMD Adapter 限制 Peer 总容量，Connector 执行传输。带版本的 manifest、资源预留和 reader lease 在所有权跨层转移时保持 checkpoint 覆盖。
@@U008
我们提出的贡献包括：一种面向工作流的优先级与可续租信用策略，用以区分 Peer 加速与下层保留；一个有界在线控制器和安全状态转换协议；以及具有匹配实机实验计划的可复现分析场景。模型展示了收益、持平结果、预测敏感性，以及相对于可行 oracle 的遗憾值。Trace 驱动的恢复模型和独立机制模型揭示了队列尾部退化，以及历史租金筛选策略的不利结果，其有界修复仍留下残余差距。这些结果为所提系统提供动机并限定其适用范围，但并非对其实现的测量。核心经验假设是：在计入正常服务和迁移成本后，面向工作流的保护可以改善有限资源分配。

背景与动机
@@U011
背景
@@U013
多 Agent 执行。
@@U014
多 Agent 应用将用户任务划分给若干相互交换中间结果的 Agent。每个 Agent 维护自己的对话，通过 LLM 请求和工具调用推进任务：模型生成响应或工具调用，返回结果成为后续请求的输入\cite{wu2023autogen}。\emph{请求}是一次模型调用；一个 \emph{Agent} 可以发起多个请求以完成其任务；\emph{工作流}则通过串行依赖、并行分支和汇合点连接这些任务。应用负责编排工作流，服务引擎执行其中的模型请求。
@@U015
图\ref{fig:agent-workflow-examples}展示了这种结构。在代码生成中，主 Agent 将 CSV 导出功能分派给 API、UI、测试编写和文档 Agent。各分支从共同规格出发，交替进行模型请求与文件读取、编辑或检查。主 Agent 随后集成修改并运行测试。在深度研究中，牵头 Agent 分派技术、成本、安全和供应调查，再将收集的证据综合为报告\cite{anthropic2025multiagent}。各分支需要的请求次数和工具调用次数可以不同，不存在共同的轮次屏障。因此，一个模型请求完成后，其所属 Agent 和整个工作流都可能仍未完成。
@@U016
工作流完成时间。
@@U017
只有在工作流产生必要输出后，用户才能获得结果。我们将这一时间区间称为\emph{工作流完成时间}（WCT）：对于在 $a_w$ 释放、在 $c_w$ 完成的工作流 $w$，$\mathrm{WCT}_w=c_w-a_w$。它包括模型执行、工具执行、排队和依赖等待。在代码示例中，集成需要等待所有必要修改。最后一个未完成分支上的延迟会推迟集成，而较早完成的分支可能在汇合前吸收同样的延迟。请求延迟通过这些依赖关系影响 WCT。
@@U018
多 Agent 工作流示例。每行代表一个 Agent：$R_i$ 表示该 Agent 的第 $i$ 次 LLM 请求，中间的工具结果进入下一次请求。各分支的请求次数不同，没有共同的轮次屏障。协调者在各分支结果汇合后继续执行。图中位置与长度不编码执行时间。
@@U020
Agent 多轮执行中的 KV 复用。
@@U021
在\emph{预填充}（Prefill）阶段，LLM 处理输入 token，并计算逐层 key 和 value（KV）；\emph{解码}（Decode）随输出 token 的生成继续扩展这些状态。Agent 的下一次请求通常会将模型输出和工具结果追加到已有对话中。在模型与位置语义兼容时，匹配的 token 前缀可以复用已有 KV，因此只需计算新增后缀\cite{gao2024cachedattention,zheng2024sglang}。例如，API Agent 读取文件后，下一次请求可以复用先前对话的 KV，同时处理返回的文件内容。前缀发生变化时，可复用范围限于仍然匹配的部分。
@@U022
即使当前没有模型请求运行，Agent 在执行工具或等待其他分支时，这些状态仍可能有用。保留它们可以避免 Agent 恢复执行时重复前缀计算。KV 是由模型计算得到的中间状态，不同于应用保存的 token 历史和工作流进度。在常规逐 token 布局中，其大小随上下文长度、层数和 KV-head 维度增长；因此，长对话的 KV 可能远比 token ID 占用更多内存。稀疏注意力减少一次操作访问的历史 KV\cite{jiang2024minference}，但本次跳过的状态仍可能在后续被使用。
@@U023
恢复与存储层级。
@@U024
Serving worker 故障可能中断请求，使 GPU KV 不可访问，并减少可用服务容量\cite{cao2026lumen}。本文考虑 fail-stop worker 故障，假定已接受的 token 历史和工作流进度保留在故障 worker 之外，并存在兼容的存活副本。该副本虽然已有模型权重，仍需要获得中断序列的状态。若没有存活 KV，它需要重放保留的 token 来重建状态。\emph{KV checkpoint} 保存已经计算完成的前缀：恢复端取回此前缀，再重放其后尚未保存 KV 的 token。异步 checkpoint 可能在故障时留下这部分尾部\cite{strati2024dejavu,jayakody2026ghostserve}。Checkpoint 必须能承受所保护的故障；同机 DRAM 可以在 GPU worker 失败后保留，但无法承受整台主机丢失。
@@U025
分层缓存通过主机 DRAM 和存储扩展 GPU HBM，使更多历史得以保留\cite{gao2024cachedattention,qin2025mooncake}。位置决定访问路径：执行端 HBM 中已有的 KV 可被算子直接访问，DRAM 需要主机到设备的传输，存储层还增加可能经过网络的读取。计算和预取可以重叠其中一部分工作。然而，状态保留仍然占用容量，复制或迁移 KV 消耗的带宽也可能同时用于前台请求。丢弃最后一份可复用 KV 可以释放空间，但之后若再次需要该状态，就必须重建。
@@U026
已有机制。
@@U027
分层缓存减少跨轮次重复前缀计算\cite{gao2024cachedattention,qin2025mooncake}；KV streaming 和 checkpoint 减少故障后的重建\cite{strati2024dejavu,jayakody2026ghostserve}。Parrot 暴露应用依赖以支持服务优化，KVFlow 则根据即将执行的 Agent 步骤指导淘汰与预取\cite{lin2024parrot,pan2025kvflow}。LUMEN 结合 worker 负载协调 checkpoint 放置和恢复路由\cite{cao2026lumen}。这些能力构成了面向工作流的恢复基础。分配有限保护资源还需要处理决策依据的两项局限。
@@U028
局限 1：请求级优先级不能完整表达工作流收益。
@@U029
最近访问、下一次使用的接近程度和重建成本，描述了状态何时可能被使用，以及恢复有多昂贵。单独依靠这些量，无法确定让某请求更早恢复会如何提前工作流的必要输出。重建昂贵的历史可能属于仍有时间余量的分支，而一次较短的恢复也可能延迟决定完成时间的分支。保护优先级必须考虑依赖关系和各分支的剩余进度。
@@U030
局限 2：只看恢复速度会遗漏保留价值与资源代价。
@@U031
一个可以容忍恢复延迟的分支，仍可能在下一次正常请求中复用其历史。删除最后一份 KV 会失去这种复用；将副本移到较慢层可以保留复用能力，但增加读取工作。反过来，把所有可恢复历史留在快速内存中，会占用其他历史和正常执行所需的空间。因此，单独最小化恢复延迟，无法决定应保留哪些状态、放在哪一层，以及服务系统能承受多少保护开销。

动机与挑战
@@U038
我们使用 Agent 执行 trace 和实测 KV 就绪成本考察上述局限。Trace 描述分支时序；模型测量在统一终点下量化重建与复用成本。两者共同引出面向工作流的保护所需满足的两项要求。
@@U039
并行分支的进度差异。
@@U041
图\ref{fig:motivation}(\subref{fig:motivation-workflow})展示四个来自 trace 的分支。A2 最晚完成，在 fork 后 151.6\,s 结束；A1 在 60.4\,s 结束。若后续 Main 阶段需要全部四个输出，A1 可以吸收 91.2\,s 的额外延迟而不推迟汇合，A2 上的任何延迟则都会推迟汇合。我们把一个分支在不推迟必要输出的情况下能够吸收的额外延迟称为 \emph{slack}。
@@U042
公开的 SemiAnalysis CC/Weka trace 包含 393 个经过筛选的 Claude Code session\cite{semianalysis2026cctraces}。我们保留执行有重叠、所有分支均已完成、且最后一个分支结束后存在 Main 请求的 subagent 组；期间允许 Main 活动。这一时序 fan-in 代理保留了 121 个工作流中的 286 个组。对每组计算最长与最短分支的时长差，再取各工作流的最大差值。图\ref{fig:motivation}(\subref{fig:motivation-branch-gap})的中位数为 138\,s，90 分位数为 1,173\,s。这些统计显示，保留的工作流内部存在较大的时长差异。Trace 没有记录显式结果消费边，因此这些统计既不能验证所有分支均需汇合，也不能测量故障时刻的 slack。四分支示例是一个符合条件的组，不能代表工作流最大差值的典型水平。

@@U050
挑战 1：估计恢复对工作流的影响。
@@U051
保护决策必须将其避免的延迟与工作流的必要输出联系起来。上述示例使用完整 trace 获得 slack，但在线系统只能看到已发生的执行：剩余模型与工具耗时存在不确定性，后续依赖也可能尚未暴露。优先级必须随分支进度变化。一个 worker 故障还可能同时中断多个分支，而这些恢复过程共享资源，因此不能将各分支独立计算的 WCT 增量简单相加。挑战在于，如何根据部分工作流进度形成有用的恢复优先级，同时考虑这些不确定性与相互影响。
@@U052
长历史的保留与访问成本。
@@U054
图\ref{fig:motivation}(\subref{fig:motivation-recompute})在相同执行配置下比较重建与 HBM、DRAM、共享存储复用。对于 $C=M+1$ 个 token，完整 Prefill 从空 KV 开始；复用从相同的 $M$-token 历史开始，并计算一个新 token。所有计时均在全部 $C$ 个 token 的 KV 就绪时结束，位于词表投影之前。HBM 是状态已驻留的参考；DRAM 和共享存储将状态恢复与计算串行执行。这些测量不包含 checkpoint 创建、故障检测和恢复路由。
